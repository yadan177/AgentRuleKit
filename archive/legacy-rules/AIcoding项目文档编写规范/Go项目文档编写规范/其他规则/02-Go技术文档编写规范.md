# 02 - Go 技术文档编写规范

> 🟢 本文件适用于 Go 工程、模块、接口、数据、测试、运行和 ADR 正文。<br>
> 🔴 不适用：将框架、依赖、命令或性能结论写成没有证据的项目事实。

---

## 1. 写作要求

- 🔴 先写用途、范围和结论，再写必要细节。
- 🔴 每段只表达一个意思；使用列表、表格和短句，删除重复背景与空话。
- 🔴 数值、接口签名、配置和 schema 指向权威来源，不复制第二份真相。
- 🔴 无证据时使用 `> ⚠️ 待确认：<问题>`，不得猜测。
- 🟡 组件、调用或数据关系复杂时才使用 Mermaid。

## 2. 正文边界与归类

- 🔴 一篇正文只回答一个可独立检索的技术问题；标题、用途、范围和来源必须与所在技术主题一致。
- 🔴 架构、模块、接口、测试、运行和技术决策有独立读者、维护节奏、操作步骤、契约或结论时，应按 `01-技术文档组织与维护规范.md` 拆为主题下的独立正文。
- 🔴 不把产品需求、策划设计、美术规范、运营或管理结论写入技术正文；技术文档只记录实现边界、工程事实和可验证结论。
- 🟡 同一主题的简短补充优先写入既有正文，避免为一两段内容新建文件。

## 3. Go 事实检查

| 主题 | 优先来源 |
|---|---|
| 版本与依赖 | `go.mod`、`go.sum`、`go.work` |
| 包与模块边界 | `cmd/`、`internal/`、`pkg/`、导入关系和现有代码 |
| 配置与构建 | 配置文件、`Makefile`/`Taskfile`、Dockerfile、CI |
| 契约与数据 | OpenAPI、Proto、消息定义、迁移文件和存储 schema |
| 质量与运行 | 测试、benchmark、日志、指标、追踪和运行记录 |

- 🔴 涉及 goroutine、`context.Context`、channel、连接或文件时，说明创建方、所有者、取消/关闭时机和错误路径。
- 🔴 涉及 HTTP、gRPC、消息或存储时，说明提供方、消费方、兼容性和权威定义。
- 🔴 构建与排障步骤写清前置条件、操作、预期结果、失败处理和验证点。
- ❌ 不默认使用 Gin、gRPC、ORM、消息系统或容器平台；以项目证据为准。

## 4. 状态与自检

| 状态 | 要求 |
|---|---|
| `草稿` | 说明提议内容、待确认项和验收条件 |
| `有效` | 说明适用范围、来源、限制和验证方式 |
| `已废弃` | 说明废弃原因、替代路径和生效时间 |

- [ ] 开头有用途、范围和不覆盖内容。
- [ ] 关键结论可定位到来源，未知项已标记。
- [ ] 生命周期、并发、资源和兼容性边界在适用时已说明。
- [ ] 所在技术主题、索引、链接和文档变更记录已同步。
