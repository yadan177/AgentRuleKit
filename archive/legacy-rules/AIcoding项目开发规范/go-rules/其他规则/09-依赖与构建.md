# 09 - Go 依赖与构建规则

> - 🟢 本文件适用于 **Go 项目的依赖管理**和**构建配置**——添加/升级依赖、编写 Dockerfile、配置交叉编译、设置编译标志
> - 🔴 **不适用**：业务代码（见 01/02）、API 设计（见 04）、数据库配置（见 05）、go.mod 基础字段定义（见 06-§ 1）
> - 🟡 本文件模板必须按项目现有工具链、模块路径、Go 版本和部署方式调整；不得未经验证直接复制执行。

## 1. go.mod 管理

> 基础结构（`module` / `go` / `require` / `replace` / `exclude`）已在 [06 - Go 项目配置](./06-项目配置规则.md) 中覆盖。本节聚焦**日常维护操作**和**依赖管理策略**。

### 1.1 `go mod tidy` 的时机

🔴 必加约束

只有 import 变化会影响模块依赖、`go.mod`/`go.sum` 已修改或仓库门禁要求时才运行 `go mod tidy`；标准库 import 和同模块包调整通常不改变模块文件。

| 操作 | 是否需要 `go mod tidy` |
|---|---|
| 添加/删除第三方 module import | ✅ 通常需要 |
| 仅调整标准库或当前 module import | ❌ 通常不需要 |
| 修改 `go.mod` 中的 `go` 版本 | ✅ 必须 |
| 添加/删除 `replace` / `exclude` | ✅ 必须 |
| 仅修改 `.go` 文件（不涉及 import 变更） | ❌ 不需要 |
| 仅修改注释 | ❌ 不需要 |

```bash
# 标准流程：改完 import → tidy → 验证 → 提交
go mod tidy
go mod verify
git diff --exit-code go.mod go.sum  # 确认无意外变更
```

### 1.2 依赖版本管理

🔴 必加约束

| 指令 | 用途 | 示例 |
|---|---|---|
| `go get pkg@v1.2.3` | 锁定精确版本 | `go get github.com/gin-gonic/gin@v1.9.1` |
| `go get pkg@latest` | 解析当前可获得的最新版本 | 仅在明确接受升级范围并完成兼容性验证时使用 |
| `go get -u ./...` | 升级所有直接依赖的次版本 | 谨慎使用——一次性改动太大 |
| `go get -u=patch ./...` | 尝试升级补丁版本 | 仍需审查变更、漏洞信息和兼容性，不视为天然安全 |

```bash
# 反例：一次性升级所有依赖（容易引入不兼容变更）
go get -u ./...

# 正例：逐个升级到经过确认的目标版本 + 跑测试
go get github.com/gin-gonic/gin@<目标版本>
go test ./...
git diff -- go.mod go.sum
```

### 1.3 `replace` 指令的纪律

🔴 必加约束

`replace` 是 Go modules 中最容易被滥用的指令。以下规则必须遵守：

| 场景 | 做法 | 是否提交 |
|---|---|---|
| 本地开发中临时引用未发布的本地模块 | 使用 `go.work`（Go 1.18+），**不修改** `go.mod` | ❌ `go.work` 一般不提交 |
| fork 了上游仓库需要长期使用 | fork 后改 `module` 路径，发布独立版本 | ✅ 作为新模块提交 |
| 上游有 bug，临时用 fork 修复 | 加 `replace` + 注释说明原因和计划移除时间 | ✅ 可临时提交（需注明到期日） |
| 调试时指向本地路径 | 临时替换或 `go.work` 均需遵循仓库 workspace 策略 | 个人临时配置通常不提交；团队正式策略可提交 |

```bash
// go.mod

// 反例：本地路径 replace 提交到仓库
replace github.com/example/lib => ../lib  // 其他人拉下来编译失败

// 反例：replace 掩盖上游问题
replace github.com/broken/lib => github.com/my-fork/lib v1.2.3-fixed
// 问题：版本号没变，但内容变了——Go module proxy 缓存可能混乱

// 正例：fork 后改 module 路径发布独立版本
// my-fork 的 go.mod: module github.com/my-org/lib-fork
// 原项目的 go.mod: require github.com/my-org/lib-fork v1.2.3

// 正例：临时修复（加注释 + 复核日期 + 上游依据）
replace github.com/broken/lib => github.com/my-fork/lib v1.2.3-fixed
// TODO(owner): 在 <YYYY-MM-DD> 前复核；上游问题 <链接或编号> 解决后删除此 replace
```

### 1.4 `exclude` 与 `retract` 的使用

🟡 推荐

| 指令 | 用途 | 示例场景 |
|---|---|---|
| `exclude` | 排除上游有已知漏洞/严重 bug 的特定版本 | `exclude github.com/vuln/lib v1.2.0` |
| `retract` | 撤回**自己**发布的有问题的版本 | `retract v1.5.0`（在 go.mod 中声明） |

```go
// go.mod

// 正例：排除有已知漏洞的版本（加注释说明原因）
exclude (
    // CVE-2026-1234: RCE vulnerability in v1.2.0
    github.com/vuln/lib v1.2.0
    // 破坏了向后兼容性
    github.com/broken/lib v2.0.0
)

// 正例：撤回自己发布的版本
// 本模块的 v1.5.0 有严重 bug，撤回它
retract v1.5.0
```

### 1.5 `go.work` 工作区

🟡 适用于 Go 1.18+ 的多模块工作区

多模块同时开发时，用 `go.work` 替代 `replace`：

```bash
# 初始化工作区
go work init ./server ./lib ./shared

# go.work 内容
go 1.22

use (
    ./server
    ./lib
    ./shared
)
```

```go
// 反例：在 go.mod 中用 replace 指向本地模块
replace github.com/my-org/lib => ../lib
replace github.com/my-org/shared => ../shared

// 正例：用 go.work 统一管理本地模块
// 是否提交由仓库的 workspace 策略决定，go.mod 保持模块自身依赖边界。
```

> 临时个人 workspace 通常不提交；团队正式采用的多模块 workspace 可以提交。`go.work` 与 `go.work.sum` 的版本控制策略必须跟随仓库约定，不得在通用 `.gitignore` 中无条件忽略。

## 2. 依赖升级策略

### 2.1 安全漏洞扫描

安全扫描必须沿用项目已有工具链和门禁：

- 🔴 项目 CI、发布流程或安全规范已经要求 `govulncheck` 时，按其版本、参数和执行时机运行。
- 🟡 项目尚未采用漏洞扫描时，可在依赖升级、安全审查或发布前把 `govulncheck` 作为候选方案；安装工具或新增 CI 门禁前必须获得授权。
- 🔴 无法运行既有安全检查时，交付中说明原因、未验证范围和风险，不得以“工具未安装”为由伪造通过。

```bash
# 仅在项目已提供或明确授权使用 govulncheck 时执行
govulncheck ./...

# 是否包含测试路径及具体参数以项目门禁为准
govulncheck -test ./...
```

> `govulncheck` 是 Go 官方工具（`golang.org/x/vuln/cmd/govulncheck`），使用 Go 漏洞数据库并结合模块、包、符号和调用图降低噪声。结果仍受构建标签、平台、测试范围和分析模式影响，需要结合目标构建与其他供应链检查解释。

### 2.2 Dependabot 配置

🟢 候选示例。仅适用于托管在 GitHub、已经采用或明确授权采用 Dependabot 的仓库；其他平台沿用现有依赖更新机制。频率、分组、标签和 PR 上限必须按项目维护能力调整。

```yaml
# .github/dependabot.yml
version: 2
updates:
  # Go 模块
  - package-ecosystem: "gomod"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
      time: "09:00"
      timezone: "Asia/Shanghai"
    # 最多同时打开的 PR 数
    open-pull-requests-limit: 5
    # 自动 rebase
    rebase-strategy: "auto"
    labels:
      - "dependencies"
      - "go"

  # Docker 镜像
  - package-ecosystem: "docker"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
    labels:
      - "dependencies"
      - "docker"

  # GitHub Actions
  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
    labels:
      - "dependencies"
      - "ci"
```

### 2.3 依赖升级决策表

🟡 候选决策。项目已有更新节奏、合规流程和自动化平台时优先遵守现有约定：

| 升级类型 | 处理原则 | 验证要求 |
|---|---|---|
| 安全修复 | 根据可利用性、暴露面和官方建议确定优先级 | 审查公告、受影响调用路径、兼容性和回归；不能仅凭 CI 自动合并 |
| 补丁/次版本 | 根据项目更新策略和维护窗口安排 | 审查 release notes、依赖图、测试和目标环境行为 |
| 主版本 | 作为显式迁移处理 | 评估 API/配置/数据兼容、回滚和完整回归范围 |
| 间接依赖 | 先确认引入路径和可控升级点 | 验证上游约束、模块解析结果和实际受影响行为 |

### 2.4 依赖审计

🟡 推荐

```bash
# 查看所有依赖（含间接依赖）
go mod graph

# 查看为什么引入了某个依赖
go mod why -m github.com/some/package

# 查看可用的升级
go list -m -u all

# 查看依赖树（需要安装 gotree）
go mod graph | grep 'github.com/some/package'
```

```bash
# 反例：不知道为何引入就盲目删除
go mod tidy  # 但没检查 go mod why

# 正例：先理解依赖链路再决策
go mod why -m github.com/indirect/package
# 输出：
# your-module
# your-module/internal/handler
# github.com/direct/dep
# github.com/indirect/package
# → 这是通过 github.com/direct/dep 间接引入的
```

## 3. 语义化版本

### 3.1 模块路径与主版本

🔴 必加约束

Go modules 的版本号与模块路径**强绑定**：

| 主版本 | 模块路径 | `go.mod` 中 `module` |
|---|---|---|
| v0 / v1 | `github.com/user/repo` | `module github.com/user/repo` |
| v2+ | `github.com/user/repo/v2` | `module github.com/user/repo/v2` |

```go
// 反例：v2 版本模块路径不带 /v2
module github.com/user/repo  // ← 错误：v2.0.0 tag 但路径没有 /v2
// 后果：go get 无法正确解析版本

// 正例
module github.com/user/repo/v2  // ← v2 必须带 /v2 后缀
```

### 3.2 版本号规则

🔴 必加约束

遵循 [Semantic Versioning 2.0.0](https://semver.org/lang/zh-CN/)：

```
vMAJOR.MINOR.PATCH
  1    .2    .3

v1.2.3 → v1.2.4  补丁版本：bug 修复，向后兼容
v1.2.3 → v1.3.0  次版本：新功能，向后兼容
v1.2.3 → v2.0.0  主版本：不兼容的 API 变更
```

```bash
# 正例：tag 命名
git tag v1.0.0
git tag v1.0.1   # bug 修复
git tag v1.1.0   # 新功能
git tag v2.0.0   # 破坏性变更

# 反例：tag 命名不规范
git tag 1.0.0       # 缺少 v 前缀
git tag v1.0        # 缺少 patch 版本号
git tag release-1.0 # 非标准格式，go get 无法识别
```

### 3.3 预发布版本

🟡 推荐

```
v1.0.0-alpha.1  # Alpha 预发布
v1.0.0-beta.1   # Beta 预发布
v1.0.0-rc.1     # Release Candidate
v1.0.0          # 正式发布
```

Go modules 中预发布版本**不会**被 `go get pkg@latest` 自动选中——需要显式指定。

### 3.4 v0 版本的特殊性

🟡 推荐

- v0.x.x 表示**API 不稳定**，任何次版本都可能包含破坏性变更
- v0.1.0 → v0.2.0 可以有不兼容改动，Go modules 不会阻止
- 一旦发布 v1.0.0，就承诺了向后兼容

```bash
# v0 阶段：API 可能变化，但仍应记录变更并评估使用方
git tag v0.1.0
# ... 大改 API ...
git tag v0.2.0  # 允许破坏性变更

# v1 阶段：不能破坏公开 API
git tag v1.0.0
# 如果要破坏 API，必须升主版本
git tag v2.0.0
```

## 4. Docker 多阶段构建

### 4.1 多阶段 Dockerfile 参考

🟡 仅在项目使用容器交付时适用。多阶段构建通常可以减少运行镜像中的编译工具和源码；若项目已有受控构建流水线或必须保留 CGO 动态库，应按实际供应链与运行依赖调整。

```dockerfile
# Dockerfile
# 镜像、digest、目标架构、CGO 和二进制路径均为占位配置，使用前必须替换并验证。
# ──── 构建阶段 ────
FROM <Go 构建镜像>@sha256:<digest> AS builder

WORKDIR /app

# 先复制依赖文件，利用 Docker 层缓存
COPY go.mod go.sum ./
RUN go mod download

# 复制源码并编译
COPY . .
RUN CGO_ENABLED=<按项目决定> GOOS=<目标系统> GOARCH=<目标架构> \
    go build -trimpath -ldflags="-s -w" \
    -o /app/server ./cmd/server

# ──── 运行阶段 ────
FROM <运行时镜像>@sha256:<digest>

# 根据 HTTPS、时区、CGO 和动态库需求准备运行依赖，不复制无关文件。
COPY --from=builder /app/server /usr/local/bin/server

# 创建非 root 用户
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser

EXPOSE 8080
ENTRYPOINT ["server"]
```

### 4.2 使用 distroless 运行时（进阶）

🟡 当应用是兼容的静态二进制、运行时依赖明确且团队具备相应调试手段时，可以评估 distroless 或其他最小运行时镜像。

```dockerfile
# ──── 构建阶段（同上）────
FROM <Go 构建镜像>@sha256:<digest> AS builder
# ... 同上 ...

# ──── distroless 运行阶段 ────
FROM <已验证的最小运行时镜像>@sha256:<digest>

COPY --from=builder /app/server /server

EXPOSE 8080
ENTRYPOINT ["/server"]
```

> 最小运行时通常不含 shell 或包管理器，可降低不必要组件数量，但会改变排障方式。是否采用应由威胁模型、运行依赖、漏洞响应和可观测性要求共同决定。

### 4.3 Dockerfile 优化要点

🟡 按项目实际部署方式检查：

| 要点 | 反例 | 正例 |
|---|---|---|
| 层顺序：先复制依赖再复制源码 | `COPY . .` 在 `go mod download` 之前 | 先 `COPY go.mod go.sum`，`RUN go mod download`，再 `COPY . .` |
| 非 root 用户 | `USER root`（默认） | `USER appuser`（显式创建） |
| 固定基础镜像 | `FROM alpine`（浮动 tag） | 使用项目已验证的不可变 digest |
| `.dockerignore` | 无 `.dockerignore` | 排除 `bin/` / `.git/` / `*.test` / `vendor/` |
| 明确运行依赖 | 未确认 CGO/证书/时区就构建 | 按目标平台验证静态或动态依赖 |
| 避免浮动 tag | `FROM golang:latest` | 使用项目锁定并持续更新的 digest |

```dockerfile
# .dockerignore 示例；仅排除构建上下文不需要的内容
.git/
.gitignore
*.md
*.test
coverage.out
bin/
vendor/
.env*
docker-compose*.yml
.idea/
.vscode/
```

### 4.4 多架构构建

🟡 推荐

```bash
# 创建多架构 builder
docker buildx create --name multiarch --use

# 构建并推送多架构镜像
docker buildx build \
    --platform linux/amd64,linux/arm64 \
    --tag my-registry/my-service:v1.0.0 \
    --push .

# Makefile 中集成
.PHONY: docker-buildx
docker-buildx:
	docker buildx build \
		--platform linux/amd64,linux/arm64 \
		--tag $(REGISTRY)/$(APP_NAME):$(VERSION) \
		--push .
```

## 5. 交叉编译

### 5.1 基本交叉编译

🔴 必加约束：交叉编译前必须检查依赖、目标系统、目标架构、C 工具链、动态库和容器运行环境；交叉编译不等于必须关闭 CGO。

纯 Go 且目标环境允许时，可以优先评估 `CGO_ENABLED=0`。存在 C 依赖、系统库、SQLite C 驱动或平台能力要求时不得强制关闭 CGO。

```bash
# 以下仅适用于已确认不依赖 CGO 的纯 Go 项目
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -o server-linux-amd64 ./cmd/server
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -o server-linux-arm64 ./cmd/server
CGO_ENABLED=0 GOOS=darwin GOARCH=amd64 go build -o server-darwin-amd64 ./cmd/server
CGO_ENABLED=0 GOOS=darwin GOARCH=arm64 go build -o server-darwin-arm64 ./cmd/server
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -o server-windows-amd64.exe ./cmd/server
```

### 5.2 Makefile 中集成交叉编译

🟡 推荐

```makefile
# Makefile
GOOS        ?= $(shell go env GOOS)
GOARCH      ?= $(shell go env GOARCH)
CGO_ENABLED ?= $(shell go env CGO_ENABLED)
BUILD_DIR   ?= ./bin

# 单平台构建（默认）
.PHONY: build
build:
	CGO_ENABLED=$(CGO_ENABLED) $(GO) build \
		-trimpath \
		-ldflags="$(LDFLAGS)" \
		-o $(BUILD_DIR)/$(APP_NAME) \
		$(CMD_DIR)

# 全平台构建
.PHONY: build-all
build-all:
	@echo "Building for all platforms..."
	@mkdir -p $(BUILD_DIR)
	GOOS=linux   GOARCH=amd64 $(GO) build -trimpath -ldflags="$(LDFLAGS)" -o $(BUILD_DIR)/$(APP_NAME)-linux-amd64   $(CMD_DIR)
	GOOS=linux   GOARCH=arm64 $(GO) build -trimpath -ldflags="$(LDFLAGS)" -o $(BUILD_DIR)/$(APP_NAME)-linux-arm64   $(CMD_DIR)
	GOOS=darwin  GOARCH=amd64 $(GO) build -trimpath -ldflags="$(LDFLAGS)" -o $(BUILD_DIR)/$(APP_NAME)-darwin-amd64  $(CMD_DIR)
	GOOS=darwin  GOARCH=arm64 $(GO) build -trimpath -ldflags="$(LDFLAGS)" -o $(BUILD_DIR)/$(APP_NAME)-darwin-arm64  $(CMD_DIR)
	GOOS=windows GOARCH=amd64 $(GO) build -trimpath -ldflags="$(LDFLAGS)" -o $(BUILD_DIR)/$(APP_NAME)-windows-amd64.exe $(CMD_DIR)
	@echo "Done. Binaries in $(BUILD_DIR)/"
```

### 5.3 CGO 决策表

🔴 必加约束

| 场景 | `CGO_ENABLED` | 说明 |
|---|---|---|
| 已确认不依赖 C/系统库的纯 Go 服务 | 可评估 `0` | 简化静态交付，但仍需在目标平台验证网络、证书和时区行为 |
| 依赖 C 库（如 SQLite C 驱动） | 通常为 `1` | 需要目标平台 C 工具链及匹配的运行时动态库 |
| 依赖系统解析、认证或平台能力 | 按目标环境验证 | 不能仅凭“Linux 容器”推断关闭 CGO |
| 交叉编译含 CGO 项目 | 按工具链配置 | 需要匹配目标系统/架构的编译器和库；不是天然不可行 |
| 本地开发 | 沿用项目配置 | 本地可编译不代表发布目标可运行 |

```go
// 检查项目是否依赖 CGO
// 方法 1：查看依赖中是否有 C 文件
find . -name "*.c" -o -name "*.h"

// 方法 2：尝试禁用 CGO 编译
CGO_ENABLED=0 go build ./...
// 编译成功只证明当前构建路径可用，仍需验证目标平台动态依赖和运行行为。

// 方法 3：查看 import 的包
// 常见需要 CGO 的包：
// - github.com/mattn/go-sqlite3
// - github.com/confluentinc/confluent-kafka-go
```

- 🔴 构建后在目标平台检查动态依赖、启动、DNS/证书、数据库驱动和关键系统调用；容器内验证不能由宿主机编译成功替代。

## 6. 编译标志

### 6.1 推荐编译标志

🟡 生产构建标志由可复现性、崩溃符号化、调试和体积要求共同决定；`-trimpath` 通常值得评估，`-s -w` 不能作为所有服务的强制项。

```bash
# 保留注释在命令外，避免破坏 shell 续行
go build -trimpath -ldflags="-s -w" -o bin/server ./cmd/server
```

| 标志 | 作用 | 效果 |
|---|---|---|
| `-trimpath` | 移除编译时的绝对路径 | 二进制中不包含开发者机器路径（安全 + 可复现构建） |
| `-s` | 去除符号表 | 可减小体积，但会降低符号化和现场排障能力 |
| `-w` | 去除 DWARF 调试信息 | 可减小体积，但无法使用依赖 DWARF 的调试方式 |
| `-race` | 启用竞态检测器 | **仅开发/测试**，生产不要用（性能开销大） |

```bash
# 可接受：项目需要保留符号用于崩溃分析
go build -o server ./cmd/server

# 另一种选择：项目确认可以舍弃符号后压缩发布产物
go build -trimpath -ldflags="-s -w" -o server ./cmd/server
```

### 6.2 注入版本信息

🟡 推荐

```go
// cmd/server/main.go
package main

var (
    Version   = "dev"       // 编译时通过 -ldflags 注入
    Commit    = "unknown"
    BuildTime = "unknown"
)

func main() {
    fmt.Printf("server version %s (commit %s, built %s)\n", Version, Commit, BuildTime)
    // ...
}
```

```makefile
# Makefile 中自动获取 git 信息
VERSION    ?= $(shell git describe --tags --always --dirty 2>/dev/null || echo "dev")
COMMIT     ?= $(shell git rev-parse --short HEAD 2>/dev/null || echo "unknown")
BUILD_TIME ?= $(shell date -u +"%Y-%m-%dT%H:%M:%SZ")

LDFLAGS += -X main.Version=$(VERSION)
LDFLAGS += -X main.Commit=$(COMMIT)
LDFLAGS += -X main.BuildTime=$(BUILD_TIME)
```

### 6.3 可复现构建

🟡 推荐

为保证相同源码始终产生完全相同的二进制（安全审计、供应链安全）：

```bash
# 1. 固定时间戳（避免每次构建时间不同）
# 2. 使用 -trimpath 移除路径差异
# 3. 固定 Go 版本

GOOS=linux GOARCH=amd64 \
    go build \
    -trimpath \
    -ldflags="-s -w -buildid= -X main.BuildTime=reproducible" \
    -o server \
    ./cmd/server
```

> Go 1.21+ 支持 `GOFLAGS=-trimpath` 环境变量全局启用。

## 7. 与版本控制规则的衔接

> 本节与 [08-版本控制规则](08-版本控制规则.md) 互引。08 负责 Git 层面的规则，本节聚焦**构建如何响应版本事件**。

### 7.1 tag 触发构建

🟡 使用 GitHub Actions 且仓库需要 tag 发布时，可按现有工作流改造下列示例。其他 CI/CD 平台应表达相同门禁，不得照搬 GitHub 专用语法。

```yaml
# .github/workflows/ci.yml 中增加 release 构建 Job
# Action 版本、任务依赖、镜像仓库和凭据名必须替换为项目已验证配置。
name: CI

on:
  pull_request:
  push:
    branches: [main]
    tags: ['v*']  # tag 推送时触发

jobs:
  # ... lint / test / tidy（同 06-§ 5）

  release:
    name: Release Build
    if: startsWith(github.ref, 'refs/tags/v')
    needs: [lint, test, tidy]
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<项目已验证版本>

      - uses: actions/setup-go@<项目已验证版本>
        with:
          go-version-file: go.mod

      - name: 构建全平台二进制
        run: make build-all

      - name: 构建 Docker 镜像
        run: |
          VERSION=${GITHUB_REF#refs/tags/}
          docker build -t my-service:${VERSION} .
          docker tag my-service:${VERSION} my-service:latest

      - name: 推送 Docker 镜像
        run: |
          echo "${{ secrets.DOCKER_PASSWORD }}" | docker login -u "${{ secrets.DOCKER_USERNAME }}" --password-stdin
          VERSION=${GITHUB_REF#refs/tags/}
          docker push my-service:${VERSION}
          docker push my-service:latest

      - name: 上传构建产物
        uses: actions/upload-artifact@<项目已验证版本>
        with:
          name: binaries
          path: bin/
```

### 7.2 版本号与构建的对应关系

🟡 推荐

```bash
# 开发期：版本号 = dev
go build -ldflags="-X main.Version=dev" ./cmd/server

# PR 构建：版本号 = commit SHA
go build -ldflags="-X main.Version=pr-$(git rev-parse --short HEAD)" ./cmd/server

# Tag 构建：版本号 = tag
go build -ldflags="-X main.Version=$(git describe --tags)" ./cmd/server

# 正式发布：版本号 = tag（精确）
git tag v1.2.3  # 触发 CI 构建 → Docker image: v1.2.3
```
