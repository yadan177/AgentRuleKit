# 11 - Go 测试与可观测性

> - 🟢 本文件适用于需要测试、质量门禁或运行期可观测性的 Go 项目；具体范围以项目风险、部署形态和既有工具链为准。
> - 🟡 **测试部分**（§ 1-6）：编写或调整测试时按风险选择。
> - 🟡 **可观测性部分**（§ 7-9）：生产服务按现有监控体系和 SLO 选择。
> - 🔴 不适用：强迫本地脚本、一次性工具或未采用对应平台的项目引入完整测试/监控栈。

---

## 1. 测试三件套：单元 / 集成 / 端到端

### 1.1 测试金字塔

🟡 推荐：优先保持低成本测试多、跨系统测试少；下列比例只是示例，不是统一门禁。

```
         ╱  E2E  ╲        ← 少量（5-10%）：关键业务流程
       ╱ 集成测试  ╲      ← 中量（20-30%）：跨模块 / 外部依赖
     ╱   单元测试     ╲    ← 大量（60-70%）：纯逻辑 / 不依赖外部
```

| 层级 | 测什么 | 依赖 | 速度 | 占比 |
|---|---|---|---|---|
| **单元测试** | 纯函数 / 方法逻辑 | 无（mock 外部依赖） | 毫秒级 | 60-70% |
| **集成测试** | 跨模块协作 / DB / 缓存 / 消息队列 | 项目已有测试环境或真实兼容依赖 | 秒至分钟级 | 20-30% |
| **端到端测试** | 完整用户流程（HTTP → Service → DB → 响应） | 完整测试环境 | 分钟级 | 5-10% |

### 1.2 单元测试

🟡 按公开契约、风险和回归成本选择测试：

- 对关键公开行为、复杂分支、错误路径和历史缺陷编写测试；简单转发或生成代码不要求机械地逐函数补测试。
- **纯逻辑**（不依赖网络 / 文件系统 / 数据库）不 mock——直接测
- 有外部依赖时优先使用项目现有 fake、stub、mock 或集成测试方式，不默认引入 `gomock`、`testify/mock` 等依赖。
- 测试文件命名：`xxx_test.go`，放在同一 package（白盒测试）或 `xxx_test` package（黑盒测试）

```go
// 正例：纯逻辑直接测
func TestAdd(t *testing.T) {
    got := Add(2, 3)
    want := 5
    if got != want {
        t.Errorf("Add(2, 3) = %d; want %d", got, want)
    }
}

// 正例：项目没有既有 mock 工具时，可用小型手写 fake
type UserStore interface {
    GetByID(ctx context.Context, id string) (*User, error)
}

type fakeUserStore struct {
    user *User
    err  error
}

func (f fakeUserStore) GetByID(context.Context, string) (*User, error) {
    return f.user, f.err
}

func TestGetUser(t *testing.T) {
    svc := NewUserService(fakeUserStore{user: &User{Name: "Alice"}})
    user, err := svc.GetUser(context.Background(), "123")
    if err != nil {
        t.Fatalf("GetUser() error = %v", err)
    }
    if user.Name != "Alice" {
        t.Errorf("GetUser().Name = %q; want Alice", user.Name)
    }
}
```

#### 白盒测试 vs 黑盒测试

| 类型 | package 声明 | 能访问 | 适用场景 |
|---|---|---|---|
| **白盒** | `package foo` | 私有函数 / 字段 | 需要测内部实现细节 |
| **黑盒** | `package foo_test` | 仅公开 API | 模拟真实调用方；避免循环依赖 |

🟡 推荐：**优先黑盒**（`package foo_test`），测试公共 API 即契约。仅在需要测未导出函数时才用白盒。

```go
// 黑盒测试（推荐）
package user_test

import "myapp/user"

func TestGetUser(t *testing.T) {
    svc := user.NewService(...)
    // 只能调用 user.GetUser——跟真实调用方一样
}

// 白盒测试（必要时）
package user

func TestValidateEmail(t *testing.T) {
    // 能调用未导出的 validateEmail
    err := validateEmail("bad@@email")
    if err == nil {
        t.Fatal("validateEmail() error = nil; want validation error")
    }
}
```

### 1.3 集成测试

🟡 按项目现有测试环境选择：

- 集成测试应覆盖真实查询语义、约束、事务和迁移；单元测试仍可使用 fake/mock 隔离数据库，不要把两类测试相互替代。
- 优先复用仓库已有的测试数据库、容器编排、CI service、内存兼容实现或测试夹具。项目已经采用 testcontainers-go 时可以沿用；否则不得因本示例新增 Docker 或第三方依赖。
- 是否使用 `//go:build integration`、独立目录或单独 CI job，沿用项目现有测试发现和执行方式。

```go
package user_test

func TestCreateUser_Integration(t *testing.T) {
    ctx := context.Background()
    db := openProjectTestDB(t) // 使用仓库已有测试夹具
    applyProjectMigrations(t, db)

    // 执行真实查询并断言约束、事务和返回结果。
    _ = ctx
}
```

使用项目已有入口运行集成测试；下列命令仅适用于仓库已经采用该 build tag 时：

```bash
go test -tags=integration ./...
```

### 1.4 端到端测试

🟢 可选（取决于团队规模）

- 仅覆盖**关键业务流程**（注册 → 登录 → 下单 → 支付）
- 用真实 HTTP 客户端调用真实端点
- CI 中**单独 stage** 运行（时间长、不稳定）
- 不要为"验证字段格式"写 E2E——那是单元测试干的活

## 2. 表驱动测试

🟡 多组输入共享相同执行和断言结构时，优先评估表驱动测试；少量场景、不同工作流或项目已有其他清晰组织方式时不必强制转换。

> 本条与 [02-模式设计](02-模式设计.md) 的表驱动测试是同一规则。02 侧重模式定义，本条侧重测试视角的补充约定。

### 2.1 基本结构

```go
func TestParseHostPort(t *testing.T) {
    tests := []struct {
        give     string
        wantHost string
        wantPort string
    }{
        {give: "192.0.2.0:8000", wantHost: "192.0.2.0", wantPort: "8000"},
        {give: "192.0.2.0:http", wantHost: "192.0.2.0", wantPort: "http"},
        {give: ":8000",          wantHost: "",         wantPort: "8000"},
        {give: "1:8",            wantHost: "1",        wantPort: "8"},
    }
    for _, tt := range tests {
        t.Run(tt.give, func(t *testing.T) {
            host, port, err := ParseHostPort(tt.give)
            if err != nil {
                t.Fatalf("ParseHostPort() error = %v", err)
            }
            if host != tt.wantHost || port != tt.wantPort {
                t.Errorf("ParseHostPort() = (%q, %q); want (%q, %q)",
                    host, port, tt.wantHost, tt.wantPort)
            }
        })
    }
}
```

### 2.2 命名约定

🟡 推荐

| 概念 | 约定 | 说明 |
|---|---|---|
| 测试切片 | `tests` | 不变 |
| 单个用例 | `tt` | 不变 |
| 输入字段 | `give` | 被测试函数的输入 |
| 期望输出 | `want` | 期望的正确输出 |
| 期望错误 | `wantErr` | 期望的错误（字符串或 error 类型） |

### 2.3 何时不用（重要）

出现以下信号时，应评估拆为多个独立 `Test...` 函数：

- 表字段中有 `shouldCallX` / `expectCall` / `setupMocks func(...)` 等条件字段
- 循环体已经难以快速看清 arrange/act/assert
- 表字段有**半数以上**在某 case 中不被使用

> 上述信号用于识别表驱动测试已经难以阅读；项目已有测试组织方式优先，不为固定行数机械拆分。

### 2.4 并行测试

🟡 推荐：测试**只读**输入时加 `t.Parallel()` 加速

```go
for _, tt := range tests {
    t.Run(tt.give, func(t *testing.T) {
        t.Parallel()
        // 测试体
    })
}
```

> 循环变量语义由模块 `go` 版本和编译器共同决定。检查 `go.mod` 后再判断是否需要 `tt := tt`，不能只看本机编译器版本。

### 2.5 断言方式选择

- 标准库 `testing` 足以表达简单断言，且不增加依赖。
- 项目已经采用 testify、gotest.tools、cmp 或自定义 helper 时，沿用其错误信息和失败控制约定。
- 未采用断言库时，不得仅因本节示例新增依赖；需要减少重复时先评估小型 `t.Helper()`。

## 3. Fuzz 测试

🟡 解析器、编码器和安全敏感输入边界适合评估 fuzz；是否作为门禁取决于风险、语料质量和 CI 预算。

### 3.1 什么是 Fuzz 测试

Go 1.18+ 原生支持的模糊测试：不断生成随机输入，直到找到导致 panic / 错误 / 超时的输入。

### 3.2 基本写法

```go
// 文件名：xxx_test.go
func FuzzParseHostPort(f *testing.F) {
    // 种子语料（可选但推荐——让 fuzzer 从合理输入开始）
    f.Add("192.0.2.0:8000")
    f.Add(":8080")
    f.Add("[::1]:80")

    f.Fuzz(func(t *testing.T, input string) {
        // Fuzz 目标：ParseHostPort 对任何输入都不应 panic
        host, port, err := ParseHostPort(input)
        if err != nil {
            t.Skip() // 解析失败是可接受的
        }
        // 如果没报错，host 和 port 不应为空字符串（业务不变量）
        if host == "" && port == "" {
            t.Errorf("both host and port empty for input %q", input)
        }
    })
}
```

### 3.3 运行

```bash
# 运行 fuzz（默认无限时间，直到 Ctrl-C）
go test -fuzz=FuzzParseHostPort -fuzztime=30s ./...

# CI 如需继续生成随机输入，可设置受控 fuzz 时间
go test -fuzz=FuzzParseHostPort -fuzztime=10s ./...

# 普通 go test 会回归已保存的种子和失败 corpus，不会启动持续 fuzz
go test ./...
```

### 3.4 什么代码该加 fuzz

🔴 必加约束

| 代码类型 | 为什么 | 示例 |
|---|---|---|
| **输入解析器**（JSON / YAML / URL / 正则） | 恶意输入最常见入口 | `ParseConfig` / `ParseURL` |
| **编码器 / 解码器** | 边界输入导致 panic | `Encode` / `Decode` |
| **校验函数** | 边界输入绕过校验 | `ValidateEmail` / `SanitizeHTML` |
| **协议实现**（HTTP / gRPC / 自定义协议） | 畸形包导致 panic | `ParseHTTPHeader` |
| **字符串 / 字节处理** | 空字符串、超长、特殊字符 | `Truncate` / `Normalize` |

### 3.5 Fuzz 原则

🟡 推荐

- **关注不变量**：不管输入多奇怪，某些条件应该成立（如"无报错时 host+port 至少一个非空"）
- **不关心性能**：fuzz 目标是找 bug，不是 benchmark
- **先 Add 种子**：让 fuzzer 从合理输入开始，更快覆盖分支
- **区分回归与继续探索**：普通 `go test` 回归 corpus；`-fuzz` 会继续生成新输入

## 4. Benchmark

🔴 必加约束：任何声称"更快"的改动，**必须附带 benchmark 结果对比**

> 本条与  互引。03 侧重**benchmark 写法 + 陷阱**，本条侧重**命名规范 + 报告格式 + 子 benchmark**。

### 4.1 命名规范

🟡 推荐

| 类型 | 命名 | 示例 |
|---|---|---|
| 基准测试函数 | `BenchmarkXxx` | `BenchmarkParseHostPort` |
| 子 benchmark | `BenchmarkXxx/场景` | `BenchmarkParseHostPort/IPv4` |
| 对比 benchmark | `BenchmarkXxx_Old` / `BenchmarkXxx_New` | 临时对比，不应提交 |

### 4.2 基本结构

```go
func BenchmarkParseHostPort(b *testing.B) {
    input := "192.0.2.0:8000"

    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        _, _, _ = ParseHostPort(input)
    }
}
```

### 4.3 子 benchmark（多场景对比）

```go
func BenchmarkParseHostPort(b *testing.B) {
    tests := []struct {
        name  string
        input string
    }{
        {"IPv4", "192.0.2.0:8000"},
        {"IPv6", "[2001:db8::1]:80"},
        {"NoPort", "192.0.2.0"},
        {"Empty", ""},
    }

    for _, tt := range tests {
        b.Run(tt.name, func(b *testing.B) {
            b.ReportAllocs()
            for i := 0; i < b.N; i++ {
                _, _, _ = ParseHostPort(tt.input)
            }
        })
    }
}
```

### 4.4 运行与结果解读

```bash
# 基础运行
go test -bench=. -benchmem ./...

# 指定时间以获得更稳定结果
go test -bench=. -benchmem -benchtime=3s ./...

# 对比两次 benchmark（benchstat）
go test -bench=. -benchmem -count=5 > old.txt
# ... 修改代码 ...
go test -bench=. -benchmem -count=5 > new.txt
benchstat old.txt new.txt
```

### 4.5 Benchmark 报告格式

🟡 推荐：提交性能 PR 时，在 PR 描述中附带 `benchstat` 输出：

```
name              old time/op    new time/op    delta
ParseHostPort-8    123ns ± 2%      85ns ± 3%   -30.89%  (p=0.000 n=5+5)

name              old alloc/op   new alloc/op   delta
ParseHostPort-8     48B ± 0%       32B ± 0%   -33.33%  (p=0.000 n=5+5)

name              old allocs/op  new allocs/op  delta
ParseHostPort-8      2.0 ± 0%       1.0 ± 0%   -50.00%  (p=0.000 n=5+5)
```

### 4.6 常见陷阱

> 完整陷阱列表见 （含 `b.ResetTimer` / 防编译器优化 / `benchstat` 对比）。关键提醒：

- **忘记 `b.ResetTimer()`**：准备工作时间被计入
- **编译器优化掉被测代码**：把结果赋给包级变量阻止优化
- **`b.N` 太小**：`-benchtime=3s` 加长时间

## 5. Example 测试

🟡 推荐：**公开 API 的包**必须写 example 测试

### 5.1 基本写法

```go
// 文件名：xxx_test.go
func ExampleParseHostPort() {
    host, port, err := ParseHostPort("192.0.2.0:8000")
    if err != nil {
        fmt.Println("error:", err)
        return
    }
    fmt.Println(host, port)
    // Output:
    // 192.0.2.0 8000
}
```

### 5.2 命名约定

| 示例类型 | 命名 | godoc 显示 |
|---|---|---|
| 包级示例 | `func Example() { ... }` | 包文档顶部 |
| 函数示例 | `func ExampleParseHostPort() { ... }` | `ParseHostPort` 函数文档中 |
| 类型示例 | `func ExampleUser() { ... }` | `User` 类型文档中 |
| 方法示例 | `func ExampleUser_Name() { ... }` | `User.Name` 方法文档中 |
| 多示例 | `func ExampleParseHostPort_ipv6() { ... }` | 下划线后缀区分多个示例 |

### 5.3 为什么重要

- **godoc 可执行**：`// Output:` 注释会被 `go test` 验证——示例即测试
- **最好的文档**：比注释更直观，调用方复制粘贴就能跑
- **防止 API 腐化**：修改函数签名时 example 编译失败 → 立即发现

### 5.4 什么必须写 example

🟡 按项目的公开 API、示例价值和维护成本选择：

- 对需要展示典型用法的公开包或核心 API 编写 example；不要求机械覆盖每个公开符号。
- 复杂类型（如 `Server` / `Client`）写"端到端" example：从构造到调用到关闭

## 6. 覆盖率门槛

🔴 覆盖率阈值必须采用仓库已有门禁或由团队根据风险明确设定；没有项目依据时不得自行写入固定百分比。

### 6.1 最低标准

| 层级 | 覆盖率要求 | 说明 |
|---|---|---|
| **package 级别** | 项目既有阈值 | 用于发现覆盖回退，不以单一数字代替测试质量 |
| **关键路径** | 按风险定义场景 | 优先覆盖成功、失败、权限和数据一致性路径 |
| **纯工具函数** | 按分支与边界 | 成本较低时充分覆盖，但不强制统一百分比 |

### 6.2 运行与检查

```bash
# 查看每包覆盖率
go test -cover ./...

# 生成 HTML 覆盖率报告
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out -o coverage.html

# CI 阈值检查应复用仓库已有脚本；没有脚本时先由团队确定阈值和统计口径
```

### 6.3 `.golangci.yml` 覆盖率配置（可选）

🟢 可选

```yaml
# .golangci.yml
issues:
  exclude-rules:
    # 排除测试文件的某些检查
    - path: _test\.go
      linters:
        - errcheck
        - gosec
```

### 6.4 覆盖率不是一切

🟡 推荐：**80% 覆盖率 ≠ 好测试**

| 好测试的特征 | 坏测试的特征 |
|---|---|
| 测行为，不测实现 | 一行一个 `assert`，没有业务语义 |
| 失败时一眼看出问题 | 失败信息是 `expected true, got false` |
| 改了实现不改行为时测试仍绿 | 改一行代码 50 个测试挂 |
| 读测试能理解 API 用法 | 读测试看不懂被测函数在干什么 |

## 7. Metrics（Prometheus）

🟡 需要 SLO、容量管理或运行时告警的服务应接入项目既有 metrics 系统；短命令、离线任务和由平台统一采集的服务不强制暴露 HTTP metrics。

### 7.1 指标命名规范

遵循 [Prometheus 命名最佳实践](https://prometheus.io/docs/practices/naming/)：

```
<namespace>_<subsystem>_<name>_<unit>
```

| 组成部分 | 说明 | 示例 |
|---|---|---|
| **namespace** | 应用 / 公司名 | `myapp` |
| **subsystem** | 子系统 / 模块名 | `api` / `db` / `cache` |
| **name** | 指标含义 | `request_duration` / `active_connections` |
| **unit** | 存在物理单位时使用基础单位后缀 | `seconds` / `bytes`；`total` 表示累计计数语义，不是单位 |

```go
// 正例：完整命名
myapp_api_request_duration_seconds
myapp_db_query_duration_seconds
myapp_cache_hit_ratio

// 反例：缺 unit
myapp_api_request_duration     // 秒还是毫秒？
myapp_db_query_time            // 是 duration 还是 timestamp？
```

### 7.2 四种指标类型

| 类型 | 用途 | 示例 |
|---|---|---|
| **Counter** | 只增不减的计数 | 请求总数、错误总数、处理的字节数 |
| **Gauge** | 可增可减的瞬时值 | 当前连接数、内存使用量、队列深度 |
| **Histogram** | 分布（分桶统计） | 请求延迟分布、响应大小分布 |
| **Summary** | 分位数（客户端计算） | P50 / P90 / P99 延迟（不推荐——见下文） |

### 7.3 推荐：Histogram 而非 Summary

🟡 推荐

- **Histogram**：服务端分桶，可以跨服务聚合。**推荐**。
- **Summary**：客户端计算分位数，无法跨服务聚合。**不推荐**，除非单机场景。

```go
// 正例：Histogram
var requestDuration = prometheus.NewHistogramVec(
    prometheus.HistogramOpts{
        Name:    "myapp_api_request_duration_seconds",
        Help:    "API request duration in seconds.",
        Buckets: prometheus.DefBuckets, // .005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5, 10
    },
    []string{"method", "endpoint", "status"},
)
```

### 7.4 常见服务指标

下列指标是常见起点，实际集合必须由 SLO、流量模型、框架自动埋点和成本决定，不能要求每个服务机械复制。

| 指标 | 类型 | 说明 |
|---|---|---|
| `{app}_api_request_duration_seconds` | Histogram | 请求延迟分布 |
| `{app}_api_requests_total` | Counter | 请求总数（按 method / endpoint / status 分组） |
| `{app}_api_requests_in_flight` | Gauge | 正在处理的请求数 |
| `{app}_api_errors_total` | Counter | 错误总数（按 error_type 分组） |

### 7.6 自定义指标示例

```go
var (
    dbQueryDuration = prometheus.NewHistogramVec(
        prometheus.HistogramOpts{
            Name:    "myapp_db_query_duration_seconds",
            Help:    "Database query duration in seconds.",
            Buckets: []float64{.001, .005, .01, .025, .05, .1, .25, .5, 1, 2.5, 5},
        },
        []string{"query", "table"},
    )

    dbQueryErrors = prometheus.NewCounterVec(
        prometheus.CounterOpts{
            Name: "myapp_db_query_errors_total",
            Help: "Total number of database query errors.",
        },
        []string{"query", "error_type"},
    )
)

func init() {
    prometheus.MustRegister(dbQueryDuration, dbQueryErrors)
}

func queryDB(ctx context.Context, sql string) error {
    timer := prometheus.NewTimer(dbQueryDuration.WithLabelValues("get_user", "users"))
    defer timer.ObserveDuration()

    err := db.QueryContext(ctx, sql)
    if err != nil {
        dbQueryErrors.WithLabelValues("get_user", "timeout").Inc()
    }
    return err
}
```

### 7.7 Label 使用原则

🔴 必加约束

- Label 数量和取值组合必须经过基数预算；固定“最多 5 个”不能替代时间序列规模评估。
- **Label 值基数要低**——不要用 `user_id` / `request_id` 做 label（基数无限）
- **枚举值用 label**（`method` / `status` / `endpoint`），**唯一值用日志 / trace**（`user_id` / `trace_id`）

```go
// 正例：低基数 label
[]string{"method", "endpoint", "status"} // 组合有限

// 反例：高基数 label——时间序列爆炸
[]string{"user_id", "request_id"} // 每个请求一条新序列
```

## 8. Tracing（OpenTelemetry）

🟡 跨服务调用复杂、需要端到端定位且平台已有采集链路时，优先沿用 OpenTelemetry 或项目现有 tracing。不要为满足规则给所有微服务强制新增依赖。

### 8.1 最小化接入

```go
package main

import (
    "context"
    "fmt"
    "log"
    "os"
    "time"

    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/exporters/otlp/otlptrace/otlptracegrpc"
    "go.opentelemetry.io/otel/sdk/resource"
    "go.opentelemetry.io/otel/sdk/trace"
    semconv "go.opentelemetry.io/otel/semconv/v1.26.0"
)

func initTracer(ctx context.Context) (*trace.TracerProvider, error) {
    // 创建 OTLP exporter（gRPC 协议，发送到 collector）
    exporter, err := otlptracegrpc.New(ctx,
        otlptracegrpc.WithEndpoint("otel-collector:4317"),
        // TLS、mTLS 或受控明文由 collector 拓扑和部署环境配置；生产示例不默认 WithInsecure。
    )
    if err != nil {
        return nil, fmt.Errorf("create otlp exporter: %w", err)
    }

    // 创建 TracerProvider
    tp := trace.NewTracerProvider(
        trace.WithBatcher(exporter),
        trace.WithResource(resource.NewWithAttributes(
            semconv.SchemaURL,
            semconv.ServiceName("myapp"),
            semconv.ServiceVersion("1.0.0"),
            semconv.DeploymentEnvironmentKey.String("production"),
        )),
    )

    // 设置全局 TracerProvider
    otel.SetTracerProvider(tp)

    return tp, nil
}

func run() (err error) {
    ctx := context.Background()

    tp, err := initTracer(ctx)
    if err != nil {
        return err
    }
    defer func() {
        shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
        defer cancel()
        if shutdownErr := tp.Shutdown(shutdownCtx); shutdownErr != nil && err == nil {
            err = fmt.Errorf("shutdown tracer provider: %w", shutdownErr)
        }
    }()

    // ... 业务逻辑
    return nil
}

func main() {
    if err := run(); err != nil {
        log.Print(err)
        os.Exit(1) // run 已返回，内部 defer 已执行完毕。
    }
}
```

### 8.2 Span 命名规范

🟡 推荐

| Span 类型 | 命名格式 | 示例 |
|---|---|---|
| HTTP handler | `HTTP {method} {route}` | `HTTP GET /users/:id` |
| gRPC handler | `gRPC {service}/{method}` | `gRPC user.UserService/GetUser` |
| DB 查询 | `DB {operation} {table}` | `DB SELECT users` |
| 缓存操作 | `Cache {operation}` | `Cache GET` |
| 外部调用 | `HTTP {method} {host}` | `HTTP POST api.stripe.com` |

```go
func GetUser(ctx context.Context, id string) (*User, error) {
    tracer := otel.Tracer("user-service")
    ctx, span := tracer.Start(ctx, "DB SELECT users")
    defer span.End()

    span.SetAttributes(
        attribute.String("db.table", "users"),
        attribute.String("db.operation", "SELECT"),
        attribute.String("user.id", id),
    )

    // ... 查询逻辑
}
```

### 8.3 Span 属性

🟡 按 span 类型设置有诊断价值且低基数的语义属性。Resource 属性由 TracerProvider 配置，不需要在每个 span 重复设置。

| 属性 | 说明 | 示例 |
|---|---|---|
| `service.name` | 服务名（Resource 级别） | `user-service` |
| `http.method` / `rpc.method` | 请求方法 | `GET` / `POST` |
| `http.route` | 路由模板 | `/users/:id` |
| `http.status_code` | 响应状态码 | `200` / `500` |
| `db.system` | 数据库类型 | `postgresql` / `redis` |
| `db.operation` | 数据库操作 | `SELECT` / `INSERT` |

### 8.4 Context 传递

🔴 必加约束：父子 span 关系通过 `context.Context` 传播。Tracer 可从全局 TracerProvider 获取或注入；全局 tracer 本身不会破坏父子关系。

```go
// Tracer 可复用；创建子 span 时仍必须传入上游 ctx
var tracer = otel.Tracer("user-service")

// 正例：从 context 获取或创建 span
func (s *Service) GetUser(ctx context.Context, id string) (*User, error) {
    ctx, span := tracer.Start(ctx, "GetUser")
    defer span.End()

    // 传递给下层
    user, err := s.store.GetByID(ctx, id) // ctx 携带 span context
    if err != nil {
        span.RecordError(err)
        span.SetStatus(codes.Error, err.Error())
        return nil, err
    }
    return user, nil
}
```

### 8.5 错误处理

🔴 必加约束

- 在最能表达失败语义的 span 边界记录错误，避免同一 error 在每层重复记录；错误描述需去敏。
- **正常返回时**：span 自动 OK 状态（或显式 `span.SetStatus(codes.Ok, "")`）
- **panic recover 时**：记录 error 到 span

```go
func DoWork(ctx context.Context) (err error) {
    ctx, span := otel.Tracer("worker").Start(ctx, "DoWork")
    defer span.End()

    defer func() {
        if r := recover(); r != nil {
            span.RecordError(fmt.Errorf("panic: %v", r))
            span.SetStatus(codes.Error, "panic recovered")
            err = fmt.Errorf("worker panic: %v", r) // 或按进程边界策略重新 panic，不能吞掉后返回 nil
        }
    }()

    if err = doRiskyWork(ctx); err != nil {
        span.RecordError(err)
        span.SetStatus(codes.Error, err.Error())
        return err
    }
    return nil
}
```

## 9. 告警阈值

🟡 需要值班和 SLO 的生产服务应配置可行动的告警。阈值必须来自业务 SLO、历史基线、容量和错误预算；下列数值只能作为讨论示例，不能直接成为通用门禁。

### 9.1 黄金信号（Four Golden Signals）

| 信号 | 指标 | 告警阈值 | 说明 |
|---|---|---|---|
| **延迟（Latency）** | `p99 request duration` | > 1s 持续 5 分钟 | p99 而非 avg——avg 会掩盖长尾 |
| **流量（Traffic）** | `requests per second` | 偏离基线 ± 50% 持续 10 分钟 | 突增（攻击）或突降（故障）|
| **错误（Errors）** | `error rate` | > 1% 持续 5 分钟 | 5xx / timeout / 业务错误 |
| **饱和度（Saturation）** | `goroutine count` / `queue depth` / `connection pool usage` | > 80% 容量 | 逼近瓶颈的早期信号 |

### 9.2 告警规则示例（Prometheus）

```yaml
# prometheus-rules.yml
groups:
  - name: myapp_alerts
    rules:
      # 延迟
      - alert: HighLatency
        expr: |
          histogram_quantile(0.99,
            rate(myapp_api_request_duration_seconds_bucket[5m])
          ) > 1
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "API p99 latency > 1s"
          description: "Endpoint {{ $labels.endpoint }} p99 latency is {{ $value }}s"

      # 错误率
      - alert: HighErrorRate
        expr: |
          rate(myapp_api_errors_total[5m]) /
          rate(myapp_api_requests_total[5m]) > 0.01
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Error rate > 1%"
          description: "Error rate is {{ $value | humanizePercentage }}"

      # 饱和度——goroutine 数量
      - alert: HighGoroutineCount
        expr: go_goroutines > 10000
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: "Goroutine count > 10000"
          description: "Current goroutine count is {{ $value }}"
```

### 9.3 告警设计原则

🟡 推荐

| 原则 | 说明 |
|---|---|
| **告警要有行动** | 收到告警的人必须知道该做什么——否则是噪音 |
| **告警要有优先级** | `critical`（立即响应）> `warning`（工作时间处理）> `info`（仅记录） |
| **避免告警疲劳** | 同一问题不要重复告警；用 `for: 5m` 过滤瞬时抖动 |
| **告警要关联 runbook** | `annotations.runbook_url` 指向修复步骤 |
| **分页只在紧急时** | 凌晨 3 点只对 `critical` 告警发 page |

### 9.4 Go 运行时指标

🟡 已采用 Prometheus 客户端的 Go 服务可按 SLO 和故障模式选择下列运行时指标；未采用 Prometheus 时映射到项目现有监控体系，不为套用示例新增依赖。

| 指标 | 含义 | 告警建议 |
|---|---|---|
| `go_goroutines` | 当前 goroutine 数量 | 结合服务基线、负载和泄漏趋势设阈值 |
| `go_memstats_alloc_bytes` | 当前堆内存分配 | 结合容器/主机内存限制设阈值 |
| `go_gc_duration_seconds` | GC 停顿时间 | 结合延迟 SLO 和历史分位值设阈值 |
| `go_threads` | OS 线程数 | 结合正常基线和持续增长趋势判断 |
