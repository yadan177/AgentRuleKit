# 05 - Go 数据库与持久化

> - 🟢 本文件适用于 **Go 项目中所有与关系型数据库交互的代码**（MySQL / PostgreSQL / SQLite 等）
> - 🔴 **不适用**：NoSQL（MongoDB / Redis / Elasticsearch）、消息队列、对象存储
> - 🟡 示例主要使用 `database/sql`/sqlx；GORM、sqlc+pgx 等方案不一定建立在 `database/sql` 上，必须按项目实际驱动和生成配置判断

---

## 1. 选型：用哪种库

### 1.1 决策表

🟡 下表仅用于比较常见方案；新项目先根据已有依赖、SQL 复杂度、团队经验和运维约束决策，不得强制限定为四选一或未经授权新增库。

| 库 | 抽象层级 | 主要特征 | 学习成本 | 可能适用的场景 |
|---|---|---|---|---|
| **`database/sql` + 手写 SQL** | 低 | 标准接口、显式 SQL；运行成本取决于驱动和查询 | 中 | 项目已采用标准接口或需要直接控制 SQL |
| **`jmoiron/sqlx`** | 低 | 在显式 SQL 上增加扫描和命名参数便利 | 低至中 | 项目已采用 sqlx 或确需薄封装 |
| **`sqlc`** | 低 | 从 SQL 生成类型安全接口，需要生成链与数据库方言支持 | 中 | 项目已采用生成流程或团队选择 SQL 优先方案 |
| **`gorm.io/gorm`** | 高 | ORM 映射与链式查询；需要观察生成 SQL 和迁移行为 | 中 | 项目已采用 GORM 或明确选择 ORM |

```go
// database/sql：最底层，完全手动
rows, err := db.QueryContext(ctx, "SELECT id, name FROM users WHERE status = ?", status)

// sqlx：薄封装，结构体自动映射
var users []User
err := db.SelectContext(ctx, &users, "SELECT id, name FROM users WHERE status = ?", status)

// sqlc：从 SQL 生成类型安全代码（编译期检查）
users, err := queries.ListUsersByStatus(ctx, status)

// GORM：全 ORM，链式调用
var users []User
db.Where("status = ?", status).Find(&users)
```

### 1.2 决策依据

1. 已有驱动、查询层、生成链、migration 方式和团队维护经验。
2. 目标数据库与方言、事务需求、查询复杂度、类型生成和可观测性要求。
3. 部署连接模型、性能证据、测试环境、升级兼容和供应链约束。
4. 新项目可以比较 `database/sql`、sqlx、sqlc、GORM 或其他候选，但必须由项目负责人确认；不能按“原型/长期维护/高吞吐”标签直接指定库。

性能结论必须来自目标驱动、真实查询、连接池配置和 benchmark/profile；不能把抽象层级直接等同于吞吐或延迟。

### 1.3 `sqlx` 示例

🟡 项目已采用 sqlx 或明确需要薄封装与结构体映射时可参考本节。它不是大多数项目的默认答案，也不得因本示例新增依赖。

```go
import (
    "github.com/jmoiron/sqlx"
    _ "github.com/lib/pq" // PostgreSQL 驱动
)

// 连接
db, err := sqlx.ConnectContext(ctx, "postgres", dsn)

// 查询单条
var user User
err := db.GetContext(ctx, &user, "SELECT * FROM users WHERE id = $1", id)

// 查询多条
var users []User
err := db.SelectContext(ctx, &users, "SELECT * FROM users WHERE status = $1", status)

// 执行修改
result, err := db.ExecContext(ctx, "UPDATE users SET name = $1 WHERE id = $2", name, id)

// 命名参数
query := `SELECT * FROM users WHERE name = :name AND status = :status`
rows, err := db.NamedQueryContext(ctx, query, map[string]any{
    "name":   name,
    "status": status,
})
```

### 1.4 GORM 使用约束

🔴 必加约束：如果项目选择了 GORM，必须遵守以下约束

```go
// 反例：GORM 隐式行为——软删除全局生效，新人不知道
db.Where("id = ?", id).Find(&user) // 自动加了 deleted_at IS NULL

// 反例：链式调用中忽略错误
db.Where("name = ?", name).Find(&users) // 没有处理返回的 *gorm.DB

// 反例：N+1 预加载不显式声明
db.Preload("Orders").Preload("Orders.Items").Find(&users) // 嵌套预加载不直观

// 正例：显式处理每一步错误
result := db.WithContext(ctx).Where("name = ?", name).Find(&users)
if result.Error != nil {
    return fmt.Errorf("find users: %w", result.Error)
}

// 可选方案：Raw SQL 比链式调用更易审查时，显式列出 SQL 并检查错误
result = db.WithContext(ctx).Raw(`
    SELECT u.id, u.name, COUNT(o.id) AS order_count
    FROM users AS u
    LEFT JOIN orders AS o ON o.user_id = u.id
    WHERE u.status = ?
    GROUP BY u.id, u.name`, status).Scan(&results)
if result.Error != nil {
    return fmt.Errorf("summarize user orders: %w", result.Error)
}
```

**GORM 核心约束**：

| 约束 | 说明 |
|---|---|
| **请求链路透传 context** | 项目使用 GORM 且上游已有 context 时，通过 `db.WithContext(ctx)` 保留取消与超时 |
| **检查 Error** | 每个链式调用末尾都要 `.Error` 检查 |
| **复杂查询保持可读与可观测** | 链式 API 难以表达、验证或分析时评估 Raw SQL；不以 JOIN 表数量设固定阈值 |
| **显式禁用软删除** | 需要查已删记录时 `db.Unscoped().Find(...)` |
| **迁移策略服从项目门禁** | 是否使用 AutoMigrate、独立 migration 或平台工具，由既有发布和回滚流程决定 |

## 2. 连接池配置

### 2.1 连接池边界

🔴 生产环境必须核对驱动或连接池的容量、空闲回收、连接生命周期、数据库总连接预算和副本数。是否显式覆盖每个默认值，取决于当前驱动、代理和部署平台；不写死通用数字。

```go
db, err := sql.Open("postgres", dsn)
if err != nil {
    return nil, err
}

// 数值由配置系统提供，并通过连接预算和压测确认。
db.SetMaxOpenConns(cfg.MaxOpenConns)
db.SetMaxIdleConns(cfg.MaxIdleConns)
db.SetConnMaxLifetime(cfg.ConnMaxLifetime)
db.SetConnMaxIdleTime(cfg.ConnMaxIdleTime)
```

| 参数 | 决策依据 | 目的 |
|---|---|---|
| `MaxOpenConns` | 由实例副本数、数据库连接预算、查询时延和压测确定 | 防止耗尽 DB 连接 |
| `MaxIdleConns` | 根据突发流量和空闲连接成本确定 | 平衡内存占用与连接复用 |
| `ConnMaxLifetime` | 小于代理/数据库连接生命周期，并加入适当抖动 | 避免连接集中失效 |
| `ConnMaxIdleTime` | 根据数据库和流量空闲周期确定 | 回收不再需要的连接 |

### 2.2 连接池配置反模式

```go
// 反例：未核对 database/sql 默认行为、数据库限额和服务副本数
db, err := sql.Open(driverName, dsn)

// 反例：从其他项目复制容量和生命周期，没有目标环境证据
db.SetMaxOpenConns(25)
db.SetConnMaxLifetime(5 * time.Minute)

// 正例：配置来自环境变量或配置文件
db.SetMaxOpenConns(cfg.DBMaxOpenConns)
db.SetMaxIdleConns(cfg.DBMaxIdleConns)
db.SetConnMaxLifetime(cfg.DBConnMaxLifetime)
db.SetConnMaxIdleTime(cfg.DBConnMaxIdleTime)
```

### 2.3 连接健康检查

🟡 服务启动是否必须等待数据库可用，由启动、就绪检查和容灾契约决定。需要启动验证时，用有界 context 执行 `PingContext`。

```go
func NewDB(ctx context.Context, cfg DBConfig) (*sql.DB, error) {
    db, err := sql.Open(cfg.Driver, cfg.DSN)
    if err != nil {
        return nil, fmt.Errorf("open db: %w", err)
    }
    db.SetMaxOpenConns(cfg.MaxOpenConns)
    db.SetMaxIdleConns(cfg.MaxIdleConns)
    db.SetConnMaxLifetime(cfg.ConnMaxLifetime)
    db.SetConnMaxIdleTime(cfg.ConnMaxIdleTime)

    pingCtx, cancel := context.WithTimeout(ctx, cfg.PingTimeout)
    defer cancel()
    if err := db.PingContext(pingCtx); err != nil {
        _ = db.Close()
        return nil, fmt.Errorf("ping db: %w", err)
    }
    return db, nil
}
```

### 2.4 `database/sql` 连接池原理

🟢 可选理解

```
sql.Open() 通常只初始化池句柄；是否验证 DSN 由驱动实现决定
PingContext() 或首次查询才会验证实际连接
连接用完后放回池子（不是关闭）
idle 连接数 > MaxIdleConns 时关闭多余连接
连接存活超过 ConnMaxLifetime 时关闭
```

> `sql.DB` 是并发安全的长生命周连接池句柄。通常由组合根创建并共享；读写分离、多租户或多数据库可合理使用多个实例，但每个池都要纳入总连接预算并在关闭时释放。

## 3. 事务边界

### 3.1 事务边界对齐业务原子性

🔴 事务覆盖必须一起成功或失败的数据库操作，不按 handler/service/repository 的方法数量机械划分。事务所有者应位于能看到完整一致性需求的应用层边界。

```go
// 反例：HTTP handler 不理解完整业务边界却直接控制事务
func createOrder(w http.ResponseWriter, r *http.Request) {
    tx, _ := db.Begin() // handler 不应该知道事务存在
    // ... 业务逻辑
    tx.Commit()
}

// 正例：应用服务根据这个用例的原子性管理事务
func (s *OrderService) CreateOrder(ctx context.Context, req CreateOrderReq) (*Order, error) {
    tx, err := s.db.BeginTxx(ctx, nil)
    if err != nil {
        return nil, fmt.Errorf("begin tx: %w", err)
    }
    defer tx.Rollback() // 函数返回时尝试回滚；Commit 后的 sql.ErrTxDone 在此可忽略

    // 1. 扣减库存
    if err := s.inventoryRepo.Deduct(ctx, tx, req.ProductID, req.Quantity); err != nil {
        return nil, fmt.Errorf("deduct inventory: %w", err)
    }
    // 2. 创建订单
    order, err := s.orderRepo.Create(ctx, tx, req)
    if err != nil {
        return nil, fmt.Errorf("create order: %w", err)
    }
    // 3. 创建支付单
    if err := s.paymentRepo.Create(ctx, tx, order.ID, req.Amount); err != nil {
        return nil, fmt.Errorf("create payment: %w", err)
    }

    return order, tx.Commit()
}
```

**事务传递模式（仅用于项目已采用 sqlx 且接口明确允许传递事务时）**：

```go
// repository 接口：接受 tx 参数
type InventoryRepo interface {
    Deduct(ctx context.Context, tx *sqlx.Tx, productID string, qty int) error
}

// 实现：有 tx 用 tx，没有用 db
func (r *inventoryRepo) Deduct(ctx context.Context, tx *sqlx.Tx, productID string, qty int) error {
    exec := r.getExecer(tx) // tx != nil → tx；tx == nil → db
    _, err := exec.ExecContext(ctx, "UPDATE inventory SET qty = qty - $1 WHERE product_id = $2", qty, productID)
    return err
}

func (r *inventoryRepo) getExecer(tx *sqlx.Tx) sqlx.ExecerContext {
    if tx != nil {
        return tx
    }
    return r.db
}
```

### 3.2 defer Rollback 模式

🔴 必加约束

```go
tx, err := db.BeginTxx(ctx, nil)
if err != nil {
    return fmt.Errorf("begin tx: %w", err)
}
defer tx.Rollback() // 保证异常时回滚

// ... 业务操作

return tx.Commit() // Commit 后 defer 中的 Rollback 通常返回 sql.ErrTxDone
```

> `defer tx.Rollback()` 是安全的惯用模式，但 `Commit()` 成功后再次 Rollback 通常返回 `sql.ErrTxDone`，不能描述为“不会报错”。defer 中可忽略该预期结果；显式回滚流程仍应处理真正的回滚错误。

### 3.3 事务超时

🔴 事务必须受有界 context 或等价的数据库端超时策略约束。时长来自请求/任务契约、查询特征和运维预算，`5s` 不是通用值。

```go
// 反例：无超时的事务——慢查询可能无限占用连接
tx, err := db.Begin()

// 正例：context 超时控制整个事务
ctx, cancel := context.WithTimeout(ctx, cfg.TransactionTimeout)
defer cancel()
tx, err := db.BeginTxx(ctx, nil)
```

### 3.4 事务中不要做的事

🔴 必加约束

| 高风险操作 | 原因 | 处理原则 |
|---|---|---|
| **外部 HTTP/RPC 调用** | 时长不可控，且数据库回滚不能撤销外部副作用 | 优先用 outbox、saga、预留/确认或幂等补偿；不能只调换调用顺序 |
| **直接发消息** | 事务回滚后消息可能已发出 | 按项目一致性契约使用 outbox 或其他可恢复机制 |
| **大量查询或长时计算** | 长时间占用连接和锁 | 缩短事务临界区；但不得把依赖一致性快照的读取擅自移出 |
| **嵌套事务假设** | `database/sql` 不提供通用嵌套事务 API | 根据数据库和驱动能力显式设计 savepoint 或重构边界 |

```go
// 反例：事务中发 HTTP
tx, _ := db.Begin()
// ... 写数据库
resp, _ := http.Post(url, ...) // 如果这里超时 30 秒，事务一直持有锁
tx.Commit()

// 具体改写取决于一致性需求。简单地调换 HTTP 与事务顺序，仍可能在数据库提交失败时
// 留下无法撤销的外部副作用，不能作为通用正例。
```

### 3.5 只读事务

🟡 多条查询需要同一一致性快照、显式隔离级别或数据库只读保护时，可评估只读事务。单条普通查询不必为形式一致额外开启事务；语义由目标数据库、驱动和隔离级别决定。

```go
// 向驱动/数据库声明只读意图；实际优化与隔离语义由数据库决定
tx, err := db.BeginTxx(ctx, &sql.TxOptions{ReadOnly: true})
if err != nil {
    return err
}
defer tx.Rollback()

// 是否共享可重复读快照取决于显式隔离级别和数据库默认配置
var stats Stats
if err := tx.GetContext(ctx, &stats.UserCount, "SELECT COUNT(*) FROM users"); err != nil {
    return err
}
if err := tx.GetContext(ctx, &stats.OrderCount, "SELECT COUNT(*) FROM orders"); err != nil {
    return err
}
return tx.Commit()
```

### 3.6 Savepoint（部分回滚）

🟢 可选：项目已验证目标数据库、驱动和事务抽象对 savepoint 的支持，且业务确需部分回滚时使用。实际代码必须处理开启事务、每次执行、回滚、释放和提交的错误；下例只展示数据库支持时的 SQL 顺序。

```sql
SAVEPOINT sp1;
-- 执行可能需要部分回滚的操作
ROLLBACK TO SAVEPOINT sp1;
RELEASE SAVEPOINT sp1;
```

## 4. Migration

### 4.1 方案对比

🔴 生产 schema 变更必须纳入项目现有的版本化、审查、执行、失败恢复和漂移检测流程。不得因为本文档的工具示例引入新依赖，也不在未确认环境和回滚策略时让应用启动自动改写生产 schema。

| 工具 | 方式 | 适用场景 |
|---|---|---|
| [**golang-migrate**](https://github.com/golang-migrate/migrate) | SQL 文件 + Go 库/CLI | 项目已采用时沿用其版本和执行流程 |
| [**goose**](https://github.com/pressly/goose) | SQL 文件或 Go 函数 | 项目已需要并审核 Go 迁移逻辑时可用 |
| [**atlas**](https://atlasgo.io/) | 声明式 schema 与 migration | 项目已采用其生成、校验和部署流程时可用 |
| **受控 SQL 流程** | SQL 文件 + 发布平台 | 平台能提供版本、审批、审计和失败恢复时可用 |

```bash
# 仅当项目已使用 golang-migrate 时参考
# 创建 migration
migrate create -ext sql -dir db/migrations -seq create_users_table

# 执行
migrate -path db/migrations -database "postgres://..." up

# 回滚
migrate -path db/migrations -database "postgres://..." down 1
```

项目已决定由应用执行 migration 时，必须使用当前工具版本与数据库驱动官方支持的适配方式，并处理并发启动、部分失败和无变更等结果。生产中是否允许应用账号修改 schema 由发布和权限契约决定。

### 4.2 Migration 文件命名

🔴 命名、版本号和 up/down 文件形式必须与已选 migration 工具一致；下方只是顺序号 + 成对 SQL 文件的一种示例。

```text
db/migrations/
├── 000001_create_users_table.up.sql
├── 000001_create_users_table.down.sql
├── 000002_add_email_to_users.up.sql
└── 000002_add_email_to_users.down.sql
```

| 规则 | 说明 |
|---|---|
| **序号递增** | `000001`、`000002`...，保证执行顺序 |
| **描述性名称** | 看到文件名就知道做了什么 |
| **回滚策略明确** | 可逆迁移可提供 down；不可逆数据变化采用前向修复、备份或分阶段迁移 |
| **已执行的 migration 保持不变** | 已在共享环境执行后通常新增 migration 修正；未执行的开发分支文件是否可修改服从项目流程 |

### 4.3 Migration 编写规范

🔴 必加约束

```sql
-- PostgreSQL 示例：000001_create_users_table.up.sql
-- 是否使用 IF NOT EXISTS 由 migration 工具的漂移检测策略决定。
CREATE TABLE users (
    id          BIGSERIAL PRIMARY KEY,
    name        VARCHAR(100) NOT NULL,
    email       VARCHAR(255) NOT NULL UNIQUE,
    status      VARCHAR(20)  NOT NULL DEFAULT 'active',
    created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_users_status ON users(status);
```

```sql
-- PostgreSQL 示例：000001_create_users_table.down.sql
DROP TABLE users;
```

| 规则 | 说明 |
|---|---|
| **是否使用 `IF EXISTS` / `IF NOT EXISTS` 由迁移工具决定** | 无条件使用可能掩盖 schema 漂移或错误执行顺序 |
| **大规模数据迁移与 DDL 分阶段** | 小型、可审计的数据修正可在 migration 中完成；大表回填需专门方案 |
| **数据迁移明确列名** | 避免 schema 新增列后无意扩大读写范围 |
| **索引变更纳入 schema 流程** | 根据真实查询和查询计划证据设计，评估创建时的锁、空间和写入成本 |

### 4.4 禁止事项

🔴 必加约束

```sql
-- 风险例：未分批的大量数据回填可能造成长事务、锁等待、日志增长和复制延迟
UPDATE users SET email = LOWER(email);

-- 风险例：不可逆变更没有前向修复、备份或分阶段发布方案

-- 反例：修改已在共享环境执行的 migration 文件
```

**正确做法**：

- 大量数据回填采用可恢复的分批策略；批大小根据锁时间、复制延迟、日志增长和压测调整，不固定为 1000 行
- 修改已执行的 schema 变更时新增 migration，不改写共享环境的历史记录
- 重型 DDL（加索引、改列类型）评估锁和执行时间；必要时使用目标数据库支持的在线方式，并确认 migration 工具的事务模式与其兼容

## 5. 慢查询与监控

### 5.1 慢查询阈值

🟡 阈值必须来自用户请求/后台任务 SLO、调用链预算、目标数据库、数据量与线上基线。主键、索引、聚合或报表标签不能单独决定 `5ms/20ms/100ms` 等通用数值，也不能未经架构确认就把报表迁到只读副本。

### 5.2 接入方式

🔴 沿用项目已采用的驱动指标、日志、trace 或 APM 集成。不为套用本节默认引入 OpenTelemetry、sqlcommenter、Prometheus 或特定驱动包装库；新增观测依赖需用户授权并核对性能、隐私和运维链路。

```go
// 仅示意：项目已有 sqlx、指标和 slog 时，可在统一边界采集耗时。
func queryWithMetrics(ctx context.Context, db *sqlx.DB, query string, args ...any) (*sqlx.Rows, error) {
    start := time.Now()
    defer func() {
        elapsed := time.Since(start)
        dbQueryDuration.Observe(elapsed.Seconds())
        if elapsed > configuredSlowQueryThreshold {
            slog.WarnContext(ctx, "slow query",
                "query", query,
                "duration", elapsed,
            )
        }
    }()
    return db.QueryxContext(ctx, query, args...)
}
```

### 5.3 EXPLAIN 审查

🔴 高影响或已识别为瓶颈的查询上线前必须检查查询计划和代表性数据。优先在生产等价的脱敏环境运行；`EXPLAIN ANALYZE` 可能真正执行查询或写操作，未经授权不得直接在生产使用。

```sql
-- PostgreSQL
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com';

-- MySQL
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
```

关注指标：

查询计划字段和含义因数据库版本而异。联合检查实际/估算行数、扫描方式、过滤率、排序/临时结构、锁、I/O 和执行时间。全表扫描、filesort 或 temporary 并非必然错误；应根据表规模、选择性和总成本判断。

## 6. 查询规范

### 6.1 应用查询明确所需列

🔴 长期维护的应用查询应明确所需列，特别是稳定 API、结构体映射和高流量路径。探索性查询、受控管理工具或确实需要整行的内部路径可按项目契约使用 `SELECT *`，但不能依赖不稳定的返回范围。

```go
// 风险例：SELECT * 在表加列后可能返回不需要的数据
rows, err := db.QueryContext(ctx, "SELECT * FROM users WHERE id = $1", id)

// 正例：明确列出需要的列
rows, err := db.QueryContext(ctx, "SELECT id, name, email FROM users WHERE id = $1", id)
```

| `SELECT *` 的问题 | 说明 |
|---|---|
| **表加列后行为改变** | 返回的数据量不可预期 |
| **浪费带宽** | 不需要的列也被传输 |
| **可能无法利用覆盖索引** | 返回额外列可能超出现有索引覆盖范围，以查询计划为准 |
| **映射契约可能漂移** | sqlx/GORM 通常按列名、别名和标签映射，直接 `rows.Scan` 才按位置；显式列可以避免新增列、别名和映射范围意外变化 |

### 6.2 避免 N+1 查询

🔴 必加约束

```go
// 反例：N+1 查询——先查用户列表，再逐个查订单
users, _ := userRepo.List(ctx)
for _, u := range users {
    orders, _ := orderRepo.ListByUser(ctx, u.ID) // 每个用户一次查询
}

// 可选方案：根据数据量、分页语义和查询计划选择 JOIN 或批量查询
// 方案 1：JOIN
query := `
    SELECT u.id, u.name, o.id AS order_id, o.amount
    FROM users u
    LEFT JOIN orders o ON u.id = o.user_id
    WHERE u.status = $1`
// 在代码中组装 user → []order

// 方案 2：批量 IN
userIDs := extractIDs(users)
orders, err := orderRepo.ListByUserIDs(ctx, userIDs) // SELECT id, user_id, amount FROM orders WHERE user_id IN (?, ?, ?)
orderMap := groupByUserID(orders)
for _, u := range users {
    u.Orders = orderMap[u.ID]
}
```

### 6.3 `IN` 子句上限

🔴 必加约束：`IN` 参数数量受数据库、驱动、协议参数上限和查询计划影响。批大小必须基于目标数据库验证，不把 1000 写成 MySQL 硬限制。

```go
// 反例：传入 5000 个 ID
ids := make([]int64, 5000)
db.SelectContext(ctx, &users, "SELECT * FROM users WHERE id IN (?)", ids)

// 仅当项目已使用 sqlx 时参考；批大小来自配置和目标数据库验证。
func batchInQuery(ctx context.Context, db *sqlx.DB, ids []int64, batchSize int) ([]User, error) {
    if batchSize <= 0 {
        return nil, errors.New("batch size must be positive")
    }
    var allUsers []User
    for i := 0; i < len(ids); i += batchSize {
        end := i + batchSize
        if end > len(ids) {
            end = len(ids)
        }
        var batch []User
        query, args, err := sqlx.In("SELECT id, name FROM users WHERE id IN (?)", ids[i:end])
        if err != nil {
            return nil, fmt.Errorf("expand user ids: %w", err)
        }
        query = db.Rebind(query)
        if err := db.SelectContext(ctx, &batch, query, args...); err != nil {
            return nil, err
        }
        allUsers = append(allUsers, batch...)
    }
    return allUsers, nil
}
```

### 6.4 参数化查询

🔴 所有用户或外部输入的**值**必须通过驱动参数绑定，不用字符串拼接。表名、列名、排序方向等通常不能作为值参数绑定；必须动态选择时，从代码内部的有限白名单映射到 SQL 片段。

```go
// 反例：SQL 注入风险
query := fmt.Sprintf("SELECT * FROM users WHERE name = '%s'", name)
db.QueryContext(ctx, query)

// 反例：动态排序用字符串拼接
query := fmt.Sprintf("SELECT * FROM users ORDER BY %s %s", sortField, sortOrder)

// 正例：参数化查询
rows, err := db.QueryContext(ctx, "SELECT id, name FROM users WHERE name = $1", name)

// 正例：动态排序用白名单校验
var allowedSortFields = map[string]bool{"id": true, "name": true, "created_at": true}
var allowedSortOrders = map[string]bool{"ASC": true, "DESC": true}

func listUsers(ctx context.Context, db *sqlx.DB, sortField, sortOrder string) ([]User, error) {
    if !allowedSortFields[sortField] {
        return nil, fmt.Errorf("invalid sort field: %s", sortField)
    }
    if !allowedSortOrders[sortOrder] {
        return nil, fmt.Errorf("invalid sort order: %s", sortOrder)
    }
    // 白名单校验通过后再拼接
    query := fmt.Sprintf("SELECT * FROM users ORDER BY %s %s", sortField, sortOrder)
    var users []User
    return users, db.SelectContext(ctx, &users, query)
}
```

### 6.5 分页查询

🔴 分页字段、排序方向和游标编码必须与 API 契约一致。数据可并发变化且不允许重复/遗漏时，使用能唯一确定顺序的复合键；偏移分页与游标分页的选择由数据规模、跳页需求和一致性契约决定。下例仅在项目已使用 sqlx 时参考。

```go
// 偏移分页
func ListUsers(ctx context.Context, db *sqlx.DB, page, pageSize int) ([]User, int, error) {
    if page < 1 || pageSize < 1 {
        return nil, 0, errors.New("page and page size must be positive")
    }
    var total int
    if err := db.GetContext(ctx, &total, "SELECT COUNT(*) FROM users"); err != nil {
        return nil, 0, fmt.Errorf("count users: %w", err)
    }

    var users []User
    offset := (page - 1) * pageSize
    err := db.SelectContext(ctx, &users,
        "SELECT id, name, created_at FROM users ORDER BY created_at DESC, id DESC LIMIT $1 OFFSET $2",
        pageSize, offset)
    return users, total, err
}

// 游标分页示例；cursor 应由 API 层按既有契约编解码
func ListUsersCursor(ctx context.Context, db *sqlx.DB, cursorTime time.Time, cursorID int64, limit int) ([]User, string, error) {
    if limit < 1 {
        return nil, "", errors.New("limit must be positive")
    }
    var users []User
    err := db.SelectContext(ctx, &users,
        `SELECT id, name, created_at FROM users
         WHERE created_at < $1 OR (created_at = $1 AND id < $2)
         ORDER BY created_at DESC, id DESC
         LIMIT $3`,
        cursorTime, cursorID, limit+1) // 多查一条判断是否有下一页

    if err != nil {
        return nil, "", fmt.Errorf("list users by cursor: %w", err)
    }
    var nextCursor string
    if len(users) > limit {
        last := users[limit-1]
        nextCursor = encodeCursor(last.CreatedAt, last.ID)
        users = users[:limit]
    }
    return users, nextCursor, nil
}
```

### 6.6 `sqlx.In` 使用

🟡 若项目使用 `sqlx` 且查询参数需要展开为 `IN (...)`，推荐使用 `sqlx.In`。使用 `database/sql`、ORM 或查询构建器时，采用其已验证的参数化列表绑定方式；无论选型如何，不得拼接未经验证的用户输入。

```go
// 反例：手动拼接 IN
ids := []int64{1, 2, 3}
// 自己拼 "SELECT ... WHERE id IN (?,?,?)" —— 容易出错

// 正例：sqlx.In 自动展开
query, args, err := sqlx.In("SELECT id, name FROM users WHERE id IN (?)", ids)
if err != nil {
    return fmt.Errorf("expand ids: %w", err)
}
query = db.Rebind(query) // 按当前驱动转换占位符
if err := db.SelectContext(ctx, &users, query, args...); err != nil {
    return fmt.Errorf("select users: %w", err)
}
```

## 7. Context 传递

### 7.1 需要取消或超时的调用透传 ctx

🔴 上游提供 context 时，数据库调用必须透传它，不在中间层用 `context.Background()` 截断取消、截止时间和 trace。

```go
// 反例：不传 ctx——查询无法超时、无法取消
rows, err := db.Query("SELECT * FROM users")

// 反例：创建了 ctx 但不传给 DB
ctx := context.Background()
db.Query("SELECT * FROM users") // 没有用 ctx！

// 正例：ctx 从头传到尾
func (r *userRepo) GetByID(ctx context.Context, id int64) (*User, error) {
    var user User
    err := r.db.GetContext(ctx, &user, "SELECT id, name FROM users WHERE id = $1", id)
    return &user, err
}
```

**传递链**：

```
HTTP request context
  → handler 获取 ctx
    → service 传递 ctx
      → repository 传递 ctx
        → db.QueryContext(ctx, ...)
```

### 7.2 不要在 struct 中存 context

🔴 必加约束

```go
// 反例：把 context 存在 struct 里
type UserRepo struct {
    db  *sqlx.DB
    ctx context.Context // 不要！
}

// 正例：context 作为方法参数
type UserRepo struct {
    db *sqlx.DB
}

func (r *UserRepo) GetByID(ctx context.Context, id int64) (*User, error) {
    // ctx 作为第一个参数
}
```

> 这是 Go 的惯例——context 表达请求或操作范围，不是对象生命周期。参见 [Go Context 官方文档](https://pkg.go.dev/context)。

### 7.3 超时与取消

🟡 只在当前层拥有时间预算、且上游截止时间不足以表达该预算时派生更短的 context。时长来自项目配置和 SLO，不写死为 3 秒。

```go
// 应用服务拥有该用例的时间预算时，派生更短的 context
func (s *UserService) GetUser(ctx context.Context, id int64) (*User, error) {
    ctx, cancel := context.WithTimeout(ctx, s.queryTimeout)
    defer cancel()
    return s.repo.GetByID(ctx, id)
}

// repository 层尊重 ctx 超时
func (r *userRepo) GetByID(ctx context.Context, id int64) (*User, error) {
    var user User
    err := r.db.GetContext(ctx, &user, "SELECT id, name FROM users WHERE id = $1", id)
    return &user, err
}
```
