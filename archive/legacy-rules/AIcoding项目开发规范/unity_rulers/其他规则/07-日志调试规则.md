# 07 - Unity 日志与调试规则

> - 🟢 本文件适用于 Unity Editor、Development Build 和正式包的运行时日志、设备诊断与错误上报边界。
> - 🔴 不适用：为单个功能引入日志框架、把客户端日志当作服务端事实，或在正式包输出未脱敏诊断信息。

---

## 1. 现有日志链路优先

> **适用条件与验证**：先检查项目已有日志门面、`Debug.Log*` 使用约定、错误上报、构建类型、Scripting Define Symbols、隐私策略和目标设备诊断方式。

- 🔴 项目已有日志门面时沿用其等级、分类、结构化字段、脱敏和输出目标；不得为套用本节另建竞争门面或引入日志依赖。
- 🟡 项目没有日志门面时，按任务规模和现有约定使用 `Debug.Log*` 或最小封装；一次性 Editor 工具和小型项目不必强制建立五级日志系统。
- 🔴 日志调用不得承载状态更新、返回控制、网络请求或其他业务副作用；调整日志策略不能改变业务行为。

## 2. 开发日志与正式诊断

### 2.1 Editor 与 Development Build

- 🟡 项目需要筛选时，可以采用现有等级和分类；不固定为 `Trace/Debug/Info/Warn/Error` 五级，也不强制默认掩码。
- 🟡 高频帧循环、输入、网络包或渲染日志需要关闭、采样或聚合策略，并验证参数构造不会造成明显分配和主线程开销。
- 🔴 临时诊断在问题确认后删除或恢复默认配置，不得无意进入正式发布路径。

### 2.2 正式包

- 🔴 正式包是否保留设备日志、结构化事件、崩溃信息或远程上报，由项目发布、运维、隐私和平台策略决定；不能统一要求全部保留或全部编译移除。
- 🔴 支付、认证、安全、资源失败和崩溃等产品要求的诊断必须有受控去向。项目没有远程上报时，不得先删除本地错误证据再声称诊断完整。
- 🟡 只用于开发的 `void` 日志 API 可以在项目已经采用相应符号时使用 `Conditional` 或条件编译剔除；正式包需要的异常和事件不能复用会被剔除的调用入口。

```csharp
// 仅示意职责分离；名称和 API 必须替换为项目真实实现。
ProjectLog.Debug("Network", "请求已发起", requestId);
ProjectDiagnostics.ReportException(exception, DiagnosticContext.ResourceLoad);
```

## 3. 数据与隐私

- 🔴 日志和错误上报不得包含令牌、密码、支付信息、完整个人数据、密钥、未脱敏请求载荷或生产服务端内部细节。
- 🔴 设备标识、账号标识、位置和语音等数据按项目隐私分级进行最小化、脱敏、采样、保留和访问控制。
- 🔴 动态日志配置、远程诊断和上传能力必须经过项目授权，并具备关闭、过期和审计边界。

## 4. 排障证据

- 🔴 性能结论先通过项目已有 Profiler、Frame Debugger、Memory Profiler 或可复现设备测试确认；日志只能辅助定位，不能替代证据。
- 🔴 异常被捕获后按项目契约上报、转换、恢复或继续抛出；不得只写日志后静默吞掉失败。
- 🟡 PICO、Android、iOS、主机或桌面平台的设备日志能力不同，交付时记录实际构建、设备、日志来源和时间范围。

## 5. 验证与交付

- 分别验证 Editor、Development Build 和正式包中实际启用的日志、设备诊断和错误上报路径。
- 验证等级或分类筛选、条件编译、异常路径、脱敏、采样和输出目标；检查日志参数是否产生不必要副作用或高频分配。
- 交付时说明保留和移除的日志类别、实际验证构建、未覆盖设备、隐私风险及缺失的正式诊断能力。

> **例外**：Editor 专用菜单、Inspector 和导入工具可以使用当前项目约定的 Editor 输出；它们必须处于 Editor 专用编译范围，不能泄漏到运行时程序集。
