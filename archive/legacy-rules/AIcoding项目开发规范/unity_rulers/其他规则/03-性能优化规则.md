# 03 - Unity 性能优化指南

> - 🟢 本文件适用于 Unity 项目的性能调优（GC/DrawCall/物理/渲染）。
> - 🔴 不适用：业务逻辑实现、美术资源优化、平台 SDK 性能调优

---

## 1. Update 循环优化

Update 循环是 Unity 常见的性能热点之一，但是否构成瓶颈应以 Profiler、目标平台帧时间与项目已有指标为准。本节讲三件事：识别每帧分配、避免重复计算、不要让不需要逐帧执行的工作持续运行。

### 1.1 避免每帧分配

- ❌ **不要在已确认的高频热路径中产生不必要分配** —— 分配频率、生命周期和目标平台 GC 行为应由 Profiler 验证。
- ❌ 避免在 update 循环中对引用类型使用 `new`。
- ❌ 避免在 update 循环中进行字符串拼接或插值。
- ❌ 避免在 update 循环中使用 LINQ 查询。
- ✅ 预分配集合并通过 `.Clear()` 复用。
- ✅ 对频繁实例化的对象使用对象池。

```csharp
// ❌ 差 —— 每帧都分配
private void Update()
{
    var enemies = FindObjectsOfType<Enemy>();           // 分配数组
    var nearbyEnemies = new List<Enemy>();              // 分配列表
    string status = $"Enemies: {enemies.Length}";      // 分配字符串

    foreach (var enemy in enemies.Where(e => e.IsAlive)) // LINQ 产生分配
    {
        nearbyEnemies.Add(enemy);
    }
}

// ✅ 好 —— 启动时缓存，Update零分配
private Enemy[] m_enemyCache;                          // Awake中缓存
private readonly List<Enemy> m_nearbyEnemies = new(50);
private readonly StringBuilder m_statusBuilder = new(64);

private void Awake()
{
    m_enemyCache = FindObjectsOfType<Enemy>();         // 只在启动时分配一次
}

private void Update()
{
    m_nearbyEnemies.Clear();                            // 复用列表
    foreach (var enemy in m_enemyCache)                 // 使用缓存的引用
    {
        if (enemy != null && enemy.IsAlive)
        {
            m_nearbyEnemies.Add(enemy);
        }
    }

    m_statusBuilder.Clear();                            // 复用 StringBuilder
    m_statusBuilder.Append("Enemies: ").Append(m_nearbyEnemies.Count);
}
// 说明：Unity 2022.2+ 可使用 Object.FindObjectsByType<T>(
//     FindObjectsInactive.Include, FindObjectsSortMode.None) 省去排序成本，
// 但它仍返回数组；不要把它当成无 GC API，更不要在 Update 中频繁扫描场景。
// 最好通过注册、注销或项目已有管理器维护引用。
```

### 1.2 缓存开销大的操作

- ✅ 在 Update 之外缓存开销较大的计算结果。
- ✅ 使用脏标记，只在状态变化时重新计算。
- ✅ 在 Awake() 中缓存 Transform、Rigidbody 等组件引用。
- ❌ 避免每帧访问 `transform`、`gameObject` 或调用 GetComponent。

```csharp
// ❌ 差 —— 反复属性访问与计算
private void Update()
{
    Vector3 pos = transform.position;                   // 属性访问开销
    Vector3 targetDir = (m_target.transform.position - pos).normalized;
    float distance = Vector3.Distance(transform.position, m_target.transform.position);
}

// ✅ 好 —— 引用与计算都缓存
private Transform m_transform;
private Transform m_targetTransform;
private Vector3 m_cachedTargetDirection;
private float m_cachedDistance;
private bool m_isDirty = true;

private void Awake()
{
    m_transform = transform;                            // 只缓存一次
    m_targetTransform = m_target.transform;
}

private void Update()
{
    if (m_isDirty)
    {
        Vector3 offset = m_targetTransform.position - m_transform.position;
        m_cachedDistance = offset.magnitude;
        m_cachedTargetDirection = offset / m_cachedDistance; // 避免重复 sqrt
        m_isDirty = false;
    }
}
```

### 1.3 节流 Update 逻辑

- ✅ 把开销大的工作分散到多个帧中执行。
- ✅ 对非关键更新使用基于时间的节流。
- ✅ 周期性检查可考虑使用协程（**全版本通用**）或 `Awaitable`（**仅 Unity 6+**）。
- ⚠️ 节流时注意与帧率相关的行为。

```csharp
// ✅ 好 —— 节流更新
[SerializeField] private float m_updateInterval = 0.1f;
private float m_nextUpdateTime;

private void Update()
{
    if (Time.time < m_nextUpdateTime) return;           // 间隔内跳过

    m_nextUpdateTime = Time.time + m_updateInterval;
    PerformExpensiveOperation();
}

// ✅ 好 —— 跨帧错峰处理
private int m_currentIndex;
private const int k_itemsPerFrame = 10;

private void Update()
{
    int endIndex = Mathf.Min(m_currentIndex + k_itemsPerFrame, m_items.Count);

    for (int i = m_currentIndex; i < endIndex; i++)
    {
        ProcessItem(m_items[i]);
    }

    m_currentIndex = endIndex >= m_items.Count ? 0 : endIndex;
}
```

## 2. 内存管理
### 2.1 字符串操作

- ❌ 不要在已确认的热路径中反复用 `+` 拼接字符串；低频日志、初始化与可读性优先的代码可按项目现有约定处理。
- ❌ 避免在热路径中使用 `string.Format()` —— 会产生分配。
- ✅ 动态构建字符串请使用 `StringBuilder`。
- ✅ 当值不常变化时，缓存格式化后的字符串。
- ✅ 高级零分配场景可使用 `string.Create()` 或 `Span<char>`。

```csharp
// ❌ 差 —— 多次分配
private void UpdateUI()
{
    m_scoreText.text = "Score: " + m_score;                     // 2 次分配
    m_healthText.text = string.Format("HP: {0}/{1}", m_hp, m_maxHp); // 会分配
}

// ✅ 好 —— 缓存与复用
private readonly StringBuilder m_sb = new(32);
private int m_lastScore = -1;
private string m_cachedScoreText;

private void UpdateUI()
{
    if (m_score != m_lastScore)
    {
        m_sb.Clear();
        m_sb.Append("Score: ").Append(m_score);
        m_cachedScoreText = m_sb.ToString();                    // 仅在变化时分配
        m_lastScore = m_score;
    }
    m_scoreText.text = m_cachedScoreText;
}
```

### 2.2 集合与分配

- ✅ 按预期容量初始化集合，避免扩容。
- ✅ 优先复用 `List<T>.Clear()`，而不是 new 一个新 List。
- ✅ 使用 Unity 自带的 `CollectionPool<T>` 或 `ListPool<T>`。
- ❌ 避免在性能关键代码中调用 `ToArray()`、`ToList()`。
- 🟡 只有在目标 Unity/C# 配置可编译、长度有明确上限且 Profiler 显示分配值得优化时，才评估 `Span<T>` 与 `stackalloc`。

```csharp
// ❌ 差 —— 扩容产生分配
private void ProcessEnemies()
{
    var enemies = new List<Enemy>();                    // 没有预分配容量，会扩容
    // ... add many items
}

// ✅ 好 —— 预分配容量
private readonly List<Enemy> m_enemies = new(100);     // 预期最大容量

// ✅ 好 —— 使用 Unity 自带的池化
using UnityEngine.Pool;

private void ProcessWithPool()
{
    var tempList = ListPool<Enemy>.Get();
    try
    {
        // 使用 tempList...
    }
    finally
    {
        ListPool<Enemy>.Release(tempList);
    }
}

// ✅ 可选 —— 长度固定且已验证目标平台支持时使用 stackalloc（C# 7.2+）
private void ProcessSmallBatch()
{
    Span<int> indices = stackalloc int[8];             // 不在堆上分配
    // 使用 indices...
}
```

### 2.3 装箱与拆箱

- ❌ 避免将值类型传给期望 `object` 的方法。
- ❌ 避免将值类型放入非泛型集合。
- ✅ 使用泛型集合（用 `List<int>` 而非 `ArrayList`）。
- ✅ 使用泛型方法与接口，避免装箱。
- ⚠️ 注意值类型在字符串插值中的隐式装箱。

```csharp
// ❌ 差 —— 发生装箱
object boxed = 42;                                      // 装箱
int unboxed = (int)boxed;                              // 拆箱

ArrayList oldList = new ArrayList();
oldList.Add(42);                                        // 装箱

ProjectLog.Write(LogLevel.Debug, "Performance", $"Value: {myStruct}"); // 若未重写 ToString 可能装箱

// ✅ 好 —— 不装箱
List<int> genericList = new List<int>();
genericList.Add(42);                                    // 不装箱

ProjectLog.Write(LogLevel.Debug, "Performance", $"Value: {myInt}");    // 基本类型高效处理
```

## 3. 对象池

### 3.1 Unity 2021.1+ ObjectPool<T>

```csharp
using UnityEngine;
using UnityEngine.Pool;

public class ProjectilePool : MonoBehaviour
{
    [SerializeField] private Projectile m_prefab;
    [SerializeField] private int m_defaultCapacity = 20;
    [SerializeField] private int m_maxSize = 100;

    private ObjectPool<Projectile> m_pool;

    private void Awake()
    {
        m_pool = new ObjectPool<Projectile>(
            createFunc: CreateProjectile,
            actionOnGet: OnGetFromPool,
            actionOnRelease: OnReturnToPool,
            actionOnDestroy: OnDestroyPooled,
            collectionCheck: false,                     // 发布版关闭以提升性能
            defaultCapacity: m_defaultCapacity,
            maxSize: m_maxSize
        );
    }

    private Projectile CreateProjectile()
    {
        var proj = Instantiate(m_prefab);
        proj.SetPool(m_pool);                           // 给弹丸一个池引用
        return proj;
    }

    private void OnGetFromPool(Projectile proj)
    {
        proj.gameObject.SetActive(true);
        proj.ResetState();
    }

    private void OnReturnToPool(Projectile proj)
    {
        proj.gameObject.SetActive(false);
    }

    private void OnDestroyPooled(Projectile proj)
    {
        Destroy(proj.gameObject);
    }

    public Projectile Get() => m_pool.Get();
    public void Return(Projectile proj) => m_pool.Release(proj);
}
```

- 🟡 对生命周期清晰、复用率高且经 Profiler 证实 `Instantiate` / `Destroy` 是瓶颈的对象（如子弹、粒子、重复 UI）评估对象池。
- ✅ 实现 `IDisposable` 模式或使用 `actionOnRelease` 重置对象状态。
- ✅ 根据预期用量设置合适的 `defaultCapacity` 和 `maxSize`。
- 🔴 不要仅按“每秒生成次数”套用对象池；先测量帧时间、GC、峰值并发和对象重置成本。低频但昂贵的对象、或高频但不可安全复用的对象，都需要单独判断。
- ⚠️ 记得将对象归还到池中 —— 池对象泄漏会让对象池失去意义。

### 3.2 旧版自己实现对象池

> **适用场景**：Unity 2020 及更早版本（无 `UnityEngine.Pool`），或需要更精细控制。

```csharp
public class SimplePool<T> where T : Component
{
    private readonly T m_prefab;
    private readonly Transform m_parent;
    private readonly Stack<T> m_pool;
    private readonly int m_maxSize;

    public SimplePool(T prefab, Transform parent, int initial = 10, int maxSize = 100)
    {
        m_prefab = prefab;
        m_parent = parent;
        m_pool = new Stack<T>(initial);
        m_maxSize = maxSize;
    }

    public T Get()
    {
        T obj = m_pool.Count > 0 ? m_pool.Pop() : Object.Instantiate(m_prefab, m_parent);
        obj.gameObject.SetActive(true);
        return obj;
    }

    public void Return(T obj)
    {
        obj.gameObject.SetActive(false);
        if (m_pool.Count < m_maxSize) m_pool.Push(obj);
        else Object.Destroy(obj);
    }
}
```

**使用示例**：

```csharp
public class EnemySpawner : MonoBehaviour
{
    [SerializeField] private Enemy m_enemyPrefab;
    private SimplePool<Enemy> m_pool;

    private void Awake()
    {
        m_pool = new SimplePool<Enemy>(m_enemyPrefab, transform);
    }

    public Enemy Spawn(Vector3 position)
    {
        var enemy = m_pool.Get();
        enemy.transform.position = position;
        enemy.Initialize();
        return enemy;
    }

    public void Despawn(Enemy enemy)
    {
        m_pool.Return(enemy);
    }
}
```

> **何时自己实现 vs 用 ObjectPool<T>**：目标 Unity 版本提供并且项目已验证 `UnityEngine.Pool.ObjectPool<T>` 时，可优先评估它；旧版本、跨线程模型、特殊生命周期或已有池化框架则沿用项目方案。先用 Profiler 证明池化收益，再决定是否引入。

## 4. 物理优化

### 4.1 LayerMask 缓存

- ✅ 使用 LayerMask 把物理查询限制在相关 Layer 上。
- ✅ 缓存 `LayerMask` 值 —— 不要每帧调用 `LayerMask.GetMask()`。
- 🔴 Layer 用 `LayerMask` 缓存（**禁止每帧 `LayerMask.GetMask()`**）。

```csharp
// ✅ 缓存到字段
private LayerMask m_enemyLayer;

private void Awake()
{
    m_enemyLayer = LayerMask.GetMask("Enemy");  // ✅ 缓存，Awake 中调一次
}
```

### 4.2 Raycast 优化

- ✅ 使用 `Physics.Raycast` 的 `maxDistance` 参数限制距离。
- ✅ 如果不需要触发器，用 `QueryTriggerInteraction.Ignore`。
- ✅ 大量 Raycast 可使用 `Physics.RaycastCommand` 配合 Jobs 批处理。

```csharp
// ✅ 好 —— 优化的 Raycast
private RaycastHit m_hitInfo;
private const float k_maxRayDistance = 100f;

private bool CheckLineOfSight(Vector3 origin, Vector3 direction)
{
    return Physics.Raycast(
        origin,
        direction,
        out m_hitInfo,
        k_maxRayDistance,
        m_lineOfSightMask,
        QueryTriggerInteraction.Ignore
    );
}
```

### 4.3 物理查询 NonAlloc

- 🟡 高频且分析确认分配有影响时，可使用 `Physics.RaycastNonAlloc`、`Physics.OverlapSphereNonAlloc`；必须同时处理固定缓冲区可能截断结果的语义。
- ✅ 优先使用简单碰撞体（球、胶囊、盒）而非 Mesh Collider。
- ❌ 避免在 Update 中进行物理查询 —— 改用 FixedUpdate 或做节流。
- ✅ 配置 Physics 碰撞矩阵，关闭不必要的层间交互。

```csharp
// ❌ 差 —— 每帧分配物理查询
private void Update()
{
    Collider[] hits = Physics.OverlapSphere(transform.position, m_radius);
    foreach (var hit in hits)
    {
        // 处理...
    }
}

// ✅ 好 —— 缓存数组 + LayerMask，零分配
private readonly Collider[] m_hitBuffer = new Collider[32];
private LayerMask m_enemyLayer;

private void Awake()
{
    m_enemyLayer = LayerMask.GetMask("Enemy");          // 缓存 LayerMask
}

private void FixedUpdate()
{
    int hitCount = Physics.OverlapSphereNonAlloc(
        transform.position,
        m_radius,
        m_hitBuffer,
        m_enemyLayer                                     // 仅检查 Enemy 层
    );

    if (hitCount == m_hitBuffer.Length)
    {
        // 无法区分“刚好填满”和“结果被截断”，按业务上限扩容或拆分查询。
        ProjectLog.Write(LogLevel.Warn, "Physics.Query", "命中缓冲区可能不足");
    }

    for (int i = 0; i < hitCount; i++)
    {
        ProcessHit(m_hitBuffer[i]);
    }
}
```

## 5. 渲染注意事项

### 5.1 .material vs sharedMaterial

- ⚠️ 首次访问 `.material` 通常会为该 Renderer 创建材质实例；不要在热路径或无所有权约定时访问。
- 🔴 单个实例只修改 Shader 属性时优先使用 `MaterialPropertyBlock`。确实需要独立材质实例时显式创建、缓存并按生命周期销毁。
- 🔴 `sharedMaterial` 适合读取或有意修改所有共享对象时使用；修改其属性会影响共享该材质的 Renderer，并可能在 Editor 中污染资源，不能作为 `.material` 的通用替代。
- ❌ 除非必要，避免运行时切换材质。
- ✅ 对大量相似对象使用 GPU Instancing。

```csharp
// ❌ 差 —— 每个对象都创建材质实例
private void Start()
{
    GetComponent<Renderer>().material.color = Color.red; // 创建实例！
}

// ❌ 也不适合单实例颜色：修改共享材质会影响所有引用者
m_renderer.sharedMaterial.color = Color.red;
```

### 5.2 MaterialPropertyBlock

- ✅ 用 `MaterialPropertyBlock` 批量修改材质属性。
- ✅ 对每个实例的属性修改，使用 `Renderer.GetPropertyBlock` / `SetPropertyBlock`。

```csharp
// ✅ 好 —— 使用 MaterialPropertyBlock（首次调用后无分配）
private static readonly int k_colorId = Shader.PropertyToID("_Color");
private MaterialPropertyBlock m_propertyBlock;
private Renderer m_renderer;

private void Awake()
{
    m_renderer = GetComponent<Renderer>();
    m_propertyBlock = new MaterialPropertyBlock();
}

private void SetColor(Color color)
{
    m_renderer.GetPropertyBlock(m_propertyBlock);
    m_propertyBlock.SetColor(k_colorId, color);
    m_renderer.SetPropertyBlock(m_propertyBlock);
}
```

### 5.3 Shader 属性 ID 缓存

- ✅ 用 `Shader.PropertyToID()` 缓存 Shader 属性 ID。
- ❌ 不要在高频更新路径中反复用字符串访问 Shader 属性；性能敏感路径可缓存 Property ID。

```csharp
// ❌ 差 —— 每次都字符串查找
m_material.SetFloat("_Intensity", value);

// ✅ 好 —— 缓存的 ID
private static readonly int k_intensityId = Shader.PropertyToID("_Intensity");

private void UpdateShader(float value)
{
    m_material.SetFloat(k_intensityId, value);
}
```

## 6. GetComponent 与 Find

### 6.1 GetComponent 缓存

- ❌ 不要在每帧且已确认高频的路径重复调用 `GetComponent`；稳定依赖可在合适的生命周期缓存，动态组件则需保留失效处理。
- ✅ 使用 `TryGetComponent` 进行空安全查找（比 GetComponent + null 略快）。

```csharp
// ❌ 差 —— 每帧高开销查找
private void Update()
{
    var rb = GetComponent<Rigidbody>();                 // 每帧查找
}

// ✅ 好 —— Awake 缓存
[SerializeField] private Rigidbody m_rigidbody;

private void Awake()
{
    if (m_rigidbody == null) TryGetComponent(out m_rigidbody);
}

private void Update()
{
    m_rigidbody.AddForce(Vector3.up);                   // 用缓存的引用
}
```

### 6.2 FindObjectOfType 禁用在热路径

- ❌ 避免运行时调用 `FindObjectOfType`、`FindObjectsOfType` —— 它们是 O(n) 的场景扫描。
- ❌ 避免使用 `GameObject.Find` —— 基于字符串，会遍历整个层级。
- ✅ 使用 `[SerializeField]` 在 Inspector 中赋值引用。
- ✅ 跨系统引用使用依赖注入或服务定位器。

```csharp
// ❌ 差 —— 每帧扫描场景
private void Update()
{
    var player = FindObjectOfType<Player>();           // 每帧 O(n) 扫描
    var enemy = GameObject.Find("Enemy");              // 每帧按字符串查找
}

// ✅ 好 —— [SerializeField] 引用
[SerializeField] private Player m_player;            // Inspector 拖入

private void Update()
{
    m_player.TakeDamage(10);                            // 用缓存的引用
}
```

### 6.3 [RequireComponent] 模式

- ✅ 使用 `[RequireComponent]` 确保依赖存在，使缓存更安全。
- 🔴 必备依赖用 `[RequireComponent(typeof(X))]`，避免空检查。

```csharp
[RequireComponent(typeof(Rigidbody))]
[RequireComponent(typeof(Collider))]
public class PhysicsController : MonoBehaviour
{
    private Rigidbody m_rigidbody;
    private Collider m_collider;

    private void Awake()
    {
        // 可放心缓存 —— RequireComponent 保证依赖一定存在
        m_rigidbody = GetComponent<Rigidbody>();
        m_collider = GetComponent<Collider>();
    }
}
```

## 7. LINQ 与委托

### 7.1 LINQ 避免在 Update 中

- ❌ 不要在每帧的性能敏感路径中使用会产生分配或枚举成本的 LINQ；初始化、编辑器工具和低频路径可在测量后权衡可读性。
- ❌ 避免在热路径中使用 lambda 表达式 —— 它们会分配闭包。
- ✅ 性能关键代码中用显式循环替代 LINQ。
- ⚠️ LINQ 适合初始化、编辑器代码或不频繁的操作。

```csharp
// ❌ 差 —— Update 中的 LINQ 分配
private void Update()
{
    var activeEnemies = m_enemies.Where(e => e.IsActive).ToList();
    var closestEnemy = m_enemies.OrderBy(e => e.Distance).FirstOrDefault();
}

// ✅ 好 —— 显式循环，无分配
private Enemy m_closestEnemy;
private readonly List<Enemy> m_activeEnemies = new(50);

private void Update()
{
    m_activeEnemies.Clear();
    float minDistance = float.MaxValue;
    m_closestEnemy = null;

    for (int i = 0; i < m_enemies.Count; i++)
    {
        var enemy = m_enemies[i];
        if (enemy.IsActive)
        {
            m_activeEnemies.Add(enemy);

            if (enemy.Distance < minDistance)
            {
                minDistance = enemy.Distance;
                m_closestEnemy = enemy;
            }
        }
    }
}
```

### 7.2 委托缓存

- ✅ 重复订阅事件时**缓存委托引用**（方法组语法，不分配）。

```csharp
// ❌ 差 —— 每次都创建委托实例
private void OnEnable()
{
    m_button.clicked += () => OnButtonClicked();       // 分配闭包
}

// ✅ 好 —— 缓存方法引用
private void OnEnable()
{
    m_button.clicked += OnButtonClicked;               // 方法组，无分配
}

private void OnButtonClicked()
{
    // 处理点击
}
```

## 8. 异步与协程

### 8.1 协程续作保护

- ✅ 协程用 `if (this == null) return;` 保护续作（对象销毁后）。
- 🔴 见 `01-代码编写规则.md` 6.1 协程的生命周期管理。

```csharp
// ✅ 协程续作保护
private IEnumerator OpenDoorCo()
{
    yield return new WaitForSeconds(2f);
    if (this == null) return;  // 对象已销毁
    m_isOpen = true;
}
```

### 8.2 跨版本选型（协程、Awaitable 与项目异步库）

- 🟡 Unity 6+ 且项目已验证 `Awaitable` 生命周期与取消行为时，可评估它处理简单异步流程；不要仅因“零分配”替换现有协程。
- ✅ 协程是跨版本可用的选择；等待对象是否缓存应由频率、并发复用行为、Profiler 和可读性共同决定。
- 🟡 若项目已安装 UniTask 或其他异步库，沿用其既有取消、异常和主线程调度约定；未安装时不得在新代码中引用。

```csharp
// 🟡 需测量 —— 每次迭代创建等待对象是否值得优化取决于频率与目标平台
private IEnumerator BadCoroutine()
{
    while (true)
    {
        yield return new WaitForSeconds(0.1f);         // 每次循环都分配
        DoSomething();
    }
}

// ✅ 可选 —— 固定间隔且复用行为已验证时缓存等待对象
private static readonly WaitForSeconds k_shortWait = new(0.1f);

private IEnumerator GoodCoroutine()
{
    while (true)
    {
        yield return k_shortWait;                       // 复用缓存对象
        DoSomething();
    }
}

// ✅ 仅 Unity 6+ —— 用 Awaitable
private async Awaitable PeriodicUpdateAsync(CancellationToken token)
{
    while (!token.IsCancellationRequested)
    {
        await Awaitable.WaitForSecondsAsync(0.1f, token);
        DoSomething();
    }
}
```

### 8.3 取消令牌

- ✅ async 方法必须接受 `CancellationToken` 参数。
- 🔴 详细见 `01-代码编写规则.md` 6.4 取消令牌的使用。

```csharp
public async Awaitable LoadDataAsync(CancellationToken token)
{
    await Awaitable.WaitForSecondsAsync(2f, token);
    if (token.IsCancellationRequested) return;
    m_data = await LoadFromDiskAsync(token);
}
```

## 9. 数据结构选择

### 9.1 集合类型选型

| 场景 | 选型 |
|------|------|
| 顺序访问、按索引 | `T[]` / `List<T>` |
| 频繁查找（O(1)） | `Dictionary<K,V>` / `HashSet<T>` |
| 队（FIFO） | `Queue<T>` |
| 栈（LIFO，撤销系统） | `Stack<T>` |
| 不可变 | `ImmutableArray<T>` / `ImmutableList<T>` |
| 临时小数组 | `Span<T>` + `stackalloc` |

- ✅ 用 `Dictionary<K,V>` 实现 O(1) 的按键查找。
- ✅ 用 `HashSet<T>` 实现 O(1) 的包含判断。
- ✅ 当顺序重要且频繁迭代时使用 `List<T>`。
- ✅ 固定大小、频繁访问的数据使用数组。
- ✅ FIFO 操作使用 `Queue<T>`。
- ✅ LIFO 操作（撤销系统、状态历史）使用 `Stack<T>`。
- ⚠️ 涉及 Jobs/Burst 时考虑使用 `NativeArray<T>`。

```csharp
// 按 ID 进行 O(1) 查找
private Dictionary<int, Enemy> m_enemyById = new();

// O(1) 包含检查
private HashSet<int> m_processedIds = new();

// 顺序迭代，动态大小
private List<Enemy> m_activeEnemies = new();

// 固定大小，频繁访问
private Enemy[] m_enemyPool = new Enemy[100];

// 命令队列
private Queue<ICommand> m_commandQueue = new();

// 撤销栈
private Stack<ICommand> m_undoStack = new();
```

### 9.2 不可变集合

- ✅ **配置数据用 `ImmutableArray<T>` / `ImmutableList<T>`**：创建后不可变，线程安全。
- ✅ 适合 ScriptableObject 配置、单例的固定数据。

```csharp
using System.Collections.Immutable;

public class GameConfig
{
    public ImmutableArray<LevelData> Levels { get; }
    public ImmutableDictionary<string, ItemData> Items { get; }

    public GameConfig(IEnumerable<LevelData> levels, IEnumerable<ItemData> items)
    {
        Levels = levels.ToImmutableArray();
        Items = items.ToImmutableDictionary(x => x.Id);
    }
}
```

> 不可变集合**修改时返回新实例**（原实例不变），适合多线程读取场景。

### 9.3 Span<T> 与 stackalloc

- 🟡 **临时小数组可评估 `Span<T>` + `stackalloc`**：它们可减少托管分配，但受 Unity/C# 配置、平台和栈空间约束。
- ✅ 适合长度固定、上限受控且已测试的缓冲区（如部分音频、几何或网络解析路径）。

```csharp
// ✅ 好 —— 栈上分配，无 GC
private void ProcessVertices(Vector3[] vertices, int count)
{
    Span<Vector3> span = vertices.AsSpan(0, count);  // 零分配切片
    for (int i = 0; i < span.Length; i++)
    {
        span[i] *= Time.deltaTime;
    }
}

// ✅ 好 —— 栈分配临时数组
private void ParsePacket(byte[] data)
{
    Span<int> fields = stackalloc int[8];             // 栈上 8 个 int
    for (int i = 0; i < fields.Length; i++)
    {
        fields[i] = BitConverter.ToInt32(data, i * 4);
    }
}
```

> **限制**：不要把经验值（如“< 1KB”）写成通用安全线。`stackalloc` 的上限应由调用深度、平台栈大小、数据规模和 Profiling/压力测试共同验证；长度不受控或来自外部输入时，改用受限池化缓冲区或托管数组。

## 10. 性能反模式清单

### 10.1 代码审查反模式清单

在审查 Unity 代码时，请标记以下反模式：

| 反模式 | 影响 | 解决方案 |
|--------------|--------|----------|
| `GetComponent` 出现在 Update | 🔴 高 | 在 Awake 中缓存 |
| 运行时调用 `FindObjectOfType` | 🔴 高 | 使用引用或事件 |
| `new List<T>()` 出现在 Update | 🔴 高 | 预分配并 `Clear()` |
| 在循环中拼接字符串 | 🟡 中 | 使用 `StringBuilder` |
| `Camera.main` 出现在 Update | 🟡 中 | 缓存引用 |
| Update 中使用 LINQ | 🟡 中 | 使用显式循环 |
| 每帧 `Physics.Raycast` | 🟡 中 | 节流或放在 FixedUpdate |
| 无意访问 `material` 或修改 `sharedMaterial` | 🟡 中 | 单实例属性使用 `MaterialPropertyBlock`；独立材质明确生命周期 |
| 事件订阅用 lambda | 🟢 低 | 使用方法组 |
| 协程循环中 `new WaitForSeconds` | 🟢 低 | 缓存 wait 对象 |

### 10.2 Update 方法危险信号识别

```csharp
// 🔴 Update 方法中的危险信号
void Update()
{
    GetComponent<T>()                    // 🔴 未缓存的查询
    FindObjectOfType<T>()                // 🔴 场景扫描
    new List<T>()                        // 🔴 分配
    new T[]                              // 🔴 分配
    string + string                      // 🔴 字符串分配
    $"interpolated {value}"              // 🔴 字符串分配
    .Where() .Select() .ToList()         // 🔴 LINQ 分配
    Camera.main                          // 🔴 未缓存的查询
    GameObject.Find()                    // 🔴 字符串查找
    Physics.OverlapSphere()              // ⚠️ 分配版本（用 NonAlloc）
}

// 🟢 推荐写法
void Update()
{
    m_cachedComponent                    // 🟢 缓存的引用
    m_cachedList.Clear()                 // 🟢 复用的集合
    m_stringBuilder.Clear().Append()     // 🟢 复用的 builder
    for (int i = 0; i < count; i++)      // 🟢 显式循环
    m_cachedCamera                       // 🟢 缓存的引用
    Physics.OverlapSphereNonAlloc()      // 🟢 零分配
}
```

### 10.3 务必做 ✅

- 在 `Awake()` 中缓存组件引用
- 按预期容量预分配集合
- 对频繁生成的对象使用对象池
- 使用零分配的物理方法（`NonAlloc` 系列）
- 缓存 Shader 属性 ID
- 对性能关键代码使用 `ProfilerMarker`
- 项目已采用 Unity 6 `Awaitable` 时按现有异步模式使用；其他版本或既有协程体系不应仅为此迁移。

### 10.4 热路径中避免做 ❌

- 在 Update 循环中 GetComponent/Find
- 在 Update 循环中分配（new）
- 在 Update 循环中使用 LINQ
- 在热路径中拼接字符串
- 每帧访问 `Camera.main`
- 在协程循环中 `new WaitForSeconds`
- 区分共享材质、独立材质和 `MaterialPropertyBlock` 的所有权，不把二者机械替换

### 10.5 可考虑 ⚠️

- 对开销大的操作做节流
- 批量执行物理查询
- 在目标平台进行 Profiler 采样
- 对重计算使用 Jobs/Burst
- 配置物理碰撞矩阵
