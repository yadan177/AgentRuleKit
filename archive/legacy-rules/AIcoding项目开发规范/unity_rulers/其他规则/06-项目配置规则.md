# 06 - Unity 项目配置

> - 🟢 本文件适用于检查或修改 Unity 的 Editor Settings、Project Settings、包、渲染管线、Build Settings 与预设。
> - 🔴 不适用：把示例配置直接覆盖到未知项目，或未经授权升级 Unity、包、渲染管线与构建体系。

---

## 1. 项目初始化与兼容性检查

🔴 **AI 修改配置前**必须先读取 `ProjectSettings/ProjectVersion.txt`、`Packages/manifest.json`、现有渲染与输入设置、目标平台、构建脚本和同项目配置。以下值是按条件选择的参考，不是可直接覆盖的默认清单。

### 1.1 Unity 版本锁定

> 🔑 **关键决策**：项目应锁定团队已验证支持的 Unity 版本；新项目根据目标平台、包/SDK 兼容性、维护周期和发布要求选择受支持版本，不得擅自升级已有项目。

✅ 推荐
- 使用项目已锁定版本；新项目可在平台、插件和发布周期均兼容时选择受支持的 LTS
- `ProjectSettings/ProjectVersion.txt` 保持由目标项目实际 Editor 写入的具体版本号
- 团队开发环境应满足项目工具链和代码格式要求；IDE 不必机械统一版本

❌ 不要
- 未经风险评估使用预发布或与目标平台不兼容的 Editor
- 团队成员使用会改写项目序列化格式或包锁定结果的不兼容 Editor

### 1.2 Packages/manifest.json 必备包

✅ 按项目需要选择
- 渲染：已采用 URP 时使用 `com.unity.render-pipelines.universal`
- 输入：沿用项目已经启用的 Input System 或 Legacy Input
- UI：沿用已采用的 UI Toolkit、UGUI 或其他 UI 体系
- 调试：仅在项目已有或用户授权时引入 Memory Profiler、Profiler Core 等工具

❌ 不要
- 引入"看起来很全"的 Asset Store 包（按需引入）
- 同时启用新旧 Input System（除非项目有兼容性需求）

### 1.3 目录结构

- 🔴 已有项目沿用当前的功能、模块、包或资源分组，不为套用 `Scenes/Scripts/Prefabs` 模板批量搬迁。
- 🟡 新项目根据规模选择按功能或资源类型组织，保证运行时、Editor 代码和第三方内容的编译边界清晰。
- 🔴 `Editor` 代码必须位于 Editor 专用编译范围；目录大小写和命名必须与项目及目标文件系统一致。
- 🔴 未核实项目资源系统时，不批量使用 `Resources/` 或迁移到 Addressables（详见 09）。


## 2. 🟠 Editor Settings（必须配置）

### 2.1 Version Control 模式

> 🔑 **关键决策**：Unity 项目必须用 **Visible Meta Files** 模式，与 Git 兼容。

✅ 推荐
```
Edit > Project Settings > Editor > Version Control Mode: Visible Meta Files
```

❌ 不要
- `Hidden Meta Files`（`.meta` 文件会被忽略，Git 无法追踪）
- 在未确认团队合并与资产序列化策略时擅自切换 Asset Serialization

### 2.2 Asset Serialization

✅ 推荐
```
Asset Serialization: Force Text
```

理由：文本格式利于 Git 合并冲突解决和版本对比。

### 2.3 Script Compilation

✅ 推荐
- 移动端/正式发布的 Scripting Backend 以目标平台、插件、热更新与构建验证结果为准；IL2CPP 是候选，不是默认切换动作
- Api Compatibility Level、C# 语言特性与包兼容性以项目当前配置和目标平台为准
- 在目标平台、插件和构建流程均验证兼容时，发布版本可评估 `IL2CPP`

❌ 不要
- 未确认目标平台、热更新方案和第三方插件兼容性时切换 Scripting Backend 或 API Compatibility Level


## 3. 🟠 Project Settings 关键项

### 3.1 Player Settings

| 项 | 决策依据 | 验证 |
|----|--------|------|
| Company / Product / Identifier | 产品与发布平台的正式标识 | 打包后核对应用标识、显示名和升级兼容性 |
| Icon / Splash | 品牌资产、平台规格和许可 | 检查各平台尺寸、透明度和构建结果 |
| Resolution / Orientation | UI 布局、设备类型和产品交互 | 用目标分辨率、方向和安全区验证 |
| Run In Background | 暂停、联机、音频和系统资源策略 | 分别验证失焦、挂起和恢复 |
| Resizable / Fullscreen | 桌面窗口产品要求 | 验证分辨率切换和 UI 重排 |

### 3.2 Quality Settings

- 画质档位数量和名称由产品设置、设备覆盖与运行时切换策略决定，不固定为 Low / Medium / High。
- VSync、目标帧率、抗锯齿、阴影和后处理需在目标设备上联合验证，不按“PC/移动端”标签套固定值。
- 多平台或设备差异足以影响性能时，再设计平台覆盖或分档；不为形式上的“分平台”复制一套相同配置。

### 3.3 Graphics Settings

- 沿用已选渲染管线和当前 Graphics Settings；切换管线属于架构变更，需要用户授权。
- 是否拆分渲染资产，以目标平台差异、构建流程和实测结果为准。
- 阴影距离、级联、LOD、Renderer Feature 和后处理不设置通用数值；记录测试场景、机型、分辨率和帧时证据。


## 4. 🟠 渲染管线选型

### 4.1 URP vs HDRP vs Built-in

| 维度 | 需要核对的事实 |
|------|------|
| 现有项目 | 当前管线、自定义 Shader、材质、Renderer Feature、第三方插件和资产转换成本 |
| 目标平台 | Unity 版本与平台支持、显卡能力、画质目标、包体和内存预算 |
| 维护与发布 | 团队经验、包/SDK 兼容、构建时间、升级路线和目标平台实测 |

✅ 推荐
- 新项目可在目标平台、插件和画质需求都兼容时评估 URP
- 高端平台或影视级渲染可评估 HDRP；已有 Built-in、URP 或 HDRP 项目应优先维持当前管线

### 4.2 渲染资产配置

- 项目已使用 URP 时，先检查当前 URP Asset、Renderer、Quality 覆盖和构建脚本的引用关系。
- 只在平台画质或性能策略确有差异时拆分资产，并验证构建实际选中的配置。
- SSAO、Bloom、LOD Bias 等选项只能基于画面需求和目标设备数据调整，不因“移动端”标签直接禁用或写死数值。


## 5. 🟠 Build Settings

### 5.1 场景列表

- 场景列表和首个场景必须服从现有启动流程、构建脚本和加载架构；不默认新建 Splash 场景。
- 场景引用使用 Unity 项目路径或项目已采用的稳定标识，避免依赖开发机绝对路径。
- 不以中文或空格本身判定错误；命名只要与项目、构建工具、平台和团队约定兼容即可。

### 5.2 平台切换

✅ 推荐
- 项目已采用且当前 Unity 版本支持 Build Profiles 时，用其按平台分组
- Android / iOS / Windows / macOS 各自的 Player Settings 覆盖
- 切换平台后立刻跑一次 Build 检查


## 6. 🟡 预设管理（按需）

### 6.1 Default Presets

- 只有大量同类资产确需一致导入时才创建 Default Preset，并先盘点现有 Preset 和 `AssetPostprocessor`。
- 存放位置沿用项目结构；项目未规定时可放在明确的 Editor 配置目录。
- 修改 Default Preset 会影响后续导入，需用代表性资产验证，不直接覆盖有特殊需求的旧资产。

### 6.2 Texture Import 决策

Texture Type、Filter Mode、Compression、Max Size 和平台 Override 取决于资产用途、源尺寸、缩放方式、内存/包体预算、目标 GPU 格式和画质验收。不将 `Bilinear`、`Normal Quality` 或 `2048` 设为所有 Texture 的默认答案。


## 7. 🟡 常见配置错误清单

### 7.1 配置陷阱

| 陷阱 | 表现 | 解决方案 |
|------|------|---------|
| Color Space 选错 | 颜色发灰 | 按渲染管线、目标平台、美术资产与现有项目设置验证；不要用“2D=Gamma、3D=Linear”替代实际测试 |
| 渲染资产引用错误 | 构建选中非预期资产，画面或性能异常 | 核对 Quality/Graphics、构建脚本与实际构建日志 |
| API Compatibility 不匹配 | 包导入失败 | 以 Unity 版本、已安装包、目标平台和项目现有兼容级别验证后调整 |
| Target Architecture 错 | 设备或商店校验失败 | 按当前发布渠道、应用中的原生代码和目标设备选择并实机验证 |

### 7.2 调试方法

> 💡 工具：
> - `Edit > Project Settings` 全面板检查
> - `Window > Analysis > Profiler` 看性能
> - `Edit > Preferences > External Tools` 配置 IDE


## 8. 🟢 高级配置（可选）

### 8.1 Custom Defines

- 日志与诊断由统一日志门面的构建策略控制；不要在业务调用点逐条使用 `#if DEVELOPMENT_BUILD`，详见 [07-日志与调试规则](./07-日志调试规则.md)
- `UNITY_ANDROID`、`UNITY_IOS`、`UNITY_EDITOR` 等是 Unity 内置条件编译符号，可用于平台边界，不得手工重复加入 Scripting Define Symbols。
- 新增自定义符号前检查 asmdef、包和构建脚本中的现有用法；命名沿用项目前缀，避免产生互相矛盾的组合。

### 8.2 Scripting Define Symbols

- 只定义项目真正需要的功能开关，并记录哪些构建配置负责注入它们。
- 团队自定义符号沿用项目命名约定；无约定时使用能区分包和业务的前缀。

### 8.3 Addressables 配置

🟡 仅当项目已采用 Addressables 或资源架构明确选择它时配置本节：
- Group、地址、Build Path 与远程加载策略遵循项目现有资源/热更新设计，而不是按场景名称机械分组。
- `RemoteBuildPath`、`LocalBuildPath`、CDN、缓存和内容更新需要与发布流程、目标平台和回滚策略一并验证。
- 是否迁移 `Resources/` 由资源盘点、包体、内存、热更新需求和迁移风险决定；不要将“用 Addressables 替代 Resources”写成默认操作。

❌ 不要
- 未核对引用、包体和加载链路就混用或批量迁移 Addressables 与 Resources，导致资源重复或引用丢失。


## 9. 项目配置完成检查清单

AI 创建 / 修改 Unity 项目配置时，必须按此清单核查：

- [ ] Unity 版本与项目锁定值、包/SDK 和目标平台一致
- [ ] `Packages/manifest.json` 与锁定文件保持项目已验证的依赖
- [ ] 目录、asmdef 和 Editor/运行时边界与项目结构一致
- [ ] Editor Settings 用 Visible Meta Files + Force Text
- [ ] Scripting Backend、API Compatibility 与热更新/插件在目标平台构建中已验证
- [ ] Player Settings 关键项配置
- [ ] Quality 和 Graphics Settings 已按产品目标与目标设备实测
- [ ] 实际构建引用的渲染资产与预期一致
- [ ] Build Settings 场景顺序正确
- [ ] 切换平台后 Build 通过

> 💡 清单用于防止遗漏，不代表未经目标平台构建和设备验证就已达到可发布基线。
