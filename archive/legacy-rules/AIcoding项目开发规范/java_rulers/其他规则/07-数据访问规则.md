# 07 - Java 数据访问规则

> 🟢 本文件适用于数据库访问层设计（SQL/索引/MyBatis/JPA/分库分表）。<br>
> 🔴 不适用：NoSQL、消息队列、对象存储、缓存设计

---

## 1. 建表规约

### 1.1 表名与字段名

🟡 **推荐**（P3C 建表规约）：

- 表名、字段名**必须使用小写字母或数字**
- **禁止出现数字开头，禁止两个下划线中间只出现数字**
- 数据库字段名的修改代价很大（无法进行预发布），所以字段名称需要慎重考虑
- **MySQL 在 Windows 下不区分大小写**，但在 Linux 下默认是区分大小写，因此**数据库名、表名、字段名都不允许出现任何大写字母**

**正例**：`aliyun_admin`、`rdc_config`、`level3_name`
**反例**：`AliyunAdmin`、`rdcConfig`、`level_3_name`

🟡 **推荐**：

- **表名不使用复数名词**
  - **正例**：`order`（一张订单）
  - **反例**：`orders`
  - 原因：表名应仅表示表里面的实体内容，不应表示实体数量；对应于 DO 类名也是单数形式
- **禁用 MySQL 保留字**：`desc` / `range` / `match` / `delayed` 等

### 1.2 索引名

🟡 **推荐**：

| 索引类型 | 命名规范 |
|---|---|
| **主键索引** | `pk_字段名` |
| **唯一索引** | `uk_字段名` |
| **普通索引** | `idx_字段名` |

- `pk_` 即 `primary key`
- `uk_` 即 `unique key`
- `idx_` 即 `index` 的简称

### 1.3 表必备 3 字段

🟡 **推荐**：

- **表必备三字段**：`id`、`gmt_create`、`gmt_modified`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `unsigned bigint` | 主键，单表时自增、步长为 1 |
| `gmt_create` | `datetime` | 主动创建时间（现在时）|
| `gmt_modified` | `datetime` | 被动更新时间（过去分词）|

### 1.4 表名推荐规范

🟡 **推荐**（P3C 建表规约）：

- **库的命名**：`业务名称_表的作用`，如 `alipay_task` / `force_project` / `trade_config`
- **库名**与应用名称尽量一致

### 1.5 逻辑删除字段

🟡 **推荐**：

- **表达"是 / 否"概念的字段，必须使用 `is_xxx` 命名**，数据类型是 `unsigned tinyint`（`1` 表示是，`0` 表示否）
  - **正例**：逻辑删除字段 `is_deleted`，`1` 表示删除，`0` 表示未删除
- 任何字段如果为非负数，必须是 `unsigned`

### 1.6 字段长度与精度

🟡 **推荐**：

- **小数类型为 `decimal`，禁止使用 `float` 和 `double`**
  - **原因**：`float` 和 `double` 存在精度损失，比较时可能得到不正确的结果
  - 如果存储的数据范围超过 `decimal` 的范围，建议将数据拆成整数和小数分开存储
- **如果存储的字符串长度几乎相等，使用 `char` 定长字符串类型**
- **`varchar` 是可变长字符串**，不预先分配存储空间，长度不要超过 5000
  - 如果存储长度大于 5000，定义字段类型为 `text`，**独立出来一张表**，用主键来对应，避免影响其它字段索引效率

🟡 **推荐**：合适的字符存储长度，**节约数据库表空间、节约索引存储，更重要的是提升检索速度**：

| 对象 | 年龄区间 | 类型 | 字节 |
|---|---|---|---|
| 人 | 150 岁之内 | `unsigned tinyint` | 1 |
| 龟 | 数百岁 | `unsigned smallint` | 2 |
| 恐龙化石 | 数千万岁 | `unsigned int` | 4 |
| 太阳 | 约 50 亿年 | `unsigned bigint` | 8 |

## 2. 字段修改与冗余

### 2.1 字段注释更新

🟡 **推荐**：

- 如果修改字段含义或对字段表示的状态追加时，**需要及时更新字段注释**

### 2.2 字段冗余

🟡 **推荐**：

- 字段允许适当冗余，**以提高查询性能**，但必须考虑数据一致
- 冗余字段应遵循：
  1. **不是频繁修改的字段**
  2. **不是 `varchar` 超长字段，更不能是 `text` 字段**
- **正例**：商品类目名称使用频率高，字段长度短，名称基本一成不变，可在相关联表中冗余存储类目名称，避免关联查询
- **反例**：`order` 表冗余 `user_name`（用户改了名字，订单里的名字也得改，频繁 UPDATE）

### 2.3 分库分表决策

🟡 **推荐**：

- **单表行数超过 500 万行或者单表容量超过 2GB，才推荐进行分库分表**
- **如果预计三年后的数据量根本达不到这个级别，请不要在创建表时就分库分表**
- **过早优化是灾难**（KISS / YAGNI 原则）

## 3. 索引设计

### 3.1 唯一索引

🟡 **推荐**：

- **业务上具有唯一特性的字段**，即使是多个字段的组合，**也必须建成唯一索引**
- 不要以为唯一索引影响了 insert 速度，这个速度损耗可以忽略，但提高查找速度是明显的
- 即使在应用层做了非常完善的校验控制，只要没有唯一索引，根据墨菲定律，必然有脏数据产生

### 3.2 索引长度

🟡 **推荐**：

- **在 `varchar` 字段上建立索引时，必须指定索引长度**，没必要对全字段建立索引，根据实际文本区分度决定索引长度即可
- **公式**：`count(distinct left(列名, 索引长度)) / count(*)` 计算区分度
  - 一般对字符串类型数据，长度为 **20** 的索引区分度会高达 **90%** 以上

**反例**：在 `varchar(255)` 上建索引不指定长度 → 索引占用空间巨大，检索速度反而慢
**正例**：`CREATE INDEX idx_user_email ON user(email(20));`

### 3.3 索引组合与顺序

🟡 **推荐**：

- 建组合索引的时候，**区分度最高的在最左边**
  - **正例**：如果 `where a=? and b=?`，`a` 列接近于唯一值，**只需要单建 `idx_a` 索引即可**
- 存在**非等号和等号混合判断条件时，在建索引时，请把等号条件的列前置**
  - **正例**：`where a>? and b=?`，即使 `a` 的区分度更高，也**必须把 `b` 放在索引的最前列**

### 3.4 ORDER BY 利用索引有序性

🟡 **推荐**：

- 如果有 `ORDER BY` 的场景，请注意**利用索引的有序性**
- `ORDER BY` 最后的字段是组合索引的一部分，**并且放在索引组合顺序的最后**，避免出现 `file_sort`

**正例**：`WHERE a=? AND b=? ORDER BY c;` 索引：`a_b_c`

**反例**：索引中有范围查找，索引有序性无法利用：
```sql
-- 索引 a_b 无法用于下面的排序
WHERE a > 10 ORDER BY b;
```

### 3.5 覆盖索引避免回表

🟡 **推荐**：

- **利用覆盖索引来进行查询操作，避免回表**
- 覆盖索引：`explain` 结果的 `extra` 列出现 `using index`

**正例**：
```sql
-- 索引 (a, b)，查询 a 和 b 都用到，覆盖索引，不回表
SELECT a, b FROM table WHERE a = ?;
```

### 3.6 模糊查询禁止左模糊

🟡 **推荐**：

- **页面搜索严禁左模糊或者全模糊**，如果需要请走搜索引擎来解决
- 索引文件具有 B-Tree 的**最左前缀匹配**特性，如果左边的值未确定，那么无法使用此索引

**反例**：
```sql
-- ❌ 无法使用索引，全表扫描
SELECT * FROM user WHERE name LIKE '%张%';
```

### 3.7 LIMIT 深分页优化

🟡 **推荐**：

- 利用**延迟关联**或者**子查询**优化超多分页场景
- MySQL 并**不是跳过 offset 行**，而是取 offset+N 行，然后返回放弃前 offset 行，返回 N 行
- 当 offset 特别大的时候，效率就非常低下
- 控制返回的总页数；超过特定阈值时进行 SQL 改写

**正例**（延迟关联）：
```sql
SELECT a.* FROM table1 a, (SELECT id FROM table1 WHERE 条件 LIMIT 100000, 20) b WHERE a.id = b.id;
```

### 3.8 SQL 性能目标

🟡 **推荐**：SQL 性能优化的目标：

| 级别 | 含义 |
|---|---|
| `consts` | 单表中最多只有一个匹配行（主键或唯一索引）|
| `ref` | 使用普通的索引（normal index）|
| `range` | 对索引进行范围检索 |
| **目标** | **至少达到 `range` 级别，要求 `ref` 级别，理想 `consts`** |

**反例**：`explain` 结果 `type=index`（索引物理文件全扫描），速度非常慢，比 range 还低

### 3.9 多表 JOIN

🟡 **推荐**：

- **超过三个表禁止 `join`**
- 需要 `join` 的字段，**数据类型必须绝对一致**
- 多表关联查询时，**保证被关联的字段需要有索引**

### 3.10 防止索引失效

🟡 **推荐**：

- **防止因字段类型不同造成的隐式转换，导致索引失效**
  - **反例**：`phone varchar(11)` 字段用 `phone = 1234567890`（数字）查询 → 索引失效
  - **正例**：`phone = '1234567890'`（字符串）

🟢 **参考**：建索引的**极端误解**（不要犯）：

| 误解 | 实际 |
|---|---|
| 宁滥勿缺（一个查询建一个索引）| 索引过多拖慢 UPDATE / INSERT |
| 宁缺勿滥（索引不建）| 影响查询性能 |
| 抵制唯一索引（业务唯一性靠应用层"先查后插"）| 并发场景下必然产生脏数据（墨菲定律）|

## 4. SQL 编写

### 4.1 count 用法

🟡 **推荐**：

- **不要使用 `count(列名)` 或 `count(常量)` 来替代 `count(*)`**
- `count(*)` 是 SQL92 定义的标准统计行数的语法，**跟数据库无关，跟 NULL 和非 NULL 无关**
  - `count(*)` 会统计值为 NULL 的行
  - `count(列名)` 不会统计此列为 NULL 值的行
- **`count(distinct col)`** 计算该列除 NULL 之外的不重复行数
- **注意**：`count(distinct col1, col2)` 如果其中一列全为 NULL，即使另一列有不同的值，也返回为 0

### 4.2 NULL 处理与 NPE

🟡 **推荐**：

- 当某一列的值全是 NULL 时：
  - `count(col)` 的返回结果为 **0**
  - `sum(col)` 的返回结果为 **NULL**（**sum() 用时需注意 NPE**）

**正例**（sum 的 NPE 防护）：
```sql
SELECT IF(ISNULL(SUM(g)), 0, SUM(g)) FROM table;
```

🟡 **推荐**：

- 使用 `ISNULL()` 来判断是否为 NULL 值
- **NULL 与任何值的直接比较都为 NULL**：
  - `NULL <> NULL` 返回 NULL（不是 `false`）
  - `NULL = NULL` 返回 NULL（不是 `true`）
  - `NULL <> 1` 返回 NULL（不是 `true`）

### 4.3 分页查询 count=0

🟡 **推荐**：

- 代码中写分页查询逻辑时，**若 count 为 0 应直接返回，避免执行后面的分页语句**

### 4.4 禁止外键与级联

🟡 **推荐**：

- **不得使用外键与级联**，一切外键概念必须在应用层解决
- **原因**：
  - 外键与级联更新适用于单机低并发，不适合分布式、高并发集群
  - 级联更新是**强阻塞**，存在数据库更新风暴的风险
  - 外键影响数据库的插入速度

### 4.5 禁用存储过程

🟡 **推荐**：

- **禁止使用存储过程**，存储过程难以调试和扩展，更没有移植性

### 4.6 数据订正先 select

🟡 **推荐**：

- **数据订正（特别是删除、修改记录操作）时，要先 `SELECT`**，避免出现误删除
- **确认无误才能执行更新语句**

### 4.7 in 操作数量限制

🟡 **推荐**：

- `IN` 操作能避免则避免
- 若实在避免不了，需要仔细评估 `IN` 后边的集合元素数量，**控制在 1000 个之内**

### 4.8 字符集与编码

🟢 **参考**：

- 如果有全球化需要，所有的字符存储与表示，**均以 `utf-8` 编码**
- 注意字符统计函数的区别：
  - `SELECT LENGTH("轻松工作")` 返回 **12**（字节数）
  - `SELECT CHARACTER_LENGTH("轻松工作")` 返回 **4**（字符数）
- 如果需要存储表情，那么选择 `utf8mb4` 来进行存储，**注意它与 utf-8 编码的区别**

### 4.9 TRUNCATE TABLE 不建议

🟢 **参考**：

- `TRUNCATE TABLE` 比 `DELETE` 速度快，且使用的系统和事务日志资源少
- 但 `TRUNCATE` **无事务**且**不触发 trigger**，有可能造成事故
- 故**不建议在开发代码中使用此语句**

## 5. ORM 映射通用规约

### 5.1 禁用 SELECT *

🟡 **推荐**：

- **在表查询中，一律不要使用 `*` 作为查询的字段列表**，需要哪些字段必须明确写明
  - **原因**：
    1. 增加查询分析器解析成本
    2. 增减字段容易与 `resultMap` 配置不一致
- **正例**：`SELECT id, name, age FROM user WHERE id = ?`
- **反例**：`SELECT * FROM user WHERE id = ?`

### 5.2 POJO 与数据库字段映射

🟡 **推荐**：

- **POJO 类的布尔属性不能加 `is`**（如 `private Boolean deleted`）
- **数据库字段必须加 `is_`**（如 `is_deleted`）
- **必须**在 ORM 映射文件中做字段与属性之间的映射（如 `<resultMap>`）
- 在 MyBatis Generator 生成的代码中，需要进行对应的修改

### 5.3 resultMap / resultClass

🟡 **推荐**：

- **不要用 `resultClass` 当返回参数**，即使所有类属性名与数据库字段一一对应，也需要定义
- **反过来，每一个表也必然有一个与之对应的 `resultMap`**
- 配置映射关系，使字段与 DO 类解耦，方便维护

### 5.4 不用 HashMap 作查询结果集

🟡 **推荐**：

- **不允许直接拿 `HashMap` 与 `Hashtable` 作为查询结果集的输出**
- **原因**：`resultClass="Hashtable"` 会置入字段名和属性值，**但是值的类型不可控**（消费方每次拿到 Object）

### 5.5 更新 gmt_modified

🟡 **推荐**：

- 更新数据表记录时，**必须同时更新记录对应的 `gmt_modified` 字段值为当前时间**
- 不然时间字段永远不变，调试 / 业务分析都看不出来

### 5.6 不用万能 update

🟡 **推荐**：

- **不要写一个大而全的数据更新接口**
- **反例**：
  ```java
  // ❌ 传入 POJO 不管是不是自己的目标更新字段都更新
  orderMapper.update(order);  // 内部 SQL：
  // UPDATE order SET c1=?, c2=?, c3=?（所有字段都更新）
  ```
- **问题**：
  1. 易出错（不打算改的字段被改了）
  2. 效率低（UPDATE 全部字段）
  3. 增加 binlog 存储
- **正例**：用 `UPDATE SET col1 = ?, col2 = ? WHERE id = ?` 显式列出要改的字段

### 5.7 @Transactional 不要滥用

🟢 **参考**：

- `@Transactional` 事务不要滥用
- 事务会影响数据库的 QPS
- 使用事务的地方需要考虑各方面的回滚方案，包括**缓存回滚 / 搜索引擎回滚 / 消息补偿 / 统计修正**等

## 6. MyBatis / MyBatis-Plus（AI 视角扩展）

### 6.1 #{} vs ${}

🟡 **推荐**：

- **MyBatis XML 配置参数使用 `#{}`**（PreparedStatement，预编译）
- **不要使用 `${}`**（字符串拼接，SQL 注入风险）

```xml
<!-- ✅ 安全：预编译 -->
SELECT * FROM user WHERE id = #{id}

<!-- ❌ 危险：注入风险 -->
SELECT * FROM user WHERE id = ${id}
```

🟡 **推荐**：

- **不可变 SQL 必须用 `#{}`**（值由用户传入）
- **表名 / 字段名 / ORDER BY 字段** 等 SQL 关键字如必须动态拼接，**应使用白名单校验**（不是直接 `${}`）

```java
// ✅ 表名白名单 + 反射设置
private static final Set<String> ALLOWED_TABLES = Set.of("user", "order", "product");

if (!ALLOWED_TABLES.contains(tableName)) {
    throw new BizException("20101", "不允许的表名");
}
```

### 6.2 iBATIS 自带 queryForList 不推荐

🟡 **推荐**：

- **iBATIS 自带的 `queryForList(String statementName, int start, int size)` 不推荐使用**
- 原因：实现方式是**在数据库取到 statementName 对应的 SQL 语句的所有记录**，再通过 `subList` 取 `start, size` 的子集合
- **正例**：用 `PageHelper.startPage()` + `LIMIT` 分页：

```java
PageHelper.startPage(pageNum, pageSize);
List<Order> orders = orderMapper.selectByCondition(query);
PageInfo<Order> pageInfo = new PageInfo<>(orders);
```

### 6.3 MyBatis-Plus 实战用法（AI 视角扩展）

🟡 **推荐**：国内项目大量使用 MyBatis-Plus 简化开发：

**LambdaQueryWrapper**（**强类型防注入**）：
```java
// ✅ 类型安全的查询
List<Order> orders = orderMapper.selectList(
    Wrappers.<Order>lambdaQuery()
        .eq(Order::getStatus, OrderStatus.PAID)
        .gt(Order::getAmount, new BigDecimal("100"))
        .orderByDesc(Order::getCreatedAt)
);

// ❌ 字符串拼接（容易拼错 / SQL 注入）
orderMapper.selectList(
    new QueryWrapper<Order>().eq("status", "PAID")
);
```

**IService 通用 CRUD**：
```java
@Service
public class OrderService extends ServiceImpl<OrderMapper, Order> {
    public Order getByOrderNo(String orderNo) {
        return lambdaQuery().eq(Order::getOrderNo, orderNo).one();
    }
}
```

**逻辑删除**（自动加 `WHERE is_deleted = 0`）：
```java
@Data
public class Order {
    @TableLogic  // 自动处理逻辑删除
    private Integer isDeleted;
}
```

### 6.4 `<isEqual>` / `<isNotEmpty>` 等动态 SQL 标签

🟢 **参考**：

- `<isEqual>` 中的 `compareValue` 是与属性值对比的常量，一般是数字
- `<isNotEmpty>` 表示不为空且不为 `null` 时执行
- `<isNotNull>` 表示不为 `null` 值时执行

## 7. JPA / Hibernate（AI 视角扩展）

### 7.1 Entity 基础规范

🟡 **推荐**：

- **Entity 必须有无参构造方法**（Hibernate 反射需要）
- **Entity 不要在 setter 里加业务逻辑**（破坏 Hibernate 的代理机制）
- **Entity 类不要有 final 字段 / 方法**（Hibernate 需要生成代理）

### 7.2 关联映射 N+1 陷阱

🟡 **推荐**：

- **避免 N+1 查询**（最容易踩的 JPA 坑）
- **反例**：
  ```java
  // ❌ 查询 10 个 Order，每个 Order 触发 1 次 lazy load user → 11 次 SQL
  @Transactional
  public List<OrderDTO> listOrders() {
      return orderRepository.findAll().stream()
          .map(o -> new OrderDTO(o, o.getUser()))
          .collect(Collectors.toList());
  }
  ```
- **正例**：
  ```java
  // ✅ 1 次 JOIN 完成
  @Transactional(readOnly = true)
  public List<OrderDTO> listOrders() {
      return orderRepository.findAllWithUser();  // @Query with JOIN FETCH
  }

  @Query("SELECT o FROM Order o JOIN FETCH o.user")
  List<Order> findAllWithUser();
  ```

### 7.3 懒加载必须在事务内

🟡 **推荐**：

- **JPA 懒加载（Lazy Loading）必须在 `@Transactional` 方法内访问**
- 反例：Controller 调 `orderRepository.findById()`，返回的 `order.getItems()` 在事务外触发懒加载 → `LazyInitializationException`

**正例**：
```java
@Service
public class OrderService {
    @Transactional(readOnly = true)
    public OrderDTO getOrder(Long id) {
        Order order = orderRepository.findById(id).orElseThrow();
        order.getItems().size();  // 事务内触发懒加载
        return OrderMapper.toDTO(order);
    }
}
```

### 7.4 Hibernate Validator 在 DTO 上的复用

🟢 **可选**：JPA 项目里 `@NotNull` / `@Size` 既可作 Hibernate Validator 校验，也可作数据库字段长度定义：

```java
@Entity
@Table(name = "user")
public class User {
    @Id
    private Long id;

    @NotBlank  // Hibernate Validator 检查
    @Size(max = 50)  // 与数据库 VARCHAR(50) 对应
    private String name;
}
```

## 8. 数据库连接池

### 8.1 HikariCP 配置示例（AI 视角扩展）

🟡 使用 `spring-boot-starter-jdbc` 或 `spring-boot-starter-data-jpa` 且未覆盖数据源时，Spring Boot 通常会带入并优先选择 HikariCP；自定义 `DataSource`、应用服务器/JNDI 或其他依赖组合可能不同。是否采用 HikariCP 及其参数必须遵循项目现有选型、数据库限制、连接数预算与压测证据，不能因本节示例直接替换连接池。

下面数值只展示配置字段，不是生产默认值；`maximum-pool-size`、超时、空闲连接和泄漏检测阈值应根据数据库容量、实例数、查询延迟与线上告警确定。

```yaml
# application.yml
spring:
  datasource:
    type: com.zaxxer.hikari.HikariDataSource
    hikari:
      pool-name: order-service-pool
      minimum-idle: 5
      maximum-pool-size: 20
      idle-timeout: 600000      # 10 分钟
      max-lifetime: 1800000     # 30 分钟（要小于数据库 wait_timeout）
      connection-timeout: 30000 # 30 秒
      connection-test-query: SELECT 1
      leak-detection-threshold: 60000  # 60 秒（连接泄漏检测）
```

### 8.2 连接池大小计算

🟡 **推荐**：

| 业务类型 | 连接池大小 |
|---|---|
| **CPU 密集**（少 IO 等待）| `CPU 核数 + 1` ≈ 5-10 |
| **IO 密集**（大量数据库查询）| `CPU 核数 × 2` ≈ 20-50 |
| **混合** | 30 起步，按压测调整 |

🟡 **推荐**：

- **连接池大小应远小于数据库 `max_connections`**（避免撑爆数据库）
  - 默认 MySQL `max_connections = 151`
  - 10 个服务实例 × 每实例 20 连接 = 200，可能超过 151 → 拒绝连接
- **`max-lifetime` 必须小于数据库 `wait_timeout`**（避免拿到数据库已关闭的连接）

### 8.3 连接泄漏检测

🟡 **推荐**：

- 启用 HikariCP 的 `leak-detection-threshold`（连接超过 N 毫秒未归还视为泄漏）
- 配合日志告警

### 8.4 Druid（阿里，国内常用）

```xml
<dependency>
```

## 9. 慢 SQL 排查与性能调优

### 9.1 慢 SQL 开关

🟡 **推荐**：

- **生产环境必须开启慢 SQL 日志**（`long_query_time`，如 1 秒）
- 慢 SQL 立即触发告警

```sql
-- MySQL 开启慢日志
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;  -- 单位：秒
SET GLOBAL slow_query_log_file = '/var/log/mysql/slow.log';
```

### 9.2 EXPLAIN 分析

🟡 **推荐**：

- **慢 SQL 必须用 `EXPLAIN` / `EXPLAIN ANALYZE` 分析**
- 重点关注：

| 字段 | 关注 |
|---|---|
| `type` | 访问类型（`ALL` 是全表扫描，不行）/ 目标 `ref` 或 `consts` |
| `key` | 实际使用的索引 |
| `rows` | 扫描行数（越少越好）|
| `Extra` | 是否用上 `using index`（覆盖索引）|

### 9.3 慢 SQL 常见原因 + 优化

🟡 **推荐**：

| 慢 SQL 类型 | 原因 | 优化 |
|---|---|---|
| **全表扫描** | 没用索引 / 索引失效 | 加索引 / 字段类型匹配 |
| **JOIN 过多** | 多表 JOIN / 无索引 | 拆表 / 加索引 |
| **大 LIMIT 翻页** | `LIMIT 100000, 20` | 延迟关联 / 游标分页 |
| **SELECT *** | 查多余字段 | 显式查字段 |
| **深嵌套子查询** | 子查询当 JOIN | 改写为 JOIN |
| **OR 查询** | `WHERE a=? OR b=?` | UNION 或单独查 |

### 9.4 索引失效常见场景

🟡 **推荐**（AI 写 SQL 后立即排查）：

| 场景 | 反例 | 索引是否失效 |
|---|---|---|
| **类型不匹配** | `varchar` 字段用数字查询 | ❌ 失效 |
| **左模糊** | `LIKE '%xxx'` | ❌ 失效 |
| **OR 查询部分无索引** | `WHERE indexed_col=? OR non_indexed_col=?` | ❌ 部分失效 |
| **`!=` / `<>` 操作** | `WHERE status != 1` | ❌ 失效（多数情况）|
| **`is null` / `is not null`** | 取决于数据分布 | ⚠️ 不确定 |
| **函数计算** | `WHERE YEAR(created_at) = 2024` | ❌ 失效 |
| **字符串拼接查询** | `WHERE CONCAT(name, '') = 'xxx'` | ❌ 失效 |

**正例**：
```sql
-- ❌ 索引失效：YEAR 函数
SELECT * FROM order WHERE YEAR(created_at) = 2024;

-- ✅ 索引有效：范围查询
SELECT * FROM order WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';
```

## 10. 分库分表

### 10.1 何时分库分表

🟡 **推荐**：

- **单表行数超过 500 万行或者单表容量超过 2GB**，才推荐进行分库分表
- **如果预计三年后的数据量根本达不到这个级别，请不要在创建表时就分库分表**（过早优化）

### 10.2 ShardingSphere 实战（AI 视角扩展）

🟡 **推荐**：Apache ShardingSphere 是国内 Java 生态最常用的分库分表框架：

```yaml
# application.yml - sharding 配置
spring:
  shardingsphere:
    datasource:
      names: ds0, ds1
      ds0:
        type: com.zaxxer.hikari.HikariDataSource
        jdbc-url: jdbc:mysql://db0:3306/order_db_0
      ds1:
        type: com.zaxxer.hikari.HikariDataSource
        jdbc-url: jdbc:mysql://db1:3306/order_db_1
    rules:
      sharding:
        tables:
          t_order:
            actual-data-nodes: ds$->{0..1}.t_order_$->{0..15}  # 2 库 × 16 表 = 32 物理表
            database-strategy:
              standard:
                sharding-column: user_id
                sharding-algorithm-name: order_db_inline
            table-strategy:
              standard:
                sharding-column: order_id
                sharding-algorithm-name: order_tbl_inline
```

### 10.3 读写分离

🟡 **推荐**：查询远多于写入时（如 100:1）：

- 主库：写入 + 强一致性读
- 从库：非一致性读（容忍秒级延迟）
- ShardingSphere 读写分离 / Dynamic DataSource

🟡 **推荐**：

- **强一致性读走主库**（如支付后立即查订单状态必须从主库读）
- **延迟容忍读走从库**（如后台导出、历史报表）

### 10.4 分库分表后的挑战

🟢 **参考**：分库分表后**没有**简单方案的事情：

| 挑战 | 说明 |
|---|---|
| **跨库 JOIN** | 必须消除（拆查询、应用层组装、用宽表） |
| **全局唯一 ID** | 必须用雪花算法 / UUID（数据库自增 ID 失效） |
| **分布式事务** | 必须用 Saga / Outbox / Seata |
| **分页排序** | `LIMIT 100, 20` 跨库不准确，按 sharding key 限定范围 |
| **数据迁移** | 一致性 hash + 双写灰度 |

## 11. 数据库迁移工具（AI 视角扩展）

### 11.1 Flyway vs Liquibase

🟢 **可选**：两个主流选择：

| 工具 | 语言 | 特点 |
|---|---|---|
| **Flyway** | Java | 简单、SQL 优先，社区版功能多 |
| **Liquibase** | 跨语言 | XML/YAML 表达，支持回滚，复杂场景 |

🟡 **推荐**：**Flyway（国内项目更常用，启动简单）**

### 11.2 Flyway 用法

🟡 **推荐**：

- **数据库结构变更必须用 Flyway / Liquibase 管理**
- **禁止直接 `ALTER TABLE` 改生产数据库**（即使 DBA 操作也要走 Flyway）

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
```

**迁移文件位置**：`src/main/resources/db/migration/`

```
src/main/resources/db/migration/
├── V1__init_schema.sql          # 第 1 次迁移
├── V2__add_user_email_index.sql # 第 2 次迁移
└── V3__add_orders_archive.sql   # 第 3 次迁移
```

**迁移文件示例**（`V2__add_user_email_index.sql`）：
```sql
-- 加索引
CREATE INDEX idx_user_email ON user(email);

-- 加字段
ALTER TABLE user ADD COLUMN phone VARCHAR(20) COMMENT '手机号';

-- 加索引
CREATE INDEX idx_user_phone ON user(phone);
```

### 11.3 迁移文件命名规范

🟡 **推荐**：

- 命名 `V<版本号>__<描述>.sql`，下划线**两个**分隔
- 版本号必须**单调递增**（V1, V2, V3... 或带时间戳 V20240601...）
- 描述用英文，下划线连接（不要空格、中文）

🟡 **推荐**：

- **已应用到生产环境的迁移文件不可修改**（如需修改写新的 V2 改回 V1）
- 否则下次启动 Flyway 会因 checksum 不匹配报错

### 11.4 Flyway 在 Spring Boot 自动集成

```yaml
# application.yml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true  # 对已有数据库启动 baseline
    validate-on-migrate: true  # 检查已执行迁移的 checksum
```

🟡 **推荐**：

- **生产环境不要禁用 Flyway 校验**（`validate-on-migrate` 必须为 `true`）
