# 08 - TypeScript 常见反模式与 AI 自检

> - 🟢 本文件适用于 TypeScript 常见反模式清单与 AI 自检要点。
> - 🔴 不适用：业务逻辑实现

---

## 1. 🔴 高风险反模式与适用边界

### 1.1 any 滥用

```ts
// ❌
function f(x: any) { return x.foo; }
const data: any = JSON.parse(input);
const handler: any = (e: Event) => {};

// ✅ unknown + 收窄；项目已有运行时校验方案时复用
function f(x: unknown) {
  if (typeof x === 'object' && x !== null && 'foo' in x) {
    return (x as { foo: string }).foo;
  }
}
```

**ESLint**：如果项目已采用 typescript-eslint，可在现有配置中评估 `@typescript-eslint/no-explicit-any`；不要把某个等级写成所有项目的强制门禁。

### 1.2 `as` 逃避类型检查

```ts
// ❌ 双断言
const value = unknownValue as unknown as User;

// ❌ JSON.parse + as 跳过校验
const user = JSON.parse(input) as User;

// ✅ 使用项目已有的 schema 或自定义守卫校验；不要因本示例新增依赖
const user = UserSchema.parse(JSON.parse(input));
```

**ESLint**：`no-unsafe-*` 是否启用、启用哪些规则及严重级别，遵循项目现有配置和可接受的误报成本。

### 1.3 `!` 非空断言

```ts
// ❌
const user = users.find(u => u.id === id)!;          // 不存在就崩

// ✅
const user = users.find(u => u.id === id);
if (!user) throw new Error('Not found');
```

**ESLint**：`no-non-null-assertion` 是否启用由项目配置决定；即使未启用，也应审查断言是否有可靠的不变量。

### 1.4 装饰器配置与迁移

```ts
// ⚠️ legacy 装饰器：仅在项目编译链和框架要求时使用
@Component({ selector: 'app' })
class AppComponent {}

// ✅ 标准装饰器：仅在项目已采用对应 TypeScript/框架配置时使用
class Calculator {
  @logged
  add(a: number, b: number) { return a + b; }
}
```

- 先检查 TypeScript 版本、`experimentalDecorators`、装饰器元数据选项、框架编译链和现有签名；标准装饰器与 legacy decorators 的类型和运行时语义不同，不能机械迁移。
- Angular、NestJS、TypeORM 等项目如果依赖 legacy decorators，应沿用锁定版本与配置；迁移需要单独授权、兼容性评估和回归测试。
- `experimentalDecorators` 不应在通用规则中强制开启或关闭；以项目实际配置和框架要求为准。

### 1.5 函数反模式

```ts
// ❌ 默认导出整个对象
export default { getUser, createUser, deleteUser };

// ❌ 一个文件多个类
// user.ts 里塞：UserService + UserController + UserValidator

// ❌ 函数 > 50 行 / 参数 > 3 个不用 options 参数
function process(user, action, params, options, callback) { /* ... */ }

// ✅ 具名导出 + 拆函数 + options 参数
export function getUser() {}
export function createUser() {}

function process(options: { user: User; action: string }) { /* ... */ }
```

### 1.6 模块反模式

```ts
// ❌ barrel exports 滥用(自动补全变慢 / 循环依赖)
// index.ts
export * from './user';
export * from './order';
export * from './product';

// ❌ 循环依赖
// a.ts -> b.ts -> a.ts

// ❌ 全局副作用
window.myApp = { init() {} };

// ✅ 直接从文件导入 + 模块内单方向依赖
import { getUser } from './user/user.api';
```

### 1.7 类型反模式

```ts
// ❌ 占位 type
type T = any;                                       // 假装有类型

// ❌ 业务代码用条件类型 / 映射类型
type GetFieldType<T, K extends keyof T> = T[K] extends infer R ? R : never;

// ❌ type / interface 混用不知道选谁
type User = { id: number; name: string };            // 应该用 interface
interface Status = 'pending' | 'done';               // ❌ 语法错误(interface 不能 union)

// ✅ interface 给对象,type 给 union / 工具类型
interface User { id: number; name: string; }
type Status = 'pending' | 'done';
```

### 1.8 import 反模式

```ts
// ❌ 全部用 import(运行时仍加载类型 import)
import { User, getUser } from './user';

// ❌ import * 整个命名空间
import * as fs from 'fs';

// ❌ require 混入 ESM
const express = require('express');

// ✅ 类型 import 用 import type
import type { User } from './user';
import { getUser } from './user';
import fs from 'node:fs';
```

## 2. 🟡 团队约定补充

### 2.1 命名补充

```ts
// ✅ type / interface PascalCase
interface User { id: number }
type Status = 'pending' | 'done';

// ✅ 工具类型以 T 结尾(自定义工具时)
type PartialUser<T> = Partial<T>;

// ❌ 命名带 I 前缀(C# 风格)
interface IUser {}                                  // 不要
```

### 2.2 注释补充

- 🔴 新增或修改的说明性注释、JSDoc 正文必须使用中文；JSDoc 标签、代码标识符与稳定事件键保持规范原样。
- 🟢 可保留英文的情形仅限：工具可识别标记或指令（如 `TODO`、`FIXME`、`@ts-expect-error`、`eslint-disable`）、协议/标准/第三方专有名词、已明确对外发布的英文 API 契约，以及外部依赖或自动生成代码；除标记和专有名词外，仍应以中文说明含义或原因。
- ❌ 不得仅因类型名、函数名、变量名或 API 为英文，就把说明性注释整体改写为英文。
- 🔴 方法内部和局部逻辑说明使用 `//`；对外公开或由项目约定要求文档化的 API 使用紧挨声明的 `/** ... */` JSDoc。
- ❌ **禁止**把普通 `/* ... */` 用作业务说明、算法说明或临时禁用代码；连续说明使用贴近代码的多行 `//` 中文注释。
- 🟢 文件级工具指令、不可改动的第三方/生成代码或授权声明需要 `/* ... */` 时，可保留其原有形式。

```ts
/**
 * 计算折扣
 * @deprecated 用 getDiscountV2 替代
 * @see getDiscountV2
 */
function getDiscount(user: User) {
  // 示例省略。
}

/**
 * @throws {ValidationError} 当输入不合法
 * @example
 * const u = createUser({ name: 'alice' });
 */
export function createUser(input: UserInput): User {
  // 示例省略。
  throw new Error('示例未实现');
}
```

### 2.3 公共 API 模式

```ts
// ✅ 显式参数 + 返回类型 + JSDoc + named export
/**
 * 获取用户
 * @param id 用户 ID
 * @returns 用户对象(不存在返回 null)
 */
export function getUser(id: number): Promise<User | null> {
  return fetch(`/api/users/${id}`).then(r => r.json());
}
```

### 2.4 内部 / 外部 API 分层

```ts
// ❌ 所有东西都 export
export function internalHelper() {}                  // 应内部用

// ✅ 明确公开 / 内部
// src/api/user.ts - 外部 API(export)
// src/internal/user-helper.ts - 内部 helper(不 export)
```

## 3. 🟢 可选 · 自检工具

以下工具只用于说明能力类别。项目已经采用或用户明确授权时才可执行对应命令、更新 lockfile 或新增 CI 门禁；否则使用现有工具完成等价检查。

### 3.1 ts-unused-exports

检测未使用的 export——定期清理。

### 3.2 dependency-cruiser

依赖图 / 循环依赖检测。

```js
// .dependency-cruiser.cjs
module.exports = {
  forbidden: [
    {
      name: 'no-circular',
      severity: 'error',
      comment: '禁止循环依赖',
      from: {},
      to: { circular: true },
    },
  ],
};
```

```bash
npx depcruise src
```

### 3.3 type-coverage

类型覆盖率门槛必须沿用项目现有配置；不得从本节写入固定百分比。覆盖率只能帮助发现未标注区域，不能证明类型设计正确。

### 3.4 knip（未使用代码检测）

检测未使用的 export / 文件 / 依赖。
