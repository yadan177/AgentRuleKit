# 06 - JavaScript 项目配置规则

> - 🟢 本文件适用于 JavaScript/TypeScript 项目的包清单、工具链、构建、脚本、环境配置和交付配置。
> - 🔴 不适用：未经授权选择或迁移框架、包管理器、构建工具、lint/format 工具、测试体系或部署方式

---

## 1. 配置事实优先

### 1.1 开始前检查

修改配置前至少检查：

1. `package.json`、`packageManager`、`engines`、现有 scripts 和 workspace 声明。
2. 仓库中的 lockfile，以及 CI 实际使用的安装命令。
3. 构建、lint、format、测试、类型检查和部署配置。
4. Node.js/浏览器目标、模块系统、SSR/SSG、浏览器兼容和运行平台。
5. 同仓其他包、共享配置和项目 `AGENTS.md` 的约定。

- 🔴 已有项目必须沿用现有包管理器、锁文件、脚本和工具链；未经授权不得切换 npm、pnpm、yarn、bun、构建工具或配置体系。
- 🔴 新项目也不能仅因“新”就自动引入框架或工具；候选方案必须基于部署目标、团队经验、生态兼容、维护成本和验证能力。
- 🟡 本文件中的工具名和片段只用于解释决策，不构成安装、升级或迁移授权。

## 2. package.json 与依赖边界

### 2.1 字段按项目需要声明

| 字段 | 决策依据 |
|---|---|
| `name` / `version` / `private` | 发布方式、workspace 和仓库约定；私有应用不套用公开包发布要求 |
| `type` | 目标运行时、现有模块系统和构建链 |
| `scripts` | 团队需要稳定调用的开发、构建和验证入口 |
| `dependencies` / `devDependencies` | 包在目标运行时、构建产物或下游消费者中的真实用途 |
| `engines` / `packageManager` | 项目需要声明并由 CI/开发环境验证的版本边界 |
| `workspaces` | 仓库确实采用单仓多包时的包管理器约定 |

- 🔴 不得为补齐模板添加项目不需要的字段、脚本或依赖。
- 🔴 调整依赖分类前确认部署方式；SSR、CLI、插件和发布库对运行时依赖的边界可能不同。

### 2.2 版本范围

| 写法 | 典型语义 | 可能适用的场景 |
|---|---|---|
| `^1.2.3` | 接受同一 major 内兼容更新 | 项目接受该范围并由 lockfile/CI 验证 |
| `~1.2.3` | 接受同一 minor 内 patch 更新 | 希望缩小自动解析范围 |
| `1.2.3` | 精确版本 | 应用、构建工具、安全修复、可复现或供应链策略要求固定版本 |
| 比较器范围 | 自定义上下限 | 库兼容声明或已有发布策略 |

- 🔴 版本写法必须沿用仓库策略；不能把 `^` 或精确版本写成所有依赖的默认答案。
- 🔴 lockfile 锁定一次解析结果，`package.json` 表达允许范围，两者职责不同，不能据此禁止精确版本。
- 🔴 修改版本范围、override/resolution 或 lockfile 后，使用项目现有命令验证解析结果、构建、测试和目标运行时。
- 🟡 无用依赖检查优先使用项目已有脚本或工具；不得只为执行本规则安装 `depcheck` 或替代工具。

## 3. 包管理器与 lockfile

### 3.1 沿用仓库选择

- 🔴 通过 lockfile、`packageManager`、workspace 配置和 CI 命令识别实际包管理器；这些证据不一致时先确认原因。
- 🔴 不得同时生成多个竞争 lockfile，也不得未经授权删除或重新生成现有 lockfile。
- 🔴 应用和团队 workspace 通常提交项目采用的 lockfile；发布库或特殊仓库是否提交由仓库策略决定。
- 🟡 新项目没有约定时，可以比较 npm、pnpm、yarn、bun 等候选方案的运行时兼容、workspace、供应链、团队经验和 CI 支持，再由项目负责人确认。

### 3.2 配置与凭据

- 🔴 `.npmrc`、`.yarnrc*` 等配置是否提交取决于内容；registry、workspace 等非敏感团队配置可以入库，token 和认证信息不得提交。
- 🔴 安装命令必须与 lockfile 匹配，并优先使用项目已有的冻结/不可变安装模式。
- 🟡 workspace 结构和任务编排工具只在项目确有多包协作需求时采用，不默认引入 pnpm、Turbo、Nx 或其他工具。

## 4. Lint、格式化与类型工具

### 4.1 现有配置优先

- 🔴 先读取 ESLint/formatter/TypeScript 的版本、配置格式、共享配置和 scripts，再修改规则。
- 🔴 不得为了使用示例升级 ESLint、迁移 flat config、引入 Prettier、切换 formatter 或安装风格包。
- 🔴 同一职责只保留一个权威配置；避免 legacy/flat ESLint、多个 formatter 或重复规则相互覆盖。
- 🟡 项目已采用 ESLint 9+ 且计划迁移时，可依据官方迁移说明评估 flat config；这不是所有项目的默认要求。

### 4.2 候选配置的使用条件

- `eslint-config-prettier` 只在项目同时采用 ESLint 与 Prettier 且确有冲突规则时评估；若采用，顺序按对应版本官方说明和现有配置确定。
- Airbnb、Standard、框架共享配置或 `typescript-eslint` 只在项目已采用或用户授权选型时使用，并核对主版本和配置格式兼容性。
- `no-console`、`no-explicit-any`、覆盖率等规则强度由项目风险和现有门禁决定，不从示例复制统一级别。
- `.prettierignore`、ESLint ignores 和生成目录必须来自项目真实产物，不照抄固定目录列表。

## 5. 构建工具

### 5.1 选择条件

| 维度 | 需要确认的事实 |
|---|---|
| 应用形态 | SPA、SSR、SSG、发布库、CLI、浏览器扩展或 Node.js 服务 |
| 兼容目标 | 浏览器、Node.js、模块格式、旧环境和 polyfill 策略 |
| 生态约束 | 框架插件、loader、代码生成、测试和现有部署集成 |
| 运维要求 | source map、缓存、监控、产物审计和回滚方式 |
| 迁移成本 | 配置、插件、CI、部署、性能基线和团队维护能力 |

- 🔴 Vite、Webpack、Rollup、esbuild、Next.js、Nuxt 等都必须按项目实际能力和版本评估；不得用未经测量的速度倍数或仅按项目新旧直接排除工具。
- 🔴 React、Vue、SSR 或库打包示例只能用于对应项目，不能从通用配置规则推断框架。
- 🟡 修改分包、tree shaking、source map、target 或缓存策略前，应记录当前产物和性能基线并验证部署环境。

### 5.2 输出目录与产物

- 🔴 输出目录由构建配置、部署脚本和仓库约定共同决定；不得强制所有工具改成 `dist/`。
- 🔴 CI、容器和静态托管配置必须读取同一实际输出目录，并避免把可再生产物误提交。
- 🟡 是否提交构建产物取决于发布方式；库发布、生成客户端或离线交付可能有明确例外。

## 6. Scripts 与 CI

### 6.1 Scripts 设计

- 🟡 为团队需要稳定调用的开发、构建、lint、测试和类型检查保留清晰 scripts；名称优先沿用仓库现状。
- 🔴 不得为凑齐“标准 scripts 集合”引入 Vitest、Prettier、Husky、`npm-run-all`、`concurrently` 或其他依赖。
- 🟡 pre/post hooks、并发脚本和聚合验证入口只有在项目已有调用链或用户明确要求时使用，避免隐藏副作用。

### 6.2 跨平台环境变量

- 🔴 先确认 scripts 实际运行在 POSIX shell、Windows、Node.js 脚本、容器还是 CI，再选择传递环境变量的方式。
- 🟡 项目已依赖 `cross-env` 时可以沿用；项目没有该依赖时，只有在确有跨平台需求且获得授权后才可引入。
- 🟡 也可按现有工具链使用 Node.js 配置脚本、CI `env`、容器环境或平台专用入口，不将裸 shell 语法写成跨平台方案。

### 6.3 CI 安装与验证

- 🔴 CI 使用的包管理器、安装命令和缓存键必须与仓库 lockfile 一致，不能把 `npm ci` 写成 pnpm/yarn/bun 项目的答案。
- 🔴 CI 执行哪些 lint、测试、构建和安全检查由项目已有门禁与改动风险决定；新增门禁需要授权并评估耗时和环境依赖。
- 🔴 CI 成功不替代目标浏览器、Node.js 版本、SSR 环境或真实部署验证。

## 7. 环境与敏感配置

### 7.1 客户端与服务端边界

- 🔴 浏览器构建可读取的环境变量最终可能进入客户端产物，必须视为公开信息；API 密钥、服务凭据和私密 token 不得注入客户端构建或通过所谓“secrets API”下发。
- 🔴 服务端敏感值应通过项目已有的部署 Secret、环境注入或密钥服务提供，不写入仓库中的 `.env*`。
- 🔴 `.env.example` 或可提交配置只能包含字段名和非敏感示例；真实 `.env*` 是否忽略按仓库策略和内容判断。

### 7.2 加载与校验

- 🔴 配置必须在明确的启动或构建边界完成与风险相称的校验；TypeScript 类型和构建工具声明不能验证外部输入。
- 🟡 复用项目已有校验函数或库；只有项目已经采用 zod、valibot 等方案时才使用对应 schema，不为示例新增依赖。
- 🔴 区分 build-time 和 runtime 配置，并记录修改后需要重新构建、重启还是动态刷新。

## 8. 容器与部署

- 🔴 仅在项目使用容器交付时修改 Dockerfile，并先确认静态站点、SSR、Node.js 服务或其他运行形态。
- 🟡 多阶段构建可用于隔离构建依赖与运行产物，但阶段数量、运行镜像和 Web 服务器由项目供应链及运行需求决定。
- ❌ 不得把 nginx、Alpine、固定 Node.js 镜像、固定端口或两阶段结构写成所有前端项目的强制答案。
- 🔴 最终镜像只包含运行所需内容，并按项目要求验证非 root 权限、证书/时区、健康检查、source map、依赖漏洞和目标平台行为。
- 🔴 镜像 tag/digest、包管理器安装方式和输出目录必须替换为项目已验证配置，不能直接执行占位模板。

## 9. 交付检查

- 包管理器、lockfile、Node.js 版本和安装命令是否一致。
- 是否未经授权新增、升级或切换依赖与工具。
- lint、format、类型、测试、构建和部署配置是否沿用项目事实。
- 浏览器/Node.js/SSR/容器等目标环境是否完成与改动相称的验证。
- 客户端公开配置和服务端 Secret 是否保持边界。
- 配置、脚本、部署方式或验证结论变化是否同步技术文档。
