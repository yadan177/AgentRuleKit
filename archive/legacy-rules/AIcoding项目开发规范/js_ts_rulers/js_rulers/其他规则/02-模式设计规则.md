# 02 - JavaScript 模式设计规则

> - 🟢 本文件适用于 JavaScript 项目的模块职责、异步协作、状态边界和通用设计模式。
> - 🔴 不适用：替代 React、Vue、Node.js 框架或目标项目已经采用的架构约定

---

## 1. 项目事实与职责边界

### 1.1 修改前检查

- 🔴 先确认代码运行在浏览器、Node.js、Worker、SSR 或其他环境，并读取 `package.json`、锁文件、入口、构建配置和同模块实现。
- 🔴 先确认项目是否采用 React、Vue 或其他框架；通用规则不得用某个框架的 Hook、Store、缓存库或目录结构覆盖项目事实。
- 🔴 只使用项目已经声明且版本兼容的依赖。需要新库时，必须先说明标准 API 或现有实现为何不足并获得授权。

### 1.2 模块组织

- 🟡 模块应围绕一个可描述的职责保持高内聚；不要按固定文件行数或“一文件一函数”机械拆分。
- 🟡 公共导出应收敛到真实调用方需要的接口；是否使用 barrel export 由项目的循环依赖、打包和 API 组织方式决定。
- 🔴 模块加载时的注册、网络请求、全局对象修改等顶层副作用必须符合项目启动契约，并明确执行时机、幂等性和清理方式。
- 🟡 业务、数据访问、状态和视图职责是否分层以及如何命名，优先沿用目标项目已有边界。

### 1.3 错误传播

- 🔴 沿用项目对异常、结果对象、缺失值和 HTTP/RPC 错误的现有契约，不把 `throw`、`null` 或 `{ ok, error }` 写成所有场景的唯一答案。
- 🔴 不得吞掉拒绝或把失败转换成看似成功的值；转换错误时保留原因、上下文和可恢复性。
- 🟡 全局错误监听只用于最后观测或隔离，不能替代调用边界的处理；是否阻止默认行为取决于运行环境和现有监控策略。

## 2. 异步与并发协作

### 2.1 Promise 组合

| 目标 | 可评估的标准 API | 关键边界 |
|---|---|---|
| 全部成功后继续 | `Promise.all` | 任一拒绝会使聚合 Promise 拒绝；底层任务不会自动取消 |
| 收集全部结果 | `Promise.allSettled` | 调用方必须显式处理 rejected 项 |
| 使用最先 settle 的结果 | `Promise.race` | 其余任务仍需取消或释放 |
| 使用最先 fulfill 的结果 | `Promise.any` | 需确认目标运行时支持，并处理全部拒绝 |
| 顺序执行 | `for...of` + `await` | 适用于存在顺序依赖或限流要求的任务 |

- 🔴 `await`、Promise 链或组合 API 的选择以可读性和现有风格为准；不得用“全部改成 await”等规则机械重写。
- 🔴 请求、订阅和后台任务必须定义超时、取消、竞态和调用方退出后的处理方式。
- 🟡 并发限制优先复用项目已有队列、调度器或数据访问层；没有现成能力时再评估小型自实现或经授权的依赖。

### 2.2 副作用所有权

- 🔴 创建事件监听、定时器、订阅、对象 URL、网络请求或缓存写入的职责，必须同时定义清理、取消和失败语义。
- 🟡 将副作用放在可识别的生命周期或服务边界，不要求所有副作用集中到某个框架 Store。
- 🔴 认证、隐私、重试、幂等和跨端契约等非直观边界变化时，同步更新原因和所有权注释。

## 3. 状态职责

### 3.1 按所有权分类

| 状态类别 | 所有权与生命周期 | 决策要求 |
|---|---|---|
| 组件或局部临时状态 | 单个视图或短生命周期交互 | 使用项目框架已有的局部状态能力，不自动提升为全局状态 |
| 跨组件客户端状态 | 多个调用方共享、由客户端拥有 | 先复用现有 Store、事件或依赖注入边界 |
| 服务端状态 | 来自 API，涉及缓存、失效、重试和并发 | 复用项目数据访问层或既有服务端状态方案 |
| URL、持久化或跨页面状态 | 需要刷新、导航或会话后保留 | 明确序列化、安全、兼容和恢复策略 |

- 🔴 React 的状态更新规则只在 [13 - React 组件规则](./13-React组件规则.md) 中应用。
- 🔴 Vue 的 `ref`、`reactive`、`computed` 和 `watch` 边界只在 [16 - Vue 3 组件规则](./16-Vue组件规则.md) 中应用。
- ❌ 不得把 Context、Redux、Zustand、Pinia、React Query、SWR 或其他库写成通用 JavaScript 状态层的默认答案。

### 3.2 更新语义

- 🔴 普通 JavaScript 对象属性可以直接修改；是否触发视图或订阅更新取决于框架和对象来源，不能笼统声称“React/Vue 都检测不到”。
- 🔴 React 状态通常通过 setter/reducer 和项目约定更新；Vue 3 `reactive` 对象的受代理属性写入会被追踪。具体限制以对应框架版本和专题规则为准。
- 🔴 Props、缓存结果、外部 Store 快照或只读对象不得因“语法允许”就原地修改；先确认所有权和更新契约。
- 🟡 不可变更新适合需要快照、时间旅行、浅比较或明确变更边界的场景，但不是所有 JavaScript 对象的强制规则。

## 4. 模式选择

### 4.1 工厂函数与类

- 🟡 简单对象构造、闭包封装或组合逻辑可使用工厂函数。
- 🟡 框架、领域模型、继承、私有字段或项目既有约定需要实例语义时可以使用类。
- ❌ 不得仅因个人偏好在同一模块中引入第二套对象模型。

### 4.2 模块实例与单例

- 🟡 ES Module 在同一模块图中通常只求值一次，可用于模块级共享实例。
- 🔴 不得假设它在多个 Realm、Worker、进程、重复打包副本或服务实例之间是全局唯一；需要跨边界唯一性时必须使用对应平台机制。
- 🔴 共享实例必须明确初始化、测试隔离、并发访问和释放方式。

### 4.3 观察者与发布订阅

| 模式 | 适用边界 |
|---|---|
| 观察者 | 被观察对象直接维护订阅者，适合边界清晰的单模块关系 |
| 发布订阅 | 通过事件通道解耦生产者和消费者，适合确有跨模块广播需求的场景 |

- 🔴 订阅必须可取消，并避免匿名回调导致无法解除。
- 🟡 直接函数调用或显式依赖已经足够时，不增加全局事件总线。

### 4.4 依赖注入

- 🟡 优先通过函数参数、构造参数或模块边界传入外部能力，便于替换和测试。
- 🟡 只有项目已经采用容器或框架注入时才使用对应容器，不为形式统一引入 DI 库。

### 4.5 状态机

- 🟡 当流程存在多个互斥状态、受控转换、重试或恢复路径时，可评估显式状态机。
- 🔴 状态、事件、非法转换和副作用所有权必须可验证；简单布尔状态不需要为套用模式升级为状态机库。

## 5. 框架路由与交付检查

- React 组件、Hooks 或 React 状态任务读取 13，不读取 Vue 专题作为实现依据。
- Vue 3、Composition API、Vue Router 或 Pinia 任务读取 16，不读取 React 专题作为实现依据。
- Node.js、无框架浏览器代码或其他框架只读取与运行时和任务直接相关的通用规则，不套用 React/Vue 示例。
- 交付前检查模块职责、状态所有权、副作用清理、错误传播、取消/竞态、依赖授权和相关技术文档是否同步。
