# 03 - JavaScript 性能优化规则

> - 🟢 本文件适用于浏览器、Node.js 和 Worker 中可测量的 JavaScript 性能问题。
> - 🔴 不适用：没有基线的猜测性优化，或用 React/Vue/构建工具示例覆盖项目现状

---

## 1. 测量与目标环境

- 🔴 优化前先确认目标浏览器、设备、Node.js 版本、数据规模、网络和构建模式，并记录可复现基线。
- 🔴 使用项目已有 profiler、性能测试和监控；没有证据时先增加最小观测，不凭代码外观断言瓶颈。
- 🔴 优化后用相同场景对比耗时、内存、网络、帧率或产物指标，并检查行为和可维护性回归。
- 🟡 性能预算和阈值由项目的用户体验、SLO、设备能力和历史数据决定，不使用通用固定数字。

## 2. CPU 与主线程

### 2.1 热路径

- 🔴 先通过采样或时间线确认热路径，再减少其中的重复计算、序列化、布局读取或不必要分配。
- 🟡 函数和小对象分配是否值得优化取决于调用频率和引擎结果；不得机械把所有回调移到循环外。
- 🔴 大量 CPU 工作不得长期阻塞浏览器主线程或 Node.js 事件循环；根据项目环境评估分片、Worker、队列或异步服务边界。
- 🟡 对象 shape、类型稳定性等引擎优化只在目标引擎的 profile 证明确有影响时处理，不牺牲正确性换取推测收益。

### 2.2 DOM 与渲染

- 🟡 批量组织 DOM 修改、分离布局读取与写入，可以减少强制同步布局；实际效果必须用目标浏览器验证。
- 🟡 动画更新可使用 `requestAnimationFrame`；滚动、输入等高频事件还需根据行为选择节流、合并或被动监听。
- 🟡 长列表在真实数据量和设备上出现布局、内存或交互问题时，再沿用项目已有分页、增量渲染或虚拟列表方案。
- 🔴 React/Vue 的渲染优化和生命周期清理分别读取 13/16，不在本文件默认具体 Hook、组件或虚拟列表库。

## 3. 内存与资源所有权

- 🔴 事件监听、订阅、定时器、Observer、对象 URL、网络请求和 Worker 必须有与生命周期对应的释放或取消路径。
- 🔴 匿名回调导致无法解除、闭包长期持有大对象、无界缓存和脱离文档的 DOM 引用都需要重点检查。
- 🟡 `WeakMap`/`WeakSet` 适合键对象不应被缓存阻止回收的场景，但不能替代容量、过期和命中率策略。
- 🔴 内存问题必须通过 heap snapshot、allocation profile 或运行监控验证；单次 GC 后下降不等于泄漏已修复。

## 4. 网络、缓存与竞态

- 🔴 请求取消、超时、重试、去重、缓存和失效必须沿用项目数据访问层，并明确旧响应是否可以覆盖新状态。
- 🟡 优先使用 HTTP 的 `Cache-Control`、`ETag` 等协议能力；客户端缓存或 Service Worker 只在项目已采用且离线/性能目标需要时使用。
- 🟡 `preconnect`、preload、prefetch 等提示会占用带宽和连接，只对关键资源使用并验证命中与副作用。
- 🔴 不得从本节自动引入 React Query、SWR、Service Worker 框架或请求库。

```js
let activeController;

async function search(keyword) {
  activeController?.abort();
  activeController = new AbortController();
  const response = await fetch(`/api/search?q=${encodeURIComponent(keyword)}`, {
    signal: activeController.signal,
  });
  return response.json();
}
```

> 上例只说明“新请求取消旧请求”的所有权模式；错误转换、超时和返回校验必须沿用项目封装。

## 5. 构建产物

- 🔴 读取项目真实构建工具、target、模块格式、source map、分包和部署缓存配置后再优化。
- 🟡 通过 bundle analyzer、构建统计或产物清单识别重复依赖和大模块；不得仅凭包名要求替换依赖。
- 🟡 动态 import、路由分包、tree shaking 和资源压缩必须验证加载瀑布、缓存命中、错误恢复和旧环境兼容。
- 🔴 不得把 Vite、Webpack、Rollup、固定 vendor chunk、WebP、gzip/Brotli 或 CDN 配置写成所有项目的统一模板。

## 6. Node.js 与服务端运行时

- 🔴 区分 CPU、事件循环、内存、文件/网络 I/O、数据库和下游服务瓶颈，并使用目标 Node.js 版本验证。
- 🟡 大文件或流式协议可评估 Stream，但必须处理背压、部分失败、取消和资源关闭；小文件不为形式统一改成流。
- 🟡 Worker Threads、子进程、集群或外部任务系统按 CPU 特征、部署拓扑和项目现有架构选择。
- 🔴 `setImmediate`、`process.nextTick` 等调度 API 不会消除 CPU 工作；不得把“让步”描述为并行优化。
- 🔴 数据库连接池、缓存和队列配置由对应客户端、服务端容量和已有运维约定决定。

## 7. 交付检查

- 记录复现场景、优化前后指标和测量工具。
- 说明目标环境、数据规模、构建模式和未验证范围。
- 检查取消、清理、错误、兼容和降级路径是否仍正确。
- 检查是否新增依赖、改变产物或部署配置，以及是否已获授权并同步文档。
