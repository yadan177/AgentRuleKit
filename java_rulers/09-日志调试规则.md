# 09 - Java 日志调试规则

> 🟢 本文件适用于 Java 项目日志与调试（SLF4J/Logback/MDC/异常脱敏）。

> 🔴 不适用：metrics 指标采集、tracing 链路追踪、APM 工具

---

## 1. SLF4J 门面（P3C 强制）

### 1.1 为什么用 SLF4J 门面

🟡 **推荐**（P3C 第 1 条）：

- **应用中不可直接使用日志系统（Log4j、Logback）中的 API**
- **应依赖使用日志框架 SLF4J 中的 API**
- **使用门面模式的日志框架**，有利于维护和各个类的日志处理方式统一

🟡 **推荐**：

| 角色 | 库 |
|---|---|
| **门面（API）** | SLF4J |
| **实现** | Logback（默认）/ Log4j2 |

✅ **正例**：
```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class OrderService {
    private static final Logger log = LoggerFactory.getLogger(OrderService.class);
}
```

❌ **反例**：
```java
// ❌ 直接用 log4j API（绑死实现）
import org.apache.log4j.Logger;
private static final Logger log = Logger.getLogger(OrderService.class);

// ❌ 直接用 logback API
import ch.qos.logback.classic.Logger;
private static final Logger log = (Logger) LoggerFactory.getLogger(...);
```

🟡 **推荐**：

- **切换日志实现不动业务代码**：日志门面 + 实现分离，换 Logback ↔ Log4j2 不改任何一行调用代码
- **Spring Boot 默认集成 spring-boot-starter-logging（logback）**，无需额外配置

### 1.2 依赖配置

🟡 **推荐**：Spring Boot 项目：

```xml
<!-- spring-boot-starter-web 已经传递依赖 slf4j-api + logback-classic -->
<!-- Maven：直接依赖 starter，logback 自动生效 -->

<!-- 如需 Log4j2 实现，排除 Logback 并引入 Log4j2 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-logging</artifactId>
    <exclusions>
        <exclusion>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-logging</artifactId>
            <artifactId>spring-boot</artifactId>
        </exclusion>
        <exclusion>
            <groupId>ch.qos.logback</groupId>
        </exclusion>
    </exclusions>
</dependency>
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-log4j2</artifactId>
</dependency>
```

## 2. 5 级日志体系（AI 视角扩展）

借鉴 Unity 07 的 5 级 Log 类。SLF4J 默认 5 级：`ERROR / WARN / INFO / DEBUG / TRACE`（比 Unity 多 `TRACE`）。

### 2.1 5 级用途对照

🟡 **推荐**：AI 写日志调用时立即判断选哪个级别：

| 级别 | 用途 | 典型场景 | 生产是否输出 |
|---|---|---|---|
| **ERROR** | 系统错误 / 异常 / 必须修的 bug | 业务异常抛了 / NPE / 数据库连不上 | ✅ **是**（且应触发告警）|
| **WARN** | 潜在问题 / 不规范输入 / 资源即将耗尽 | 参数值用默认值 / 重试一次成功 | ✅ 是 |
| **INFO** | 业务关键节点（用户登录 / 订单创建）| 用户登录成功 / 支付完成 | ✅ 是（按需）|
| **DEBUG** | 开发期调试（变量值、状态变化）| 进入函数 / 中间变量 | ❌ 生产 **关** |
| **TRACE** | 最细粒度（每步细节）| 进入某个循环迭代 / 字段值 | ❌ 生产 **必须剔除** |

### 2.2 何时用哪个级别（决策表）

🟡 **推荐**：

| 场景 | 级别 | 原因 |
|---|---|---|
| **业务异常被捕获** | ERROR | 必须告警 / 必须人工处理 |
| **外部接口失败 / 重试 | ERROR**（重试中）/ WARN（终失败）| 业务风险 |
| **参数校验失败** | WARN | 用户错误，不需要告警 |
| **用户登录成功** | INFO | 审计需要 |
| **订单创建成功** | INFO | 业务流程关键节点 |
| **进入函数** | DEBUG | 开发期信息 |
| **变量值观察** | DEBUG / TRACE | TRACE 比 DEBUG 更细 |
| **性能监控** | INFO | 周期性 QPS |

🟡 **推荐**（P3C 第 7 条）：

- **生产环境禁止输出 DEBUG 日志**
- **有选择地输出 INFO 日志**
- **生产 WARN 切忌爆量**（可能撑爆磁盘）
- 思考：**"这些日志真的有人看吗？看到这条日志你能做什么？能不能给问题排查带来好处？"**

### 2.3 TRACE 与 DEBUG 的取舍

🟢 **可选**：

- **TRACE** 通常不在生产启（性能 + 噪声），但要保留代码（调试时开启）
- **DEBUG** 作为开发期常态
- 09 § 10 Logback 配置中，prod 环境 `root level="INFO"`，dev 环境 `root level="DEBUG"`

## 3. Logger 声明与命名

### 3.1 Logger 声明规范

🟡 **推荐**：

- 每个类声明**独立的** `Logger`
- Logger 名 = **类全限定名**（用 `getLogger(Class)` 或 `getLogger("xxx")`）

✅ **正例**：

```java
public class OrderService {
    private static final Logger log = LoggerFactory.getLogger(OrderService.class);
}

public class OrderController {
    private static final Logger log = LoggerFactory.getLogger(OrderController.class);
}

public class SomeUtil {
    private static final Logger log = LoggerFactory.getLogger(SomeUtil.class);
}
```

🟡 **推荐**：

- Logger **必须 `private static final`**（每个类一个，类加载时初始化）

❌ **反例**：
```java
// ❌ 每个方法 new 一个（浪费性能）
public void process() {
    Logger log = LoggerFactory.getLogger(OrderService.class);  // 每次调用都查询
}

// ❌ 共享一个 logger（不能分类别级别）
private final Logger log = LoggerFactory.getLogger(getClass().getName() + ".something");
```

### 3.2 Logger 命名约定

🟢 **可选**：

| 项目组织 | Logger 名 |
|---|---|
| **默认**（自动）| `com.example.order.OrderService` |
| **按模块分类** | `com.example.order.dao` / `com.example.order.service` |

🟡 **推荐**：在 `logback.xml` 中按 logger 名分别配置级别：

```xml
<!-- DAO 层输出更多 debug 日志看 SQL -->
<logger name="com.example.order.dao" level="DEBUG"/>

<!-- 框架层只关心 WARN 以上 -->
<logger name="org.springframework" level="WARN"/>
<logger name="org.hibernate" level="WARN"/>
```

### 3.3 占位符 vs 字符串拼接

🟡 **推荐**（P3C 第 4 条）：

- **`trace / debug / info` 级别的日志输出必须使用条件输出形式或者使用占位符的方式**
- **不要用字符串拼接**：日志级别是 WARN 时不打印，但**字符串拼接仍执行**，浪费系统资源

**反例**：
```java
// ❌ 即使日志不打印，字符串拼接 + toString() 也执行了
log.debug("Processing trade with id: " + id + " and symbol: " + symbol);
```

**正例**（占位符方式 — **推荐**）：
```java
// ✅ SLF4J 懒求值，参数只在要打印时序列化
log.debug("Processing trade with id: {} and symbol: {}", id, symbol);
```

**正例**（条件方式）：
```java
// ✅ 显式判断，性能最优（但代码冗长）
if (log.isDebugEnabled()) {
    log.debug("Processing trade with id: {} and symbol: {}", id, symbol);
}
```

🟡 **推荐**：

- **生产 99% 场景用占位符方式**（简洁 + 懒求值）
- **循环内/超长链路拼接**才用 `if (isDebugEnabled())` 包裹

## 4. Category 关键词筛选（借鉴 Unity 07，AI 视角扩展）

借鉴 Unity 07 的 Category 关键词设计 —— 业务方按业务关键词过滤日志，方便聚焦单条逻辑线路。

### 4.1 Category 设计

🟡 **推荐**：每个日志调用带 **Category 字符串**（业务关键词，如"订单创建"、"支付"、"库存"）：

```java
private static final String CAT = "Order.Create";

log.info(CAT, "用户 {} 下单，订单号 {}", userId, orderNo);
```

### 4.2 Category 命名规范

🟡 **推荐**：

| 场景 | Category 格式 | 示例 |
|---|---|---|
| **业务模块 + 子域** | `<模块>.<子域>` | `Order.Create` |
| **层次 + 模块** | `<层>.<模块>` | `DAO.User`、`Service.Payment` |
| **业务流程** | `<流程>` | `OrderFlow.Lifecycle` |

🟡 **推荐**：

- **Category 在类顶部用常量声明**（避免拼写错误）
- 命名统一**小驼峰**或**全大写**（团队约定）

### 4.3 类别继承 / 多关键词

🟡 **推荐**：

- 想看 `Order.Create` 和 `Order.Payment` **两条线路**：用多关键词
- 子类别自动继承（类似 Maven 模块树）：`Order.Create` 匹配 `Order`（具体实现见 § 5）

### 4.4 日志输出格式

🟢 **可选**：可读性高的统一前缀格式：

```
[timestamp][level][category][traceId] message
2024-06-30 22:30:15.123 [INFO ] [Order.Create] [a1b2c3d4] 用户 100 下单，订单号 ORDER-001
```

## 5. 自定义 Log 门面类（借鉴 Unity 07）

P3C 没要求做自定义门面类，但**借鉴 Unity 07 的设计 + SLF4J** 实现，能给 AI 写日志调用时**统一风格 + 拦截增强**。

### 5.1 为什么自定义 Log 门面

🟡 **推荐**：

- **统一调用风格**：`Log.info(CAT, "msg {}", arg)` 而非 `log.info("msg {}", arg)`
- **统一注入增强点**：MDC traceId 自动注入 / 敏感字段自动脱敏
- **易于重构**：换日志实现不影响业务代码
- **Category 强制必填**：AI 写日志不能跳过 Category

### 5.2 Log 门面类完整实现

🟡 **推荐**：参考 Unity 07 实现 Java 版：

```java
package com.example.common.log;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;

/**
 * 5 级日志 + Category 关键词 + MDC 自动注入。
 * AI 写代码时使用 Log 门面，不用直接调 SLF4J。
 */
public final class Log {

    private Log() {}

    // === 5 级输出方法 ===
    public static void trace(String category, String msg, Object... args) {
        log(LogLevel.TRACE, category, msg, args, null);
    }
    public static void debug(String category, String msg, Object... args) {
        log(LogLevel.DEBUG, category, msg, args, null);
    }
    public static void info(String category, String msg, Object... args) {
        log(LogLevel.INFO, category, msg, args, null);
    }
    public static void warn(String category, String msg, Object... args) {
        log(LogLevel.WARN, category, msg, args, null);
    }
    public static void error(String category, String msg, Object... args) {
        log(LogLevel.ERROR, category, msg, args, null);
    }

    /** 异常专用：自动加 cause */
    public static void exception(String category, Throwable ex) {
        log(LogLevel.ERROR, category, ex.getMessage(), null, ex);
    }
    public static void exception(String category, String msg, Throwable ex) {
        log(LogLevel.ERROR, category, msg, null, ex);
    }

    private static void log(LogLevel level, String category, String msg,
                            Object[] args, Throwable ex) {
        try {
            // 1. 获取调用方 Logger（栈反射，可选；这里用简单方法：要求调用方传 class）
            Logger slf4jLog = LoggerFactory.getLogger(category);
            // 注：实际上推荐 caller-aware，但为了简化这里传入 category 作为 logger 名

            // 2. 格式化（自动脱敏 —— 见 § 8）
            String safeMsg = SensitiveMask.mask(msg);

            // 3. 调用 SLF4J
            switch (level) {
                case TRACE: slf4jLog.trace(safeMsg, args); break;
                case DEBUG: slf4jLog.debug(safeMsg, args); break;
                case INFO:  slf4jLog.info(safeMsg, args);  break;
                case WARN:  slf4jLog.warn(safeMsg, args);  break;
                case ERROR:
                    if (ex != null) slf4jLog.error(safeMsg, ex);
                    else slf4jLog.error(safeMsg, args);
                    break;
            }
        } catch (Throwable t) {
            // 日志框架本身不能抛异常影响业务
        }
    }

    enum LogLevel { TRACE, DEBUG, INFO, WARN, ERROR }
}
```

### 5.3 使用示例

```java
public class OrderService {
    // 类别常量在类顶部声明
    private static final String CAT = "Order.Create";
    private static final org.slf4j.Logger log = LoggerFactory.getLogger(OrderService.class);

    public OrderDTO create(CreateOrderRequest req) {
        Log.info(CAT, "用户 {} 下单, items={}", req.getUserId(), req.getItems().size());
        try {
            // ... 业务逻辑
            Log.debug(CAT, "订单已持久化, orderId={}", order.getId());
            return OrderMapper.toDTO(order);
        } catch (Exception e) {
            Log.exception(CAT, "创建订单失败, userId=" + req.getUserId(), e);
            throw e;
        }
    }
}
```

### 5.4 ⚠️ 注意 Trade-off

🟡 **推荐**：

- **不要让 Log 门面吃掉异常** —— 必须把 cause 传到 SLF4J（栈是关键证据）
- **Log 门面本身不能抛异常影响业务** （封装在 try / catch `Throwable` 里）
- **StackTrace 一定要传**：`SLF4J log.error(msg, throwable)`，不要只 log `e.getMessage()`

## 6. 日志格式（Logback pattern）

### 6.1 标准 pattern 模板

🟡 **推荐**：`logback.xml` 中：

```xml
<configuration>
    <property name="LOG_PATTERN_CONSOLE" value="
        %d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level [%-20.20X{traceId}] %logger{36} [%X{category}] - %msg%n
    "/>

    <!-- 文件 pattern 多加主机/线程信息 -->
    <property name="LOG_PATTERN_FILE" value="
        %d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level [%-20.20X{traceId}] %logger{36} [%X{category}] - %msg%n%wex
    "/>

    <!-- 控制台输出（带颜色） -->
    <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>${LOG_PATTERN_CONSOLE}</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>
</configuration>
```

### 6.2 常见 Pattern 占位符

🟡 **推荐**：

| 占位符 | 含义 |
|---|---|
| `%d{...}` | 时间戳（默认 ISO 8601，可格式化）|
| `%thread` / `%t` | 线程名 |
| `%-5level` | 日志级别（左对齐 5 字符宽度）|
| `%logger{36}` | Logger 名（最长 36 段缩写）|
| `%X{key}` | MDC 字段（traceId / category / userId）|
| `%msg` / `%m` | 日志消息 |
| `%n` | 换行 |
| `%wex` | 异常带 cause（`%ex` 不带，但 Logback 默认 %ex 等同 %wex）|

### 6.3 时间戳格式

🟡 **推荐**：

- 用 `yyyy-MM-dd HH:mm:ss.SSS`（毫秒精度，UTC+8 友好）
- **生产时间戳格式必须明确**（不同格式难聚合）

### 6.4 文件输出加 `%X{traceId}`

🟡 **推荐**：

- **文件输出必须加 `%X{traceId}`**（链路追踪关键）
- 否则日志无法按 traceId 聚合

## 7. MDC 链路追踪（Java 后端特色）

MDC（Mapped Diagnostic Context）是 SLF4J / Logback 的**线程本地**存储，用于在**同一线程的整个调用链**传 traceId 等上下文。

### 7.1 为什么要用 MDC

🟡 **推荐**：

- **生产日志必须能按 traceId 聚合**（排查一次请求的完整调用链）
- HTTP 请求进来时生成 traceId 放进 MDC，跨服务调用时透传
- 每个日志自动带 traceId，无需手动传参

### 7.2 MDC 基本用法

🟡 **推荐**：

```java
import org.slf4j.MDC;

public class OrderController {
    public void createOrder(HttpServletRequest req) {
        String traceId = UUID.randomUUID().toString().replace("-", "");
        MDC.put("traceId", traceId);  // 放进去
        try {
            // 业务代码，整个调用栈都能看到 traceId
            orderService.createOrder(req);
        } finally {
            MDC.remove("traceId");  // 必须清理（线程池场景必清！）
        }
    }
}
```

**自动注入到日志**：
```
2024-06-30 22:30:15.123 [http-nio-8080-exec-1] INFO  [a1b2c3d4] OrderService - 创建订单
```

### 7.3 MDC + Spring Interceptor / Filter

🟡 **推荐**：用拦截器 / 过滤器自动注入：

```java
public class TraceIdFilter extends OncePerRequestFilter {
    private static final String TRACE_ID_HEADER = "X-Trace-Id";

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse resp, FilterChain chain) {
        // 1. 优先从上游 HTTP header 取（链路追踪）
        String traceId = req.getHeader(TRACE_ID_HEADER);
        if (traceId == null || traceId.isEmpty()) {
            traceId = UUID.randomUUID().toString().replace("-", "");
        }
        MDC.put("traceId", traceId);
        resp.setHeader(TRACE_ID_HEADER, traceId);  // 回传给前端（便于排查）
        try {
            chain.doFilter(req, resp);
        } finally {
            MDC.clear();  // 用 clear() 比 remove() 更彻底（清所有 key）
        }
    }
}
```

```java
@Configuration
public class FilterConfig {
    @Bean
    public FilterRegistrationBean<TraceIdFilter> traceIdFilter(TraceIdFilter filter) {
        FilterRegistrationBean<TraceIdFilter> reg = new FilterRegistrationBean<>(filter);
        reg.setOrder(Ordered.HIGHEST_PRECEDENCE);  // 最先执行
        reg.addUrlPatterns("/*");
        return reg;
    }
}
```

### 7.4 MDC 线程池传递

🟡 **推荐**：

- **线程池场景 MDC 必须显式传递**（线程复用，MDC 不会自动跨线程）
- 用 `MDC.getCopyOfContextMap()` + `MDC.setContextMap()` 配合 `ExecutorService`：

```java
// ❌ 异步任务中 traceId 丢失
executor.submit(() -> {
    log.info("异步任务");  // MDC 中没有 traceId！
});

// ✅ 用 TransmittableThreadLocal 或 MDC 的 Context 包装
Map<String, String> contextMap = MDC.getCopyOfContextMap();
executor.submit(() -> {
    try {
        MDC.setContextMap(contextMap);
        log.info("异步任务");  // MDC 中有 traceId
    } finally {
        MDC.clear();
    }
});
```

🟡 **推荐**：更优解 —— **Alibaba TransmittableThreadLocal（TTL）** + 线程池装饰器：

```xml
<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>transmittable-thread-local</artifactId>
    <version>2.14.5</version>
</dependency>
```

```java
// 用 TTL 装饰线程池，自动跨线程传递
ExecutorService executor = TtlExecutors.getTtlExecutorService(
    Executors.newFixedThreadPool(10, namedFactory)
);
```

### 7.5 traceId 全链路透传

🟡 **推荐**：

- **HTTP 透传**：`X-Trace-Id` header
- **RPC 透传**：Dubbo / Spring Cloud OpenFeign 的 `Interceptor` / `RequestInterceptor`

**OpenFeign 透传示例**：
```java
@Component
public class TraceIdFeignInterceptor implements RequestInterceptor {
    @Override
    public void apply(RequestTemplate template) {
        String traceId = MDC.get("traceId");
        if (traceId != null) {
            template.header("X-Trace-Id", traceId);
        }
    }
}
```

🟡 **推荐**：

- **跨服务调用必须透传 traceId / spanId**
- 否则跨服务聚合日志不可能

## 8. 敏感信息脱敏

### 8.1 必须脱敏的字段

🟡 **推荐**（P3C 隐含在"参数错误"日志中）：

- **敏感数据禁止直接展示 / 记录**
- **必须**对日志中的敏感字段脱敏

| 字段 | 脱敏示例 |
|---|---|
| **手机号** | `138****1234` |
| **身份证** | `110101****1234` |
| **银行卡** | `6225 **** **** 1234` |
| **邮箱** | `z****@example.com` |
| **密码 / 密钥** | 完全不记日志 |
| **姓名** | `张*` |

### 8.2 脱敏实现

🟡 **推荐**：

```java
public class SensitiveMask {

    public static String mask(String input) {
        if (input == null) return null;
        if (input.contains("手机号") || input.contains("phone")) {
            return maskPhone(input);
        }
        // ... 其它类型
        return input;
    }

    private static final Pattern PHONE = Pattern.compile("(?<!\d)1[3-9]\d{9}(?!\d)");

    public static String maskPhone(String msg) {
        return PHONE.matcher(msg).replaceAll(match -> {
            String phone = match.group();
            return phone.substring(0, 3) + "****" + phone.substring(7);
        });
    }
}
```

### 8.3 最佳实践

🟡 **推荐**：

- **不记密码 / 密钥 / 完整身份证**到日志（**完全不带**而不是脱敏）
- **手机 / 邮箱**等用 `maskPhone` / `maskEmail`
- 数据库查出的敏感字段**先脱敏**再日志
- 异常堆栈也走脱敏（**敏感信息不应当泄露给客户端日志**）

## 9. 异常日志（P3C 强制）

### 9.1 异常信息必须包含两类

🟡 **推荐**（P3C 第 6 条）：

- 异常信息应该包括两类信息：**案发现场信息 + 异常堆栈信息**
- 如果不处理，那么通过关键字 `throws` 往上抛出

✅ **正例**：
```java
log.error("订单创建失败, userId=" + req.getUserId() + ", items=" + items.size() + ", errorCode=901", e);
// 输出：
// ERROR - 订单创建失败, userId=100, items=3, errorCode=901
//   at OrderService.create(OrderService.java:42) ...
//   at ...
```

🟡 **推荐**：

- **`logger.error(message, throwable)` 必须传 `Throwable`**（栈是关键证据）
- **不要只 log `e.getMessage()`**（丢失栈）

**反例**：
```java
// ❌ 丢失栈
log.error("操作失败: " + e.getMessage());

// ❌ 完全不传异常
log.error("操作失败: {} {}", userId, e.getMessage());

// ✅ 完整
log.error("订单创建失败, userId=" + userId, e);
```

### 9.2 重复打印防止浪费磁盘

🟡 **推荐**（P3C 第 5 条）：

- **避免重复打印日志，浪费磁盘空间**
- 务必在 `logback.xml` 中设置 `additivity="false"`（防止日志冒泡到 root logger）

```xml
<!-- 防止日志重复（每个 Logger 默认会冒泡到 root） -->
<logger name="com.example.order" level="DEBUG" additivity="false"/>
```

### 9.3 异常级别选择

🟡 **推荐**：

| 异常类型 | 日志级别 |
|---|---|
| **业务异常**（BizException / 用户参数错误）| **WARN**（用户输入错，不需要告警）|
| **可恢复系统异常**（超时 / 重试后成功）| **WARN** |
| **不可恢复系统异常**（NPE / 数据库挂）| **ERROR**（必须告警） |
| **第三方服务错误** | **ERROR**（业务风险）|

🟡 **推荐**（P3C 第 8 条）：

- **可以用 WARN 级别记录用户输入参数错误的情况，避免用户投诉时无所适从**
- **如非必要，请不要在此场景打出 ERROR 级别**，避免频繁报警
- **ERROR 级别只记录系统逻辑出错 / 异常 / 重要错误信息**

### 9.4 异常捕获的最佳实践

🟡 **推荐**：

- **业务异常不打 ERROR**（避免告警风暴）
- **可预期的 checked 异常打 WARN**
- **不可预期的 RuntimeException 打 ERROR**

```java
try {
    return externalService.call();
} catch (BizException e) {
    // 业务异常，不需要 ERROR（日志已经在 AbstractExceptionHandler 里打了）
    throw e;
} catch (IOException e) {
    // 第三方 IO，可预期重试
    log.warn("外部服务 IO 失败，准备重试, endpoint={}", endpoint, e);
    throw new BizException("40101", "外部服务调用失败", e);
} catch (Exception e) {
    // 不可预期，必须 ERROR 触发告警
    log.error("未预期异常, operation={}, params={}", operation, params, e);
    throw e;
}
```

## 10. Logback 配置

### 10.1 标准 logback-spring.xml 结构

🟡 **推荐**：Spring Boot 推荐用 `logback-spring.xml`（带 Spring Boot 的 profile 支持）：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>

    <!-- 控制台输出 -->
    <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level [traceId=%X{traceId:-}] %logger{36} - %msg%n%wex</pattern>
            <charset>UTF-8</charset>
        </encoder>
    </appender>

    <!-- 业务日志文件 -->
    <appender name="BIZ_FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${LOG_PATH}/biz.log</file>
        <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
            <!-- 按天 + 按大小归档 -->
            <fileNamePattern>${LOG_PATH}/biz.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
            <maxFileSize>100MB</maxFileSize>
            <maxHistory>30</maxHistory>
            <totalSizeCap>50GB</totalSizeCap>
        </rollingPolicy>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level [traceId=%X{traceId:-}] %logger{36} - %msg%n%wex</pattern>
        </encoder>
    </appender>

    <!-- 错误日志单独 -->
    <appender name="ERROR_FILE" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <file>${LOG_PATH}/error.log</file>
        <filter class="ch.qos.logback.classic.filter.ThresholdFilter">
            <level>ERROR</level>
        </filter>
        <rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
            <fileNamePattern>${LOG_PATH}/error.%d{yyyy-MM-dd}.%i.log.gz</fileNamePattern>
            <maxFileSize>100MB</maxFileSize>
            <maxHistory>60</maxHistory>
        </rollingPolicy>
        <encoder>
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level [traceId=%X{traceId:-}] %logger{36} - %msg%n%wex</pattern>
        </encoder>
    </appender>

    <!-- 框架 WARN 以上才输出（减少噪声）-->
    <logger name="org.springframework" level="WARN"/>
    <logger name="org.hibernate" level="WARN"/>
    <logger name="org.apache.tomcat" level="WARN"/>

    <!-- 业务代码 DEBUG 级别 -->
    <logger name="com.example.order" level="DEBUG" additivity="false">
        <appender-ref ref="BIZ_FILE"/>
    </logger>

    <!-- Root 只接收 ERROR 报警（即使 additivity=false 也接收 ERROR_FILE）-->
    <root level="INFO">
        <appender-ref ref="STDOUT"/>
        <appender-ref ref="BIZ_FILE"/>
        <appender-ref ref="ERROR_FILE"/>
    </root>

</configuration>
```

### 10.2 Spring Boot Profile 区分

🟡 **推荐**：dev / prod 用不同日志级别：

```xml
<springProfile name="dev">
    <root level="DEBUG">
        <appender-ref ref="STDOUT"/>
    </root>
</springProfile>

<springProfile name="prod">
    <root level="INFO">
        <appender-ref ref="STDOUT"/>
        <appender-ref ref="BIZ_FILE"/>
        <appender-ref ref="ERROR_FILE"/>
    </root>
</springProfile>
```

### 10.3 日志文件命名（P3C 强制）

🟡 **推荐**（P3C 第 3 条）：

- 应用中的扩展日志（如打点 / 临时监控 / 访问日志等）命名方式：`appName_logType_logName.log`
- `logType`：日志类型，推荐分类 `stats / monitor / visit`
- `logName`：日志描述

**正例**：
```
mppserver_monitor_timeZoneConvert.log
order-service_biz_2024-06-30.log
order-service_error_2024-06-30.log
```

🟡 **推荐**：

- 推荐对日志进行分类，将错误日志和业务日志分开存放
- 便于开发人员查看，便于通过日志对系统进行及时监控

### 10.4 日志保留时间

🟡 **推荐**（P3C 第 2 条）：

- **日志文件推荐至少保存 15 天**（有些异常具备以"周"为频次发生的特点）
- 重要业务系统（支付 / 订单）：建议 **至少 30 天**
- 法规要求的系统：按法规（如等保 2.0 要求至少 6 个月）

## 11. 日志归档与 ELK（AI 视角扩展）

### 11.1 本地归档 vs ELK

🟢 **可选**：

| 规模 | 推荐 |
|---|---|
| **小项目** | 本地文件 + 按天归档（logback RollingFile） |
| **中大型项目** | 本地 + 同步到 ELK / Loki |
| **大型分布式** | ELK + 链路追踪（Sleuth / SkyWalking / OpenTelemetry）|

### 11.2 ELK 简介

🟢 **参考**：

- **E**lasticsearch：日志存储 + 全文搜索
- **L**ogstash：日志收集、解析、转发
- **K**ibana：日志可视化、查询面板
- 国产替代：**Loki + Promtail + Grafana**（更轻量）

### 11.3 JSON 格式日志

🟡 **推荐**：往 ELK 传日志用 JSON 格式（便于解析）：

```xml
<encoder class="net.logstash.logback.encoder.LogstashEncoder">
    <includeMdcKeyName>traceId</includeMdcKeyName>
    <customFields>{"app":"order-service","env":"prod"}</customFields>
</encoder>
```

输出：
```json
{"@timestamp":"2024-06-30T22:30:15.123+08:00","level":"INFO","logger":"OrderService","message":"用户 100 下单","traceId":"a1b2c3d4","app":"order-service","env":"prod"}
```

### 11.4 异步日志（性能优化）

🟡 **推荐**：高并发服务用**异步 Appender**（避免日志写盘阻塞业务线程）：

```xml
<appender name="ASYNC_BIZ" class="ch.qos.logback.classic.AsyncAppender">
    <queueSize>2048</queueSize>
    <discardingThreshold>0</discardingThreshold>
    <neverBlock>true</neverBlock>
    <appender-ref ref="BIZ_FILE"/>
</appender>
```

🟡 **推荐**：

- `queueSize` 足够大（4K-8K），否则高并发丢日志
- `neverBlock=true` 保证队列满时业务线程**不阻塞**（宁可丢日志也不阻塞主流程）

### 11.5 日志切割避免单文件过大

🟡 **推荐**：

- `RollingFileAppender` 自动按天 / 大小切割
- `maxFileSize=100MB` + `maxHistory=30` 是常见配置
- 避免单文件过大（搜索 / 复制都慢）

### 11.6 日志也是性能开销

🟢 **参考**：

- **日志是隐性的性能瓶颈**：每条日志都要格式化 + 序列化 + 写文件
- 高 QPS 服务慎用 `+` 拼接（见 § 3.3）
- DEBUG 级别生产禁开（性能影响 5-10%）
