# 11 - Java 性能优化规则

> 🟢 本文件适用于 Java 服务或工具的延迟、吞吐、内存、GC、I/O、数据库和容量问题。
>
> 🔴 不适用：没有基线的 JVM 参数套用、缓存/线程池迁移或为了优化改变正确性和安全边界。

---

## 1. 先复现与测量

> **适用条件与验证**：存在性能症状、SLO、压测、诊断数据或可复现负载时适用。

- 🔴 **必须**：记录环境、JDK、容器/主机资源、数据规模、负载、基线和测量区间；不得把经验值当作瓶颈结论。
- 🔴 **必须**：优先使用项目已有指标、日志、trace、profiler、慢查询和压测工具；未在目标条件验证时不得声称生产收益。
- 🟡 **推荐**：一次修改一个可解释瓶颈，并同时关注正确性、尾延迟、错误率、资源和成本。

## 2. 代码、数据与 I/O

> **适用条件与验证**：测量显示 CPU、分配、锁、线程池、数据库、远程调用、序列化、缓存或文件 I/O 是实际瓶颈时适用。

- 🔴 **必须**：只优化已定位热路径；缓存、批量、异步、对象池、索引、连接池和并发度的选择必须符合一致性、容量和失效语义。
- 🔴 **必须**：超时、背压、取消、重试和资源释放不能为吞吐优化而被移除；写操作重试仍需幂等或补偿保障。
- 🟡 **推荐**：通过查询计划、分配/锁分析和负载数据决定实现，而非默认某个集合、GC、NIO 或框架更快。

## 3. JVM 与运行环境

> **适用条件与验证**：任务明确涉及 JVM、GC、容器资源、基础镜像或启动参数，且当前运行环境可验证时适用。

- 🔴 **必须**：参数、GC、堆、线程栈、内存比例、转储和日志位置以当前 JDK、启动脚本、资源限制、监控和回滚方式为准；不得复制“生产模板”。
- 🟢 **可选**：仅在项目 JDK、框架、构建链和发布平台已支持时评估 CDS、原生镜像或其他运行时能力。

## 4. 验证与例外

- 🔴 **必须**：复测与基线相同条件，并检查功能、错误率、资源、稳定性和回滚；报告无法覆盖的负载或环境。
- 🟡 **推荐**：收益不明确时保留更简单可维护的实现，并记录后续观测计划。

> **例外**：紧急容量缓解可先做最小可回退调整，但后续必须补齐测量和根因验证。
