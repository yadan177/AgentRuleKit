# 02 - Java 代码风格规则

> 🟢 本文件适用于 Java 源文件的格式、命名、注释、import 和静态检查调整。
>
> 🔴 不适用：以风格为由进行公共 API 重命名、全仓格式化、工具链升级或架构改造。

---

## 1. 配置优先

> **适用条件与验证**：先检查 `.editorconfig`、Formatter、Checkstyle、SpotBugs、Error Prone、IDE 设置、构建插件和 CI。

- 🔴 **必须**：以仓库实际配置和同模块代码为准；没有配置时，保持受影响区域的现有风格，不发明团队级阈值或命名体系。
- 🔴 **必须**：不得把未安装的 linter、插件或 IDE 行为写成项目要求，也不得将未运行的检查称为通过。
- 🟡 **推荐**：把纯格式修改与行为修改分开提交/审查，减少合并冲突和回归定位成本。

## 2. 可读性与注释

> **适用条件与验证**：新增或修改 Java 源、测试、配置绑定类和公开接口时适用。

- 🔴 **必须**：命名表达领域含义并与同包一致；缩写、可空性、布尔命名、异常和日志字段遵循项目既有约定。
- 🔴 **必须**：注释、Javadoc 和 suppress 标记必须真实反映当前行为、限制与原因；不得保留失效注释、凭证、生产数据或无依据的性能结论。
- 🟡 **推荐**：用清晰的结构和小范围重构改善可读性，避免为固定行宽、空行或大括号偏好触发无关改动。

## 3. 自动化与例外

> **适用条件与验证**：项目已配置格式化或静态分析命令时适用。

- 🔴 **必须**：只运行仓库已有且与任务相关的检查；自动修复后检查 diff，确保不改变生成物、公开 API 或无关文件。
- 🟡 **推荐**：在交付中说明实际执行的格式/静态检查和未执行原因。

> **例外**：统一风格迁移、规则升级或大规模 suppress 清理需要独立授权、完整 CI 验证和可回滚范围。
