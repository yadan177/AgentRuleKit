# 05 - Java 模式设计规则

> 🟢 本文件适用于 Java 项目的架构设计模式（SOLID/IoC/AOP/事件驱动等）。

> 🔴 不适用：业务逻辑实现、具体 API 端点设计、Spring 配置细节

---

## 1. SOLID 5 大原则

AI 写类设计时立即要遵循的最基本设计原则。**跨语言通用**。

### 1.1 SOLID 总览

| 字母 | 原则 | 关注什么 |
|---|---|---|
| **S** | 单一职责 (Single Responsibility) | 一个类只做一件事 |
| **O** | 开闭原则 (Open-Closed) | 对扩展开放，对修改关闭 |
| **L** | 里氏替换 (Liskov Substitution) | 子类可替换父类 |
| **I** | 接口隔离 (Interface Segregation) | 接口要小而专 |
| **D** | 依赖倒置 (Dependency Inversion) | 依赖抽象不依赖具体 |

### 1.2 单一职责 (SRP)

🟡 **推荐**：

- **一个类应当只有一个引起它变化的原因**
- 一个类承担多项职责是代码异味（同时改了多个需求点都会动到它）

**反例**：
```java
// ❌ 一个类管太多事
public class OrderManager {
    public void saveOrder() { /* 持久化 */ }
    public void sendEmail() { /* 邮件通知 */ }
    public void generateReport() { /* 报表 */ }
    public void logToAudit() { /* 审计日志 */ }
}
```

**正例**：
```java
// ✅ 拆分为职责单一的类
public class OrderRepository { public void save(Order o) { ... } }
public class OrderNotifier { public void sendEmail(Order o) { ... } }
public class OrderReporter { public void generate(Order o) { ... } }
public class OrderAuditor { public void log(Order o) { ... } }
```

🟡 **推荐**：Java 实践提示——把"业务流程控制"放到一个 `XxxService`，把"持久化"放到 `XxxRepository`，把"输出格式化"放到 `XxxFormatter`，把"外部依赖"放到 `XxxClient`。每个类 30-200 行最舒服。

### 1.3 开闭原则 (OCP)

🟡 **推荐**：

- **对扩展开放，对修改关闭**
- 增加新功能应该通过**新增代码**（子类 / 策略 / 装饰器），而不是**修改已有代码**

**反例**：
```java
// ❌ 频繁修改 if/else 分支
public BigDecimal calculateDiscount(String userType) {
    if (userType.equals("VIP")) return amount.multiply(new BigDecimal("0.8"));
    if (userType.equals("NEW")) return amount.multiply(new BigDecimal("0.9"));
    if (userType.equals("LOYAL")) return amount.multiply(new BigDecimal("0.85"));
    return amount;
}
```

**正例**：
```java
// ✅ 通过多态扩展
public interface DiscountStrategy {
    BigDecimal apply(BigDecimal amount);
}

@Component public class VipDiscount implements DiscountStrategy {
    public BigDecimal apply(BigDecimal amount) { return amount.multiply(new BigDecimal("0.8")); }
}
@Component public class NewUserDiscount implements DiscountStrategy {
    public BigDecimal apply(BigDecimal amount) { return amount.multiply(new BigDecimal("0.9")); }
}

// 新增类型只需新增一个 @Component，不修改已有代码
```

### 1.4 里氏替换 (LSP)

🟡 **推荐**：

- **子类对象必须能够替换父类对象而不出错**
- 子类**不能改变**父类已有的行为契约

**反例**：
```java
// ❌ 违反 LSP
public class Rectangle {
    protected double width, height;
    public void setWidth(double w) { this.width = w; }
    public void setHeight(double h) { this.height = h; }
    public double area() { return width * height; }
}

public class Square extends Rectangle {
    @Override public void setWidth(double w) { this.width = w; this.height = w; } // 改了父类约定
}

// 测试代码：Rectangle 期望 setWidth 后 area 跟随 width 变化，但 Square 同时改 height
Rectangle r = new Square();
r.setWidth(5); r.setHeight(4);
assert r.area() == 20; // ❌ 实际是 16
```

🟡 **推荐**：发现违反 LSP 时，**重构继承层次**（拆出独立的抽象），而不是加 `if (obj instanceof Square)` 之类的类型判断。

### 1.5 接口隔离 (ISP)

🟡 **推荐**：

- **客户端不应被迫依赖它们不用的接口**
- 接口拆分要小而专

**反例**：
```java
// ❌ 臃肿接口
public interface UserOperations {
    void login();
    void logout();
    void uploadAvatar();
    void changePassword();
    void sendFriendRequest();
    void postMoment();
    void likeContent();
}
```

**正例**：
```java
// ✅ 拆分小接口
public interface AuthOperations { void login(); void logout(); }
public interface ProfileOperations { void uploadAvatar(); void changePassword(); }
public interface SocialOperations { void sendFriendRequest(); void likeContent(); }

// 用户类只实现需要的能力
public class LoginService implements AuthOperations { ... }
public class ProfileService implements ProfileOperations { ... }
```

### 1.6 依赖倒置 (DIP)

🟡 **推荐**：

- **高层模块不应依赖低层模块；二者都应依赖抽象**
- **抽象不应依赖细节；细节应依赖抽象**

**反例**：
```java
// ❌ 直接依赖具体类（MySQLDatabase）
public class OrderService {
    private final MySQLDatabase db = new MySQLDatabase();
    public void createOrder(Order o) { db.insert(o); }
}
```

**正例**：
```java
// ✅ 依赖抽象
public interface OrderRepository {
    void save(Order order);
}

@Repository
public class MySQLOrderRepository implements OrderRepository {
    public void save(Order order) { /* JPA / MyBatis */ }
}

@Service
public class OrderService {
    private final OrderRepository repository;
    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
```

🟡 **推荐**：Java 里 DIP 靠 **Spring IoC** 自动完成（构造函数注入 / `@Autowired`）。**别 `new` 具体实现**。

### 1.7 KISS / YAGNI / DRY 三原则

除了 SOLID，还有 3 条**更高层**的设计原则（跨语言通用）：

| 原则 | 含义 | AI 写代码时 |
|---|---|---|
| **KISS**（Keep It Simple, Stupid）| 简单优于复杂 | 能用一个方法解决就别拆 5 个类 |
| **YAGNI**（You Aren't Gonna Need It）| 你不会需要它 | 别为"未来可能用到"写代码 |
| **DRY**（Don't Repeat Yourself）| 别重复自己 | 同一段逻辑在 3 处以上出现就提取 |

**实战判断**：

```
犹豫"要不要拆成更小的类" → 先 KISS
犹豫"要不要为未来加这个功能" → YAGNI
发现"这逻辑在 3 个地方都有" → DRY
```

**反例**（违反三原则）：
```java
// ❌ 违反 KISS：抽象太多层（"for the sake of abstraction"）
public interface IItemFactoryProviderFactory { ... }

// ❌ 违反 YAGNI：未使用的"预留"扩展点
public class OrderService {
    private final Strategy futureStrategy; // ❌ 还没需求就预留
    public OrderService() { futureStrategy = null; }
}

// ❌ 违反 DRY：同一逻辑在 3 个方法复制
public void calcA(Order o) { o.amount = o.amount.subtract(BigDecimal.TEN); }
public void calcB(Order o) { o.amount = o.amount.subtract(BigDecimal.TEN); }
public void calcC(Order o) { o.amount = o.amount.subtract(BigDecimal.TEN); }
```

## 2. GoF 常用模式

GoF 23 种模式中选择 Java 后端最常用的 6 种。AI 写非平凡代码时优先想到这些。

### 2.1 单例模式

🟡 **推荐**：

- 全局唯一且全局可访问的实例（配置类 / 线程池 / 连接池 / 日志工厂）

🟡 **推荐**：Java 5+ 最佳实现 —— **枚举单例**（Effective Java 作者 Josh Bloch 推荐）：

```java
// ✅ 枚举单例（最简洁、防反射攻击、序列化安全）
public enum ConfigManager {
    INSTANCE;

    private final Properties props = new Properties();

    public String get(String key) { return props.getProperty(key); }
}

// 使用：ConfigManager.INSTANCE.get("app.name");
```

🟡 **推荐**：Spring 项目直接用 `@Component` + `singleton` scope（默认）：

```java
@Component  // Spring 默认就是单例
public class OrderService { ... }
```

🟡 **推荐**：单例的反模式（**不要用**）：

- ❌ DCL（double-checked locking）自己写：易错，spring 帮你做
- ❌ `public static final Foo INSTANCE = new Foo();` 用静态字段：不可延迟初始化，且类加载时就要创建
- ❌ 双重判断懒加载（`if (instance == null)`）：多线程不安全

### 2.2 工厂模式 + 策略模式

🟡 **推荐**：

- **工厂模式（Factory）**：创建对象不直接 `new`，用工厂方法
- **策略模式（Strategy）**：同一行为有多种实现，运行时选择
- **两者经常组合**：工厂创建策略对象

**正例**（Spring 风格的工厂 + 策略）：
```java
// 1. 策略接口
public interface NotificationStrategy {
    void send(String to, String content);
}

// 2. 多种策略实现
@Component("email") public class EmailNotification implements NotificationStrategy {
    public void send(String to, String content) { /* SMTP */ }
}
@Component("sms") public class SmsNotification implements NotificationStrategy {
    public void send(String to, String content) { /* 短信网关 */ }
}
@Component("push") public class PushNotification implements NotificationStrategy {
    public void send(String to, String content) { /* 推送 SDK */ }
}

// 3. 工厂：根据类型返回对应策略
@Component
public class NotificationFactory {
    private final Map<String, NotificationStrategy> strategies;

    public NotificationFactory(
            @Qualifier("email") NotificationStrategy email,
            @Qualifier("sms") NotificationStrategy sms,
            @Qualifier("push") NotificationStrategy push) {
        this.strategies = Map.of("email", email, "sms", sms, "push", push);
    }

    public NotificationStrategy get(String type) {
        return strategies.get(type);
    }
}

// 4. 使用
notificationFactory.get("email").send(user.getEmail(), "订单创建成功");
```

### 2.3 观察者模式（Spring Event）

🟡 **推荐**：

- 对象间一对多依赖关系，一个对象状态改变时通知所有依赖者
- Java 标准库有 `java.util.Observable`（**已废弃**），**用 Spring Event 替代**

**正例**（Spring Event）：
```java
// 1. 定义事件
public class OrderCreatedEvent extends ApplicationEvent {
    private final Order order;
    public OrderCreatedEvent(Object source, Order order) {
        super(source);
        this.order = order;
    }
    public Order getOrder() { return order; }
}

// 2. 发布
@Service
public class OrderService {
    private final ApplicationEventPublisher publisher;

    public void createOrder(OrderDTO dto) {
        Order order = orderRepository.save(new Order(dto));
        publisher.publishEvent(new OrderCreatedEvent(this, order));
    }
}

// 3. 多个监听器（解耦）
@Component
public class InventoryDeductionListener {
    @EventListener
    public void onOrderCreated(OrderCreatedEvent e) {
        // 扣减库存
    }
}

@Component
public class NotificationListener {
    @Async @EventListener
    public void onOrderCreated(OrderCreatedEvent e) {
        // 异步发通知
    }
}

@Component
public class AuditLogListener {
    @EventListener
    public void onOrderCreated(OrderCreatedEvent e) {
        // 记录审计日志
    }
}
```

### 2.4 装饰器模式

🟡 **推荐**：

- 动态给对象添加职责，比继承更灵活
- Java IO 经典案例：`BufferedReader` 装饰 `Reader`

**Java 现代装饰器实现**（基于接口 + 包装）：
```java
public interface DataSource {
    void write(String data);
    String read();
}

// 基础实现
public class FileDataSource implements DataSource {
    public void write(String data) { /* 写文件 */ }
    public String read() { /* 读文件 */ }
}

// 装饰器：加密
public class EncryptionDecorator implements DataSource {
    private final DataSource wrapped;
    public EncryptionDecorator(DataSource wrapped) { this.wrapped = wrapped; }
    public void write(String data) { wrapped.write(encrypt(data)); }
    public String read() { return decrypt(wrapped.read()); }
}

// 装饰器：压缩
public class CompressionDecorator implements DataSource {
    private final DataSource wrapped;
    public CompressionDecorator(DataSource wrapped) { this.wrapped = wrapped; }
    public void write(String data) { wrapped.write(compress(data)); }
    public String read() { return decompress(wrapped.read()); }
}

// 自由组合
DataSource ds = new CompressionDecorator(
    new EncryptionDecorator(
        new FileDataSource()
    )
);
```

### 2.5 外观模式（Facade）

🟡 **推荐**：

- 为一组复杂子系统提供**统一的高层接口**，隐藏内部复杂性
- 典型场景：聚合多个 Service 完成一个用例

**正例**：
```java
@Service
public class OrderFacade {
    private final OrderService orderService;
    private final PaymentService paymentService;
    private final InventoryService inventoryService;
    private final NotificationService notificationService;

    // 客户端只调一个方法，内部协调多个子系统
    public OrderResult placeOrder(OrderRequest req) {
        // 1. 校验库存
        inventoryService.checkAvailability(req.getItems());
        // 2. 创建订单
        Order order = orderService.create(req);
        // 3. 处理支付
        PaymentResult payment = paymentService.charge(req.getPaymentInfo(), order);
        if (!payment.isSuccess()) {
            orderService.cancel(order);
            throw new BizException("40101", "支付失败");
        }
        // 4. 发送通知
        notificationService.sendOrderCreated(order);
        return new OrderResult(order, payment);
    }
}
```

🟡 **推荐**：

- **不要让 Controller 直接调多个 Service**——应该调 Facade / 单个聚合 Service（否则 Controller 变成"上帝类"）

### 2.6 模板方法模式

🟡 **推荐**：

- 定义算法骨架，把某些步骤延迟到子类
- 典型应用：JUnit 的 `@Before` / `@Test` / `@After`、Spring `AbstractView`

**正例**：
```java
public abstract class AbstractExportTask<T> {
    public final void execute(T data) {  // 模板方法，final 防止子类覆盖
        validate(data);
        List<Row> rows = transform(data);
        String file = render(rows);
        upload(file);
    }

    protected abstract void validate(T data);
    protected abstract List<Row> transform(T data);
    protected abstract String render(List<Row> rows);
    protected abstract void upload(String file);
}
```


## 3. Spring 生态模式

Java 后端必备（Spring 是 Java 后端的"事实标准"）。AI 写 Spring 项目时立即用。

### 3.1 IoC / DI（控制反转 / 依赖注入）

🟡 **推荐**：

- **不要 `new` 出具体实现**（违反 DIP）
- 用 **构造函数注入**（而不是 `@Autowired` 字段注入）

**反例**：
```java
@Service
public class OrderService {
    @Autowired  // ❌ 字段注入（Spring 4.3 之前用，现在不推荐）
    private OrderRepository orderRepository;

    public Order create(OrderDTO dto) {
        // 无法在构造时保证 repository 不为 null
        // 难以单元测试（不能传 mock）
    }
}
```

**正例**（构造函数注入）：
```java
@Service
public class OrderService {
    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {  // 构造注入
        this.orderRepository = orderRepository;
    }

    public Order create(OrderDTO dto) {
        return orderRepository.save(new Order(dto));
    }
}
```

🟡 **推荐**：构造函数注入的 3 个好处：

1. **不可变性**：`final` 字段，构造后不可改
2. **可测试性**：单元测试可以传 mock
3. **NPE 预防**：依赖在构造时确保不为 null

🟡 **推荐**：

- **循环依赖必须重构**（不要靠 `@Lazy` 或者 setter 注入绕过）
- **超过 5 个依赖时拆类**（构造方法参数太多是 SRP 违反）

### 3.2 AOP（面向切面编程）

🟡 **推荐**：横切关注点（日志 / 权限 / 事务 / 缓存）抽到切面，业务代码专注核心逻辑。

**正例**（自定义注解 + AOP）：
```java
// 1. 自定义注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface AuditLog {
    String operation();
}

// 2. AOP 切面
@Aspect
@Component
public class AuditAspect {
    @Autowired private AuditLogRepository repository;

    @Around("@annotation(auditLog)")
    public Object audit(ProceedingJoinPoint pjp, AuditLog auditLog) throws Throwable {
        long start = System.currentTimeMillis();
        try {
            Object result = pjp.proceed();
            repository.save(new AuditLogRecord(
                auditLog.operation(),
                "SUCCESS",
                System.currentTimeMillis() - start
            ));
            return result;
        } catch (Throwable t) {
            repository.save(new AuditLogRecord(
                auditLog.operation(),
                "FAILED: " + t.getMessage(),
                System.currentTimeMillis() - start
            ));
            throw t;
        }
    }
}

// 3. 使用：业务方法上一个注解搞定
@Service
public class OrderService {
    @AuditLog(operation = "创建订单")
    public Order create(OrderDTO dto) { ... }
}
```

🟡 **推荐**：

- AOP 拦截的方法**不能是 `private` / `final`**
- **类内部调用本类方法不触发 AOP**（代理失效，跟 § 03 事务失效一样的坑）
- **`@Transactional` / `@Async` / 自定义 `@Cacheable` 都是 AOP，都遵守上述限制**

### 3.3 责任链模式（Spring 拦截器）

🟡 **推荐**：

- **多个对象依次处理请求**，每个处理器决定处理或传给下一级
- Spring 典型应用：`HandlerInterceptor` / `Filter` / AOP 多个 advice 串联

**正例**（Filter Chain）：
```java
@Component
public class AuthFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse resp, FilterChain chain) {
        String token = req.getHeader("Authorization");
        if (!authService.verify(token)) {
            resp.setStatus(401);
            resp.getWriter().write("未授权");
            return; // 不传下一级
        }
        chain.doFilter(req, resp); // 传给下一级
    }
}

@Component
public class LoggingFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse resp, FilterChain chain) {
        long start = System.currentTimeMillis();
        chain.doFilter(req, resp);
        log.info("{} {} {}ms", req.getMethod(), req.getRequestURI(), System.currentTimeMillis() - start);
    }
}
```

🟡 **推荐**：规则引擎（风控 / 业务规则）也用责任链：

```java
public interface Rule {
    void apply(OrderContext context);  // 处理或 context.setAborted(true) 中止
}

@Component @Order(1) public class StockRule implements Rule {
    public void apply(OrderContext ctx) {
        if (!inventoryService.isAvailable(ctx.getItems())) ctx.setAborted(true);
    }
}

@Component @Order(2) public class UserStatusRule implements Rule {
    public void apply(OrderContext ctx) {
        if (userService.isBlocked(ctx.getUserId())) ctx.setAborted(true);
    }
}

@Service
public class OrderRuleChain {
    private final List<Rule> rules;

    public OrderRuleChain(List<Rule> rules) {  // Spring 自动注入所有 Rule 实现
        this.rules = rules.stream()
            .sorted(Comparator.comparingInt(r -> AnnotationUtils.getAnnotation(...).order()))
            .collect(Collectors.toList());
    }

    public void check(OrderContext ctx) {
        for (Rule r : rules) {
            r.apply(ctx);
            if (ctx.isAborted()) return;
        }
    }
}
```

## 4. 企业架构模式（AI 视角扩展）

DDD / CQRS / Saga / Outbox 是分布式 Java 后端的**"模式工具箱"**。AI 在大型项目初始化时立即要想到这些。

### 4.1 DDD 分层架构

🟡 **推荐**：领域驱动设计（DDD）4 层架构：

```
┌─────────────────────────────────────────────┐
│  User Interface（用户接口层）                │  ← Controller / DTO 转换
├─────────────────────────────────────────────┤
│  Application（应用层）                       │  ← 用例编排 / 事务边界 / Facade
├─────────────────────────────────────────────┤
│  Domain（领域层）                            │  ← 业务规则 / 实体 / 值对象 / 领域服务
├─────────────────────────────────────────────┤
│  Infrastructure（基础设施层）               │  ← Repository 实现 / 外部服务 / 持久化
└─────────────────────────────────────────────┘
```

**正例**（目录结构）：
```
src/main/java/com/example/order/
├── interfaces/                   # 用户接口层
│   ├── OrderController.java
│   └── dto/                      # DTO
├── application/                  # 应用层
│   ├── OrderApplicationService.java  # 用例编排
│   └── command/                  # CQRS 命令
├── domain/                       # 领域层
│   ├── model/                    # Aggregate / Entity / ValueObject
│   │   ├── Order.java
│   │   └── OrderItem.java
│   ├── service/                  # 领域服务
│   └── repository/               # Repository 接口（不实现）
└── infrastructure/               # 基础设施层
    ├── persistence/              # Repository 实现（JPA / MyBatis）
    ├── messaging/                # MQ 发送
    └── external/                 # 外部服务调用
```

🟡 **推荐**：

- **Domain 层不依赖其他层**（不能 import interfaces / application / infrastructure）
- Repository 接口放 domain 层，实现放 infrastructure 层（**依赖倒置**）
- 领域逻辑（业务规则）**不写在 Controller 也不写在 Application Service**，写在 Domain 层的 Entity 或 Domain Service

### 4.2 CQRS（命令查询职责分离）

🟡 **推荐**：

- **读写分离**：写入用 Command Model（含业务规则），读取用 Query Model（无业务规则、扁平结构）
- 适用：**读写负载严重不对称**（如电商订单读写比 1:100）

🟡 **推荐**：

- **不是所有项目都需要 CQRS**（KISS）—— 只在读写差异巨大时用
- 共享的领域逻辑放 Domain 层，**不放在 Command 或 Query 单边**

### 4.3 Saga 模式（分布式事务）

🟡 **推荐**：

- **跨服务的事务用 Saga 模式**（而不是分布式事务 2PC）
- 每个本地事务有补偿操作

```java
// Saga 示例：创建订单 → 扣库存 → 扣款 → 发通知
// 任一步失败，回滚前几步

public class OrderSaga {
    public void execute(OrderRequest request) {
        Saga saga = new Saga();

        saga.step()
            .invoke(() -> orderService.createOrder(request))  // 创建订单
            .withCompensation(() -> orderService.cancelOrder(orderId));

        saga.step()
            .invoke(() -> inventoryService.deduct(items))  // 扣库存
            .withCompensation(() -> inventoryService.restore(items));

        saga.step()
            .invoke(() -> paymentService.charge(amount))  // 扣款
            .withCompensation(() -> paymentService.refund(amount));

        saga.step()
            .invoke(() -> notificationService.send(orderId));  // 发通知

        saga.execute();
    }
}
```

🟡 **推荐**：用 **Apache ServiceComb Saga** / **Seata** 等框架实现（自己手写 Saga 容易出错）。

### 4.4 Outbox 模式（事件可靠发布）

🟡 **推荐**：

- 在**同一事务**写业务数据和**事件到 outbox 表**
- 后台 poller 读 outbox 表发布到 MQ
- 解决"事务提交成功但 MQ 发送失败"的问题

```sql
CREATE TABLE outbox_event (
    id BIGINT PRIMARY KEY,
    aggregate_type VARCHAR(100),
    aggregate_id VARCHAR(100),
    event_type VARCHAR(100),
    payload TEXT,
    created_at TIMESTAMP,
    published_at TIMESTAMP NULL,
    INDEX idx_published_at (published_at, id)
);
```

```java
@Transactional
public void createOrder(OrderDTO dto) {
    Order order = orderRepository.save(new Order(dto));
    outboxRepository.save(new OutboxEvent(
        "Order",
        order.getId(),
        "OrderCreated",
        serialize(order)
    ));
    // 同一个事务，业务数据 + 事件要么都成功要么都失败
}
```


## 5. 反模式清单（AI 视角重点）

借鉴 Unity 02 § 4 + GoF 反模式 + AI 在 Java 后端实际踩坑。AI 写代码时**主动避开**这些反模式。

### 5.1 上帝类（God Class）

🟡 **推荐**：

- **不要写 1000+ 行的类**
- **拆类依据**：当一个类有 **3 个以上不相关职责**时就该拆

**反例**：~500 行的 `OrderService` 同时管订单创建 / 库存 / 支付 / 通知 / 报表 / 统计。

### 5.2 上帝配置（God Configuration）

🟡 **推荐**：

- **`@ConfigurationProperties` 类不超 20 个字段**
- 拆分：`AppConfig` / `DatabaseConfig` / `CacheConfig` / `MqConfig`

### 5.3 贫血模型 vs 充血模型

🟡 **推荐**：

- **领域对象有行为**（不只是 getter/setter）
- 业务逻辑放 Entity / Domain Service，**不放 Service**

**反例**（贫血模型）：
```java
// ❌ 只有 setter/getter
public class Order {
    private Long id;
    private OrderStatus status;

    public void setStatus(OrderStatus status) { this.status = status; }
    public OrderStatus getStatus() { return status; }
}

@Service
public class OrderService {
    public void cancel(Long orderId) {
        Order o = orderRepository.findById(orderId).orElseThrow();
        if (o.getStatus() == OrderStatus.PAID) {
            // 业务规则散落在 Service 里
            o.setStatus(OrderStatus.CANCELLED);
            // 还要退款、恢复库存、发通知...
        }
        orderRepository.save(o);
    }
}
```

**正例**（充血模型）：
```java
public class Order {
    private Long id;
    private OrderStatus status;

    public void cancel() {
        if (status != OrderStatus.PAID && status != OrderStatus.UNPAID) {
            throw new BizException("30101", "订单当前状态不可取消: " + status);
        }
        this.status = OrderStatus.CANCELLED;
        // 行为属于 Order，不是 Service
    }
}

@Service
public class OrderService {
    private final OrderRepository repo;
    private final PaymentService payment;
    private final InventoryService inventory;

    @Transactional
    public void cancel(Long orderId) {
        Order order = repo.findById(orderId).orElseThrow();
        order.cancel();  // 业务规则属于 Order
        payment.refund(order);
        inventory.restore(order.getItems());
        repo.save(order);
    }
}
```

### 5.4 不加区分的 @Autowired

🟡 **推荐**：

- **禁止在 `static` 字段上加 `@Autowired`**（Spring 不保证静态字段注入时机）
- **禁止在 `final` 字段上加 `@Autowired`**
- **必须用构造注入**（见 § 3.1）

### 5.5 滥用 @Component

🟡 **推荐**：

- **不要把 Utils / Helper 类都加 `@Component`**
- 加 `@Component` 的标准：**有依赖需要注入** 或 **有状态需要 Spring 管理**
- 静态 Utils 类不加注解，直接用静态方法

**反例**：
```java
// ❌ 纯静态工具类加 @Component
@Component
public class StringUtils {
    public static boolean isBlank(String s) { return s == null || s.trim().isEmpty(); }
}
```

**正例**：
```java
// ✅ 静态工具不加 @Component
public final class StringUtils {
    private StringUtils() {}
    public static boolean isBlank(String s) { return s == null || s.trim().isEmpty(); }
}
```

### 5.6 业务异常吞掉 / 转 RuntimeException 后吞

🟡 **推荐**：

- 见 见 03-异常处理规则 § 3.2，不在 Service 里 catch 后只 log 不 throw

### 5.7 序列化 LocalDateTime 没配 Jackson

🟢 **参考**：

- `LocalDateTime` 默认 Jackson 序列化是数组（`[2024,1,15,10,30]`），**不是 ISO 字符串**
- 加依赖 `jackson-datatype-jsr310` + `@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")`

### 5.8 不写 equals/hashCode

🟡 **推荐**：

- 凡是用作 `Set` / `Map.key` / Hibernate 实体 / JSON 反序列化目标的**必须重写** `equals` 和 `hashCode`
- 用 `Lombok` 的 `@EqualsAndHashCode` 或 IDE 生成（见 见 01-代码编写规则 § 3.2）

### 5.9 用 Thread.sleep 做"等待"

🟡 **推荐**：

- **业务等待用 `CountDownLatch.await(timeout)` 或 `CompletableFuture.get(timeout)`**
- `Thread.sleep` 只用于测试或主动让出 CPU

### 5.10 事务里做远程调用

🟡 **推荐**：

- 见 见 03-异常处理规则 § 7.3
- 事务里调 RPC / HTTP / MQ 发送 → 长事务 / 死锁 / 数据不一致
