# 05 - Java 模式设计规则

> 🟢 本文件适用于 Java 模块职责、依赖方向、扩展点、领域边界和架构决策。
>
> 🔴 不适用：把 SOLID、GoF、DDD、Spring 或分布式模式当作所有项目必须采用的方案。

---

## 1. 从已有模块边界出发

> **适用条件与验证**：先检查模块声明、包结构、构造入口、依赖、数据模型、对外契约和同类实现。

- 🔴 **必须**：保持既有依赖方向与公开边界；新增跨模块依赖、接口或事件前检查初始化、事务、序列化、测试和部署影响。
- 🔴 **必须**：职责拆分以真实变化原因、调用关系和可测试性为依据，不以固定类行数、层名或模式名称作为判断标准。
- 🟡 **推荐**：优先采用最小的具体实现；仅在存在稳定替换点、多个调用者或明确测试隔离需求时抽象接口/策略。

## 2. 框架与模式的条件使用

> **适用条件与验证**：项目已使用 DI 容器、事件总线、ORM、消息系统或领域分层，且任务确实涉及其扩展时适用。

- 🔴 **必须**：复用项目已有的构造、Bean/组件、事务、事件和配置模型；不得因示例引入注解、容器、消息、CQRS、Saga、Outbox 或新依赖。
- 🔴 **必须**：异步事件、缓存、远程调用和持久化之间明确一致性、幂等、失败补偿、重放与可观测性责任；客户端/消息不能假定服务端已实现。
- 🟡 **推荐**：把模式作为沟通和权衡工具，记录为何当前方案比更简单的实现更合适。

## 3. 反模式与演进边界

> **适用条件与验证**：新增全局服务、跨层访问、重复模型、复杂工厂或共享可变状态时适用。

- 🔴 **必须**：避免隐式全局状态、循环依赖、未经验证的泛化、绕过领域/权限边界和在事务中执行不可控远程工作。
- 🟡 **推荐**：对长期架构选择使用仓库已有 ADR/设计记录，说明事实、备选、决定、影响、验证和回退；不得伪造批准状态或责任人。

## 4. 验证与例外

- 🔴 **必须**：验证模块编译、依赖方向、关键构造路径、受影响 API 与测试；架构演进还要验证兼容与回退。
- 🟡 **推荐**：交付时说明保留的项目模式、未采用的替代方案及需要跨团队确认的边界。

> **例外**：明确授权的架构迁移可以新增模式或框架，但须限定范围、提供迁移步骤和回退证据。
