# 04 - Java 并发编程规则

> 🟢 本文件适用于 Java 并发编程（线程池/Lock/CompletableFuture/虚拟线程）。

> 🔴 不适用：业务逻辑实现、UI 事件处理

---

## 1. 线程基础

### 1.1 单例对象必须线程安全

🟡 **推荐**：

- **获取单例对象需要保证线程安全**，其中的方法也要保证线程安全
- **资源驱动类、工具类、单例工厂类**都需要注意

### 1.2 线程必须有意义的名称

🟡 **推荐**：

- **创建线程或线程池时请指定有意义的线程名称**，方便出错时回溯

**正例**：
```java
public class TimerTaskThread extends Thread {
    public TimerTaskThread() {
        super.setName("TimerTaskThread");
        // ...
    }
}
```

**线程池命名**（AI 视角扩展）：
```java
ThreadFactory namedFactory = new ThreadFactory() {
    private final AtomicInteger seq = new AtomicInteger(1);
    @Override
    public Thread newThread(Runnable r) {
        return new Thread(r, "order-service-pool-" + seq.getAndIncrement());
    }
};
```

### 1.3 线程资源必须通过线程池

🟡 **推荐**：

- **线程资源必须通过线程池提供**，不允许在应用中自行显式创建线程
- **使用线程池的好处**：减少创建和销毁线程所花的时间以及系统资源开销；如果不使用，可能造成系统创建大量同类线程导致**消耗完内存**或者"**过度切换**"的问题

## 2. 线程池（核心）

### 2.1 不允许用 Executors 创建

🟡 **推荐**：

- **线程池不允许使用 `Executors` 去创建**，而是通过 `ThreadPoolExecutor` 方式
- **原因**：让编写者**明确线程池的运行规则**，规避资源耗尽风险

`Executors` 返回的线程池弊端：

| 工厂方法 | 隐患 |
|---|---|
| `FixedThreadPool` / `SingleThreadExecutor` | 允许的请求队列长度为 `Integer.MAX_VALUE`，可能堆积大量请求 → OOM |
| `CachedThreadPool` / `ScheduledThreadPool` | 允许的创建线程数量为 `Integer.MAX_VALUE`，可能创建大量线程 → OOM |

### 2.2 ThreadPoolExecutor 标准构造

🟡 **推荐**：7 大参数标准配置：

```java
ThreadPoolExecutor executor = new ThreadPoolExecutor(
    corePoolSize,                        // 核心线程数
    maximumPoolSize,                     // 最大线程数
    keepAliveTime,                       // 空闲线程存活时间
    TimeUnit.SECONDS,                    // 时间单位
    new ArrayBlockingQueue<>(queueCapacity), // 工作队列（有界）
    namedFactory,                        // 线程工厂
    new ThreadPoolExecutor.AbortPolicy() // 拒绝策略
);
```

🟡 **推荐**：AI 配置线程池参数的计算公式：

| 参数 | 计算方式 |
|---|---|
| **corePoolSize** | CPU 密集型：`CPU核数 + 1`；IO 密集型：`CPU核数 × 2`（依 IO 等待时间调整）|
| **maximumPoolSize** | 通常 = corePoolSize × 2 或按业务压测确定 |
| **keepAliveTime** | 默认 60 秒；CPU 密集型可缩短 |
| **workQueue** | **必须有界**（`ArrayBlockingQueue`），不要用 `LinkedBlockingQueue` 默认大小（`Integer.MAX_VALUE`）|

### 2.3 4 种拒绝策略

🟡 **推荐**：

| 策略 | 行为 | 何时用 |
|---|---|---|
| `AbortPolicy`（默认）| 抛 `RejectedExecutionException` | 大多数场景（让上游知道） |
| `CallerRunsPolicy` | 由提交任务的线程自己执行 | 任务不能丢弃，**慢一点也要执行**（如关键业务） |
| `DiscardPolicy` | 静默丢弃 | 任务可丢弃（如日志聚合） |
| `DiscardOldestPolicy` | 丢弃队列头部任务，提交新任务 | 总是跑最新数据 |

🟡 **推荐**：

- **拒绝策略必须显式指定**（不要用默认 AbortPolicy 然后忘记 catch `RejectedExecutionException`）

### 2.4 线程池使用规范

🟡 **推荐**（AI 写线程池时立即遵守）：

| 规范 | 原因 |
|---|---|
| **线程池必须 `shutdown()`**（服务关闭时）| 避免 JVM 退出阻塞 |
| **不同业务用不同线程池** | 避免一个慢业务拖垮其他业务（隔离舱） |
| **任务执行 try-catch 整个 Runnable** | 任务未捕获异常导致 worker 线程退出 |
| **不要用 `Thread.stop()` / `Thread.suspend()`** | 已废弃，会破坏状态 |
| **能用无锁数据结构就不用锁** | 锁竞争开销大 |

## 3. 锁

### 3.1 锁的代价与替代

🟡 **推荐**（高并发）：

- **同步调用应该去考量锁的性能损耗**
- **能用无锁数据结构就不要用锁**：优先 `AtomicInteger` / `LongAdder` / `ConcurrentHashMap`
- **能锁区块就不要锁整个方法体**
- **能用对象锁就不要用类锁**
- **尽可能使加锁代码块工作量尽可能的小**
- **避免在锁代码块中调用 RPC 方法**

### 3.2 多资源加锁顺序

🟡 **推荐**：

- **对多个资源、数据库表、对象同时加锁时，需要保持一致的加锁顺序**，否则可能造成死锁
- 线程一需要对表 A、B、C 依次全部加锁后才更新；线程二的加锁顺序也必须 A、B、C

🟡 **推荐**：

- **按固定的全局排序加锁**（如按 `id` 大小，或按对象 `hashCode` 排序）
- **使用 `tryLock(timeout)` 替代无限 `lock()`**：带超时的锁获取

### 3.3 synchronized vs ReentrantLock

🟡 **推荐**：

| 维度 | `synchronized` | `ReentrantLock` |
|---|---|---|
| **实现** | JVM 内置（monitor） | JDK 代码实现 |
| **可重入** | ✅ | ✅ |
| **公平锁** | ❌ | ✅ 可选 |
| **可中断** | ❌ | ✅ `lockInterruptibly()` |
| **超时** | ❌ | ✅ `tryLock(timeout)` |
| **条件变量** | 单个（`wait`/`notify`）| 多个（`Condition`）|
| **性能** | JDK 6+ 已经优化，差距很小 | 复杂场景略好 |

**选择建议**：
- **简单同步**用 `synchronized`（代码少、不易错）
- **需要公平锁 / 中断 / 超时 / 多条件**用 `ReentrantLock`

### 3.4 双重检查锁与 volatile

🟡 **推荐**：

- 通过双重检查锁（double-checked locking）实现**延迟初始化**有隐患（参考 "Double-Checked Locking is Broken"）
- **推荐**：JDK 5+ 把目标属性声明为 `volatile` 类型

**正例**（DCL + volatile）：
```java
class Singleton {
    private volatile Helper helper;

    public Helper getHelper() {
        Helper local = helper;
        if (local == null) {                  // 第一次检查（无锁）
            synchronized (this) {
                local = helper;
                if (local == null) {           // 第二次检查（有锁）
                    local = helper = new Helper();
                }
            }
        }
        return local;
    }
}
```

🟢 **可选**（Java 5+）：用更优雅的实现 —— **静态内部类（Initialization-on-demand holder）**：

```java
class Singleton {
    private Singleton() {}

    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() {
        return Holder.INSTANCE; // JVM 类加载保证线程安全 + 延迟加载
    }
}
```

### 3.5 悲观锁 vs 乐观锁

🟡 **推荐**（并发修改同一条记录）：

- **并发修改同一记录时，避免更新丢失，需要加锁**
- 要么在**应用层加锁**，要么在**缓存加锁**，要么在**数据库层使用乐观锁**
- 使用 `version` 作为更新依据

**冲突概率与策略**：

| 冲突概率 | 推荐策略 | 重试次数 |
|---|---|---|
| < 20% | **乐观锁**（CAS / version）| 不少于 3 次 |
| ≥ 20% | **悲观锁**（`SELECT ... FOR UPDATE`）| — |


## 4. volatile 与可见性

### 4.1 volatile 语义

🟢 **可选**：

- **volatile 解决多线程内存不可见问题**
- **一写多读**场景可解决变量同步问题
- **多写场景无法解决线程安全问题**（如 `count++` 不是原子的）

### 4.2 volatile 三层语义

🟡 **推荐**：

| 语义 | 说明 |
|---|---|
| **可见性** | 一个线程修改 volatile 变量，其他线程立即看到新值（CPU 缓存一致性协议）|
| **禁止指令重排序** | 内存屏障防止 JVM/CPU 重排（volatile 前后代码）|
| **不保证原子性** | `i++` 仍然是"读-改-写"三步，不是原子操作 |

**正例**（一写多读适合用 volatile）：
```java
private volatile boolean shutdownRequested;

public void shutdown() {
    shutdownRequested = true;  // 任何线程立即可见
}

// 工作线程循环判断
public void doWork() {
    while (!shutdownRequested) {
        // do stuff
    }
}
```

## 5. ThreadLocal

### 5.1 ThreadLocal 基本使用

🟡 **推荐**：

- `ThreadLocal` 提供**线程内部的局部变量**（每个线程有自己的副本）
- 典型用途：上下文传递（用户 ID / traceId / transaction ID）

### 5.2 ThreadLocal 必须 try-finally 清理

🟡 **推荐**：

- **ThreadLocal 必须 `remove()`**（在 `finally` 块中），避免**内存泄漏**
- **尤其在使用线程池时**：线程复用，ThreadLocal 不清理会一直累积

**正例**：
```java
try {
    UserContext.setCurrentUser(user);
    // 业务逻辑
} finally {
    UserContext.clear(); // 实际是 threadLocal.remove()
}
```

### 5.3 ThreadLocal 父子线程继承

🟡 **推荐**：

- JDK 默认 ThreadLocal **不继承**父线程到子线程
- 用 `InheritableThreadLocal` 可以让子线程继承父线程值（但**线程池场景下不生效**——线程被复用，不是新创建的子线程）
- **线程池场景**用 **`TransmittableThreadLocal`**（Alibaba 开源 TTL）解决跨线程值传递

### 5.4 ThreadLocal 无法解决共享对象更新

🟢 **参考**（P3C 第 15 条）：

- `ThreadLocal` **无法解决共享对象的更新问题**，`ThreadLocal` 对象建议使用 `static` 修饰
- 这个变量是针对一个线程内所有操作共享的，所以设置为静态变量，所有此类实例共享此静态变量

## 6. 原子类与无锁并发

### 6.1 原子类

🟡 **推荐**（替代 `count++` 等非原子操作）：

```java
AtomicInteger count = new AtomicInteger();
count.addAndGet(1); // 原子操作
```

### 6.2 AtomicLong vs LongAdder

🟡 **推荐**：

- **JDK 8+ 推荐用 `LongAdder`**，比 `AtomicLong` 性能更好
- **原因**：`LongAdder` 采用**分段 CAS**（按线程分散到不同 Cell），高并发竞争下减少乐观锁重试次数
- **代价**：`sum()` 需要累加所有 Cell，不是精确瞬时值（弱一致性）

🟡 **推荐**：根据场景选择：

| 场景 | 选择 |
|---|---|
| 精确实时值（如库存余额）| `AtomicLong` |
| 高并发统计 / 监控（如 QPS / 计数）| `LongAdder` |
| 多 CPU 内核争抢激烈 | `LongAdder` |
| 低并发 | `AtomicLong` 即可 |

### 6.3 Random 多线程陷阱

🟡 **推荐**（P3C 第 11 条）：

- **避免 `Random` 实例被多线程使用**，虽然共享是线程安全的，但会因**竞争同一 seed** 导致性能下降
- `Math.random()` 内部也用 `Random`，同样问题
- **JDK 7+**：直接使用 **`ThreadLocalRandom.current()`**（每个线程独立 seed）

**正例**：
```java
// ✅ 每个线程独立的 Random
ThreadLocalRandom.current().nextInt(0, 100);

// ❌ 多线程共享一个 Random
private static final Random RANDOM = new Random();
int n = RANDOM.nextInt(100);  // 高并发下竞争激烈
```


## 7. CompletableFuture（AI 视角扩展）

P3C 黄山版（基于 JDK 8）只有 `Future` 概念，**没有 CompletableFuture**。现代 Java 异步编程的核心。

### 7.1 CompletableFuture 创建

🟡 **推荐**：

| 方法 | 何时用 |
|---|---|
| `CompletableFuture.runAsync(Runnable)` | 异步执行无返回值的任务 |
| `CompletableFuture.supplyAsync(Supplier)` | 异步执行有返回值的任务 |
| `CompletableFuture.completedFuture(value)` | 已经完成的 future，返回固定值（用于分支合并）|

**正例**：
```java
// 默认用 ForkJoinPool.commonPool()
CompletableFuture<User> future = CompletableFuture.supplyAsync(() -> userDao.findById(id));

// 推荐：指定独立线程池（隔离业务）
CompletableFuture<User> future = CompletableFuture.supplyAsync(
    () -> userDao.findById(id),
    orderExecutor  // 自定义线程池
);
```

🟡 **推荐**：

- **不要用 `ForkJoinPool.commonPool()`** 做业务异步任务（共享，阻塞会拖垮整个 JVM）

### 7.2 链式调用

🟡 **推荐**：

```java
CompletableFuture.supplyAsync(this::queryOrder, orderExecutor)
    .thenApply(order -> order.calculateAmount())              // 转换结果
    .thenCompose(amount -> queryDiscount(amount))              // 串联另一个异步任务
    .thenAccept(amount -> notifyUser(amount))                 // 消费结果
    .exceptionally(ex -> {                                    // 异常处理
        log.error("订单处理失败", ex);
        return null;
    });
```

| 方法 | 触发时机 |
|---|---|
| `thenApply` | 上一步正常完成，转换结果 |
| `thenAccept` | 上一步正常完成，消费结果 |
| `thenRun` | 上一步正常完成，执行 Runnable |
| `thenCompose` | 上一步返回 `CompletionStage`，串联异步 |
| `exceptionally` | 链上任何一步异常触发 |

### 7.3 并行编排：allOf / anyOf

🟡 **推荐**：

**等待全部完成**（`allOf`）：
```java
CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(this::loadUser);
CompletableFuture<Order> orderFuture = CompletableFuture.supplyAsync(this::loadOrder);
CompletableFuture<Coupon> couponFuture = CompletableFuture.supplyAsync(this::loadCoupon);

CompletableFuture.allOf(userFuture, orderFuture, couponFuture)
    .thenRun(() -> {
        User u = userFuture.join();
        Order o = orderFuture.join();
        Coupon c = couponFuture.join();
        // 合并处理
    });
```

**任一完成即返回**（`anyOf`）：
```java
CompletableFuture<Object> any = CompletableFuture.anyOf(
    queryMasterDB(),
    querySlaveDB()
);
```

### 7.4 异常处理陷阱

🟡 **推荐**：

- **`exceptionally` 和 `handle` 必须加**，否则上游失败时**结果被吞掉**
- 子线程异常**不会自动传播到主线程**，必须 `.join()` 抛 `CompletionException` 包原始异常

**反例**：
```java
// ❌ 没 exception handler，失败被吞掉
CompletableFuture.supplyAsync(this::riskyOp)
    .thenAccept(result -> process(result));
```

**正例**：
```java
CompletableFuture.supplyAsync(this::riskyOp, executor)
    .exceptionally(ex -> {
        log.error("异步任务失败", ex);
        return FALLBACK_VALUE;
    })
    .thenAccept(result -> process(result));
```

### 7.5 CompletableFuture vs Reactive

🟢 **可选**：

| 库 | 适用场景 |
|---|---|
| **`CompletableFuture`** | 单次 / 少量异步任务编排（4-5 个）|
| **Reactor / RxJava** | 流式数据处理、高并发背压（1000+ 异步）|
| **Kotlin Coroutines** | Kotlin 项目（不考虑）|

不要为了用 `CompletableFuture` 而硬上 —— 简单场景用同步 + 线程池更清晰。

## 8. 定时任务

### 8.1 不要用 Timer

🟡 **推荐**（P3C 第 9 条）：

- **多线程并行处理定时任务时，`Timer` 运行多个 `TimeTask` 任何一个没捕获抛出的异常，其他任务便会自动终止运行**
- 使用 **`ScheduledExecutorService`** 没有这个问题

### 8.2 ScheduledExecutorService 替代

🟡 **推荐**：

```java
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2, namedFactory);

// 延迟 1 秒后每隔 60 秒执行一次
scheduler.scheduleAtFixedRate(
    this::reportStats,    // 任务
    1,                    // 初始延迟
    60,                   // 周期
    TimeUnit.SECONDS
);

// service 关闭时清理
scheduler.shutdown();
```

### 8.3 Spring @Scheduled 注意事项

🟡 **推荐**：

- `@Scheduled(fixedDelay = 60000)` 间隔 60 秒执行
- **任务执行超过 60 秒**：默认 `@Scheduled` 是单线程，会阻塞后续任务
- **必须配置 taskScheduler 线程池**：

```java
@Configuration
public class ScheduleConfig implements SchedulingConfigurer {
    @Override
    public void configureTasks(ScheduledTaskRegistrar taskRegistrar) {
        taskRegistrar.setScheduler(
            Executors.newScheduledThreadPool(4, namedFactory)
        );
    }
}
```

### 8.4 CountDownLatch 异步转同步

🟡 **推荐**（P3C 第 10 条）：

- 使用 `CountDownLatch` 进行异步转同步操作
- **每个线程退出前必须调用 `countDown`** 方法
- **线程执行代码注意 catch 异常**，确保 `countDown` 方法被执行到
- 避免主线程无法执行至 `await` 方法，直到超时才返回结果

```java
CountDownLatch latch = new CountDownLatch(N);
for (int i = 0; i < N; i++) {
    executor.submit(() -> {
        try {
            doWork();
        } catch (Exception e) {
            log.error("worker 失败", e);
        } finally {
            latch.countDown();  // 必须保证执行
        }
    });
}
latch.await(10, TimeUnit.SECONDS); // 必须带超时！
```

🟡 **推荐**：

- **`latch.await()` 必须带超时**（不能用 `await()` 无限等待）
- **子线程抛出异常堆栈不能在主线程 try-catch 到**


## 9. 虚拟线程（Java 21+，AI 视角扩展）

P3C 黄山版基于 JDK 8，**完全没有虚拟线程**。Java 21 是里程碑，AI 必须掌握。

### 9.1 虚拟线程基础

🟡 **推荐**：

- **虚拟线程（Virtual Thread）** 是 Java 21 引入的轻量级线程（JEP 444 最终化）
- **底层**：M:N 调度，由 JVM 调度到少量 OS 线程（载体线程 / carrier thread）
- **创建开销**：约几百字节（vs 平台线程约 1MB 栈）
- **适合**：**高并发 I/O 密集型**（HTTP / RPC / 数据库连接）

**创建方式**：

```java
// ✅ Java 21+ 写法
Thread vt = Thread.ofVirtual()
    .name("vt-order-", 1)
    .start(() -> processOrder(orderId));

// ✅ 或者
Thread.startVirtualThread(() -> processOrder(orderId));
```

### 9.2 虚拟线程 vs 平台线程决策

🟡 **推荐**：

| 场景 | 选择 |
|---|---|
| **HTTP / RPC / DB 等 I/O 密集** | **虚拟线程**（高并发同步代码也能扛） |
| **CPU 密集计算** | **平台线程**（虚拟线程无优势，反而增加调度）|
| **需要 ThreadLocal + 同步阻塞** | **虚拟线程**（避免 OOM）|
| **使用 `synchronized` 块** | **慎用**（见 § 9.3）|
| **已有线程池，CPU 核数固定** | **平台线程池** |

### 9.3 虚拟线程与 synchronized

🟡 **推荐**（JDK 21 / JDK 24 前）：

- **虚拟线程在 `synchronized` 块内执行 I/O 操作时，会 pin 到载体线程**（无法卸载到其他载体）
- **JDK 21 已知缺陷**：进入 `synchronized` + 阻塞 I/O 会限制并发扩展性
- **JDK 24+**（JEP 491 同步化虚拟线程）：pin 限制解除

🟡 **推荐**（JDK 21/22/23）：

- 避免在虚拟线程中使用 `synchronized` 阻塞 I/O
- 用 **`ReentrantLock`** 替代 `synchronized`（不对虚拟线程 pin）

```java
// ❌ 不好：synchronized 阻塞 I/O
synchronized (lock) {
    httpClient.send(req);  // pin 住载体线程
}

// ✅ 好：ReentrantLock
lock.lock();
try {
    httpClient.send(req);
} finally {
    lock.unlock();
}
```

### 9.4 ExecutorService 虚拟线程化

🟢 **可选**：Java 21 提供 `Executors.newVirtualThreadPerTaskExecutor()`：

```java
// ✅ 高并发同步代码直接改用虚拟线程池
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 10_000).forEach(i -> {
        executor.submit(() -> {
            // 每个任务一个虚拟线程
            handle(i);
        });
    });
}
// 等价于 10000 个虚拟线程，内存占用极小
```

### 9.5 Spring Boot 3.2+ 虚拟线程集成

🟢 **可选**：

```yaml
# application.yml
spring:
  threads:
    virtual:
      enabled: true
```

启用后，Tomcat / Jetty / `@Async` 默认使用虚拟线程（依赖 Spring Boot 3.2+）。

## 10. 并发集合（AI 视角补充）

P3C 第 14 条提到 HashMap 高并发死链。这里扩展开。

### 10.1 选型决策表

🟡 **推荐**（AI 写并发集合时立即用）：

| 场景 | 选型 |
|---|---|
| 高并发 `Map` | `ConcurrentHashMap`（**JDK 8+ 用 `compute` / `merge`**） |
| 高并发 `List` | **用 `Collections.synchronizedList`** 或 `CopyOnWriteArrayList`（读多写少）|
| 高并发 `Set` | `ConcurrentHashMap.newKeySet()`（JDK 8+）或 `CopyOnWriteArraySet` |
| 高并发 `Queue`（生产者-消费者）| `LinkedBlockingQueue` / `ArrayBlockingQueue` |
| 高并发 `Deque`（栈 / 双端队列）| `LinkedBlockingDeque` |
| 阻塞等待获取元素 | `BlockingQueue` 接口（`put` / `take`）|
| 优先级队列 | `PriorityBlockingQueue` |
| 延迟队列（定时任务）| `DelayQueue`（元素到时间后才能 take）|

### 10.2 ConcurrentHashMap 重要方法

🟡 **推荐**：

```java
// ✅ JDK 8+ 原子操作
map.computeIfAbsent(key, k -> newValue());  // key 不存在时计算
map.computeIfPresent(key, (k, v) -> update(v)); // key 存在时更新
map.merge(key, value, (old, new) -> combine);   // 合并

// ❌ 错误的多步操作（非原子）
if (!map.containsKey(key)) {
    map.put(key, value);  // 另一线程可能 put 了相同 key
}
```

### 10.3 HashMap 高并发死链

🟢 **参考**（P3C 第 14 条）：

- `HashMap` 在容量不够进行 `resize` 时由于高并发**可能出现死链**，导致 CPU 飙升
- **开发过程中可以使用其他数据结构或加锁来规避此风险**（推荐用 `ConcurrentHashMap`）

### 10.4 SimpleDateFormat 线程不安全

🟡 **推荐**（P3C 第 5 条）：

- **`SimpleDateFormat` 是线程不安全的类**，一般不要定义为 `static` 变量
- 如果必须定义为 `static`，必须加锁，或者使用 `DateUtils` 工具类

**正例**（JDK 8+ 推荐用新日期 API）：
```java
// 用 ThreadLocal 隔离
private static final ThreadLocal<DateFormat> df = ThreadLocal.withInitial(
    () -> new SimpleDateFormat("yyyy-MM-dd")
);

// ✅ 更好：用 JDK 8+ 的 DateTimeFormatter（不可变、线程安全）
private static final DateTimeFormatter dtf = DateTimeFormatter.ofPattern("yyyy-MM-dd");
```

🟡 **推荐**：JDK 8+ 用新日期 API：

| 旧（线程不安全）| 新（线程安全 / 不可变）|
|---|---|
| `Date` | `Instant` |
| `Calendar` | `LocalDateTime` / `LocalDate` / `LocalTime` |
| `SimpleDateFormat` | `DateTimeFormatter` |

官方形容：`simple beautiful strong immutable thread-safe`
