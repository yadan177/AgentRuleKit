# 04 - Java 并发编程规则

> 🟢 本文件适用于 Java 线程、线程池、异步任务、锁、调度、上下文与共享状态。
>
> 🔴 不适用：仅因规则提到而启用虚拟线程、替换执行器或改造全局并发模型。

---

## 1. 并发模型先行

> **适用条件与验证**：先检查 JDK/toolchain、现有执行器、框架线程模型、请求上下文、调度器、监控和关闭流程。

- 🔴 **必须**：明确任务由谁创建、在哪执行、如何限流、何时取消、如何传播错误和如何停止；不得创建无人管理的线程或后台任务。
- 🔴 **必须**：沿用项目现有的执行器、调度和上下文传递机制；不能因更现代的 API 存在而升级 JDK、迁移线程池或引入反应式框架。
- 🟡 **推荐**：先评估顺序实现、批处理或队列化是否已满足需求，再增加并发度。

## 2. 共享状态与资源

> **适用条件与验证**：多个线程/任务读写内存、缓存、连接、事务、文件或请求上下文时适用。

- 🔴 **必须**：为每份共享可变状态定义同步策略、可见性、原子性和生命周期；锁、并发集合、原子类型和 ThreadLocal 的选择以访问模型和已有代码为准。
- 🔴 **必须**：不得在锁、事务或受限线程中执行不可控的远程调用、长 I/O 或等待；需要这样做时先定义超时、隔离、补偿和容量影响。
- 🟡 **推荐**：限制锁范围，避免锁顺序不明、阻塞队列无限增长和 ThreadLocal 泄漏；使用项目已有指标观察队列、拒绝、超时和线程饱和。

## 3. Future、调度与语言能力

> **适用条件与验证**：项目已使用 CompletableFuture、ScheduledExecutor、虚拟线程或其他异步抽象时适用。

- 🔴 **必须**：组合异步操作时处理异常、取消、超时、执行器归属和上下文；不要让默认执行器或隐式线程决定关键生产行为。
- 🔴 **必须**：虚拟线程、结构化并发或版本相关 API 仅在项目 JDK、框架、监控与部署环境均已验证时采用。
- 🟡 **推荐**：为关键并发路径设置有意义的任务命名、指标和可重复的压力/竞争测试。

## 4. 验证与例外

- 🔴 **必须**：验证正常、超时、取消、拒绝、关闭和竞争条件下的行为，并检查线程、连接、事务和上下文是否泄漏。
- 🟡 **推荐**：交付时报告并发模型、容量假设和未覆盖的负载风险。

> **例外**：全局执行器、JDK 并发特性或调度平台迁移必须独立评审并提供压测与回退计划。
