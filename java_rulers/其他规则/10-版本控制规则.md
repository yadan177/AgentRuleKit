# 10 - Java 版本控制规则

> 🟢 本文件适用于 Java 仓库中的提交、审查、忽略文件、生成物、发布分支与 CI 相关变更。
>
> 🔴 不适用：未经授权的提交、推送、合并、打 tag、历史改写、分支删除、LFS 迁移或托管平台配置修改。

---

## 1. 仓库约定优先

> **适用条件与验证**：先检查仓库贡献指南、分支保护、CI、`CODEOWNERS`、`.gitignore`、`.gitattributes`、发布和托管平台规则。

- 🔴 **必须**：提交、分支、PR/MR、审查、签名、版本号和合并策略遵循仓库及团队实际约定；Conventional Commits 仅在已采用或用户明确要求时使用。
- 🔴 **必须**：提交说明真实描述改动、测试、迁移、配置和安全影响；不得伪造审查/发布状态或通过改写历史隐藏问题。
- 🟡 **推荐**：保持提交范围可审查；将行为、格式、生成物和基础设施的大范围改动分开处理。

## 2. Java 生成物与敏感文件

> **适用条件与验证**：修改构建、依赖、代码生成、IDE、容器或测试配置时适用。

- 🔴 **必须**：以现有 `.gitignore`、构建输出、Wrapper、锁定/校验文件、生成代码和许可证策略为准；不得套用通用模板删除项目有意跟踪的文件。
- 🔴 **必须**：不得提交密钥、生产配置、日志、构建产物或未获授权的大型二进制；发现已跟踪敏感信息时遵循项目安全事件流程，不擅自改写历史。
- 🟡 **推荐**：在生成代码或依赖元数据变更时一并提交其声明的源文件和必要产物，并验证可复现构建。

## 3. 验证与例外

- 🔴 **必须**：提交/审查前检查 diff、受影响构建与测试、忽略规则、迁移和公开契约；未获授权不得执行远程 Git 操作。
- 🟡 **推荐**：交付时说明实际本地验证、待审查项和需要发布负责人确认的风险。

> **例外**：紧急修复、发布分支或历史修复按仓库既有应急和权限流程执行，并保留可审计记录。
