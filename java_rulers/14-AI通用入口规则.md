# 14 - Java AI 通用入口规则

> 🟢 本文件适用于任何 AI 工具执行 Java 项目的开发、修改、审查、排障或文档任务。
>
> 🔴 不适用：替代项目事实、自动批准技术迁移、伪造构建或测试结果。

---

## 1. 使用方式

本文件是 Java 规则库的最小入口。AI 必须先遵守本文件，再按 [00 - 文档总览](./00-文档总览.md) 选择与任务相关的专题规则。

- 🔴 用户当前任务、工具安全限制和目标项目事实优先于通用建议。
- 🟡 只加载完成当前任务必要的专题文档，避免把整套规则作为不加区分的指令。
- 🟢 在不支持持久规则的工具中，可手动附加本文件和所需专题文档。

## 2. 项目能力探测

### 2.1 开始前检查

在编写或修改 Java 内容前，检查能够获得的以下证据：

1. `pom.xml`、`build.gradle`、`build.gradle.kts`、版本目录和 toolchain/JDK 设置。
2. `mvnw`、`gradlew`、`.mvn/`、`gradle/`、CI 和已有的构建、测试、格式化命令。
3. 多模块声明、包结构、模块描述符、同模块接口和已有实现。
4. 已安装的框架、日志、测试、数据访问、序列化、安全与观测依赖。
5. migration、配置模板、容器/部署文件及现有的运行环境约束。

### 2.2 决策规则

- 🔴 只调用项目已安装、版本兼容且已有证据支持的依赖、插件与 API。
- 🔴 沿用同模块的异常、事务、线程、日志、测试、配置和安全处理模式，除非用户明确授权重构。
- 🔴 版本、依赖或运行环境无法判断时，说明不确定点；优先复用已有兼容实现，无法安全决策时询问用户。
- ❌ 不得把特定 JDK、Spring、Maven、Gradle、JUnit、数据库、容器或云平台设为本规则库的全局前提。

## 3. 变更边界

### 3.1 必须遵守的边界

- 🔴 未获明确授权时，不升级 JDK、构建工具、依赖、BOM、插件、框架或基础镜像。
- 🔴 未获明确授权时，不新增第三方依赖、不迁移 ORM/日志/安全/消息方案、不批量改动模块或部署配置。
- 🔴 修改数据库、接口和配置时，必须遵循已有 migration、契约、密钥管理和发布流程。
- 🔴 线程池、事务、连接、文件句柄、请求上下文和异步任务必须明确生命周期、取消/超时和所有权。

### 3.2 推荐做法

- 🟡 先完成最小可验证改动，再讨论可选重构或依赖替换。
- 🟡 性能优化先通过项目已有指标、Profiler、JFR 或其他已安装工具定位问题，再决定缓存、并发或 JVM 参数。
- 🟡 对跨模块、跨服务或跨语言改动，先写清调用方、契约所有者、失败处理与验证责任。

## 4. 禁止臆造

- ❌ 不得臆造依赖已安装、配置键存在、环境变量、数据库表/字段、接口、消息主题、测试夹具、镜像或部署资源。
- ❌ 不得把规则示例中的类、Bean、注解、SQL、命令或配置当成项目已有内容。
- ❌ 未执行验证时，不得声称编译、测试、打包、部署或安全扫描已经通过。

## 5. 验证与交付

### 5.1 验证要求

- 🔴 执行项目可用且与改动相称的验证；无法执行时说明原因、未验证范围和风险。
- 🔴 优先使用仓库已有 wrapper、脚本或 CI 命令；不虚构 `mvn test`、`gradle test`、Docker/Kubernetes 命令。
- 🔴 检查改动是否超出任务范围，新增依赖、配置、迁移和外部调用是否已经获得授权。
- 🟡 对数据、并发、安全、性能和部署改动给出需要在集成环境或生产前复核的项目清单。

### 5.2 交付说明

每次任务结束时，AI 应说明：

1. 修改了什么以及为什么。
2. 执行了哪些验证及其结果。
3. 哪些验证未执行、原因和剩余风险。
4. 需要用户确认的项目事实、迁移、密钥或外部协作事项。

## 6. 规则编写模板

新增或改写专题规则时使用以下结构：

```markdown
### N.M 规则名称

**适用条件**：项目满足的 JDK、依赖、框架、模块或运行环境前提。

🔴 **必须**：可执行的强制要求。

🟡 **推荐**：有条件的推荐做法。

🟢 **可选**：可按项目选择的方案。

**验证**：可检查的构建、测试、配置、日志、指标或审查操作。

**例外**：允许偏离规则的明确条件和处理方式。
```
