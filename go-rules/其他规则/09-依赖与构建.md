# 09 - Go 依赖与构建规则

> 🟢 本文件适用于 Go 模块依赖、构建脚本、容器构建、交叉编译和发布制品的维护。
>
> 🔴 不适用：未经授权的依赖批量更新、Go/toolchain 升级、基础镜像迁移、架构迁移或发布操作。

---

## 1. 依赖变更前先确认边界

> **适用条件与验证**：检查 `go.mod`、`go.sum`、`go.work`、`replace`/`exclude`、代码生成、构建脚本、CI、镜像和许可证/安全约束。以当前依赖版本和项目已验证的 API 为准。

🔴 **必须**：不得为了完成一个功能猜测模块、版本、镜像标签或命令；不得把浮动“最新”版本或全量依赖升级作为默认操作。新增、升级、替换或删除直接依赖需要用户授权或仓库明确任务。

🟡 **推荐**：一次只处理具备明确目的和兼容性范围的依赖变更；阅读 release notes、许可证和现有调用点，再运行项目允许的测试与构建。

## 2. `go.mod`、`go.sum` 与工作区

> **适用条件与验证**：`go.mod`/`go.sum` 是模块状态的一部分；是否使用和提交 `go.work`、是否允许 `replace` 由仓库与团队约定决定。

🔴 **必须**：不得提交指向个人绝对/相对目录的 `replace`，不得手工伪造校验和，不能删除不理解的间接依赖。模块路径或主版本变化可能影响下游，须单独评审。

🟡 **推荐**：当依赖图确实发生变化且仓库工作流使用 `go mod tidy` 时，执行该命令并审查 `go.mod` 与 `go.sum` 的完整 diff；没有可运行环境或变更范围不明确时，记录为未验证项，不要虚报同步完成。

🟢 **可选**：使用 `go mod why`、`go mod graph`、项目现有 SBOM 或依赖报告理解间接依赖来源；不以清理为由盲删依赖。

## 3. 漏洞、许可证与供应链

> **适用条件与验证**：以项目已配置的漏洞扫描、许可证策略、私有代理、校验数据库和 CI 规则为准。

🔴 **必须**：高风险漏洞、未知来源模块、校验失败或许可证冲突不能静默忽略；不能关闭校验、绕过私有代理或把凭证写入 `go.env`、脚本、日志和 Dockerfile。

🟡 **推荐**：项目已接入 `govulncheck`、SBOM、镜像扫描或依赖审计时，随依赖变更运行相应检查；对无法立即升级的风险记录受影响范围、缓解措施和待办。

## 4. 构建与交叉编译

> **适用条件与验证**：构建目标、入口包、build tags、CGO、目标系统/架构、编译标志和制品位置以仓库脚本、CI 和部署环境为准。

🔴 **必须**：不得假定所有项目可使用 `CGO_ENABLED=0`、`-trimpath`、`-ldflags=-s -w` 或同一目标平台。改变这些参数前必须验证依赖的 C 库、运行时证书、调试需求、可复现性和目标环境兼容性。

🟡 **推荐**：按现有任务入口生成最小相关制品；对跨平台或发布构建，在目标平台/CI 中验证。只有项目已注入版本信息时才维护其字段和构建参数。

## 5. 容器构建

> **适用条件与验证**：只在仓库已有 Dockerfile/容器部署或用户明确要求时适用。基础镜像、包管理器、运行用户、端口、证书、时区和镜像仓库以当前实现为准。

🔴 **必须**：不得无授权替换基础镜像、切换发行版、修改运行用户、删除运行依赖或推送镜像。镜像版本应遵循项目维护和安全更新策略，不能把浮动标签当作默认。

🟡 **推荐**：已有多阶段构建、非 root 运行、`.dockerignore` 和扫描要求时保持其安全基线；修改后至少验证镜像可构建及程序可启动，或明确说明未验证原因。

## 6. AI 完成检查

> **验证**：执行仓库已有且与改动相关的依赖、测试、构建或镜像验证；所有命令及结果必须如实说明。

- [ ] 已识别依赖、工作区、构建、CGO、容器和发布约定。
- [ ] 没有未经授权的版本升级、批量更新、基础镜像/架构迁移或发布。
- [ ] 已审查 `go.mod`/`go.sum`（若发生变化）并说明依赖风险。
- [ ] 已报告实际验证、未验证项以及兼容性/供应链风险。

> **例外**：安全更新、模块主版本变更、镜像重建和发布须按项目变更流程单独授权；紧急修复也必须保留可追溯的验证记录。
