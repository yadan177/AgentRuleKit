# 03 - Go 性能优化规则

> 🟢 本文件适用于 Go 服务或工具的延迟、吞吐、CPU、内存、GC、锁、I/O 和容量问题。
>
> 🔴 不适用：没有基线的微优化、无授权的运行时/依赖迁移或牺牲正确性的性能改动。

---

## 1. 复现与基线

> **适用条件与验证**：存在可复现症状、benchmark、profile、指标、trace 或生产诊断证据时适用。

- 🔴 **必须**：记录 Go/toolchain、构建选项、数据规模、负载、环境、基线和测量区间；不得把直觉当成瓶颈结论。
- 🔴 **必须**：优先使用仓库已有 benchmark、pprof、指标、trace、日志或压测入口；未在相近条件复测时不得声称收益。
- 🟡 **推荐**：每次改动针对一个已定位热点，并同时观察正确性、尾延迟、错误率、分配、资源和成本。

## 2. CPU、内存与 I/O

> **适用条件与验证**：测量显示算法、分配、编码、缓存、数据库、网络、文件或日志是实际瓶颈时适用。

- 🔴 **必须**：缓存、对象复用、批量、池化、预分配和替代编码器必须有明确失效、并发、所有权、兼容性和测量依据；不得默认它们更快。
- 🔴 **必须**：优化不得移除错误检查、关闭、超时、取消、权限或数据一致性保障；写操作重试需要项目已有的幂等/补偿机制。
- 🟡 **推荐**：按数据量、访问模式和 profile 决定集合、序列化、分页、查询和缓冲策略，优先保留可读、可测的实现。

## 3. 并发与运行环境

> **适用条件与验证**：性能问题涉及 goroutine、锁、channel、连接、容器资源、镜像或 Go runtime 时适用。

- 🔴 **必须**：并发优化验证 goroutine 退出、阻塞、背压、竞争、连接/文件泄漏和容量边界；不能仅用吞吐结果掩盖稳定性风险。
- 🔴 **必须**：运行时环境、`GOMAXPROCS`、镜像、资源限制、GC 调优和启动参数以当前部署与监控为准，不能复制通用生产模板。
- 🟡 **推荐**：对收益不明确的优化保持简单，并记录后续观测或回滚条件。

## 4. 验证与例外

- 🔴 **必须**：在同等条件复测并检查功能、错误率、资源、数据一致性和回退；报告未覆盖的负载/设备风险。
- 🟡 **推荐**：将基线、改动、结果和风险写入交付或性能记录。

> **例外**：紧急容量缓解可先做最小可回退调整，但必须在后续补齐根因和回归验证。
