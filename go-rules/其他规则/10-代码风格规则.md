# 10 - Go 代码风格规则

> 🟢 本文件适用于 Go 源码的格式、命名、注释和仓库既有静态检查约定。
>
> 🔴 不适用：以风格为理由的公共 API 重命名、包迁移、批量重构或工具链升级。

---

## 1. 格式化与导入

> **适用条件与验证**：先检查仓库已有的 `gofmt`、`goimports`、gofumpt、编辑器设置、pre-commit 和 CI。工具、参数和版本以当前配置为准。

🔴 **必须**：修改的 Go 文件必须符合项目已有格式化约定；不得手工对抗 `gofmt` 的输出。不要用会写入整个仓库的格式化命令处理局部变更。

🟡 **推荐**：仅格式化本次改动文件或调用仓库提供的格式任务；检查模式应使用当前项目真实支持的文件范围或脚本，不要臆造命令。

🟢 **可选**：若用户授权新增格式化工具，先固定或记录版本、更新 CI/文档，并验证不会造成无关全仓 diff。

## 2. 静态检查

> **适用条件与验证**：`go vet`、golangci-lint、staticcheck、gofumpt 等仅在仓库已安装、锁定或 CI 已配置时使用。

🔴 **必须**：不得为一次需求安装浮动“最新”版本的工具、新增 linter 配置或修改规则阈值；不得将工具未执行的结果称为通过。

🟡 **推荐**：现有检查报错时，优先修复本次改动导致的问题；若发现存量问题，分开报告，除非用户要求一并修复。

## 3. 命名、包与接口

> **适用条件与验证**：以同包公共 API、生成代码、序列化/反射标签、跨包调用和仓库命名约定为准。

🔴 **必须**：不为套用风格规则重命名已被外部调用、序列化、反射或生成代码引用的符号。导出标识符、包名、receiver 和接口名称应保持同一包内的一致性与可读性。

🟡 **推荐**：遵循 Go 惯用 MixedCaps 和清晰的包名；接口优先由使用方按所需行为定义，避免为很小的实现过早抽象。缩写、错误变量和 receiver 名称以项目既有写法一致为先。

## 4. 注释与文档

> **适用条件与验证**：公开库、生成文档、lint 规则和对外 API 的注释要求按项目现有约定执行。

🔴 **必须**：注释不能与实现或公开契约相矛盾，不能泄露密钥、内部地址、真实用户数据或安全绕过方法。

🟡 **推荐**：为导出 API、复杂并发/资源生命周期、非显然约束和设计取舍补充说明；解释“为什么”及调用方需要知道的行为，而不是复述代码。TODO 应包含可追溯上下文（如项目已有 issue 格式）。

## 5. 编辑器与自动化

> **适用条件与验证**：`.editorconfig`、编辑器插件、git hook 和 CI 是团队/仓库配置，不应由 AI 为一次变更擅自加入或覆盖。

🔴 **必须**：不得要求所有开发者使用某个编辑器、插件或格式化插件；多 AI 编辑器的入口只加载本规则库，不改变项目的编辑器设置。

🟡 **推荐**：已有 EditorConfig 或钩子时遵守它；发现本地编辑器自动改写无关文件时，先缩小变更并报告。

## 6. AI 完成检查

> **验证**：使用仓库已有格式或静态检查；仅对本次改动的范围执行，并如实记录结果。

- [ ] 改动文件已按项目实际工具格式化，未产生无关批量 diff。
- [ ] 未安装/升级工具或改写 lint 配置来“通过检查”。
- [ ] 命名、注释和接口改动与当前调用方、生成代码和约定兼容。
- [ ] 已说明执行的检查、未执行项和存量问题边界。

> **例外**：全仓风格迁移、linter 升级和公开 API 重命名应是单独授权、可审查且可回滚的任务。
