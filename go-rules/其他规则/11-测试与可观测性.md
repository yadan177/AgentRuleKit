# 11 - Go 测试与可观测性规则

> 🟢 本文件适用于 Go 代码的测试、基准、诊断、指标、追踪和告警相关改动。
>
> 🔴 不适用：未经授权新增测试平台、容器依赖、指标后端、追踪供应商或生产告警策略。

---

## 1. 以风险和既有测试为起点

> **适用条件与验证**：先检查同包测试、CI、测试数据、mock/fixture、测试环境、覆盖率门槛和已有可观测性组件。测试类型由改动风险、依赖边界和项目能力决定，而不是固定比例。

🔴 **必须**：行为变更应有与风险相称的验证；不能把未执行的测试称为通过，不能为了通过测试删除必要断言、降低既有门槛或跳过安全关键分支。

🟡 **推荐**：优先扩展与改动相邻的单元、集成或契约测试。纯逻辑通常适合单元测试；跨数据库、网络、消息和真实部署边界时，按项目已有方式选择集成或端到端测试。测试金字塔是权衡参考，不是百分比配额。

## 2. 单元测试与测试替身

> **适用条件与验证**：使用标准 `testing`、断言库、mock 工具、测试 package 形式和 fixture 结构时，均遵循当前仓库已有实践。

🔴 **必须**：测试应验证可观察的契约、错误处理和边界条件；不得为实现细节制造脆弱断言，也不要为了 mock 而无授权重构公开接口。

🟡 **推荐**：多组相同形状的输入/输出可用表驱动子测试；复杂流程、不同前置条件或独立失败语义则拆为清晰的测试。纯函数直接测试，外部副作用按项目已有边界替身。

🟢 **可选**：仅当仓库已使用 mock 生成器、`testify`、`gomock` 或其他框架时才复用；不要因规则示例新增依赖。

## 3. 并发、基准与模糊测试

> **适用条件与验证**：race、benchmark、fuzz 的可用性取决于当前 Go/toolchain、平台、CI 时限与测试对象。

🔴 **必须**：声称性能改善时，提供可重复的前后测量条件和结果；并发改动必须说明如何验证竞态、取消、泄漏或关闭顺序。不能把一次不稳定的本机结果写成普遍结论。

🟡 **推荐**：项目支持时，用 `go test -race` 覆盖修改到的并发路径；有性能证据时使用同类 benchmark 或 profile；处理不可信格式、解析器或协议时，评估是否扩展现有 fuzz 测试。

## 4. 指标、日志与追踪

> **适用条件与验证**：仅在服务已接入指标、日志、追踪或 SLO/告警体系时适用。指标命名、标签、采样、保留期、隐私和成本以当前平台约定为准。

🔴 **必须**：不得为了单个需求引入 Prometheus、OpenTelemetry、trace SDK 或告警渠道；不得用用户 ID、请求正文、token、完整 URL 查询参数等高基数或敏感值作为指标标签。

🟡 **推荐**：对已有服务的关键失败、延迟、容量或依赖调用沿用既有指标/trace 约定；日志、指标和 trace 的关联遵循 [07-日志与调试规则](07-日志调试规则.md)。

## 5. 健康检查与诊断端点

> **适用条件与验证**：仅在项目已有 health/readiness、pprof、管理端口或平台探针约定时适用。

🔴 **必须**：健康检查不能执行破坏性操作、泄露密钥或内部拓扑；pprof、profile、debug 和管理端点不得默认公开暴露。

🟡 **推荐**：区分进程存活和依赖就绪；对外部依赖检查采用项目已有超时与降级策略，避免探针本身造成级联压力。

## 6. AI 完成检查

> **验证**：优先执行受本次改动影响的仓库已有测试；环境、外部服务或权限不足时，明确记录。

- [ ] 已识别相邻测试、CI、fixture 和观测组件。
- [ ] 行为、并发或性能变更有匹配的验证或明确未验证说明。
- [ ] 未新增未授权的 mock、测试容器、metrics/tracing 依赖或告警平台。
- [ ] 新测试和观测数据不含真实密钥、生产数据或敏感高基数标签。

> **例外**：发布级端到端、压测、告警和 SLO 变更需要项目既有的环境与审批；本地单测不能替代这些验证。
