# 07 - Go 日志与调试规则

> 🟢 本文件适用于已存在的 Go 日志、错误排查、请求关联和受控调试能力。
>
> 🔴 不适用：未经授权的日志库替换、可观测性平台接入、生产调试端点暴露或保留策略变更。

---

## 1. 日志实现与等级

> **适用条件与验证**：先检查当前 logger 门面、具体实现、初始化、配置、采集平台、字段约定、采样和测试。Go 版本是否提供某个标准库 API，只是可用性事实，不能作为升级或替换日志体系的理由。

🔴 **必须**：沿用当前项目已验证的日志实现、构造方式和等级定义；不得因单个需求引入 `log/slog`、zap、zerolog、OpenTelemetry 或替换全局 logger。

🟡 **推荐**：消息使用稳定、可检索的事件描述，变量放入项目规定的结构化字段；选择 Debug/Info/Warn/Error 以告警和排障需要为准，避免把正常高频路径记录为错误。

🟢 **可选**：新项目在明确授权后可选择结构化日志；要同时确定输出格式、字段、脱敏、采样、采集和成本，而不是只选择一个库。

## 2. 字段、隐私与错误

> **适用条件与验证**：字段名称、请求标识、调用位置、保留期和数据分级遵循项目既有约定、隐私要求和日志平台限制。

🔴 **必须**：不得记录密码、token、cookie、认证头、连接串、密钥、完整支付信息、未脱敏个人数据或不可信原始请求体。错误记录也必须遵守脱敏和访问控制。

🔴 **必须**：错误需要保留给调用方处理时，使用项目既有错误包装/分类方式；避免在每一层重复记录同一个错误，导致告警和检索噪声。

🟡 **推荐**：使用当前约定的字段名并保持同一语义一致；对可排障事件记录必要的关联 ID、操作结果和耗时，不强制为每条日志添加项目不存在的 trace、caller 或用户字段。

## 3. 请求关联与追踪

> **适用条件与验证**：仅在 HTTP/gRPC/消息消费者等请求边界以及项目已有 trace/request ID 或传播约定时适用。

🔴 **必须**：关联信息通过请求上下文或项目已有载体传播，不得使用可变全局状态串联并发请求；不信任上游传入的关联 ID，需按项目约定验证、生成或覆盖。

🟡 **推荐**：已有分布式追踪时，将日志与现有 trace/span 关联；没有该体系时，先保持已有 request ID 方案，不要为单个日志新增遥测依赖。

## 4. 调试与 pprof

> **适用条件与验证**：仅在项目已有 pprof、诊断路由或用户明确授权的故障排查中适用；先确认监听地址、认证、网络边界和数据泄露风险。

🔴 **必须**：不得把 pprof、变量转储、调试路由或性能 profile 暴露到公网；不得在生产环境捕获、上传或分享含敏感数据的 profile。

🟡 **推荐**：使用时间有限、访问受控的诊断方式；分析完成后记录结论和证据，而不是保留长期开启的调试端点。

## 5. AI 完成检查

> **验证**：使用项目已有日志测试、集成环境或受控请求验证；无法验证采集平台时，明确说明未验证项。

- [ ] 已识别当前日志库、格式、等级、字段和采集边界。
- [ ] 没有新增/替换日志或追踪依赖，也没有暴露调试端点。
- [ ] 新日志不包含密钥、凭证、敏感个人信息或完整不可信输入。
- [ ] 已说明验证结果、未验证的采集链路及潜在成本/隐私风险。

> **例外**：安全事件、合规审计和事故响应需要更严格或不同的记录策略时，以项目安全流程和数据保留要求为准。
