# 04 - Go API 设计规则

> 🟢 本文件适用于 Go 服务的 HTTP、RPC、消息消费入口及其公开契约。
>
> 🔴 不适用：擅自改变协议、鉴权、网关、序列化、版本或发布策略。

---

## 1. 契约与兼容性

> **适用条件与验证**：先检查路由/IDL、调用方、错误模型、认证、版本、文档和部署顺序。

- 🔴 **必须**：请求、响应、字段、状态/错误码、分页、排序、时间、幂等键和弃用语义以已确认契约为准；不得臆造端点、主题或默认值。
- 🔴 **必须**：公开变更评估消费者兼容、生成代码、灰度与回退；单服务改动不能替代跨团队契约确认。
- 🟡 **推荐**：复用项目已有的路由、IDL、文档和版本策略，并让空结果、验证失败和业务拒绝的语义可测试。

## 2. 输入、授权与输出

> **适用条件与验证**：处理外部输入、身份、权限、上传、序列化和错误响应时适用。

- 🔴 **必须**：在服务端可信边界按现有策略校验、规范化、限制和授权；客户端字段、反向代理位置或隐藏功能不能作为权限证明。
- 🔴 **必须**：响应遵循最小数据、脱敏和错误暴露策略，不返回内部堆栈、数据库细节、令牌或未授权资源。
- 🟡 **推荐**：使用项目已验证的绑定、校验、认证和序列化机制；缺少能力时说明需要授权而非引入新库。

## 3. 可靠性与外部调用

> **适用条件与验证**：写操作、远程调用、超时、重试、限流、缓存、消息或流式处理受影响时适用。

- 🔴 **必须**：定义 deadline、取消、重试边界、幂等/去重、错误映射和用户可见失败；不得对非幂等写操作盲目重试。
- 🔴 **必须**：限流、熔断、队列、缓存和观测沿用网关、库或平台既有实现，不能为单个端点引入全局基础设施。
- 🟡 **推荐**：在已有安全环境中为关键契约补充集成/契约验证，并记录未覆盖消费者。

## 4. 验证与例外

- 🔴 **必须**：验证授权、输入失败、成功、错误响应、超时/取消、重试/幂等和受影响调用方。
- 🟡 **推荐**：交付时说明契约、发布顺序、回退和外部依赖风险。

> **例外**：协议、认证或 API 版本迁移需要接口所有者、消费者和发布流程的明确批准。
