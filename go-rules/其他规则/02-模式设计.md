# 02 - Go 模式设计规则

> 🟢 本文件适用于 Go 包边界、依赖方向、配置、接口、状态和架构取舍。
>
> 🔴 不适用：为了套用 SOLID、设计模式或“Go 惯例”而重构已有包或新增抽象。

---

## 1. 包边界与依赖

> **适用条件与验证**：先检查模块路径、包结构、`internal`、依赖图、构造入口、调用方和同类实现。

- 🔴 **必须**：保持既有包边界、导入方向和公开 API；新增跨包依赖前检查循环、初始化、测试、生成代码和部署影响。
- 🔴 **必须**：包只暴露调用方真正需要的行为；不能用固定目录模板、单例、服务定位器或“分层”名称替代实际职责分析。
- 🟡 **推荐**：优先以小而具体的包和类型解决当前问题；在多个稳定调用方存在替换/隔离需要时，再由消费者定义小接口。

## 2. 配置、构造与扩展

> **适用条件与验证**：新增可选配置、构造函数、插件、策略或外部依赖时适用。

- 🔴 **必须**：配置默认值、来源、校验、覆盖顺序和敏感项遵循项目已有机制；不得从范例推断环境变量、配置文件或密钥。
- 🔴 **必须**：函数选项、构造器、接口、回调和注册表都是可选工具，只有实际配置复杂度、扩展点或测试边界证明需要时使用。
- 🟡 **推荐**：对新扩展点说明所有权、并发、失败、关闭和向后兼容；简单、一次性的参数优先保持直接。

## 3. 状态、事件与一致性

> **适用条件与验证**：模块管理缓存、后台工作、消息、事务或跨服务流程时适用。

- 🔴 **必须**：明确状态权威来源、写入入口、重试幂等、失败补偿、关闭与恢复；客户端和消息消费者不能假定上游已实现未确认契约。
- 🔴 **必须**：避免隐式全局可变状态、循环依赖、无界队列和未经验证的抽象层；不要把 Go 写成另一语言的类层次结构。
- 🟡 **推荐**：长期架构取舍使用项目现有 ADR/设计记录，写清事实、备选、决定、影响、验证和回退，而不是伪造批准状态。

## 4. 验证与例外

- 🔴 **必须**：验证包编译、依赖方向、关键构造/关闭路径、公开接口和相关测试；架构演进还要验证兼容与回退。
- 🟡 **推荐**：交付时说明为何未引入更复杂的模式，以及需要跨服务/平台确认的边界。

> **例外**：明确授权的模块或架构迁移可以调整包结构和抽象，但需限制范围并提供迁移和回退证据。
