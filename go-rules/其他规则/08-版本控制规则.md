# 08 - Go 版本控制规则

> 🟢 本文件适用于 Go 项目的 Git 状态检查、提交准备、忽略规则和版本发布协作。
>
> 🔴 不适用：未经用户授权的提交、推送、合并、打 tag、历史改写、分支删除或 Git LFS 迁移。

---

## 1. 先尊重仓库工作流

> **适用条件与验证**：先读取仓库中的 `AGENTS.md`、贡献指南、分支保护、提交历史、CI、`.gitignore`、`.gitattributes` 和发布说明。托管平台、分支模型、提交格式和审批政策均以当前仓库为准。

🔴 **必须**：未经用户明确请求，不执行 `git commit`、`git push`、`git tag`、合并、rebase、force push、`git clean`、`git reset --hard` 或丢弃工作区变更的命令。不得覆盖、回退或暂存用户的无关改动。

🟡 **推荐**：提交前使用只读状态与差异检查确认改动范围、生成文件和敏感信息；将功能、修复和无关格式化分为可审查的独立变更，前提是符合仓库既有流程。

## 2. 提交信息与分支

> **适用条件与验证**：仅在用户授权创建提交或仓库要求某种格式时适用；以仓库已有提交、提交钩子和 PR 模板为准。

🔴 **必须**：提交说明应准确描述实际变更，不能伪造测试、审查或发布状态；公开 API、数据库迁移、配置和安全影响要在合适的提交/PR 描述中明确。

🟡 **推荐**：仓库采用 Conventional Commits、语义化版本或 `type/description` 分支命名时才沿用该约定。没有既有约定时，不要强行为整个项目迁移格式。

## 3. 忽略文件与二进制资产

> **适用条件与验证**：以已有 `.gitignore`、`.gitattributes`、制品策略、生成代码约定和合规要求为准。

🔴 **必须**：不得提交真实密钥、`.env` 中的敏感值、私钥、访问令牌、生产数据、临时 profile 或意外生成的构建产物。发现疑似敏感文件时停止并报告。

🟡 **推荐**：按项目约定忽略可再生的本地构建、覆盖率和编辑器临时文件；`go.work`、`vendor`、IDE 配置和生成代码是否提交不能一概而论，须遵从仓库事实。

🟢 **可选**：仓库已使用 Git LFS 且托管端允许时，按现有 `.gitattributes` 追踪指定的大型二进制资产。新增 LFS 类型、阈值或迁移历史都需要单独授权；不要凭固定文件大小或扩展名批量迁移。

## 4. 发布与标签

> **适用条件与验证**：仅在项目已有发布流程、模块版本或用户明确要求时适用。检查 tag 格式、模块路径、制品签名、发布审批和 CI 触发器。

🔴 **必须**：不得自行创建或推送 tag、发布制品、修改 release、推送镜像或变更版本号。发布版本与公开 API 兼容性必须按项目当前策略评估。

🟡 **推荐**：若项目发布 Go module 并采用语义化版本，保持模块主版本和导入路径的既有约定；若项目不对外发布 module，不要为此新增版本体系。

## 5. AI 的验证边界

> **适用条件与验证**：只运行当前环境可用、仓库已有且与改动相关的格式化、测试、构建或静态检查命令。

🔴 **必须**：不要对仓库根目录执行会写入所有 Go 文件的格式化命令来验证小改动；不要运行会自动升级依赖、重写历史或修改大量文件的命令。

🟡 **推荐**：对改动文件使用项目规定的格式化方式；先做只读检查，再执行最小相关测试或构建。交付时说明已执行的命令、未执行项和原因。

## 6. AI 完成检查

- [ ] 已查看 Git 状态、差异和仓库约定，且未触碰无关变更。
- [ ] 没有未经授权的提交、推送、tag、历史改写、LFS 迁移或删除操作。
- [ ] 已检查新增/修改文件不含敏感值、意外二进制或不应提交的本地产物。
- [ ] 已如实记录验证结果、未验证项和提交/发布风险。

> **例外**：用户明确授权的提交或发布仍应遵循仓库保护规则；有冲突、保护限制或敏感信息风险时先报告，不绕过控制。
