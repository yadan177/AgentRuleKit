# 13 - Go AI 通用入口规则

> 🟢 本文件适用于任何 AI 工具执行 Go 项目的开发、修改、审查、排障或文档任务。
>
> 🔴 不适用：替代项目事实、自动批准技术迁移、伪造构建或测试结果。

---

## 1. 使用方式

本文件是 Go 规则库的最小入口。AI 必须先遵守本文件，再按 [00 - 文档总览](./00-文档总览.md) 选择与任务相关的专题规则。

- 🔴 用户当前任务、工具安全限制和目标项目事实优先于通用建议。
- 🟡 只加载完成当前任务必要的专题文档，避免把整套规则作为不加区分的指令。
- 🟢 在不支持持久规则的工具中，可手动附加本文件和所需专题文档。

## 2. 项目能力探测

### 2.1 开始前检查

在编写或修改 Go 内容前，检查能够获得的以下证据：

1. `go.mod`、`go.work`、`go.sum`、`toolchain`、Go 版本与 build tag。
2. `Makefile`、`Taskfile`、脚本、CI、`go:generate` 与已有构建、测试、格式化命令。
3. `cmd/`、`internal/`、包边界、同包接口与既有实现。
4. 已安装的 HTTP/RPC、日志、数据库、配置、测试、观测与安全依赖。
5. migration、配置模板、容器/部署文件和已有运行环境约束。

### 2.2 决策规则

- 🔴 只调用项目已安装、版本兼容且已有证据支持的包、工具与 API。
- 🔴 沿用同包的错误处理、`context.Context` 传递、goroutine 生命周期、日志、测试和配置模式，除非用户明确授权重构。
- 🔴 Go 版本、依赖或运行环境无法判断时，说明不确定点；优先复用已有兼容实现，无法安全决策时询问用户。
- ❌ 不得把特定 Go 版本、Web/RPC 框架、日志库、ORM、测试框架、容器镜像或云平台设为本规则库的全局前提。

## 3. 变更边界

### 3.1 必须遵守的边界

- 🔴 未获明确授权时，不升级 Go、`toolchain`、依赖、`go.mod`、构建工具、框架或基础镜像。
- 🔴 未获明确授权时，不新增第三方依赖、不迁移 HTTP/RPC/日志/数据访问方案、不批量改动包结构或部署配置。
- 🔴 修改 API、数据和配置时，必须遵循已有契约、migration、密钥管理和发布流程。
- 🔴 goroutine、timer、ticker、channel、文件、连接、事务与请求上下文必须明确所有权、取消/关闭、超时和退出条件。

### 3.2 推荐做法

- 🟡 先完成最小可验证改动，再讨论可选重构或依赖替换。
- 🟡 性能优化先通过项目已有 benchmark、pprof、trace、日志或指标定位问题，再决定缓存、并发或内存优化。
- 🟡 对跨包、跨服务或跨语言改动，先写清调用方、契约所有者、失败处理与验证责任。

## 4. 禁止臆造

- ❌ 不得臆造模块路径、包已安装、环境变量、数据库表/字段、接口、消息主题、测试夹具、镜像或部署资源。
- ❌ 不得把规则示例中的包、函数、配置、命令、SQL 或测试当成项目已有内容。
- ❌ 未执行验证时，不得声称编译、测试、静态检查、打包、部署或安全扫描已经通过。

## 5. 验证与交付

### 5.1 验证要求

- 🔴 执行项目可用且与改动相称的验证；无法执行时说明原因、未验证范围和风险。
- 🔴 优先使用仓库已有脚本、Make/Task 目标或 CI 命令；不虚构 `go test ./...`、`go vet ./...`、Docker 或部署命令。
- 🔴 检查改动是否超出任务范围，新增依赖、配置、migration 和外部调用是否已经获得授权。
- 🟡 对并发、数据、安全、性能和部署改动给出需要在集成环境或生产前复核的项目清单。

### 5.2 交付说明

每次任务结束时，AI 应说明：

1. 修改了什么以及为什么。
2. 执行了哪些验证及其结果。
3. 哪些验证未执行、原因和剩余风险。
4. 需要用户确认的项目事实、迁移、密钥或外部协作事项。

## 6. 规则编写模板

新增或改写专题规则时使用以下结构：

```markdown
### N.M 规则名称

**适用条件**：项目满足的 Go 版本、依赖、框架、模块或运行环境前提。

🔴 **必须**：可执行的强制要求。

🟡 **推荐**：有条件的推荐做法。

🟢 **可选**：可按项目选择的方案。

**验证**：可检查的构建、测试、配置、日志、指标或审查操作。

**例外**：允许偏离规则的明确条件和处理方式。
```
