# 13 - Go AI 通用入口规则

> 🟢 适用于任何 AI 工具在 Go 项目中进行开发、审查、排障与规则维护。
> 🔴 不适用：替代仓库事实、自动批准依赖或架构迁移，或伪造验证结果。

---

## 1. 使用方式

本文件是 Go 规则库的执行入口。AI 先遵守本文件，再按 [00 - Go AI 编码规则总览](./00-文档总览.md) 和当前任务读取必要专题规则；它不替代 01 至 12 的完整经验、边界与示例。

- 🔴 **必须**将用户当前任务、仓库已有约束与工具安全限制置于通用建议之前。
- 🟡 **推荐**只加载当前任务直接相关的专题规则；不要把整个规则库误读为每次改动都必须重构的清单。
- 🟢 **可选**在一次性对话中手动附加本文件、总览和相关专题规则。

## 2. 项目事实检查

### 2.1 开始前证据

修改 Go 项目前，AI 应按任务检查可获得的下列证据：

1. `go.mod`、`go.sum`、Go 版本和 workspace 配置。
2. `Makefile`、`Taskfile`、CI 脚本、容器构建和已有验证命令。
3. 包目录、`internal/` 边界、接口与错误处理惯例、同模块既有实现。
4. 已采用的 HTTP/gRPC、数据库、迁移、日志、可观测性与配置方案。
5. 测试基线、目标部署环境、性能/安全要求和团队贡献约定。

### 2.2 决策边界

- 🔴 **必须**只调用项目已声明、版本兼容且有代码或配置证据支持的包与 API。
- 🔴 **必须**优先复用同模块已验证的 `context` 传播、错误包装、资源关闭、日志与测试模式。
- 🔴 **必须**在证据缺失时说明不确定点；无法安全判断时询问用户，不得以本规则库示例替代项目事实。
- ❌ **禁止**把 Web 框架、ORM、日志库、断言库、lint 工具或部署平台写成所有 Go 项目的默认前提。

## 3. 变更边界

### 3.1 未授权时不得改变的事项

- 🔴 未获明确授权时，不升级 Go 版本、替换框架、修改模块路径、重写构建链路或批量重构包结构。
- 🔴 未获明确授权时，不引入第三方依赖、不改动生成代码来源、不修改 CI/发布配置或秘密管理方式。
- 🔴 对 goroutine、连接、文件、事务、锁和取消信号，必须保持明确所有权和关闭/退出路径。
- 🔴 对外 API、数据库 schema、配置项和可观测性字段的兼容性影响必须先确认。

### 3.2 最小可验证改动

- 🟡 推荐先完成可验证的最小改动，再讨论抽象、性能优化或可选迁移。
- 🟡 性能问题先使用基准、pprof、trace 或项目既有指标定位，再决定缓存、并发或内存优化。
- 🟡 安全相关改动应先明确威胁模型、信任边界和线上配置，不能只凭代码示例下结论。

## 4. 专题规则选择

| 任务 | 优先阅读 |
|---|---|
| 包、函数、错误、context、goroutine 或资源释放 | 01、02、10 |
| 模块接口、可选参数、并发设计或测试组织 | 02、11 |
| 热路径、GC、并发、benchmark 或 pprof | 03 |
| HTTP、gRPC、认证接口或对外契约 | 04、12 |
| SQL、事务、迁移、连接池或存储 | 05、12 |
| `go.mod`、构建、CI、容器或依赖升级 | 06、09、10 |
| 日志、排障、指标、追踪或测试 | 07、11 |
| Git、版本、LFS 或提交前检查 | 08 |
| 认证、授权、加密、上传、外部请求或敏感数据 | 12 |

## 5. 验证与交付

- 🔴 **必须**执行项目中可用且与改动相称的验证；无法执行时必须说明原因、未验证范围和风险。
- 🔴 **必须**核对改动是否超出用户任务范围，新增依赖和兼容性变更是否获授权。
- 🟡 改动 Go 代码时，优先运行仓库现有格式化、静态检查、测试或构建命令；没有统一脚本时再按项目事实选择 `gofmt`、`go test`、`go vet` 等检查。

每次任务完成时，AI 应说明修改内容、执行的验证及结果、未验证范围与需要用户确认的项目事实。
