# 06 - JavaScript 项目配置规则

> 🟢 本文件适用于 JavaScript 项目的构建与配置（package.json/Vite/Webpack/ESLint）。

> 🔴 不适用：业务逻辑实现、API 设计

---



## 1. 配置选型总览

🔴 必查。**新建项目前**先按 5 维度选型:

| 维度 | 选项 | 选型建议 |
|---|---|---|
| **包管理器** | npm / yarn / pnpm / bun | 🟡 **pnpm**(workspace / 速度快) / npm(默认) |
| **构建工具** | webpack / vite / next.js / nuxt / remix | 🟡 **vite**(新项目)/ **next.js**(SSR/SSG)/ webpack(老项目) |
| **Linter** | ESLint + airbnb / standard / 自定义 | 🟡 **airbnb-base**(通用) / 项目自定 |
| **Formatter** | Prettier(dominant) | 🟢 **Prettier**(90% 项目的唯一选择) |
| **测试框架** | Jest / Vitest / Mocha | 🟡 **Vitest**(新项目)/ Jest(React 老项目) |
| **类型系统** | JS / TS | 按项目定(TS 见 `ts_rulers/`) |

🔴 **决策树**:

```
新项目?
├─ 仅前端 SPA / 静态站 → Vite + React/Vue + TS + Vitest + ESLint + Prettier
├─ SSR / SSG / SEO 重要 → Next.js + TS + ESLint + Prettier
├─ Node 后端 / 全栈 → Nest.js / Express + TS + Jest + ESLint + Prettier
├─ 微前端 / Monorepo → pnpm workspace + Turbo / Nx
└─ 老项目维护 → 沿用现有 stack,只补 ESLint / Prettier
```

🔴 **避免**:
- ❌ 新项目用 webpack + 自己配 React 模板(Vite 比这好 10 倍)
- ❌ TS 项目不开 ESLint `strict` 配置(等于没类型)
- ❌ SSR 项目用 SPA 选型(SEO 救不回来)

## 2. package.json 必填字段

### 2.1 最小化 package.json

🔴 必查。新项目从最小开始,按需加字段:

```json
{
  "name": "my-app",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "test": "vitest",
    "lint": "eslint . --fix",
    "format": "prettier --write ."
  },
  "dependencies": {
    "react": "^18.2.0"
  },
  "devDependencies": {
    "vite": "^5.0.0",
    "typescript": "^5.3.0",
    "eslint": "^9.0.0",
    "prettier": "^3.1.0",
    "vitest": "^1.0.0"
  },
  "engines": {
    "node": ">=18.0.0",
    "pnpm": ">=8.0.0"
  }
}
```

### 2.2 关键字段说明

🟡 推荐。

| 字段 | 作用 | 何时必填 |
|---|---|---|
| **`name`** | 包名（npm 唯一） | 必填 |
| **`version`** | semver 版本 | 必填（private 也需要） |
| **`private`** | 不发布到 npm | 内部项目 / 应用 |
| **`type`** | `"module"` 用 ESM,`"commonjs"` 用 CJS | 现代项目默认 `"module"` |
| **`scripts`** | CLI 命令 | 几乎必填 |
| **`dependencies`** | 生产依赖 | 几乎必填 |
| **`devDependencies`** | 开发依赖 | 几乎必填 |
| **`engines`** | Node / 包管理器版本 | CI 卡口 / 团队规范 |
| **`workspaces`** | monorepo | 单仓多包 |

### 2.3 dependencies vs devDependencies

🔴 必查。**生产代码用到的依赖放 dependencies**,**只在 build / test / lint 时用到的放 devDependencies**:

```json
{
  "dependencies": {
    "react": "^18.2.0",       // 生产代码用
    "react-dom": "^18.2.0",
    "axios": "^1.6.0"          // fetch 库
  },
  "devDependencies": {
    "vite": "^5.0.0",          // 只 build 用
    "typescript": "^5.3.0",    // 只 type-check
    "@types/react": "^18.2.0", // 只类型,生产代码看不到
    "vitest": "^1.0.0",        // 只 test
    "eslint": "^9.0.0"         // 只 lint
  }
}
```

🔴 **判断标准**:这个包运行时是否需要?运行 / 启动项目 → `dependencies`;只开发用 → `devDependencies`。

🟡 推荐用 [`depcheck`](https://www.npmjs.com/package/depcheck) 检测无用依赖。

### 2.4 版本范围

🟡 推荐。

| 范围 | 含义 | 何时用 |
|---|---|---|
| `^1.2.3` | >=1.2.3 <2.0.0（minor 升级） | 默认 ✅ 大多数依赖 |
| `~1.2.3` | >=1.2.3 <1.3.0（patch 升级） | 严格点 |
| `1.2.3` | exact | **绝不**用（锁死在 lockfile） |
| `>=1.2.3` | 任意上限 | 不推荐（可能有 breaking） |
| `*` | 任意 | 几乎不用 |

🔴 **`package.json` 不锁版本** —— lockfile 锁。`package.json` 只写"兼容范围"。

### 2.5 engines 字段与 CI 卡口

🟡 推荐。**engines 字段**让 CI / 团队成员用对的版本:

```json
{
  "engines": {
    "node": ">=18.0.0",
    "pnpm": ">=8.0.0"
  }
}
```

🔴 **CI 卡口** — 在 CI 加:

```yaml
# .github/workflows/ci.yml
- uses: pnpm/action-setup@v3
  with:
    version: 8
```

## 3. 包管理器与 lockfile

### 3.1 选型对比

🟡 推荐。

| 工具 | 优点 | 缺点 | 何时用 |
|---|---|---|---|
| **npm** | Node 自带、零配置 | 慢、磁盘浪费 | 默认 / 简单项目 |
| **pnpm** 🟡 推荐 | 快、磁盘省、workspace 强大 | 老项目迁移需测试 | **monorepo / 团队项目** |
| **yarn** | workspace / Plug'n'Play | 复杂、性能不如 pnpm | 老项目 |
| **bun** | 极快 | 新兴,兼容性需测 | 实验性项目 |

🔴 **团队项目统一一个包管理器** —— 不要混用,lockfile 不互通。

### 3.2 lockfile 必须提交

🔴 必查。**`package-lock.json`(npm)/ `pnpm-lock.yaml`(pnpm)/ `yarn.lock`(yarn) 必须 commit**。

```bash
# .gitignore 中不应忽略 lockfile
git add package-lock.json  # 必须 commit
```

🟡 推荐在 .gitignore 加 `.npmrc` 阻止意外删除:

```ini
# .npmrc
package-lock=true
```

### 3.3 pnpm workspace（monorepo）

🟡 推荐。**单仓多包**项目用 pnpm workspace:

```yaml
# pnpm-workspace.yaml
packages:
  - 'apps/*'
  - 'packages/*'
```

```
my-monorepo/
├── apps/
│   ├── web/            # 主前端
│   └── admin/          # 后台
├── packages/
│   ├── ui/             # 共享组件
│   ├── api-client/     # API 客户端
│   └── config/         # 共享 ESLint / TS 配置
├── package.json
└── pnpm-workspace.yaml
```

🟡 推荐用 **Turbo** 或 **Nx** 加速 monorepo 构建/测试。

### 3.4 workspaces 字段（npm / yarn）

🟡 推荐。

```json
{
  "workspaces": ["packages/*", "apps/*"]
}
```

🔴 **npm workspaces** + **pnpm workspace** 字段不同——混用会冲突。

## 4. ESLint 配置

### 4.1 ESLint 9+ flat config

🟡 对已使用 ESLint 9+、且没有既有兼容配置约束的项目，可优先评估 flat config（`eslint.config.js`）；具体配置格式仍以仓库现状为准：

```javascript
// eslint.config.js
import js from '@eslint/js';

export default [
  js.configs.recommended,
  {
    languageOptions: {
      ecmaVersion: 2022,
      sourceType: 'module',
    },
    rules: {
      // 自定义规则
      'no-console': 'warn',
      'prefer-const': 'error',
      'eqeqeq': ['error', 'smart'],  // 允许 == null
    },
  },
];
```

🟡 ESLint 9+ 项目可优先评估 flat config；已有 `.eslintrc.*`、共享配置或兼容性要求的项目应遵循现有链路。不要仅为新增一条规则混用两种配置系统或强制迁移。

### 4.2 经典 airbnb / Standard 风格包

🟡 推荐。已有团队风格或确有选型需要时，可评估现成包；先确认其与 ESLint 主版本及配置格式兼容：

| 风格包 | 适用 |
|---|---|
| `eslint-config-airbnb-base` | 通用 JS（30 条 Airbnb 条目） |
| `eslint-config-airbnb-typescript` | TS 项目 + Airbnb |
| `eslint-config-standard` | Standard JS 风格 |
| `eslint-config-next` | Next.js |
| `@typescript-eslint/eslint-plugin` | TS 特有规则 |

```javascript
// 先确认 airbnb-base 是否提供可直接使用的 flat config。
// 若只提供 legacy config，按官方迁移方式或项目已有兼容层接入，
// 不要假定它能用展开运算符直接放进 eslint.config.js。
```

🟡 风格包按项目现有约定选择；AI 不得默认推荐 `airbnb-base` 或用它覆盖现有规则。

### 4.3 TS 项目集成

🟡 推荐。

```javascript
// eslint.config.js
import js from '@eslint/js';
import tseslint from 'typescript-eslint';

export default [
  js.configs.recommended,
  ...tseslint.configs.recommended,
  {
    files: ['**/*.ts', '**/*.tsx'],
    languageOptions: {
      parser: tseslint.parser,
    },
    rules: {
      // TS 特有规则
      '@typescript-eslint/no-explicit-any': 'error',
      '@typescript-eslint/no-unused-vars': ['error', { argsIgnorePattern: '^_' }],
      '@typescript-eslint/consistent-type-imports': 'error',
    },
  },
];
```

详见 `ts_rulers/07-ESLint + Prettier TS 集成`（待写）。

### 4.4 关键 ESLint 规则

🟡 推荐。下表是 **AI 默认开启**的核心规则:

| 规则 | 含义 | 强度 |
|---|---|---|
| `prefer-const` | 优先 const | 🔴 error |
| `no-var` | 禁用 var | 🔴 error |
| `eqeqeq` | 必须 `===`(smart 允许 `== null`) | 🔴 error |
| `no-unused-vars` | 禁用未用变量 | 🔴 error |
| `no-console` | 禁用 console(默认 warn) | 🟡 warn |
| `no-debugger` | 禁用 debugger | 🔴 error |
| `@typescript-eslint/no-explicit-any` | 禁用 any | 🔴 error |
| `@typescript-eslint/consistent-type-imports` | 强制 type import | 🟡 warn |

## 5. Prettier 配置

### 5.1 基础配置

🟡 推荐。

```json
// .prettierrc
{
  "printWidth": 100,
  "tabWidth": 2,
  "useTabs": false,
  "semi": true,
  "singleQuote": true,
  "quoteProps": "as-needed",
  "trailingComma": "all",
  "bracketSpacing": true,
  "arrowParens": "always",
  "endOfLine": "lf"
}
```

🔴 **核心选项定下就别改** —— 否则团队代码风格漂移。

### 5.2 与 ESLint 冲突解决

🟡 推荐。Prettier 管格式,ESLint 管代码质量,**避免 ESLint 规则与 Prettier 重叠**:

```bash
# 安装 eslint-config-prettier 关闭冲突规则
npm install -D eslint-config-prettier
```

```javascript
// eslint.config.js
import prettier from 'eslint-config-prettier';

export default [
  // ... 其他规则
  prettier,  // 仅项目采用 Prettier 时加入，并放在冲突规则之后
];
```

🔴 **eslint-config-prettier 必须在最后** —— 否则前面的规则重新打开冲突。

### 5.3 .prettierignore

🟡 推荐。

```gitignore
# .prettierignore
node_modules
dist
build
.next
coverage
*.min.js
package-lock.json
pnpm-lock.yaml
```

## 6. 构建工具：webpack / vite / next.js

### 6.1 选型对比

🟡 推荐。

| 工具 | 类型 | 优势 | 劣势 | 适用 |
|---|---|---|---|---|
| **vite** | SPA / 静态站 | 极快（esbuild / Rollup） | SSR 弱 | 🟡 **新 SPA / 库** |
| **next.js** | 全栈 | SSR / SSG / 路由 / API | 体积大 | 🟡 **SSR / SEO 重要** |
| **nuxt** | Vue 全栈 | SSR / SSG | Vue only | Vue 项目 |
| **webpack** | 通用 | 配置最灵活 | 慢、配置复杂 | 老项目维护 |
| **esbuild** | 库 / 工具 | 极快 | 不支持完整 bundle | 库 / CLI 工具 |
| **rollup** | 库 | tree-shaking 强 | SPA 弱 | 🟡 **类库打包** |

### 6.2 vite 最小配置（推荐新项目）

🟡 推荐。

```typescript
// vite.config.ts
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  build: {
    target: 'es2020',
    sourcemap: true,
    rollupOptions: {
      output: {
        manualChunks: {
          // vendor 拆分
          'react-vendor': ['react', 'react-dom'],
        },
      },
    },
  },
  server: {
    port: 3000,
    proxy: {
      '/api': 'http://localhost:8080',
    },
  },
});
```

详见 `03-性能优化规则` § 7 打包与加载。

### 6.3 next.js 路由 + SSR

🟡 推荐。SSR / SEO 项目用 Next.js:

```typescript
// app/page.tsx (App Router)
export default function Home() {
  return <main>Hello, Next.js</main>;
}
```

🔴 **next.js 项目自带 ESLint 配置**(`.eslintrc.json` 含 `next/core-web-vitals`),**不要**自己重复配。

### 6.4 webpack 5 最小配置

🟡 推荐(老项目维护)。

```javascript
// webpack.config.js
module.exports = {
  mode: 'production',  // 'development' / 'production'
  entry: './src/index.ts',
  output: {
    path: __dirname + '/dist',
    filename: '[name].[contenthash].js',
  },
  module: {
    rules: [
      { test: /\.ts$/, use: 'ts-loader' },
      { test: /\.css$/, use: 'css-loader' },
    ],
  },
};
```

🔴 **新项目不推荐 webpack** —— vite 比它简单 10 倍,启动快 10 倍。

### 6.5 公共构建配置原则

🟡 推荐。所有构建工具通用:

- ✅ `[contenthash]` 文件名(long cache)
- ✅ 生产 source map(便于调试,但部署时限制访问)
- ✅ vendor 拆分(react / 业务代码分开)
- ✅ tree shaking(自动,前提是 ESM)
- ❌ 不要把 dev 配置混到生产

## 7. npm scripts 设计模式

### 7.1 标准 scripts 集合

🟡 推荐。

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "preview": "vite preview",
    "test": "vitest",
    "test:watch": "vitest --watch",
    "test:coverage": "vitest --coverage",
    "lint": "eslint .",
    "lint:fix": "eslint . --fix",
    "format": "prettier --write .",
    "format:check": "prettier --check .",
    "type-check": "tsc --noEmit",
    "validate": "npm run lint && npm run type-check && npm run test",
    "prepare": "husky install"
  }
}
```

🔴 **`validate` 脚本** 是核心 — 本地 + CI 都跑这一条。

### 7.2 pre / post hooks

🟡 推荐。npm 自带 `pre` / `post` 自动执行:

```json
{
  "scripts": {
    "build": "vite build",
    "prebuild": "npm run lint",
    "postbuild": "npm run notify-slack"
  }
}
```

执行 `npm run build` 自动跑顺序:`prebuild` → `build` → `postbuild`。

### 7.3 并发 / 串行

🟡 推荐。用 `npm-run-all` 或 `concurrently`:

```bash
npm install -D npm-run-all
```

```json
{
  "scripts": {
    "dev": "run-p dev:*",  // 并行所有 dev:* 脚本
    "dev:server": "node server.js",
    "dev:client": "vite",
    "dev:mock": "json-server --watch db.json"
  }
}
```

### 7.4 跨平台兼容

🟡 推荐。**Mac/Linux 用 `NODE_ENV=production`,Windows 不识别**:

```bash
npm install -D cross-env
```

```json
{
  "scripts": {
    "build": "cross-env NODE_ENV=production vite build"
  }
}
```

🔴 **AI 默认推荐 cross-env**,不写裸的 `NODE_ENV=...`。

### 7.5 CI 脚本

🟡 推荐。**CI 应该跑 validate + build**:

```yaml
# .github/workflows/ci.yml
- name: Validate
  run: npm run validate
- name: Build
  run: npm run build
```

🔴 **CI 不需要 devDependencies 安装太多** —— 用 `npm ci` 替代 `npm install`(严格按 lockfile):

```yaml
- name: Install
  run: npm ci
```

## 8. 环境变量与运行时配置

### 8.1 .env 文件体系

🟡 推荐。

```
.env                # 默认(所有环境共享,git-ignore)
.env.local          # 本地覆盖(每个开发者,git-ignore)
.env.development    # 开发环境(可 commit)
.env.production     # 生产环境(可 commit)
.env.test           # 测试环境(可 commit)
```

🔴 含密钥、令牌或环境私密值的 `.env*` 文件必须忽略并使用安全的交付方式；不含敏感数据的示例/公开配置是否入库由团队约定，并应与真实配置文件明确区分。

### 8.2 dotenv + 加载时机

🟡 推荐。若项目已使用 zod，可采用下面的 schema 示例；否则使用现有的校验库或显式校验函数。不要只为本节新增运行时依赖。

```typescript
// src/config.ts
import { z } from 'zod';

const ConfigSchema = z.object({
  VITE_API_URL: z.string().url(),
  VITE_SENTRY_DSN: z.string().optional(),
});

export const config = ConfigSchema.parse(import.meta.env);
```

🔴 环境变量必须在启动或构建边界完成与风险相称的运行时校验；TypeScript 类型、`.env` 文件或构建工具声明本身不能保证值正确。zod 只是其中一种实现。

### 8.3 build-time vs runtime

🟡 推荐。**关键区分**:

| 类型 | 何时替换 | 适用 |
|---|---|---|
| **build-time** | 构建时打包进去 | 公开配置、特性开关 |
| **runtime** | 启动时从环境 / 配置中心读 | 敏感配置、动态配置 |

```typescript
// ✅ build-time(import.meta.env)
const apiUrl = import.meta.env.VITE_API_URL;

// ✅ runtime(启动时读)
const secrets = await fetch('/api/secrets').then(r => r.json());

// ❌ 把密钥硬编码
const apiKey = 'sk-xxxx';  // git 历史暴露
```

🔴 **敏感信息永不进 .env**(应放运行时 secret 管理 —— Vault / AWS Secrets Manager / K8s Secret)。

### 8.4 环境分层

🟡 推荐。

| 环境 | 来源 | 谁改 |
|---|---|---|
| **代码常量** | 代码 | 开发 |
| **build-time 配置** | .env.production | DevOps |
| **runtime 配置** | 部署环境变量 | 运维 |
| **动态配置** | 配置中心 / API | 业务 / 运维 |

## 9. Docker 与构建产物约定

### 9.1 Dockerfile 必须多阶段构建

🔴 硬约束。**绝对不要写单阶段 Dockerfile**（镜像 1.5GB+，含源码、node_modules、devDependencies）。

```dockerfile
# ❌ 错误：单阶段构建，巨无霸镜像
FROM node:18
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build
EXPOSE 3000
CMD ["npm", "start"]
# 结果：镜像 > 1.5GB，含完整 node_modules、源码、devDependencies
```

```dockerfile
# ✅ 正确：多阶段构建，最终只有 nginx + dist
FROM node:18 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# 最终阶段只拿产物，其他都扔掉
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/nginx.conf
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
# 结果：镜像 < 50MB，只有静态产物，无源码无依赖
```

> 📌 规则：
> - 前端 Dockerfile 必须是至少 2 阶段：builder 阶段 + nginx 阶段
> - 不要在最终镜像里放 node / npm / 源码
> - 生产镜像用 nginx:alpine，不要用 node 镜像跑前端

### 9.2 构建产物目录名统一

🟡 推荐。**全项目统一输出目录名，不要每个项目一个名字**。

```javascript
// ❌ 错误：各种目录名，CI 脚本每个项目都要改
build/    // webpack 老项目
out/      // Next.js 默认
dist/     // vite 默认
output/   // 某人自定义

// ✅ 正确：统一用 dist/
// vite.config.ts
export default defineConfig({
  build: {
    outDir: 'dist',  // 统一用这个
  },
});

// 所有 CI / Docker 脚本都统一读 dist/
```

> 📌 规则：
> - 构建产物统一输出到 `dist/` 目录
> - 不要自定义其他名字，避免 CI 脚本每个项目都改
> - .gitignore 里必须忽略 `dist/`
