# 09 - JavaScript 版本控制规则

> 🟢 本文件适用于 JS/TS 项目的 Git 状态检查、提交准备、忽略规则和发布协作。
>
> 🔴 不适用：未经用户授权的提交、推送、tag、合并、历史改写、分支删除或 LFS 迁移。

---

## 1. 仓库工作流优先

> **适用条件与验证**：先读取 `AGENTS.md`、贡献指南、提交历史、分支保护、`.gitignore`、`.gitattributes`、CI 和发布说明。

🔴 **必须**：未经明确请求，不执行 `git commit`、`git push`、tag、rebase、force push、`git clean`、`git reset --hard` 或丢弃改动的命令。不得覆盖、暂存或回退用户无关变更。

## 2. 提交、分支与发布

> **适用条件与验证**：提交格式、分支模型、版本号、发布和审批均以仓库当前规则为准。

🔴 **必须**：提交/PR 说明如实描述实际改动与验证，不得伪造审查、测试或发布状态。公开 API、配置、迁移和安全影响要按仓库方式说明。

🟡 **推荐**：仅在仓库已采用 Conventional Commits、语义化版本或特定分支命名时沿用；不要为单次任务迁移整个团队工作流。

## 3. 忽略文件、生成物与 LFS

> **适用条件与验证**：以现有 `.gitignore`、制品策略、生成代码、工作区和托管平台能力为准。

🔴 **必须**：不得提交真实密钥、`.env` 敏感值、token、私钥、生产数据、意外生成物或临时 profile。发现疑似敏感文件时停止并报告。

🟡 **推荐**：`node_modules`、构建产物、覆盖率、编辑器配置、lockfile、生成代码和 LFS 的提交策略不能一概而论，必须遵从仓库事实。

## 4. AI 验证边界

🔴 **必须**：不要用可能全仓改写的格式化、依赖更新或生成命令验证局部改动。先做只读检查，再运行仓库已有且与本次变更相关的最小验证。

🟡 **推荐**：交付时说明实际执行的命令、未执行项和原因。
