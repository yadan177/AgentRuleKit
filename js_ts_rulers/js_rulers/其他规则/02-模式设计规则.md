# 02 - JavaScript 模式与架构规则

> 🟢 本文件适用于项目已有的模块边界、状态、依赖、领域逻辑和框架组件架构设计。
>
> 🔴 不适用：未经授权引入状态库、依赖注入容器、模式库、全局 store 或将前端/Node 项目机械套入固定分层。

---

## 1. 先识别当前架构

> **适用条件与验证**：检查现有包边界、数据流、状态所有者、请求层、组件/路由边界、依赖方向、调用方和测试。

🔴 **必须**：既有项目沿用当前架构边界；不得为单个需求新增 `service`、`repository`、store、factory、DI 容器或全局单例。跨包公开契约变更须获得授权并通过调用方验证。

## 2. 状态与副作用

> **适用条件与验证**：局部状态、共享状态、服务端数据缓存、持久化和副作用以当前框架与项目实现为准。

🔴 **必须**：状态必须有明确所有者与更新入口；异步副作用不能绕过项目已有请求、错误和取消边界。不得假定所有框架都要求同一种不可变更新或变更检测方式。

🟡 **推荐**：优先局部状态；仅当状态确实跨边界共享、需要缓存/同步或已有架构要求时使用项目既有共享状态方案。新增抽象前先确认真实调用方和可替换需求。

## 3. 抽象与依赖

> **适用条件与验证**：函数式、类、接口、组合、依赖注入和目录层级的选择以语言、框架、当前代码和维护成本为准。

🔴 **必须**：不得只为“未来扩展”创建接口、基类、工厂或容器；不得在依赖未明确时把实例创建、全局状态或网络调用散布到难以测试的边界。

🟡 **推荐**：当调用方只依赖少量行为、需要隔离外部系统、已有多实现或公开契约稳定时，再提取最小抽象。对 Node 服务端分层、前端组件分层和 BFF 结构分别遵从当前项目，而不是互相复制。

## 4. 验证与交付

- [ ] 已识别状态所有者、数据流、依赖方向和相邻实现。
- [ ] 没有为局部需求新增框架、全局状态或无依据的抽象层。
- [ ] 架构/契约调整有调用方、测试或集成验证。
- [ ] 已说明未验证边界与后续重构建议。
