# 03 - JavaScript 性能优化规则

> 🟢 本文件适用于浏览器、Node.js、组件渲染、DOM、内存、网络和构建性能问题的诊断与优化。
>
> 🔴 不适用：没有可复现问题或测量证据时，以“优化”为由引入缓存、worker、虚拟化、memo、复杂数据结构或打包迁移。

---

## 1. 证据优先

> **适用条件与验证**：目标设备、浏览器/Node 版本、真实负载、性能预算、profile、指标、trace、benchmark 和发布环境以项目事实为准。

🔴 **必须**：先明确用户可感知问题、测量方法和基线；优化后在相同或可比较条件下验证。不得把固定列表数量、固定 Web 指标、bundle 大小或单页请求数作为所有项目的硬门槛。

## 2. 浏览器与组件渲染

> **适用条件与验证**：仅在当前页面确有 DOM/渲染瓶颈且项目支持相应诊断时适用。

🟡 **推荐**：减少不必要的布局读写交错、超长主线程任务和不可见内容的工作；长列表、分页、懒加载、虚拟化或 memo 的选择以测量、可访问性、设备和交互语义为准。

🔴 **必须**：优化不能破坏焦点、键盘操作、滚动定位、动画偏好、数据一致性或错误/加载状态。

## 3. 内存、异步与网络

> **适用条件与验证**：事件、订阅、cache、请求、流、SSR、Service Worker 和资源释放以当前运行时和项目实现为准。

🔴 **必须**：泄漏判断以 profile、生命周期或可复现证据为准；创建的监听器、timer、请求与缓存要有清理/失效边界。不得把任何对象都放入 WeakMap、缓存或全局状态来“优化”。

🟡 **推荐**：对可取消的用户驱动请求沿用现有取消逻辑；缓存、预取、重试和离线策略须考虑数据新鲜度、网络成本、权限与失效。

## 4. Node 与构建性能

> **适用条件与验证**：仅在当前项目实际运行 Node 服务或维护构建链路时适用。

🔴 **必须**：不得凭直觉修改并发、worker、压缩、代码分割、polyfill、模块格式或构建器。Node 性能改动还须验证事件循环延迟、资源关闭、错误处理和目标运行环境。

## 5. AI 完成检查

- [ ] 已记录问题、基线、测量方式和优化后的结果。
- [ ] 没有未经授权的框架、缓存、worker 或构建迁移。
- [ ] 优化未破坏可访问性、正确性、资源生命周期和安全边界。
- [ ] 已说明未覆盖的设备、负载或生产验证风险。
