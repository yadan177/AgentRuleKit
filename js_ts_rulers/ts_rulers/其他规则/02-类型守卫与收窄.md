# 02 - TypeScript 类型守卫与收窄规则

> 🟢 本文件适用于网络、存储、表单、环境变量、插件、消息和 JavaScript 互操作带来的不可信数据收窄。
>
> 🔴 不适用：仅用 `as`、`!` 或 TypeScript 编译结果替代运行时输入验证，或未经授权引入 schema/validator 库。

---

## 1. 先定义运行时边界

> **适用条件与验证**：检查输入来源、服务端/第三方契约、项目已有 guard、schema、错误格式和当前 TypeScript 能力。

🔴 **必须**：跨越不可信边界的值先视为 `unknown`，再通过结构、范围、枚举和值关系验证后进入业务类型。只确认 `JSON.parse` 输入是字符串，不能证明解析结果满足某个业务接口。

## 2. 守卫、断言与错误语义

> **适用条件与验证**：`typeof`、`instanceof`、`in`、自定义谓词、判别联合和第三方校验以数据来源与现有项目实现为准。

🔴 **必须**：类型守卫应检查调用方真正依赖的字段和值，不得只检查对象非空就断言完整类型。失败路径必须符合项目既有错误、降级、日志和用户提示语义。

🟡 **推荐**：已有 schema/validator 时复用；没有时以最小、可测试的手写 guard 验证必要字段。`as` 仅用于已有证据无法被编译器表达的窄边界，并在附近说明依据。

## 3. 可空值与数组访问

> **适用条件与验证**：空值、数组索引、DOM 查询和配置缺失语义以实际数据模型和 tsconfig 严格度为准。

🔴 **必须**：不得用非空断言绕过可能不存在的元素、字段或异步结果；先处理缺失路径、默认值或错误分支。

## 4. AI 完成检查

- [ ] 已标识不可信输入边界和项目已有校验方式。
- [ ] 守卫验证了业务实际依赖的字段、类型和范围。
- [ ] 没有用 `any`、双重断言或非空断言掩盖输入问题。
- [ ] 成功与失败路径均有现有测试或可复现验证。
