# 01 - TypeScript 类型系统规则

> 🟢 本文件适用于项目已使用 TypeScript 的类型建模、公开 API、联合、泛型和类型维护。
>
> 🔴 不适用：把 TypeScript 当作运行时校验、无授权升级 TypeScript、批量替换 `type`/`interface`，或重写公开类型契约。

---

## 1. 类型前先确认契约

> **适用条件与验证**：检查当前 TypeScript 版本、tsconfig、生成代码、序列化、公开 API、同目录类型风格和调用方。

🔴 **必须**：类型必须表达已经确认的运行时和业务契约；不得凭名称臆造字段、可选性、空值、枚举值或返回类型。外部数据在运行时验证前仍是不可信的 `unknown`，不能用断言直接变为业务类型。

## 2. 建模与公开边界

> **适用条件与验证**：`type`、`interface`、class、enum、字面量对象、联合和品牌类型的选择以当前项目、运行时输出和调用方需求为准。

🔴 **必须**：公开类型、参数、返回值和错误语义的变更必须评估下游兼容性；不要为了“统一风格”批量改写现有 `type`/`interface`、enum 或推断写法。

🟡 **推荐**：用可区分联合表达有限状态；以清晰的具体类型优先，只有真实复用和稳定契约需求时再引入泛型、品牌类型或复杂工具类型。

## 3. `any`、断言与推断

> **适用条件与验证**：现有 lint、类型守卫、schema、声明文件和错误边界以项目配置为准。

🔴 **必须**：`any`、双重断言、非空断言和宽泛类型断言不能用来掩盖未知输入或编译错误。类型推断可用于项目已有的局部代码；公开/复杂边界是否显式标注由项目约定和可读性决定。

🟡 **推荐**：需要运行时保证时使用 [02-类型守卫与收窄](./02-类型守卫与收窄.md) 中项目已采用的校验方式；不要因规则示例新增 lint 插件或 schema 库。

## 4. 泛型与类型复杂度

🔴 **必须**：不得仅为减少少量重复而引入多层泛型、条件类型或难以理解的约束。公开泛型 API 需要考虑推断质量、错误信息和调用方兼容性。

🟡 **推荐**：先选具体类型、联合或小接口；当多个真实调用点有相同抽象且可通过 typecheck/调用方证明时再泛化。

## 5. AI 完成检查

- [ ] 类型与现有运行时契约、生成物和调用方一致。
- [ ] 外部数据未通过断言绕过运行时校验。
- [ ] 未为局部改动批量改变类型风格、tsconfig 或公开 API。
- [ ] 已执行相关 typecheck 与调用方验证，或说明未验证项。
