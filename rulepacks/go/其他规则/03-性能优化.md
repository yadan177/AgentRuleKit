# 03 - Go 性能优化

> - 🟢 本文件适用于 Go 项目的性能优化（热路径/内存分配/GC 等）。
> - 🔴 不适用：业务逻辑实现、UI 样式细节、第三方业务 SDK

---

参考来源：[Uber Go Style Guide 的 Performance 章节](https://github.com/uber-go/guide/blob/1d60a91aa5e87d443002e23c21903c49489dbde5/style.md#performance)（[上游 Apache-2.0 许可](https://github.com/uber-go/guide/blob/1d60a91aa5e87d443002e23c21903c49489dbde5/LICENSE)）。下文热路径原则为中文译述；`fmt`/`strconv`、重复字符串转字节切片及容器预分配的部分示例沿用或改写自该章节。其余具体建议仍以目标项目测量结果为准。

## 1. 何时优化（最重要的规则）

🔴 必加约束：**未测量，不优化**

> 性能相关的指导**仅适用于热路径**（hot path）。
> —— [Uber Go Style Guide，Performance 章节](https://github.com/uber-go/guide/blob/1d60a91aa5e87d443002e23c21903c49489dbde5/style.md#performance)（中文译述）

**绝大多数代码不需要性能优化**。**过早优化**是万恶之源——会让代码变复杂、可读性变差、维护成本上升，**却没有可测量的收益**。

### 1.1 优化前的问题

1. **用户或系统指标是什么？** 明确延迟、吞吐、CPU、内存、分配、GC、包体或成本目标。
2. **证据指向哪里？** 根据问题选择生产指标、trace、pprof、benchmark 或负载测试，不固定只用 pprof。
3. **变更在代表性负载下有收益吗？** 对比变更前后的目标指标、正确性和资源取舍。

没有明确目标或可重复证据时，先补测量，不直接改写代码。低频路径也可能因单次耗时、内存峰值或安全风险需要优化，不以“每秒 1000 次”设通用门槛。

### 1.2 优化顺序（先低风险，后高风险）

```
1. 确认语义、负载和瓶颈证据
2. 优先减少不必要的工作、I/O 和复杂度
3. 再评估数据结构、批处理、缓存、预分配或 API 替换
4. 对象池、unsafe、汇编和架构变更只在证据充分且回归完整时使用
```

顺序不是收益大小保证；选择以当前瓶颈、风险和可验证性为准。

## 2. pprof 信号识别（什么时候哪里慢）

🟡 CPU、heap、分配、锁或 goroutine 问题适合使用 pprof；单请求跨服务延迟、调度时序、系统调用或外部 I/O 可能需要 trace、指标或其他项目工具。

### 2.1 CPU profile

```bash
# 端点必须是项目已授权并受保护的诊断地址；采集时长按问题选择。
go tool pprof 'http://localhost:6060/debug/pprof/profile?seconds=30'
```

**信号**：

- **`runtime.scanobject`** 占比高：检查活对象规模、指针密度、GC 频率与分配速率，不直接归因为某一种代码。
- **`runtime.mallocgc`** 占比高：通过 alloc profile 定位分配来源，再评估减少工作、预分配或复用；不默认引入 `sync.Pool`。
- 某个业务函数占比高：继续下钻到调用和输入，区分必要成本、算法、I/O 和锁等待。

### 2.2 内存 profile

```bash
# heap profile（默认单位：字节）
go tool pprof http://localhost:6060/debug/pprof/heap

# 看哪些对象分配最多
(pprof) top 10
(pprof) list <funcname>  # 看某函数具体的分配
```

**信号**：

- **`inuse_space`** 对比多个可比时点后仍增长：可能是正常缓存/负载变化，也可能是引用未释放；需要结合 GC、流量和对象所有权判断。
- **`alloc_space`** 是累计分配量：重点是在同等负载和采样窗口下比较分配速率与来源，不能因数值随时间增长就判定异常。

### 2.3 goroutine profile

```bash
go tool pprof http://localhost:6060/debug/pprof/goroutine
```

**信号**：

- goroutine 数持续异常增长 → 检查没有停止信号、取消传播或所有权不清的 goroutine，参见 [01 - goroutine 与并发](./01-代码编写规则.md#3-goroutine-与并发)

### 2.4 三个关键指标

| 指标 | 命令 | 关心的信号 |
|---|---|---|
| **CPU** | `pprof profile` | 哪个函数耗时最多 |
| **内存分配** | `pprof heap` | 哪个对象 / 哪行代码分配最多 |
| **goroutine 数** | `pprof goroutine` | 是否泄漏 |

> 详细 pprof 教程见 [Go 官方博客：Profiling Go programs](https://go.dev/blog/pprof)

### 2.5 trace（高级）

Go execution trace 记录采集窗口内的 goroutine 调度、GC、syscall 和网络阻塞等运行时事件。它不自动等同于单请求的分布式链路；请求关联需要项目自身的 trace 或标识。

```bash
# 1. 示例：采集 5 秒；窗口越长，数据量和运行开销越大
curl -o trace.out http://localhost:6060/debug/pprof/trace?seconds=5

# 2. 用 go tool trace 打开（启动浏览器查看）
go tool trace trace.out
```

> 注意：trace 是独立工具，不走 pprof。`go tool trace` 会启动本地 Web UI，可以查看 goroutine 调度、GC 暂停、网络阻塞、syscall 等细粒度时间线。

### 2.6 在线服务接入 pprof 的安全提示

- 🔴 pprof 包含内存、goroutine、命令行和代码路径等敏感运行信息，不得公开暴露。
- 🔴 沿用项目已有的诊断端口、网络隔离、身份验证、授权和审计方式；单独绑定回环地址可以降低暴露面，但不替代部署边界检查。
- 🟡 项目已采用持续 profiling 平台时沿用其采样、脱敏和访问控制；不因本节引入 Pyroscope、Parca 或其他依赖。

## 3. 字符串与字节转换

🔴 必加约束：热路径上的字符串 / 字节操作必须遵守本节

### 3.1 优先使用 `strconv` 而非 `fmt`

```go
// 需要格式化能力时使用 fmt；仅做数值转换时语义过重
s := fmt.Sprint(rand.Int())

// 仅做整数到字符串转换时，使用对应的类型化 API
s := strconv.Itoa(rand.Int())
```

性能差异取决于 Go 版本、输入和调用上下文。确认是热路径后，应以 benchmark 和 profile 结果决定是否使用 `strconv`：

| 转换 | `fmt` | `strconv` |
|---|---|---|
| `int → string` | `fmt.Sprint(i)` | `strconv.Itoa(i)` |
| `string → int` | `fmt.Sscanf(s, "%d", &i)` | `strconv.Atoi(s)` |
| `float → string` | `fmt.Sprint(f)` | `strconv.FormatFloat(f, 'f', -1, 64)` |
| `bool → string` | `fmt.Sprint(b)` | `strconv.FormatBool(b)` |

> `fmt.Sprintf("%v", x)` 提供通用格式化语义；仅在确实需要该语义时使用，热路径性能以测量结果为准。

### 3.2 避免重复字符串与字节切片转换

```go
// 反例：在循环中重复转换
for i := 0; i < b.N; i++ {
    w.Write([]byte("Hello world"))
}

// 正例：数据不变时在循环外转换并复用
data := []byte("Hello world")
for i := 0; i < b.N; i++ {
    w.Write(data)
}
```

是否产生分配及收益大小受 Go 版本和编译上下文影响；修改前后使用项目基准测试确认。

### 3.3 `string` ↔ `[]byte` 的拷贝成本

🟡 推荐

- `[]byte` → `string`：`string(b)` 遵守字符串不可变语义，通用情况下不能保证无拷贝；只有在具体编译器、版本和上下文确认消除分配时，才可把它视为优化结果。
- `string` → `[]byte`：结果具有可修改的字节切片语义，通用代码不能假设无拷贝；避免在热路径反复转换，并以具体编译器结果为准
- **构造修改后的字符串**：字符串本身不可变；根据操作选择 `strings` API、`strings.Builder`、`[]byte` 或 `[]rune`，并注意字节与 Unicode 码点语义。

```go
// 反例：两边本来都是字符串，却在循环中转成 []byte
prefixBytes := []byte("/api/")
for _, path := range paths {
    if bytes.HasPrefix([]byte(path), prefixBytes) { /* ... */ }
}

// 正例：直接使用字符串 API
prefixText := "/api/"
for _, path := range paths {
    if strings.HasPrefix(path, prefixText) { /* ... */ }
}
```

## 4. 容器预分配

🟡 在热路径、集合规模较大或分析确认扩容成本有意义时，按可靠的长度或上限预分配。不要仅因“知道上限”就为稀疏或不可信输入分配大块内存；收益与内存峰值需要通过 benchmark/profile 验证。

### 4.1 map 容量提示

```go
// 输入 files 已在测量范围外加载并检查过错误。
// 未提供容量提示：map 可能多次增长
withoutHint := make(map[string]os.DirEntry)
for _, f := range files {
    withoutHint[f.Name()] = f
}

// 文件数量可靠且内存预算允许时，提供容量提示
withHint := make(map[string]os.DirEntry, len(files))
for _, f := range files {
    withHint[f.Name()] = f
}
```

**注意**：map 的容量提示**不是硬保证**——只是 hint。即使容量未满，添加元素时仍可能发生分配（用于 hashmap 桶调整）。

### 4.2 slice 容量（关键）

```go
// 未预分配：append 可能触发多次扩容
data := make([]int, 0)
for k := 0; k < size; k++ {
    data = append(data, k)
}

// 规模可靠时，可预分配容量
data := make([]int, 0, size)
for k := 0; k < size; k++ {
    data = append(data, k)
}
```

预分配可减少扩容和元素搬移，但具体收益取决于元素类型、规模和运行环境，示例数字不能作为通用结论。`make([]T, 0, cap)` 保证初始容量至少为 `cap`；在长度未超过该容量且底层数组未被其他操作替换时，`append` 不会因扩容重新分配底层数组。

**与 `make([]T, length)` 的区别**：

```go
make([]T, 0)       // 长度 0，容量 0
make([]T, length)  // 长度 = capacity = length
make([]T, 0, cap)  // 长度 0，容量 cap（可 append 到 cap）
```

**热路径上**：

- 知道最终长度且会按索引填充 → `make([]T, length)`
- 知道上限但边 append 边填充 → `make([]T, 0, cap)`

### 4.3 `sync.Pool` 复用临时对象（高级）

🟡 只有 profile/benchmark 证明临时对象分配是瓶颈，且复用不会保留过大内存、泄漏敏感数据或破坏所有权时，才评估 `sync.Pool`。

```go
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func process(data []byte, maxPooledCapacity int) {
    buf := bufPool.Get().(*bytes.Buffer)
    defer func() {
        if maxPooledCapacity <= 0 || buf.Cap() > maxPooledCapacity {
            return
        }
        buf.Reset()
        bufPool.Put(buf)
    }()
    buf.Write(data)
    // ...
}
```

**注意**：

- `sync.Pool` 里的对象**随时可能被 GC 清空**——不能依赖它存数据
- 放回前必须重置所有可观测状态；容量过大的 buffer 是否回池需设上限
- **不要**用它管理**带状态的长生命周期对象**（连接池用其他方案）

## 5. 反射与类型断言的成本

🟡 推荐

### 5.1 反射（reflect）的成本

反射会弱化部分编译期类型保证，并可能带来间接调用、分配或无法内联的路径。实际成本取决于 API、Go 版本、输入和调用频率，不写成通用 `10-100x`。

**使用原则**：

- 序列化、框架和工具代码可以合理使用反射，但需保留错误边界和测试。
- 热路径中如果反射已被证明是瓶颈，再比较具体类型 API、接口、泛型或代码生成，不默认某一方案更快。

```go
// 反例：热路径用反射
func process(v any) {
    rv := reflect.ValueOf(v)
    // ... 复杂逻辑
}

// 可选方案：语义适合且项目 Go 版本支持时评估泛型
func process[T any](v T) {
    // 仍需用 benchmark 验证目标 Go 版本的实现和性能
}
```

### 5.2 类型断言的成本

- 类型断言和 `reflect` 的目的与能力不完全等价，不仅凭“快/慢”替换。
- 已知具体候选类型时，类型断言或 type switch 通常更直接；处理未知运行时结构时反射可能是必要能力。

```go
// 热路径上：用类型断言，不用 reflect
if s, ok := x.(string); ok {
    return s
}
```

### 5.3 JSON 序列化

- 沿用项目现有 JSON 实现和契约；性能比较必须包含真实结构、数据分布、错误行为、数字/时间语义和安全边界。
- 不从本节引入 `json-iterator/go`、`easyjson` 或其他库，也不宣称通用 `5-10x` 收益。
- 项目已采用第三方库或代码生成时，升级后要用兼容性测试和 benchmark 同时验证，不只比吞吐。

## 6. benchmark 怎么写

🔴 修改热路径后必须使用与原问题匹配的变更前/后测量验证。可隔离的 CPU/分配逻辑适合 benchmark；跨服务 I/O、并发、内存峰值或尾延迟可能需要 profile、trace 或代表性负载测试。

### 6.1 基本模板

```go
// 1、benchmark 函数名以 BenchmarkXxx 开头
// 2、参数 *testing.B
// 3、内部用 for i := 0; i < b.N; i++ { ... } 控制循环
func BenchmarkSplitHostPort(b *testing.B) {
    // 准备测试数据（不计入 benchmark 时间）
    input := "192.0.2.0:8000"

    // 重置 timer（如果准备阶段有分配）
    b.ResetTimer()

    for i := 0; i < b.N; i++ {
        _, _, _ = net.SplitHostPort(input)
    }
}
```

### 6.2 运行 benchmark

```bash
# 跑单个 benchmark
go test -bench=BenchmarkSplitHostPort -benchmem

# 跑包内所有 benchmark
go test -bench=. -benchmem

# 跑多次取平均（更稳定）
go test -bench=BenchmarkXxx -benchmem -count=10

# 比较两个版本：仅当项目已安装 benchstat 或用户授权时使用
# 1、当前代码保存
go test -bench=BenchmarkXxx -benchmem -count=10 > old.txt
# 2、改完代码
go test -bench=BenchmarkXxx -benchmem -count=10 > new.txt
# 3、对比
benchstat old.txt new.txt
```

### 6.3 benchmark 编写规范

🟡 推荐

- 准备成本是否计入基准取决于测量目标；需排除时用当前 Go 版本支持的 timer API 明确边界
- 让结果可观测，避免整个被编译器消除；可用结果校验、合理 sink 或 `runtime.KeepAlive`，不强制所有 benchmark 写 package 级变量
- 并发行为是测量目标时，可用 `b.RunParallel`
- 需比较多个输入或实现时，可用 `b.Run("case_name", func(b *testing.B) { ... })`

```go
var result string  // 防止编译器优化掉

func BenchmarkConcat(b *testing.B) {
    b.Run("plus", func(b *testing.B) {
        for i := 0; i < b.N; i++ {
            result = ""
            for j := 0; j < 100; j++ {
                result += "x"
            }
        }
    })
    b.Run("builder", func(b *testing.B) {
        for i := 0; i < b.N; i++ {
            var sb strings.Builder
            for j := 0; j < 100; j++ {
                sb.WriteString("x")
            }
            result = sb.String()
        }
    })
}
```

### 6.4 跑 benchmark 必看 3 个指标

```
BenchmarkConcat-8   1000000   1234 ns/op   128 B/op   2 allocs/op
^^^^^^^^^^^^^^^^^   ^^^^^^^   ^^^^^^^^^^   ^^^^^^^^   ^^^^^^^^^^^
基准名/GOMAXPROCS      迭代数      每操作时间    分配字节    分配次数
```

- **`ns/op`**：每次操作耗时（越低越好）
- **`B/op`**：每次操作分配字节数（越低越好）
- **`allocs/op`**：每次操作分配次数（越低越好）

> 优先级取决于目标：延迟/吞吐看 `ns/op`，分配与 GC 问题看 `B/op` 和 `allocs/op`，并结合稳定性、样本数和差异显著性。

## 7. 常见热路径反模式

🔴 必加约束：热路径上**避免**这些写法

### 7.1 用 `+` 拼大量字符串

```go
// 反例：每次 + 都产生新 string + 拷贝
for i := 0; i < 10000; i++ {
    s += strconv.Itoa(i)
}

// 正例：用 strings.Builder 或 strings.Join
var sb strings.Builder
sb.Grow(estimatedSize) // 只在有可靠估算时预分配
for i := 0; i < 10000; i++ {
    sb.WriteString(strconv.Itoa(i))
}
s := sb.String()
```

重复 `+=` 可能反复分配和拷贝；收益取决于输入数量、字符串长度、Go 版本和编译器，不使用通用 `100x+` 结论。

### 7.2 用 `fmt.Sprintf` 拼字符串

```go
// 语义清晰的格式化写法；只在 profile 确认为瓶颈时考虑替换
s := fmt.Sprintf("user %s (id=%d) created at %s", name, id, time.Now())

// 可选写法：更快与否以目标 Go 版本的 benchmark 为准
s := "user " + name + " (id=" + strconv.Itoa(id) + ") created at " + time.Now().Format(time.RFC3339)

// 多个变量时：strings.Builder
var sb strings.Builder
sb.WriteString("user ")
sb.WriteString(name)
sb.WriteString(" (id=")
sb.WriteString(strconv.Itoa(id))
sb.WriteString(") created at ")
sb.WriteString(time.Now().Format(time.RFC3339))
s := sb.String()
```

### 7.3 defer 在热路径

🟡 默认使用 `defer` 保证资源释放。只在 profile/benchmark 证明其是有意义的热点，且改写后所有返回、panic 与解锁路径仍正确时，才考虑手动释放。

```go
// 普通代码：defer 是好的（可读性 >> 性能）
p.Lock()
defer p.Unlock()

// 仅当当前代码块无提前返回，且测量证明有收益时考虑手动解锁
p.Lock()
// ... 操作
p.Unlock()
```

> `defer` 的额外开销通常很小；仅在性能分析已证明其处于纳秒级热点时再考虑替代方案。默认优先保证资源释放与可读性。

### 7.4 在循环里 append 字符串

```go
// 反例：循环里 += 字符串
for _, v := range values {
    s += v
}

// 正例：Builder
var sb strings.Builder
for _, v := range values {
    sb.WriteString(v)
}
s := sb.String()
```

### 7.5 `range` 复制大切片 / 大结构体

🟡 大结构体的 range 值拷贝可能有成本，但改用指针会改变可变性、别名和逃逸行为。只在语义允许且测量证实有收益时修改。

```go
// 值语义：每次迭代拷贝结构体
for _, item := range bigStructs {
    process(item)
}

// 指针语义：确认允许别名和修改元素后才使用
for i := range bigStructs {
    process(&bigStructs[i])
}
```

### 7.6 频繁创建临时 slice / map

```go
// 返回独立快照时，新 map 可能是正确的所有权设计。
func (s *Stats) Snapshot() map[string]int {
    m := make(map[string]int, len(s.data))
    for k, v := range s.data {
        m[k] = v
    }
    return m
}
```
