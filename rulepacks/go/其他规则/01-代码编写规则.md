# 01 - Go 代码编写规则

> - 🟢 本文件适用于 Go 代码的基础编写规范（命名/错误处理/并发/资源管理等）。
> - 🔴 不适用：项目级架构决策、第三方库深度用法、CI/CD 流水线配置

---

## 1. 命名规范

### 1.1 包命名

🔴 必加约束

- **全部小写**，不混用大写 / 下划线 / 中划线
- **简短精炼**——包名会在每个调用点完整写出（`http.Get` 而非 `httpclient.Get`）
- 单数或复数由领域含义决定；标准库中的 `bytes`、`errors`、`strings`、`slices`、`maps` 都是合理命名，不能统一禁止复数。
- 避免职责不清的 `common` / `util` / `shared` / `lib` / `helpers` / `misc`；仓库已有且职责明确的包不应仅因名称被机械重命名。

| 反例 | 正例 |
|---|---|
| `package url_utils` | `package urlutil` |
| `package common`（无信息量） | 按职责拆：`package auth` / `package logging` / `package retry` |

### 1.2 函数与变量命名

🔴 必加约束

- 采用 **MixedCaps**（大驼峰或小驼峰），不用下划线
- **测试函数例外**：可包含下划线以分组用例——`TestParse_EmptyInput`

### 1.3 import 别名

🟡 推荐

- **包名 ≠ import 路径最后一段**时才必须用别名
- **存在 import 冲突**时才用别名
- 除此之外**避免**别名（让包名直接读出来）

```go
// 反例：为了"清晰"加别名，但增加了心智负担
import (
    runtimetrace "runtime/trace"
    nettrace    "golang.net/x/trace"
)

// 正例：只在包名冲突或不可读时才加
import (
    "runtime/trace"
    nettrace "golang.net/x/trace" // 必须：包名 nettrace 已存在
)
```

### 1.4 import 分组排序

🔴 必加约束

**两组**：标准库 / 其他全部。`goimports` 默认就是这个分组。

```go
import (
    "fmt"
    "os"

    "example.com/project/internal/trace"
)
```

### 1.5 相似声明分组

🟡 推荐

- 相关的 `const` / `var` / `type` / `import` **放进同一个 `()` 块**
- **不要硬凑**——无关的声明保持分组外的单独声明

```go
// 正例：相关常量成组
const (
    defaultPort = 8080
    defaultHost = "localhost"
)

// 正例：无关常量分别成组
const (
    Add    Operation = iota + 1
    Subtract
    Multiply
)

const envVar = "MY_ENV" // 单独声明，与 Operation 无关
```

### 1.6 未导出顶层变量命名

🟡 推荐

- 未导出的顶层 `var` / `const` 使用小写首字母即可；命名应遵循 Go 的 MixedCaps 惯例，不要求添加 `_` 前缀。
- **错误值**通常使用有意义的 `err` 前缀或后缀（与 § 2.3 错误命名配合）。

```go
// 正例
const (
    defaultPort = 8080
    defaultHost = "localhost"
)

var errNotFound = errors.New("not found") // 错误值例外
```

### 1.7 避免内建名

🔴 必加约束

**绝不**用 Go 预声明标识符（`error` / `string` / `int` / `len` / `cap` / `new` / `make` 等）作变量 / 字段 / 函数名。

```go
// 反例：遮蔽内建
var error string
func handleErrorMessage(error string) {}

// 正例
var errorMessage string
func handleErrorMessage(msg string) {}
```

> `go vet` 不会报错（合法但糟糕），但用 `_` 之类变量名仍是强烈反模式。

## 2. 错误处理

### 2.1 错误类型选择

🔴 必加约束

| 错误匹配 | 错误信息 | 选用 |
|---|---|---|
| ❌ 不需要 | 静态字符串 | `errors.New("...")` |
| ❌ 不需要 | 动态字符串 | `fmt.Errorf("...: %v", ...)` |
| ✅ 需要 | 静态字符串 | 顶层 `var ErrXxx = errors.New("...")` |
| ✅ 需要 | 动态字符串 | 自定义 `error` 类型（实现 `Error() string`） |

```go
// 不需要匹配
func Open() error {
    return errors.New("could not open")
}

// 需要匹配（导出错误变量供 errors.Is 使用）
var ErrCouldNotOpen = errors.New("could not open")

func Open() error {
    return ErrCouldNotOpen
}

// 调用方
if err := foo.Open(); err != nil {
    if errors.Is(err, foo.ErrCouldNotOpen) { /* ... */ }
}
```

### 2.2 错误包装（`%w` vs `%v`）

🔴 必加约束

- **`%w`**：调用方需要 `errors.Is` / `errors.As` 匹配底层错误时
- **`%v`**：需要**隐藏**底层错误时（不想让上游匹配）
- **不要**用"failed to"等废话前缀——会随调用栈堆叠成"failed to x: failed to y: ..."

```go
// 反例：堆叠冗余前缀
return fmt.Errorf("failed to create new store: %w", err)
// 上游会得到: "failed to x: failed to y: failed to create new store: ..."

// 正例：简洁 + 包装
return fmt.Errorf("new store: %w", err)
```

### 2.3 错误命名

🔴 必加约束

| 类型 | 命名 | 示例 |
|---|---|---|
| 导出错误变量 | `ErrXxx` | `ErrCouldNotOpen` |
| 私有错误变量 | `errXxx`（小写） | `errNotFound` |
| 自定义错误类型 | `XxxError`（导出）/ `xxxError`（私有） | `NotFoundError` / `resolveError` |

```go
var (
    ErrBrokenLink   = errors.New("link is broken")    // 导出
    ErrCouldNotOpen = errors.New("could not open")    // 导出
    errNotFound     = errors.New("not found")         // 私有
)

type NotFoundError struct { File string } // 导出类型
type resolveError struct { Path string }  // 私有类型
```

### 2.4 错误只处理一次

🔴 必加约束

**每个错误只应被处理一次**。不要既 `log.Printf` 又 `return err`——上游还会再处理一次，造成日志噪音。

四种正确处理方式：

1. **包装返回**（最常见）：`return fmt.Errorf("get user %q: %w", id, err)`
2. **匹配后降级**：`if errors.Is(err, ErrUserNotFound) { ... }`
3. **记录并降级**（操作非关键）：`log.Printf("...: %v", err); continue`
4. **匹配 + 部分降级 + 其他包装返回**：

```go
tz, err := getUserTimeZone(id)
if err != nil {
    if errors.Is(err, ErrUserNotFound) {
        tz = time.UTC // 已知错误：降级
    } else {
        return fmt.Errorf("get user %q: %w", id, err) // 未知错误：包装返回
    }
}
```

### 2.5 处理类型断言失败

🔴 必加约束

**始终**用 `comma ok` 形式。单返回值形式断言失败会 panic。

```go
// 反例：失败时 panic
t := i.(string)

// 正例
t, ok := i.(string)
if !ok {
    return fmt.Errorf("expected string, got %T", i)
}
```

## 3. goroutine 与并发

### 3.1 不要"开火后不管"的 goroutine

🔴 必加约束

**生产代码中不要泄漏 goroutine**。每个 goroutine 必须满足：

1. 有可预测的停止时间，**或**
2. 有方式发出停止信号

两种情况都必须有方式阻塞并等待它结束。

```go
// 反例：无法停止
go func() {
    for {
        flush()
        time.Sleep(delay)
    }
}()

// 正例：可停止 + 可等待
var (
    stop = make(chan struct{})
    done = make(chan struct{})
)
go func() {
    defer close(done)
    ticker := time.NewTicker(delay)
    defer ticker.Stop()
    for {
        select {
        case <-ticker.C:
            flush()
        case <-stop:
            return
        }
    }
}()

close(stop) // 通知停止
<-done      // 等待退出
```

**检测 goroutine 泄漏**：在可能启动 goroutine 的包内用 [`goleak`](https://pkg.go.dev/go.uber.org/goleak)。

### 3.2 等待 goroutine 退出

🟡 推荐

- **单个 goroutine**：用 `chan struct{}` 关闭信号
- **多个 goroutine**：用 `sync.WaitGroup`

```go
// 单个
done := make(chan struct{})
go func() {
    defer close(done)
    // ...
}()
<-done

// 多个
var wg sync.WaitGroup
for i := 0; i < N; i++ {
    wg.Add(1)
    go func(i int) {
        defer wg.Done()
        // ... 使用 i 做实际工作
    }(i)
}
wg.Wait()
```

### 3.3 `init()` 中不要启动 goroutine

🔴 必加约束

- `init()` 中**绝不**`go ...`
- 需要后台 goroutine 的包必须**暴露**一个**管理生命周期**的对象（带 `Close` / `Stop` / `Shutdown` 方法）

```go
// 反例
func init() {
    go doWork()
}

// 正例
type Worker struct{ /* ... */ }

func NewWorker(...) *Worker {
    w := &Worker{
        stop: make(chan struct{}),
        done: make(chan struct{}),
    }
    go w.doWork()
    return w
}

func (w *Worker) Shutdown() {
    close(w.stop)
    <-w.done
}
```

### 3.4 信道大小

🔴 必加约束

**信道大小通常应为 1 或 0（无缓冲）**。其他大小必须经过严格审视——能解释清楚"为什么是这个值"、"什么能防止它被填满"、"满了怎么办"。

```go
// 反例：拍脑袋的"足够大"
c := make(chan int, 64)

// 正例
c := make(chan int)   // 无缓冲
// 或
c := make(chan int, 1) // 1 个缓冲
```

## 4. 零值与初始化

### 4.1 零值互斥锁是合法的

🔴 必加约束

`sync.Mutex` / `sync.RWMutex` 的零值即可使用——**几乎从不需要指针**。

```go
// 反例
mu := new(sync.Mutex)
mu.Lock()

// 正例
var mu sync.Mutex
mu.Lock()
```

导出类型应避免匿名嵌入互斥锁，否则会把 `Lock` / `Unlock` 提升到公开方法集。私有实现即使不会泄露公开 API，也通常优先使用命名字段，以明确锁保护哪些状态，并避免结构体被意外复制。

```go
// 反例：Mutex 字段 + Lock 方法暴露
type SMap struct {
    sync.Mutex
    data map[string]string
}

// 正例：互斥锁作为非指针字段，方法不暴露
type SMap struct {
    mu   sync.Mutex
    data map[string]string
}
func (m *SMap) Get(k string) string {
    m.mu.Lock()
    defer m.mu.Unlock()
    return m.data[k]
}
```

### 4.2 零值结构体使用 `var`

🟡 推荐

声明空结构体用 `var T`，**不要**用 `T{}`——视觉上区分"零值"和"含非零字段"。

```go
// 正例
var user User
```

### 4.3 用字段名初始化结构体

🔴 必加约束

**几乎始终**指定字段名。`go vet` 强制要求。

```go
// 反例
k := User{"John", "Doe", true}

// 正例
k := User{
    FirstName: "John",
    LastName:  "Doe",
    Admin:     true,
}

// 例外：测试表中字段数 ≤ 3 时可省略
tests := []struct {
    op   Operation
    want string
}{
    {Add, "add"},
    {Subtract, "subtract"},
}
```

### 4.4 省略零值字段

🟡 推荐

用字段名初始化时，**省略取零值的字段**——除非字段名提供有意义的上下文（典型场景：表驱动测试）。

```go
// 正例
user := User{
    FirstName: "John",
    LastName:  "Doe",
    // MiddleName: "" 省略
    // Admin: false 省略
}
```

### 4.5 初始化结构体指针

🟡 推荐

用 `&T{}`，**不要**用 `new(T)`——与结构体初始化写法保持一致。

```go
// 正例
sval := T{Name: "foo"}
sptr := &T{Name: "bar"} // 不用 new(T)
```

### 4.6 初始化映射

🔴 必加约束

- **空 map / 编程式填充**：用 `make()`（必要时给容量提示，详见 [03-性能优化 § 3](03-性能优化.md)）
- **固定元素列表**：用 map 字面量

```go
// 编程填充
m1 := make(map[T1]T2)          // 容量未知
m2 := make(map[T1]T2, 100)     // 容量已知

// 固定列表
m := map[T1]T2{
    k1: v1,
    k2: v2,
    k3: v3,
}
```

### 4.7 `nil` 是合法的切片

🔴 必加约束

- 不要显式返回 `[]T{}`——返回 `nil`
- 检查空用 `len(s) == 0`，**不要**用 `s == nil`
- 零值（`var s []T`）无需 `make()` 即可直接 `append`

```go
// 反例
if x == "" {
    return []int{} // 多此一举
}
nums := []int{} // 后续还要 append

// 正例
if x == "" {
    return nil
}
var nums []int // 可直接 append
```

> `nil` 切片 ≠ 长度为 0 的已分配切片——**序列化**时两者表现不同（如 `json.Marshal`）。

### 4.8 缩小变量作用域

🟡 推荐

**尽可能缩小变量作用域**。但**与 [§ 5.1 减少嵌套](#51-减少嵌套)冲突时，优先减少嵌套**。

```go
// 正例：err 仅在 if 内使用
if err := os.WriteFile(name, data, 0644); err != nil {
    return err
}

// 反例：err 在 if 外也要用，却硬塞进 if
if data, err := os.ReadFile(name); err == nil {
    if err = cfg.Decode(data); err != nil { return err } // 难看
    fmt.Println(cfg)
    return nil
} else {
    return err
}

// 正例：data 后续要使用，err 留在 if 外
data, err := os.ReadFile(name)
if err != nil { return err }
if err := cfg.Decode(data); err != nil { return err }
```

**常量**不需要是全局的，除非多文件 / 多函数共享。

### 4.9 私有全局变量加下划线前缀

🔴 必加约束（已在 § 1.6 详述）

**本条与 § 1.6 是同一条规则**，§ 4.9 为交叉引用占位。

## 5. 控制流

### 5.1 减少嵌套

🔴 必加约束

**先处理错误情况 / 特殊条件，提前 return / continue**——让正常路径保持线性。

```go
// 反例：缩进金字塔
for _, v := range data {
    if v.F1 == 1 {
        v = process(v)
        if err := v.Call(); err == nil {
            v.Send()
        } else {
            return err
        }
    } else {
        log.Printf("Invalid v: %v", v)
    }
}

// 正例：guard clause
for _, v := range data {
    if v.F1 != 1 {
        log.Printf("Invalid v: %v", v)
        continue
    }
    v = process(v)
    if err := v.Call(); err != nil {
        return err
    }
    v.Send()
}
```

### 5.2 去除不必要的 `else`

🔴 必加约束

如果一个变量在 `if` 两个分支都被赋值，**用单个 `if` 替代 `if/else`**。

```go
// 反例
var a int
if b {
    a = 100
} else {
    a = 10
}

// 正例
a := 10
if b {
    a = 100
}
```

### 5.3 避免裸参数

🟡 推荐

**bool / int 等裸参数**会损害可读性。优先用**自定义类型**取代裸 bool；无法立即调整时，也应重构调用处或补充中文说明，不能用行内 `/* ... */` 猜测参数含义。

```go
// 临时边界：调用方用具名局部变量表达含义，后续仍应收敛为自定义类型或配置结构。
isLocal := true
isDone := true
printInfo("foo", isLocal, isDone)
```

```go
// 更好：自定义类型，未来可扩展
type Region int
const (
    UnknownRegion Region = iota
    Local
)

type Status int
const (
    StatusReady Status = iota + 1
    StatusDone
)
```

### 5.4 使用原始字符串字面量

🟢 可选

包含引号 / 多行的字符串优先用反引号（原始字符串字面量），**避免手工转义**。

```go
// 反例
wantError := "unknown name:\"test\""

// 正例
wantError := `unknown error:"test"`
```

### 5.5 函数分组与排序

🟡 推荐

- **同一文件中的函数按接收者分组**——同一类型的方法放一起
- **导出函数放最前面**——位于 `struct` / `const` / `var` 定义之后
- **`newXYZ()` / `NewXYZ()` 放在类型定义之后**，该接收者的其他方法之前
- **工具函数放文件末尾**

```go
// 正例
type something struct{ /* ... */ }

func newSomething() *something { return &something{} }

func (s *something) Cost() int { return calcCost(s.weights) }
func (s *something) Stop()      { /* ... */ }

func calcCost(n []int) int { /* 工具函数放末尾 */ }
```

### 5.6 行长度限制

🟡 推荐（以项目既有格式化和 lint 配置为准）

- 优先通过拆分复杂表达式和改善命名提高可读性，不设置所有项目统一的字符数。
- 仅当仓库已经配置行长度检查时遵守对应阈值；不得为了本规则擅自引入 `lll` 或 golangci-lint。
- `gofmt` 结果与项目现有规则优先，不为追求固定宽度制造反常换行。

### 5.7 局部变量声明

🟡 推荐

**显式赋值**时用短变量声明（`:=`）：

```go
// 正例
s := "foo"
```

**但**在零值语义更清晰的场景下用 `var`（如空切片——见 § 4.7）：

```go
// 正例：var 让"零值 + append"的语义更清晰
var filtered []int
for _, v := range list {
    if v > 10 { filtered = append(filtered, v) }
}
```

### 5.8 顶层变量声明

🟡 推荐

- 顶层用标准 `var` 关键字
- **类型与表达式一致时不显式指定类型**

```go
// 正例
var _s = F() // F() 返回 string，无需重复

// 反例
var _s string = F() // 重复
```

**类型不一致时显式指定**：

```go
type myError struct{}
func (myError) Error() string { return "error" }
func F() myError { return myError{} }

var _e error = F() // F 返回 myError，但变量声明为 error——显式类型
```

### 5.9 Printf 风格函数

🔴 必加约束（**`go vet` 检查**）

- 声明 `Printf` 风格函数时，使用**预定义函数名**让 `go vet` 默认检查
- 预定义名见 [go vet: Printf family](https://pkg.go.dev/cmd/vet#hdr-Printf_family)
- **无法用预定义名时**，名称必须以 `f` 结尾（如 `Wrapf` 而非 `Wrap`）
- 用 `-printfuncs` flag 让 `go vet` 检查自定义名：

```shell
go vet -printfuncs=wrapf,statusf
```

**格式化字符串应在 `Printf` 之外定义为 const**——便于 `go vet` 静态分析：

```go
// 正例
const msg = "unexpected values %v, %v\n"
fmt.Printf(msg, 1, 2)

// 反例
msg := "unexpected values %v, %v\n"
fmt.Printf(msg, 1, 2)
```

## 6. 同步原语

### 6.1 优先使用标准库 `sync/atomic`

- 🔴 先读取 `go.mod` 的 Go 版本和项目既有封装；不得为了类型化 API 自动引入第三方 atomic 包。
- 🟡 Go 1.19+ 可使用标准库的 `atomic.Bool`、`atomic.Int32`、`atomic.Int64`、`atomic.Pointer` 等类型化 API。
- 🟡 更早 Go 版本使用标准库函数或项目已有封装；项目已经采用 `go.uber.org/atomic` 时可以沿用，新增依赖仍需授权。
- 🔴 同一字段的读、写和比较交换必须全部通过同一原子 API；原子操作不能替代需要维护多字段不变量的锁。

```go
import "sync/atomic"

// 反例：原始字段与原子访问混用
type foo struct {
    running int32
}
func (f *foo) isRunning() bool {
    return f.running == 1 // race!
}

// 正例（Go 1.19+）：标准库类型化原子值
type foo struct {
    running atomic.Bool
}
func (f *foo) isRunning() bool {
    return f.running.Load()
}
```

### 6.2 避免可变全局变量

🔴 必加约束

**避免修改全局变量**，**转用依赖注入**。函数指针和其他类型的值同样适用。

```go
// 反例：可变的全局
var _timeNow = time.Now
func sign(msg string) string {
    return signWithTime(msg, _timeNow())
}

// 正例：依赖注入
type signer struct {
    now func() time.Time
}
func newSigner() *signer { return &signer{now: time.Now} }
func (s *signer) Sign(msg string) string {
    return signWithTime(msg, s.now())
}
```

## 7. 公共 API 设计

### 7.1 序列化结构体使用字段标签

参考来源：[Uber Go Style Guide：Use field tags in marshaled structs](https://github.com/uber-go/guide/blob/1d60a91aa5e87d443002e23c21903c49489dbde5/style.md#use-field-tags-in-marshaled-structs)（[上游 Apache-2.0 许可](https://github.com/uber-go/guide/blob/1d60a91aa5e87d443002e23c21903c49489dbde5/LICENSE)）。本节 `Stock` 示例与该章节相近；适用条件仍应按项目实际序列化工具和外部契约判断。

🔴 必加约束

对外部契约或持久化格式有稳定性要求时，应显式声明相应字段标签。若编码器、生成器或数据库工具不使用标签，或项目明确以 Go 字段名作为内部临时格式，则不要添加无效标签；以实际序列化工具和契约为准。

```go
// 反例：依赖字段名作为契约
type Stock struct {
    Price int
    Name  string
}

// 正例：显式标签
type Stock struct {
    Price int    `json:"price"`
    Name  string `json:"name"` // 重命名为 Symbol 时 json key 不变
}
```

> 序列化形式是**不同系统之间的契约**——显式声明可避免重构时意外破坏。

### 7.2 避免在公开结构体中嵌入类型

🔴 必加约束

公开结构体只有在被嵌入类型的完整方法集和字段确实属于外层类型的长期 API 时才嵌入。为复用实现、减少转发代码或临时方便而嵌入，会扩大 API 并增加后续演进成本，此时使用命名字段。

```go
// 反例：嵌入泄露了 AbstractList 的所有方法
type ConcreteList struct {
    *AbstractList
}

// 正例：私有字段 + 手工委托
type ConcreteList struct {
    list *AbstractList
}
func (l *ConcreteList) Add(e Entity)    { l.list.Add(e) }
func (l *ConcreteList) Remove(e Entity) { l.list.Remove(e) }
```

> 嵌入类型很难移除（向嵌入接口加方法 = 破坏性变更）——会让"公开 API 稳定"变成谎言。

### 7.3 结构体嵌入的位置

🟡 推荐

**被嵌入的类型应放在结构体字段列表的顶部**，并**用空行与普通字段分隔**。

```go
// 正例
type Client struct {
    http.Client

    version int
}
```

**嵌入不应**：

- 仅出于美观 / 便利
- 让外部类型更难以构造 / 使用
- 影响外部类型的零值可用性
- 暴露未导出类型
- 暴露外部类型的实现细节

**好的检验标准**："这些内部类型的导出方法 / 字段，是否全都应该被直接加到外部类型中？"——如果答案是"部分"或"不"，**不要嵌入，改用普通字段**。

### 7.4 在边界处拷贝切片与映射

🔴 必加约束

**接收**外部传入的 map / slice 时，如果**存储**了引用，必须**拷贝**（防止调用方后续修改影响内部状态）。

**返回**内部 map / slice 时，如果返回的是引用，调用方可绕过同步原语——必须**拷贝**。

```go
// 反例：存储外部引用，调用方可改
func (d *Driver) SetTrips(trips []Trip) {
    d.trips = trips // 危险
}

// 正例：拷贝
func (d *Driver) SetTrips(trips []Trip) {
    d.trips = make([]Trip, len(trips))
    copy(d.trips, trips)
}

// 反例：返回内部 map，绕过锁
func (s *Stats) Snapshot() map[string]int {
    s.mu.Lock()
    defer s.mu.Unlock()
    return s.counters // 危险：s.mu 释放后无保护
}

// 正例：返回拷贝
func (s *Stats) Snapshot() map[string]int {
    s.mu.Lock()
    defer s.mu.Unlock()
    result := make(map[string]int, len(s.counters))
    for k, v := range s.counters {
        result[k] = v
    }
    return result
}
```

## 8. 入口与退出

### 8.1 限制 `panic` 与 `recover`

🔴 必加约束

- 普通运行期错误应返回 `error`，由调用方决定如何处理；不要用 panic 替代业务错误或输入校验。
- 启动期不变量或明确失败即应终止的 `Must` API 可以使用 panic；这类例外必须有清晰契约和测试覆盖。
- nil pointer 通常表示程序缺陷，不应作为主动 panic 的推荐理由；应修复不变量、返回错误或在边界统一记录并隔离故障。
- `recover` 只放在经过设计的进程、请求或任务隔离边界，并记录故障、清理资源和返回受控结果；不要在任意业务函数中吞掉 panic。
- 测试中优先使用 `t.Fatal` / `t.FailNow` 表达测试失败。

```go
// 反例
func run(args []string) {
    if len(args) == 0 {
        panic("an argument is required")
    }
}

// 正例
func run(args []string) error {
    if len(args) == 0 {
        return errors.New("an argument is required")
    }
    return nil
}
```

### 8.2 仅在 `main()` 中退出

🔴 必加约束

`os.Exit` / `log.Fatal*` **仅**在 `main()` 中调用。**所有其他函数应返回错误**。

```go
// 反例：多个函数都退出
func readFile(path string) string {
    f, err := os.Open(path)
    if err != nil {
        log.Fatal(err) // 在普通函数退出
    }
    // ...
}

// 正例：readFile 返回错误，main 统一处理
func readFile(path string) (string, error) {
    f, err := os.Open(path)
    if err != nil {
        return "", err
    }
    // ...
}

func main() {
    body, err := readFile(path)
    if err != nil {
        log.Fatal(err)
    }
    fmt.Println(body)
}
```

原因：控制流不直观 / 难以测试 / defer 被跳过（清理不执行）。

### 8.3 退出一次

🟡 推荐

`main()` 中**至多调用一次** `os.Exit` / `log.Fatal`。业务逻辑放到**独立函数**（如 `run()`），返回错误。

```go
// 反例：main 中多次 log.Fatal
func main() {
    if len(os.Args) != 2 { log.Fatal("missing file") }
    f, err := os.Open(os.Args[1])
    if err != nil { log.Fatal(err) }
    defer f.Close()
    // 如果这里又 log.Fatal，defer f.Close() 不会执行
}

// 正例：run() 函数 + main 统一退出
func main() {
    if err := run(); err != nil {
        log.Fatal(err)
    }
}

func run() error {
    if len(os.Args) != 2 {
        return errors.New("missing file")
    }
    f, err := os.Open(os.Args[1])
    if err != nil { return err }
    defer f.Close()
    // ...
    return nil
}
```

### 8.4 避免使用 `init()`

🔴 必加约束

尽可能**避免** `init()`。`init()` 必须满足：

1. **完全确定**（不受程序环境 / 调用方式影响）
2. **不依赖其他 `init()` 顺序 / 副作用**
3. **不访问 / 操作全局 / 环境状态**（机器信息 / 环境变量 / 工作目录 / 程序参数）
4. **不进行 I/O**（文件系统 / 网络 / 系统调用）

无法满足的，改成 `main()` 调用的辅助函数。

```go
// 反例：init() 里做 I/O
var _config Config
func init() {
    cwd, _ := os.Getwd()
    raw, _ := os.ReadFile(path.Join(cwd, "config.yaml"))
    yaml.Unmarshal(raw, &_config)
}

// 正例：显式 loadConfig()
func loadConfig() (Config, error) {
    cwd, err := os.Getwd()
    if err != nil { return Config{}, err }
    raw, err := os.ReadFile(path.Join(cwd, "config.yaml"))
    if err != nil { return Config{}, err }
    var config Config
    if err := yaml.Unmarshal(raw, &config); err != nil {
        return Config{}, err
    }
    return config, nil
}
```

`init()` **可能**合理的场景：

- 复杂表达式无法用单一赋值
- 可插拔钩子（如 `database/sql` 的方言注册、`encoding` 注册表）
- Google Cloud Functions 等确定性预计算

### 8.5 枚举值从 1 开始

🟡 推荐

由于变量默认零值是 0，**通常**应从非零值开始枚举（用 `iota + 1`）。

```go
// 正例
const (
    Add Operation = iota + 1
    Subtract
    Multiply
)
// Add=1, Subtract=2, Multiply=3
```

**例外**：零值对应期望的默认行为时，可以用 0：

```go
const (
    LogToStdout LogOutput = iota // 0 = 默认 stdout
    LogToFile
    LogToRemote
)
```

### 8.6 使用 `time` 包处理时间

🟡 推荐

**永远不要假设时间**：

- 一天 ≠ 24 小时（DST 切换 / 时区调整可能让"加 24 小时"≠"下一天"）
- 一年 ≠ 365 天（闰年 / 闰秒）
- 一周固定 7 天但**每周的开始**因 locale 而异

**时间点**用 `time.Time`，**时间段**用 `time.Duration`：

```go
// 正例：时间段用 Duration
func poll(delay time.Duration) {
    for { time.Sleep(delay) }
}
poll(10 * time.Second) // 一看就知道是 10 秒

// 反例
func poll(delay int) {
    for { time.Sleep(time.Duration(delay) * time.Millisecond) }
}
poll(10) // 究竟是秒还是毫秒？必须看函数实现
```

**外部交互**用 `time.Time` / `time.Duration`：

- JSON / YAML：默认 `time.RFC3339`（自动 `UnmarshalJSON`）
- SQL：依赖底层驱动支持
- `flag`：`time.ParseDuration` 支持
- `encoding/json` 不支持 `time.Duration`——字段名加 `Millis` 后缀

**加 24 小时 vs 下一天**取决于意图：

```go
// 下一天的同一时刻（受 DST 影响）
newDay := t.AddDate(0, 0, 1)

// 严格 24 小时后（不受 DST 影响）
maybeNewDay := t.Add(24 * time.Hour)
```

## 9. 资源管理

### 9.1 使用 `defer` 清理资源

🔴 必加约束

**文件、锁、连接等资源**用 `defer` 清理。

```go
// 反例：多 return 分支容易遗漏 Unlock
p.Lock()
if p.count < 10 {
    p.Unlock()
    return p.count
}
p.count++
p.Unlock()
return p.count

// 正例
p.Lock()
defer p.Unlock()
if p.count < 10 {
    return p.count
}
p.count++
return p.count
```

> `defer` 开销极小——仅当函数执行时间在纳秒级时才考虑不用。**可读性收益 >> 性能成本**。

### 9.2 切片与映射的边界拷贝

🔴 必加约束（与 § 7.4 同源，此处为交叉引用）

**接收 / 返回**切片 / 映射时的拷贝规则见 § 7.4。

## 10. Go 1.18+ 泛型最佳实践（新增）

### 10.1 何时用泛型（决策表）

🟡 推荐：先写具体类型，在以下情况下再考虑泛型

| 场景 | 是否用泛型 | 示例 |
|---|---|---|
| **通用容器**（slice/map/set/queue） | ✅ 是 | `type Set[T comparable] map[T]struct{}` |
| **相同算法，不同数据类型** | ✅ 是 | `Min[T Ordered](a, b T)` / `Sort` / `Filter` |
| **需要类型安全的函数签名** | ✅ 是 | `func Must[T any](v T, err error) T { ... }` |
| **只是为了减少几行重复代码** | ❌ 否 | 两个不同函数就够用，不要强行泛化 |
| **只有一种类型在用** | ❌ 否 | 等出现第二种类型再重构为泛型 |
| **泛型参数超过 3 个** | ❌ 谨慎考虑 | 复杂度超过收益，考虑接口或结构体 |

### 10.2 `any` vs `comparable` vs 自定义约束

🔴 必加约束：理解三者差异，不要过度约束或过度放松

```go
// any = 任意类型（对应 interface{}，Go 1.18+ 内置别名）
func Print[T any](v T) { fmt.Println(v) }

// comparable = 支持 == 和 != 的类型（所有可比较类型：基本类型、指针、struct字段全可比较）
func Contains[T comparable](slice []T, target T) bool {
    for _, v := range slice {
        if v == target { return true }
    }
    return false
}

// 自定义约束：用 interface 指定方法集合或类型集
type Number interface {
    int | int64 | float64 // 类型集
}

func Sum[T Number](a, b T) T { return a + b }

type Ordered interface {
    ~int | ~int64 | ~float64 | ~string // ~ 表示"包含底层类型"——兼容别名
}

func Min[T Ordered](a, b T) T {
    if a < b { return a }
    return b
}
```

**命名建议**：泛型约束通常是 `-er` 结尾（`Number` / `Ordered` / `Stringer`），单字母参数名（T/U/V）。

### 10.3 泛型常见反模式

🔴 必加约束：避免以下泛型滥用

```go
// ❌ 反模式：用泛型替代 interface{}，毫无收益
func DoSomething[T any](v T) { ... }  // 不如直接用 interface{} / any

// ❌ 反模式：泛型包装了业务逻辑，可读性差
type Service[T Request, U Response] struct { ... }
func (s *Service[T, U]) Handle(req T) (U, error) { ... }
// → 更难阅读，每个 Service 只有 1 种 Request/Response，泛型没收益

// ❌ 反模式：接口 + 泛型混合，复杂度过高
type Repository[T any, ID comparable] interface {
    Get(ctx context.Context, id ID) (T, error)
    Save(ctx context.Context, v T) error
}
// → 通常只需要 Repository[T]，ID 用 string / int64 足够

// ✅ 正例：泛型只用于真正的算法/容器
type Set[T comparable] map[T]struct{}

func (s Set[T]) Add(v T)     { s[v] = struct{}{} }
func (s Set[T]) Has(v T) bool { _, ok := s[v]; return ok }
```

### 10.4 泛型函数 vs 接口

🟡 推荐：记住区别，选最合适的抽象

| 维度 | 泛型函数 | 接口 |
|---|---|---|
| **类型约束** | 编译期按类型集合检查 | 编译期按方法集检查 |
| **性能** | 取决于编译器实现、类型和调用路径，需基准验证 | 可能发生动态派发或逃逸，需基准验证 |
| **可读性** | 类型明确，签名自文档 | 更通用，但丢失类型细节 |
| **适用场景** | 算法、容器、工具函数 | 业务抽象、依赖注入、多态 |

**经验法则**：
- 写**通用算法** → 泛型
- 写**业务抽象** → 接口
- 两者都能解决时 → 先用接口，除非能证明泛型带来显著收益

### 10.5 标准库泛型工具

🟡 项目支持对应 Go 版本时，优先评估标准库能力，避免维护重复实现。

```go
import "slices"   // Go 1.21+
import "maps"     // Go 1.21+

// 切片工具
slices.Sort(s)           // 排序
slices.Contains(s, v)    // 包含
slices.Index(s, v)       // 查找索引
slices.Clone(s)          // 浅拷贝切片；元素引用的对象不会递归复制
slices.Delete(s, i, j)   // 删除元素
slices.Insert(s, i, v)   // 插入元素
slices.Compact(s)        // 去重相邻元素

// Map 工具
maps.Equal(m1, m2)       // 相等判断
maps.Clone(m)            // 拷贝
maps.Copy(dst, src)      // 复制
maps.DeleteFunc(m, f)    // 按条件删除
```

> **说明**：使用前先核对项目 `go.mod` 与目标平台支持范围。标准库能满足语义和性能要求时优先使用；否则应记录自定义实现的必要性并补充测试或基准。

## 11. 注释与文档语言

### 11.1 中文注释与例外

- 🔴 新增或修改的说明性注释、导出符号文档和包文档必须使用中文。
- 🔴 导出符号注释仍须以符号名开头；包文档仍须以 `Package <包名>` 开头，以满足 Go 文档工具链约定，其后的用途说明使用中文。
- 🟢 可保留英文的情形仅限：工具可识别指令（如 `//go:build`、`//go:generate`、`//nolint`）、协议/标准/第三方专有名词、已明确对外发布的英文 API 契约，以及外部依赖或自动生成代码；除指令和专有名词外，仍应以中文说明含义或原因。
- ❌ 不得仅因包名、类型名、变量名或 API 为英文，就把说明性注释整体改写为英文。

### 11.2 注释形式

- 🔴 普通局部说明、导出符号文档和包文档统一使用 `//`；需要多行说明时连续使用多行 `//`，不使用 `///` 或普通 `/* ... */`。
- 🔴 导出符号文档紧挨声明上方并以符号名开头；包文档紧挨 `package` 声明上方并以 `Package <包名>` 开头。
- ❌ **禁止**将普通 `/* ... */` 用作业务说明、算法说明或临时禁用代码；临时事项使用 `// TODO:`、`// FIXME:` 等行注释。
- 🟢 cgo 导言、不可改动的第三方/生成代码、授权声明或项目既有工具指令要求块注释时，可以保留其原有形式。

### 11.3 代码与注释并行维护

- 🔴 修改公共 API、鉴权与隐私边界、并发/重试、状态机、生命周期、资源所有权、跨端契约、兼容或降级逻辑时，必须在同一改动中新增或更新注释。
- 🔴 注释优先解释原因、约束、所有权、失败语义和非直观行为；不逐行复述代码，也不以注释行数或覆盖率为目标。
- 🔴 交付前同时检查错误注释、过时注释和应有但缺失的注释；不能只扫描英文注释。
- 🟢 第三方、自动生成和上游同步代码保持原文；包名、API 字段、协议字段、工具指令和 `Package <name>` 等 Go doc 契约保留英文原文，由中文解释用途和边界。
- 🟡 承担独立业务职责、流程复杂或明显较长的自研文件应包含模块职责说明；具体行数阈值由目标项目规则决定，纯 DTO、生成代码和简单文件可以例外。
