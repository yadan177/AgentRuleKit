# 11 - JavaScript 安全规则（🟠 强制）

> - 🟢 本文件适用于浏览器、Node.js、SSR/SSG 和 JavaScript/TypeScript 服务的安全边界。
> - 🔴 具体认证协议、部署平台、框架中间件、依赖版本和组织安全要求优先于本文件；不适用：把某个库或固定参数当作所有项目的默认答案。

---

## 1. 🟠 安全边界与输入

### 1.1 先确认运行边界

- 🔴 修改安全代码前，先确认代码运行在浏览器、Node.js 服务、SSR/SSG 构建阶段还是共享模块中。
- 🔴 明确认证凭据是 Cookie、`Authorization: Bearer`、短期一次性凭据还是其他协议，并以服务端契约为准。
- 🔴 安全规则应覆盖数据流、信任边界、部署配置和依赖来源；不能只凭文件后缀或框架名称判断。

### 1.2 输出编码与 HTML

- 🔴 默认使用框架或平台的文本渲染 API；不要把未信任输入直接写入 `innerHTML`、`outerHTML`、`document.write` 或模板的原始 HTML 插槽。
- 🔴 业务确实需要渲染受控富文本时，先定义允许的标签、属性和 URL 协议，再使用项目已经采用且经过审查的净化方案。`DOMPurify` 只是候选库，不得未经项目授权直接新增。
- 🔴 URL、跳转地址、资源地址和 iframe 来源按允许协议、来源和路径白名单校验，拒绝 `javascript:` 等危险协议。

```js
element.textContent = userInput;

const parsed = new URL(candidate, window.location.origin);
if (!['http:', 'https:'].includes(parsed.protocol)) {
  throw new Error('不允许的 URL 协议');
}
```

### 1.3 服务端输入与查询

- 🔴 服务端在边界处校验类型、长度、格式、范围和业务权限；不能把客户端校验当作授权或安全边界。
- 🔴 SQL 使用参数化查询或 ORM 的参数绑定；NoSQL、命令、路径、模板和正则输入同样使用项目已有的安全 API 和白名单。
- 🟡 运行时 schema 库（例如项目已经采用的 zod、valibot、yup、joi 或 class-validator）可以复用；未采用时优先使用现有校验函数或标准类型检查，不为示例新增依赖。

## 2. 🟠 认证、授权与 CSRF

### 2.1 授权必须在服务端完成

- 🔴 每个受保护资源都由服务端验证身份、权限、租户范围和资源归属；客户端隐藏按钮不构成授权。
- 🔴 令牌、Cookie、会话和刷新机制遵循项目身份系统与服务端契约；不要凭本文件臆造有效期、轮换次数或撤销策略。

### 2.2 Cookie 与 Bearer Token 的区别

- 🟡 Cookie 会被浏览器自动附带，通常需要 `Secure`、合适的 `HttpOnly`、`SameSite`、来源校验和会话过期策略；具体属性按跨站登录、嵌入和部署拓扑确定。
- 🟡 浏览器中的 Bearer Token 通常通过 `Authorization` 头显式发送，CSRF 风险模型与 Cookie 不同，但 XSS、泄露、重放和日志脱敏风险仍需处理。
- 🔴 不把访问令牌写入日志、URL、错误信息或未经评估的持久化存储。内存、受保护 Cookie、平台凭据存储等方案根据威胁模型和项目契约选择，不能写成一个适用于所有项目的绝对结论。

### 2.3 CSRF 适用条件

- 🔴 只有当浏览器会自动携带 Cookie 或其他隐式凭据，并且请求会改变服务端状态时，才按服务端契约启用 CSRF Token、SameSite、Origin/Referer 校验或等效防护。
- 🔴 不得把“所有 POST 都带 CSRF Token”当作通用规则；只读请求、Bearer 认证、同源策略和已有网关防护都需要结合项目事实判断。

```js
// 仅示意：Cookie 会话的状态变更请求按服务端契约附加 CSRF Token。
await fetch('/api/transfer', {
  method: 'POST',
  credentials: 'include',
  headers: { 'X-CSRF-Token': csrfToken },
  body: JSON.stringify(data),
});
```

## 3. 🟠 浏览器与服务端防护

### 3.1 CORS 与 CSP

- 🔴 CORS 允许的来源、方法、请求头、凭据和缓存时间按实际调用方白名单配置；不能用 `*` 配合凭据，也不能把 CORS 当作服务端授权。
- 🟡 CSP、`frame-ancestors`、SRI、HSTS、`nosniff`、Referrer-Policy 和 Permissions-Policy 按浏览器页面、静态资源、SSR 响应和反向代理的责任边界配置，并验证最终响应头。

```http
Content-Security-Policy: default-src 'self'; object-src 'none'; base-uri 'self'
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
```

### 3.2 密码、密钥与加密

- 🔴 密码在服务端使用组织批准的密码哈希方案和参数；前端哈希不能替代 HTTPS 或服务端密码存储策略。
- 🔴 私钥、数据库凭据、签名密钥和长期令牌不得进入前端包、仓库、日志、源码映射或客户端可读配置。
- 🔴 传输和存储加密使用项目批准的协议、密钥管理和轮换机制；不自行发明加密算法或固定密钥。

### 3.3 日志与错误信息

- 🔴 日志、异常、埋点和错误上报不得包含密码、令牌、Cookie、密钥、支付数据或未脱敏个人信息。
- 🟡 浏览器诊断、Node.js 服务日志和远程错误上报分别遵循各自的采样、保留、访问控制和脱敏策略；未授权不得接入新的上报平台。

## 4. 🟡 依赖与交付检查

- 🔴 沿用仓库的包管理器、lockfile、审计命令和 CI 门禁；不得为了本节示例自动安装安全库或扫描工具。
- 🟡 项目已有 `npm audit`、Dependabot、Snyk、OSV 或其他供应链检查时，按现有版本、参数和执行时机运行；没有既有门禁时，将候选检查和未覆盖范围记录在交付说明中。
- 🔴 依赖升级前检查来源、许可证、维护状态、漏洞公告、构建产物和运行时兼容性，确保变更经过项目授权和回归验证。

## 5. 🟢 可选主题

OAuth/OIDC、WebAuthn、SRI nonce、速率限制、CSRF 双提交 Cookie 等方案只在项目确实需要且已有协议、框架或安全评审支持时采用。示例不构成引入 `@auth/core`、`next-auth`、schema 库或其他依赖的授权。

## 6. 交付前自检

- 明确浏览器、Node.js、SSR/SSG 和共享模块的运行边界。
- 明确 Cookie/Bearer 认证方式、CSRF 适用条件和服务端授权位置。
- 验证 XSS、注入、CORS/CSP、敏感数据脱敏、依赖来源和目标部署配置。
- 记录实际执行的检查、未覆盖环境、未采用的候选方案及其原因。
