# 01 - Java 代码编写规则

> 🟢 本文件适用于 Java 代码的基础编写规范（命名/集合/Stream/Optional 等）。<br>
> 🔴 不适用：项目级架构决策、第三方库深度用法、Maven/Gradle 配置细节

---

## 1. 命名规范

类名、方法名、变量名、常量名、包名的标准约定。AI 写代码时**第一步**就要确定命名。

### 1.1 命名禁区

🟡 **推荐**：

- ❌ 命名不能以下划线 `_` 或美元符 `$` 开始或结束（`$` 是 Java 内部类命名保留，编译器/反射会冲突）
  - **反例**：`_name`、`__name`、`$name`、`name_`、`name$`、`name__`
- ❌ 严禁**拼音 + 英文**混用，禁止**纯中文**
  - **反例**：`DaZhePromotion`（打折）、`getPingfenByName()`（评分）、`int 某变量 = 3`
  - **正例**：`alibaba`、`taobao`、`youku`、`hangzhou` 这类约定俗成的国际通用名称视同英文

🟡 **推荐**：

- 自定义编程元素命名时使用**尽量完整的单词组合**表达其意（自解释优先于短名）
  - **正例**：`PullCodeFromRemoteRepository` 而非 `PullCode`
  - **反例**：`int a` 这种随意命名

### 1.2 类与接口

🟡 **推荐**：

- 类名用 `UpperCamelCase` 风格，**以下情形例外**：`DO` / `BO` / `DTO` / `VO` / `AO` / `PO` 等领域模型后缀
  - **正例**：`MarcoPolo`、`UserDO`、`XmlService`、`TcpUdpDeal`、`TaPromotion`
  - **反例**：`macroPolo`、`UserDo`、`XMLService`、`TCPUDPDeal`、`TAPromotion`
- **抽象类**用 `Abstract` 或 `Base` 开头（如 `AbstractService`）
- **异常类**用 `Exception` 结尾（如 `BizException`）
- **测试类**以"被测类名 + Test"结尾（如 `OrderServiceTest`）
- **枚举类**建议带 `Enum` 后缀，枚举成员名全大写 + 下划线分隔
  - **正例**：`ProcessStatusEnum` 的成员 `SUCCESS` / `UNKNOWN_REASON`

🟡 **推荐**：

- 如果类使用了**设计模式**，命名时体现具体模式（有利于快速理解架构）
  - **正例**：`OrderFactory`、`LoginProxy`、`ResourceObserver`
- **接口**中的方法和属性不加任何修饰符（`public` 也不要加），保持简洁性，加有效 Javadoc
  - **正例**：接口方法 `void f();`、接口常量 `String COMPANY = "alibaba";`
  - **反例**：接口方法 `public abstract void f();`

🟡 **推荐**（Service/DAO 接口 vs 实现）：

- Service 和 DAO 类：暴露的是**接口**，实现类用 `Impl` 后缀
  - **正例**：`CacheServiceImpl` 实现 `CacheService`
- 形容能力的接口名取**形容词**（通常 `-able` 形式），实现类用对应抽象名
  - **正例**：`AbstractTranslator` 实现 `Translatable`

### 1.3 方法、参数、变量

🟡 **推荐**：

- 方法名、参数名、成员变量、局部变量统一 `lowerCamelCase` 驼峰风格
  - **正例**：`localValue`、`getHttpMessage()`、`inputUserId`
- **常量**全部大写，单词间下划线分隔，**力求语义完整**（不要嫌长）
  - **正例**：`MAX_STOCK_COUNT`
  - **反例**：`MAX_COUNT`（语义不明）
- **POJO** 类的 `Boolean` 类型变量**不要**加 `is` 前缀（部分框架序列化会出错）
  - **反例**：`Boolean isDeleted;` 的 getter 是 `isDeleted()`，RPC 框架反序列化时误以为属性名是 `deleted`，导致属性获取不到
  - **正例**：`Boolean deleted;` getter 用 `getDeleted()` 或自定义 `isDeleted()`

### 1.4 数组与包

🟡 **推荐**：

- 定义数组时**类型与中括号紧挨**：`int[] arrayDemo;`（不要 `String args[]`）
- **包名**统一小写，点分隔符之间**仅一个**自然语义的英文单词，**单数形式**（类名可以有复数含义）
  - **正例**：`com.alibaba.ai.util` 包，类名 `MessageUtils`

### 1.5 缩写与命名分层

🟡 **推荐**：

- 杜绝不规范的缩写，避免望文不知义
  - **反例**：`AbstractClass` 缩写成 `AbsClass`，`condition` 缩写成 `condi`

🟡 **推荐**：

**各层命名规约**（AI 写 Controller/Service/DAO 时立即套用）：

**A) Service/DAO 层方法命名**

| 动作 | 前缀 |
|---|---|
| 获取单个对象 | `get` |
| 获取多个对象 | `list` |
| 获取统计值 | `count` |
| 插入 | `save` / `insert` |
| 删除 | `remove` / `delete` |
| 修改 | `update` |

**B) 领域模型命名**

| 模型 | 命名 | 用途 |
|---|---|---|
| 数据对象 | `xxxDO` | `xxx` 是数据表名，与表结构一一对应 |
| 数据传输对象 | `xxxDTO` | `xxx` 是业务领域相关的名称 |
| 展示对象 | `xxxVO` | `xxx` 一般是网页名称 |
| 业务对象 | `xxxBO` | Service 层输出的封装业务逻辑对象 |
| 应用对象 | `xxxAO` | Web 层与 Service 层之间抽象的复用对象 |
| 查询对象 | `xxxQuery` | 各层接收上层的查询请求 |

🟡 **推荐**：`POJO` 是 `DO`/`DTO`/`BO`/`VO` 的统称，**禁止命名成 `xxxPOJO`**。

## 2. 常量与字面量

常量定义、魔法值、Long 字面量、enum 替换常量类的标准做法。

### 2.1 魔法值

🟡 **推荐**：

- 代码中**不允许任何魔法值**（未经预先定义的常量）直接出现
  - **反例**：
    ```java
    String key = "Id#taobao_" + tradeId;
    cache.put(key, value);
    ```

### 2.2 Long 字面量

🟡 **推荐**：

- `long` 或 `Long` 初始赋值时使用**大写 L**，不能用小写 `l`（小写容易跟数字 1 混淆）
  - **反例**：`Long a = 2l;` —— 写的是数字 `21` 还是 `Long` 类型的 `2`？读不出来
  - **正例**：`Long a = 2L;`

### 2.3 常量分类维护

🟡 **推荐**：

- **不要用一个常量类维护所有常量**，按功能分类，分开维护
  - **正例**：缓存相关常量放在 `CacheConsts`；系统配置相关常量放在 `ConfigConsts`
  - **反例**：所有常量堆在一个 `Constants` 类里，找都要找半天

### 2.4 常量复用层次

🟡 **推荐**：常量复用分 5 层：

| 层次 | 位置 |
|---|---|
| 跨应用共享常量 | 二方库 `client.jar` 的 `constant` 目录 |
| 应用内共享常量 | 一方库子模块的 `constant` 目录 |
| 子工程内部共享常量 | 当前子工程的 `constant` 目录 |
| 包内共享常量 | 当前包下单独的 `constant` 目录 |
| 类内共享常量 | 类内部 `private static final` 定义 |

⚠️ **反例**（实际生产事故）：
```java
// 类 A 中
public static final String YES = "yes";
// 类 B 中
public static final String YES = "y";
// A.YES.equals(B.YES) 预期 true，实际 false → 线上 bug
```

### 2.5 用 enum 替代常量类

🟡 **推荐**：

- 变量值仅在一个固定范围内变化时，用 `enum` 类型定义（比常量类更类型安全）
- 如果存在名称之外的延伸属性（如编号、描述），`enum` 更合适

**正例**：
```java
public enum SeasonEnum {
    SPRING(1), SUMMER(2), AUTUMN(3), WINTER(4);

    private final int seq;

    SeasonEnum(int seq) {
        this.seq = seq;
    }
}
```

## 3. 数据类型与 OOP

数据类型选择、equals/hashCode、覆写、可变参数、POJO、构造方法、final、访问控制的标准做法。

### 3.1 静态访问与覆写

🟡 **推荐**：

- 避免通过类的**对象引用**访问**静态变量**或**静态方法**，直接用类名访问
  - **反例**：`someInstance.staticMethod()`（增加编译器解析成本）
  - **正例**：`MyClass.staticMethod()`
- 所有**覆写**方法必须加 `@Override` 注解（避免 `getObject()` vs `get0bject()` 这种字母 O 与数字 0 的笔误）
- 外部调用或二方库依赖的**接口不允许修改方法签名**；接口过时时加 `@Deprecated` 注解，清晰说明新接口是什么
- **不能使用过时的类或方法**（调用方有义务考证新实现）

### 3.2 equals 与 hashCode

🟡 **推荐**：

- `Object.equals()` 容易抛 NPE，**应使用常量或确定有值的对象调用**
  - **正例**：`"test".equals(object);`
  - **反例**：`object.equals("test");`（`object` 为 null 时 NPE）
  - **推荐**：JDK 7+ 用 `java.util.Objects#equals`（null-safe）
- **相同类型的包装类对象**之间值的比较，**全部用 `equals`**，不要用 `==`
  - **陷阱**：`Integer var = ?` 在 **-128 到 127** 范围内，`Integer` 对象在 `IntegerCache.cache` 中复用，此区间内 `==` 可以用；**区间之外**全部在堆上新建，不会复用，`==` 失效

🟡 **推荐**（hashCode/equals 三件套）：

- 只要**重写 `equals`，就必须重写 `hashCode`**
- `Set` 存储的对象必须重写这两个方法（Set 去重依赖 `hashCode` + `equals`）
- 自定义对象作为 `Map` 的 key，必须重写 `hashCode` 和 `equals`

### 3.3 基本类型 vs 包装类型

🟡 **推荐**：

- 所有的 **POJO 类属性**必须使用**包装数据类型**（`Integer` / `Long` / `Boolean`）
- **RPC 方法的返回值和参数**必须使用**包装数据类型**

🟡 **推荐**：

- 所有的**局部变量**使用**基本数据类型**（`int` / `long` / `boolean`）

**为什么**：POJO 属性无初值，使用者必须显式赋值，NPE 和入库检查由使用者保证；自动拆箱用基本类型接收数据库 null 值有 NPE 风险；包装类型的 `null` 能表示额外信息（如远程调用失败）。

### 3.4 可变参数

🟡 **推荐**：

- 只有**相同参数类型、相同业务含义**才可以使用 Java 的可变参数，避免使用 `Object`
- 可变参数**必须放在参数列表的最后**
- 提倡尽量不用可变参数编程

**正例**：
```java
public User getUsers(String type, Integer... ids) { ... }
```

### 3.5 POJO 类

🟡 **推荐**：

- 定义 `DO` / `DTO` / `VO` 等 POJO 类时**不要设定任何属性默认值**
  - **反例**：`POJO` 类的 `gmtCreate` 默认值为 `new Date();`，数据提取时未置入具体值，更新其他字段时又附带更新了此字段，导致创建时间被修改成当前时间
- 序列化类新增属性时**不要修改 `serialVersionUID`**（避免反序列化失败）；如果不兼容升级，**修改 `serialVersionUID`**
- POJO 类必须写 `toString` 方法（异常时直接 `toString()` 打印属性值便于排查）；如果继承另一个 POJO 类，前面加 `super.toString()`

### 3.6 构造方法

🟡 **推荐**：

- **构造方法里面禁止加入任何业务逻辑**，初始化逻辑放在 `init` 方法中
- 工具类不允许有 `public` 或 `default` 构造方法
- 类不允许外部通过 `new` 直接创建对象时，构造方法必须是 `private`

### 3.7 String.split 索引

🟡 **推荐**：

- 用索引访问 `String.split` 得到的数组时，**必须做最后一个分隔符后有无内容的检查**，否则可能抛 `IndexOutOfBoundsException`
  - **反例**：`"a,b,c,,".split(",")` 预期长度大于 3，实际为 3

### 3.8 字符串拼接

🟡 **推荐**：

- 循环体内的字符串拼接使用 `StringBuilder.append` 而非 `+`
  - **反例**：循环里 `str = str + "hello";` 反编译显示**每次循环都 new 一个 `StringBuilder`**，最后 `toString()` 返回新对象，浪费内存

### 3.9 final 关键字使用场景

🟡 **推荐**：以下场景使用 `final` 关键字：

1. **不允许被继承的类**（如 `String`）
2. **不允许修改引用的域对象**（如 POJO 类的域变量）
3. **不允许被重写的方法**（如 POJO 类的 setter）
4. **不允许运行过程中重新赋值的局部变量**
5. 避免上下文重复使用一个变量（`final` 强制重新定义，便于重构）

### 3.10 慎用 clone

🟡 **推荐**：

- 慎用 `Object.clone()` —— **默认是浅拷贝**，若要深拷贝必须重写 `clone` 方法实现属性对象的拷贝（容易踩坑）

### 3.11 访问控制从严

🟡 **推荐**：类成员与方法访问控制**从严**（任何类、方法、参数、变量都要严控访问范围）：

| 场景 | 修饰符 |
|---|---|
| 不允许外部 `new` 创建对象 | 构造方法 `private` |
| 工具类 | 不允许 `public` / `default` 构造方法 |
| 非 static 成员变量，子类共享 | `protected` |
| 非 static 成员变量，仅本类使用 | `private` |
| static 成员变量，仅本类使用 | `private` |
| static 成员变量，考虑是否 `final` | `final` |
| 成员方法只供类内部调用 | `private` |
| 成员方法只对继承类公开 | `protected` |

**理念**：变量像自己的小孩，尽量在自己的视线内；作用域太大，到处跑，你会担心的。`private` 方法想删就删，`public` service 方法删一下不慌吗？

### 3.12 类内方法定义顺序

🟡 **推荐**：

- 一个类有多个构造方法或多个同名方法时，**按顺序放置在一起**（优先于方法顺序规则）
- 类内方法定义的顺序：**公有方法或保护方法 → 私有方法 → getter/setter 方法**

**理念**：公有方法是调用者和维护者最关心的方法，首屏展示最好；保护方法可能是模板设计模式的核心；私有方法外部不需要特别关心，是黑盒实现；getter/setter 信息价值低，放最后。

### 3.13 setter 不要加业务逻辑

🟡 **推荐**：

- `setter` 方法参数名与类成员变量名一致，`this.成员名 = 参数名`
- **getter/setter 方法中不要增加业务逻辑**（增加排查问题的难度）
  - **反例**：
    ```java
    public Integer getData() {
        if (condition) {
            return this.data + 100;
        } else {
            return this.data - 100;
        }
    }
    ```


## 4. 集合处理

ArrayList、HashMap、subList、Comparator、foreach、null 容忍度等集合使用规范。AI 写 `List`/`Map`/`Set` 操作时立即要遵守。

### 4.1 subList 与 toArray

🟡 **推荐**：

- `ArrayList.subList()` 结果**不可强转**成 `ArrayList`，会抛 `ClassCastException`（`java.util.RandomAccessSubList cannot be cast to java.util.ArrayList`）
  - **原因**：`subList` 返回的是 `ArrayList` 的内部类 `SubList`，是 `ArrayList` 的**视图**，对子列表的所有操作最终反映到原列表
- **高度注意**：在 `subList` 场景中修改原集合元素个数会导致子列表的遍历、增加、删除均产生 `ConcurrentModificationException`

🟡 **推荐**（集合转数组）：

- 使用集合转数组方法必须用 `toArray(T[] array)`，传入**类型完全一样**的数组，大小就是 `list.size()`
  - **原因**：无参 `toArray()` 返回 `Object[]`，强转其他类型数组会抛 `ClassCastException`

**正例**：
```java
List<String> list = new ArrayList<>(2);
list.add("guan");
list.add("bao");
String[] array = new String[list.size()];
array = list.toArray(array);
```

### 4.2 Arrays.asList 陷阱

🟡 **推荐**：

- 使用 `Arrays.asList()` 把数组转集合时**不能使用其修改集合相关的方法**（`add` / `remove` / `clear` 会抛 `UnsupportedOperationException`）
  - **原因**：`asList` 返回的是一个 `Arrays` 内部类，没有实现集合的修改方法，体现适配器模式，后台数据仍是数组

```java
String[] str = new String[] { "you", "wu" };
List list = Arrays.asList(str);
// 第一种情况：list.add("yangguanbao"); 运行时异常
// 第二种情况：str[0] = "gujin"; 那么 list.get(0) 也会随之修改
```

### 4.3 泛型通配符 PECS

🟡 **推荐**：

- 泛型通配符 `<? extends T>` 接收返回数据时，**此写法的泛型集合不能使用 `add` 方法**
- `<? super T>` 不能使用 `get` 方法（作为接口调用赋值时易出错）

**PECS 原则（Producer Extends Consumer Super）**：

- **频繁往外读取内容的**：适合用 `<? extends T>`
- **经常往里插入的**：适合用 `<? super T>`

### 4.4 foreach 中 remove/add

🟡 **推荐**：

- **不要在 foreach 循环里进行元素的 remove/add 操作**
- `remove` 元素请使用 `Iterator` 方式（并发操作需要对 `Iterator` 对象加锁）

**正例**：
```java
Iterator<String> iterator = list.iterator();
while (iterator.hasNext()) {
    String item = iterator.next();
    if (删除元素的条件) {
        iterator.remove();
    }
}
```

**反例**（执行结果出乎意料）：
```java
List<String> list = new ArrayList<>();
list.add("1");
list.add("2");
for (String item : list) {
    if ("1".equals(item)) {
        list.remove(item);
    }
}
```

### 4.5 Comparator 三条件

🟡 **推荐**（JDK 7+）：

- `Comparator` 必须满足三个条件，否则 `Arrays.sort` / `Collections.sort` 会报 `IllegalArgumentException`：

1. `x`、`y` 的比较结果和 `y`、`x` 的比较结果相反
2. `x > y`，`y > z`，则 `x > z`
3. `x = y`，则 `x`、`z` 比较结果和 `y`、`z` 比较结果相同

**反例**（没处理相等情况，实际使用可能出现异常）：
```java
new Comparator<Student>() {
    @Override
    public int compare(Student o1, Student o2) {
        return o1.getId() > o2.getId() ? 1 : -1;
    }
};
```

### 4.6 集合初始化指定大小

🟡 **推荐**：

- **集合初始化时指定初始值大小**：`HashMap` 使用 `HashMap(int initialCapacity)` 初始化
  - **公式**：`initialCapacity = (需要存储的元素个数 / 负载因子) + 1`
  - 默认负载因子 0.75；如果暂时无法确定初始值大小，设置为 16（默认值）
- **反例**：`HashMap` 放置 1024 个元素没设初始容量，随着元素增加容量 7 次被迫扩大，`resize` 重建 hash 表严重影响性能

### 4.7 Map 遍历方式

🟡 **推荐**：

- 使用 `entrySet` 遍历 `Map` 类集合 KV，**而不是 `keySet` 方式**
  - **原因**：`keySet` 遍历了 2 次（一次转为 `Iterator`，一次取 value）；`entrySet` 只遍历 1 次
  - **JDK 8+**：使用 `Map.forEach` 方法

**返回类型对比**：
| 方法 | 返回 |
|---|---|
| `values()` | V 值集合（list）|
| `keySet()` | K 值集合（Set）|
| `entrySet()` | K-V 值组合集合 |

### 4.8 Map 的 null 容忍度

🟡 **推荐**：高度注意 `Map` 类集合 K/V 能不能存储 null 值：

| 集合类 | Key | Value | Super | 说明 |
|---|---|---|---|---|
| `Hashtable` | 不允许 null | 不允许 null | Dictionary | 线程安全 |
| `ConcurrentHashMap` | 不允许 null | 不允许 null | AbstractMap | 锁分段技术（JDK8: CAS）|
| `TreeMap` | 不允许 null | 允许 null | AbstractMap | 线程不安全 |
| `HashMap` | 允许 null | 允许 null | AbstractMap | 线程不安全 |

⚠️ **反例**：很多人认为 `ConcurrentHashMap` 可以置入 null 值，**实际存储 null 值时抛 NPE**。

### 4.9 集合的有序性与稳定性

🟢 **可选**：合理利用集合的有序性（sort）和稳定性（order），避免无序性（unsort）和不稳定性（unorder）的负面影响：

- 有序性：遍历结果按某种比较规则依次排列
- 稳定性：集合每次遍历的元素次序是一定的

| 集合 | 顺序特性 |
|---|---|
| `ArrayList` | order / unsort |
| `HashMap` | unorder / unsort |
| `TreeSet` | order / sort |

### 4.10 Set 去重

🟢 **可选**：利用 `Set` 元素唯一性可快速对一个集合去重，**避免使用 `List.contains` 进行遍历对比去重**（O(n²)）。

## 5. 流程控制

if/else、switch、循环、参数校验的规范。

### 5.1 switch 必须有 default

🟡 **推荐**：

- `switch` 块内每个 `case` 要么通过 `break`/`return` 终止，要么注释说明将继续执行到哪个 `case` 为止
- `switch` 块内必须包含 `default` 语句放在最后（即使空代码）

### 5.2 大括号强制使用

🟡 **推荐**：

- `if` / `else` / `for` / `while` / `do` 语句中**必须使用大括号**，即使只有一行代码
- 避免单行编码：`if (condition) statements;`

### 5.3 高并发避免"等于"判断

🟡 **推荐**：

- **高并发场景中，避免使用"等于"判断作为中断或退出条件**
- 如果并发控制没处理好，容易产生等值判断被"击穿"的情况；使用**大于或小于的区间判断**代替
- **反例**：判断剩余奖品数量等于 0 时终止发放，并发处理错误导致奖品瞬间变负数，活动无法终止

### 5.4 卫语句替代深层 if-else

🟡 **推荐**：

- 表达异常的分支时**少用 if-else 方式**，用卫语句（提前 return）改写
- 如果非要 `if()...else if()...else...`，**避免超过 3 层**

**卫语句正例**：
```java
public void today() {
    if (isBusy()) {
        System.out.println("change time.");
        return;
    }
    if (isFree()) {
        System.out.println("go to travel.");
        return;
    }
    System.out.println("stay at home to learn Alibaba Java Coding Guidelines.");
    return;
}
```

### 5.5 复杂条件提取变量

🟡 **推荐**：

- 除常用方法（`getXxx` / `isXxx`）外，**不要在条件判断中执行其它复杂语句**
- 将复杂逻辑判断的结果赋值给一个**有意义的布尔变量名**提高可读性

**正例**：
```java
final boolean existed = (file.open(fileName, "w") != null) && (...) || (...);
if (existed) {
    ...
}
```

### 5.6 循环体性能考量

🟡 **推荐**：

- 循环体中的语句要考量性能，以下操作尽量移至循环体外处理：
  - 定义对象、变量
  - 获取数据库连接
  - 进行不必要的 `try-catch` 操作（这个 `try-catch` 是否可以移至循环体外）

### 5.7 避免取反逻辑

🟡 **推荐**：

- **避免采用取反逻辑运算符**（取反不利于快速理解，且取反写法必然存在对应的正向写法）
- **正例**：`if (x < 628)` 表达 x 小于 628
- **反例**：`if (!(x >= 628))` 表达 x 小于 628

### 5.8 接口入参保护

🟡 **推荐**：

- **接口入参保护**：常见于批量操作的接口（防止参数过大撑爆内存、SQL 注入、ReDoS 等）

### 5.9 参数校验场景

🟢 **参考**：下列情形**需要**进行参数校验：

1. 调用频次低的方法
2. 执行时间开销很大的方法（参数校验时间可忽略）
3. 需要极高稳定性和可用性的方法
4. 对外提供的开放接口（RPC / API / HTTP）
5. 敏感权限入口

🟢 **参考**：下列情形**不需要**进行参数校验：

1. 极有可能被循环调用的方法（方法说明里必须注明外部参数检查要求）
2. 底层调用频度比较高的方法（如 DAO 层，与 Service 同应用、同服务器，可省略）
3. 被声明成 `private` 只会被自己代码调用的方法（能确定调用方已做过检查）


## 6. 注释与文档

类、方法、字段、特殊标记（TODO/FIXME）的注释规范。

### 6.1 Javadoc 强制

🟡 **推荐**：

- 类、类属性、类方法的注释**必须使用 Javadoc 规范**（`/** 内容 */`），**不得**使用 `// xxx` 方式
- 所有**抽象方法**（包括接口方法）必须用 Javadoc 注释；除返回值、参数、异常说明外，**必须指出该方法做什么事情、实现什么功能**
- 所有**类**都必须添加**创建者和创建日期**
- 所有**枚举类型字段**必须要有注释，说明每个数据项的用途

### 6.2 方法内部注释

🔴 **必须**：

- 方法内部**单行注释**在被注释语句**上方另起一行**，使用 `//` 注释
- 方法内部需要连续说明时，使用贴近代码的多行 `//` 中文注释；普通 `/* */` 不作为业务说明格式

### 6.3 中文注释

🔴 **必须**：

- 新增或修改的说明性注释、Javadoc 正文必须使用中文；`@param`、`@return`、`@throws` 等 Javadoc 标签和代码标识符保持规范原样。
- 可保留英文的情形仅限：工具可识别标记或指令（如 `TODO`、`FIXME`）、协议/标准/第三方专有名词、已明确对外发布的英文 API 契约，以及外部依赖或自动生成代码；除标记和专有名词外，仍应以中文说明含义或原因。
- ❌ 不得仅因类名、变量名或 API 为英文，就把说明性注释整体改写为英文。
- **专有名词与关键字**保持英文原文。
  - 例如：写“TCP 连接超时”，不要把 TCP 生硬翻译为“传输控制协议”。

### 6.4 注释同步更新

🟡 **推荐**：

- **代码修改的同时，注释也要进行相应的修改**（参数、返回值、异常、核心逻辑等的修改）
  - **理念**：代码与注释更新不同步，就像路网与导航软件更新不同步，导航严重滞后就失去意义

### 6.5 谨慎注释掉代码

🟢 **参考**：

- 谨慎注释掉代码，**在上方详细说明**，而不是简单注释掉；如无用**直接删除**（代码仓库保存了历史代码）

🟡 **推荐**（特殊注释标记）：

- 待办事宜（**TODO**）：`（标记人，标记时间，[预计处理时间]）`，表示需要实现但目前还未实现的功能；只能应用于类、接口和方法
- 错误，不能工作（**FIXME**）：`（标记人，标记时间，[预计处理时间]）`，标记某代码是错误的且不能工作，需要及时纠正
- 标记时及时处理；线上故障有时来源于这些标记处的代码

### 6.6 注释的度

🟢 **参考**：

- 好的命名、代码结构是**自解释**的，注释力求**精简准确、表达到位**
- 避免注释的一个极端：**过多过滥的注释**，代码逻辑修改时修改注释是相当大的负担
  - **反例**：
    ```java
    // put elephant into fridge
    put(elephant, fridge);
    // 方法名 put + 两个有意义的变量名 elephant 和 fridge 已经说明在干什么
    ```

## 7. Lambda、Stream、Optional（AI 视角扩展）

P3C 黄山版基线 JDK 8，**未涵盖** JDK 9+ 新特性。AI 写现代 Java 代码时立即要用的核心规范。

### 7.1 Lambda 表达式

🟡 **推荐**：

- 单行 Lambda 可省略大括号和 `return`；多行必须用大括号
  - **正例**：`list.forEach(item -> log.info(item));`
  - **反例**：`list.forEach(item -> { log.info(item); });`（多此一举）

🟡 **推荐**：

- Lambda 不要捕获外部可变变量（Java 事实上的 `final` 限制），需要可变状态用 `AtomicReference` 等
  - **反例**：
    ```java
    int[] counter = {0};
    list.forEach(item -> counter[0]++); // 编译能过但语义糟糕
    ```

### 7.2 方法引用优先级

🟡 **推荐**：

- 能用方法引用就不要用 Lambda
  - **正例**：`list.forEach(System.out::println);` 比 `list.forEach(s -> System.out.println(s));` 更好
- 4 种方法引用：
  - 静态方法引用：`String::valueOf`
  - 实例方法引用（绑定）：`instance::method`
  - 实例方法引用（未绑定）：`String::length`
  - 构造器引用：`ArrayList::new`

### 7.3 Stream API 使用

🟡 **推荐**：

- 简单的转换/过滤/聚合用 Stream；**复杂的状态机用 for 循环**（Stream 不擅长状态管理）
- Stream 操作分**中间操作**（filter / map / sorted / distinct）和**终端操作**（collect / forEach / reduce / count）

🟡 **推荐**：

- Stream **不能复用**（已被消费过的 Stream 会抛 `IllegalStateException`）
  - **反例**：
    ```java
    Stream<String> stream = list.stream();
    stream.filter(s -> s.length() > 2).count();
    stream.forEach(System.out::println); // 抛 IllegalStateException
    ```
- Stream 操作**不要修改外部状态**（影响可读性和并行化能力）

🟢 **可选**：

- 数据量大且无状态操作时用 `parallelStream()`（注意线程安全问题）
- `parallelStream()` 不适合：
  - 数据量小（并行开销 > 收益）
  - 涉及共享可变状态
  - 涉及阻塞 IO（线程被阻塞在 IO 上，反而更慢）

### 7.4 Optional 使用

🟡 **推荐**：

- 方法返回值**可能为 null** 时，**返回 `Optional<T>` 而不是 null**（强制调用方处理缺失情况）
- **`Optional` 不作为字段、参数、集合元素**（`List<Optional<T>>` 是反模式）
- 不要用 `Optional` 做 getter/setter 的包装（破坏 JavaBean 规范）

🟡 **推荐**：

- **优先用 `orElseGet(Supplier)` 而不是 `orElse(T)`**，避免不必要的对象创建
  - **正例**：`opt.orElseGet(() -> createDefault());`（`createDefault()` 只在 Optional 为空时调用）
  - **反例**：`opt.orElse(createDefault());`（无论是否为空都会调用 `createDefault()`）

🟡 **推荐**：

- **`Optional.get()` 是最后选择**，调用前必须先用 `isPresent()` 或其他函数式方法
  - **反例**：
    ```java
    Optional<String> opt = ...;
    String s = opt.get(); // 不安全
    ```
  - **正例**：
    ```java
    String s = opt.orElseThrow(() -> new BizException("缺失"));
    // 或
    opt.ifPresent(s -> doSomething(s));
    opt.map(s -> s.toUpperCase()).ifPresent(System.out::println);
    ```

### 7.5 Stream vs for 循环决策

🟡 **推荐**：

| 场景 | 写法 |
|---|---|
| 简单遍历 + 处理 | `forEach` |
| 转换 / 过滤 / 聚合 | Stream |
| 需要 break / continue / 嵌套 | for 循环（Stream 难以表达）|
| 需要修改外部状态 | for 循环（Stream 应保持无状态）|
| 涉及异常处理 | for 循环（Lambda 内 checked exception 处理繁琐）|

## 8. 字符串、数值、IO

字符串拼接、数值精度、IO 关闭、try-with-resources 的规范。

### 8.1 字符串拼接

🟡 **推荐**：

- **循环体内**用 `StringBuilder.append`（已见 § 3.8）
- **单次或少量拼接**用 `String.format` 或 `+` 都可以（编译器优化后差异不大）
- **禁止** `String.intern()` 用于动态生成的字符串（PermGen / Metaspace 溢出风险）

🟡 **推荐**：

- 字符串拼接**优先 `StringBuilder` 而不是 `StringBuffer`**（单线程下 `StringBuilder` 更快，不需要同步）
- 多线程下共用一个 `StringBuilder` 才有线程安全问题，每个线程自己的实例用 `StringBuilder`

### 8.2 数值精度

🟡 **推荐**：

- **金额、订单、库存等精确计算用 `BigDecimal`，不要用 `float` / `double`**
  - **原因**：`float` / `double` 存在精度损失，比较时可能得到不正确的结果
- `BigDecimal` 必须用 **`String` 构造**而不是 `double` 构造（避免 `0.1` 这种二进制无法精确表示的问题）
  - **正例**：`new BigDecimal("0.1")`
  - **反例**：`new BigDecimal(0.1)`（实际值是 `0.1000000000000000055511151231257827021181583404541015625`）

🟡 **推荐**：

- `BigDecimal` 除法必须指定**保留位数和舍入模式**
  - **正例**：`a.divide(b, 2, RoundingMode.HALF_UP)`
  - **反例**：`a.divide(b)`（无限循环小数抛 `ArithmeticException`）

### 8.3 自动装箱与拆箱

🟡 **推荐**：

- **禁止**在循环中无脑自动装箱（造成大量 GC 压力）
  - **反例**：`Long sum = 0L; for (long i = 0; i < 10000; i++) sum += i;`（每次 `+=` 都装箱）
  - **正例**：`long sum = 0L;` 或 `LongAdder`（高并发场景）

🟡 **推荐**：

- 包装类型比较**始终用 `equals`**（不要 `==`，已见 § 3.2）

### 8.4 IO 与资源关闭

🟡 **推荐**：

- **所有 IO、流、连接必须用 try-with-resources 关闭**（JDK 7+）
  - **正例**：
    ```java
    try (InputStream in = new FileInputStream("a.txt");
         OutputStream out = new FileOutputStream("b.txt")) {
        // 使用 in / out
    }
    // 自动关闭，无需 finally
    ```
  - **反例**（JDK 7 之前的写法，已不推荐）：
    ```java
    InputStream in = null;
    try {
        in = new FileInputStream("a.txt");
        // ...
    } finally {
        if (in != null) {
            in.close(); // 异常路径可能不关闭
        }
    }
    ```

🟡 **推荐**：

- 实现 `AutoCloseable` 的资源**必须在 try-with-resources 中使用**，否则关闭时机不确定
- **不要在 `try` 块中返回或抛出异常后忘记释放资源**（finally 不可靠）

### 8.5 字符流 vs 字节流

🟡 **推荐**：

- 处理**文本文件**（UTF-8 / GBK 等）用**字符流**：`InputStreamReader` / `OutputStreamWriter` / `Files.newBufferedReader`
- 处理**二进制文件**（图片、音频、压缩包）用**字节流**：`FileInputStream` / `FileOutputStream` / `Files.newInputStream`
- **不要**用 `Reader` / `Writer` 读取二进制（字符编码转换会破坏数据）

🟢 **可选**：

- JDK 7+ 优先用 **`java.nio.file.Files`** API（更简洁）：
  - `Files.readAllBytes(Paths.get("a.txt"))`
  - `Files.write(Paths.get("a.txt"), bytes)`
  - `Files.lines(Paths.get("a.txt"))` 逐行读取（`Stream<String>`，记得关闭）
