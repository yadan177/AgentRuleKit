# 10 - Java 版本控制规则

> - 🟢 本文件适用于 Git 版本控制（Conventional Commits/.gitignore/PR/CI）。
> - 🔴 不适用：GitHub PR/MR 流程、Code Owner 配置

---

## 1. Conventional Commits

### 1.1 为什么用 Conventional Commits

🟡 **推荐**：

- AI 写 commit message **必须**遵循 Conventional Commits 规范
- 原因：CHANGELOG 自动生成、版本号自动 bump、`git log` 可搜索、code review 标准化

### 1.2 Commit message 格式

🟡 **推荐**：

```
<type>(<scope>): <subject>

<body>

<footer>
```

| 部分 | 必填 | 说明 |
|---|---|---|
| **type** | ✅ 必填 | 类型（feat / fix / docs / style / refactor / perf / test / chore / build / ci / revert）|
| **scope** | 推荐 | 影响范围（如 `order`、`user`、`logging`，可选）|
| **subject** | ✅ 必填 | 简短描述（中文 ≤ 50 字符，**不**以大写开头、**不**加句号）|
| **body** | 可选 | 详细描述（72 字符换行，说明 what + why，**不**说明 how）|
| **footer** | 可选 | 关联 issue / 重大变更说明（`BREAKING CHANGE:`）|

### 1.3 11 种 Commit 类型

🟡 **推荐**（AI 必须用以下 11 种类型）：

| 类型 | 含义 | 使用场景 |
|---|---|---|
| **feat** | 新功能 | 新增 API / 新增模块 / 新增选项 |
| **fix** | 修复 bug | 修复功能性 bug（不是 typo / format）|
| **docs** | 文档变更 | 改文档、注释、README |
| **style** | 代码风格 | 缩进 / 空行 / 引号等格式调整（不改语义）|
| **refactor** | 重构 | 不改行为的代码结构调整（如提取方法、抽象类）|
| **perf** | 性能优化 | 性能改进（不修 bug 不加功能）|
| **test** | 测试相关 | 新增 / 修改 / 重构测试（不算业务代码）|
| **chore** | 杂项 | 构建配置 / 依赖更新 / 非业务的杂项 |
| **build** | 构建相关 | 依赖 / 构建工具 / CI 配置的变更 |
| **ci** | CI 相关 | CI 配置文件变更（GitHub Actions / Jenkins）|
| **revert** | 回滚 | 撤销先前的 commit |

🟡 **推荐**：

- **不发明新 type**（11 种已经够用）
- 类型必须小写（**feat** 不是 **Feat**）

### 1.4 Subject 编写要求

🟡 **推荐**：

- Subject **≤ 50 字符**（中文约 20 字）
- **不以大写字母开头**（除非是专有名词）
- **不以句号结尾**
- 使用**祈使语气**（"添加"而非"添加了"）

**正例**：
```
feat(order): 添加订单取消接口
fix(payment): 修复支付回调幂等校验失败
refactor(user): 提取 UserMapper 为独立类
```

**反例**：
```
❌ fix(payment): 修复了支付回调的 bug.         // 大写、句号
❌ Feat: 加了新功能                             // 大写、无 scope、无 subject 描述
❌ update code                                 // 类型乱、subject 不清楚
```

### 1.5 Body 与 Footer

🟡 **推荐**：

**Body 模板**：
```
feat(order): 接收订单状态机重构

把订单状态机从 if-else 重构为枚举驱动的 State 模式
- 增加 OrderState 接口
- 移除 OrderStatusTransitioner 服务
- 单元测试覆盖率从 60% 提升到 95%

业务影响：行为不变，无功能差异
```

**Footer 模板**（关联 issue）：
```
fix(payment): 修复支付重复扣款

- Closes #1234
- Refs #1230
- BREAKING CHANGE: pay 接口返回值从 boolean 改为 PaymentResult
```

### 1.6 关联中文规范（团队级可选）

🟢 **可选**：如果团队 commit 历史是中文，可以用中文 type，但需要工具支持：

```
新增：订单取消接口
修复：支付回调幂等校验失败
重构：提取 UserMapper 为独立类
```

🟡 **推荐**：

- **全项目统一**（要么全英文 type，要么全中文 type，不可混用）
- 一致性 > 个人偏好

## 2. Commit 内容规范

### 2.1 Atomic Commit（原子提交）

🟡 **推荐**：

- **一个 commit 做一件事**（一个 feature / 一个 fix / 一个 refactor）
- **不要把多个不相关变更混在一个 commit 里**（难以 revert / bisect）

**反例**（一个 commit 包含 3 件不相关事）：
```
fix(payment): 修复支付 bug，顺手改了日志，加了 user 模块

- 修复支付回调
- 改 Log.info 为 Log.error（无关）
- 新增 UserController（无关）
```

### 2.2 Commit 频率

🟢 **可选**：

- **建议**：1 个功能点 = 1 个 commit（feature / method / class）
- **避免**：1 个大文件全改 = 1 个 commit（拆成多个小 commit）
- **避免**：每修改一行代码 = 1 个 commit（过度拆分）

### 2.3 Commit 前必跑检查清单

🟡 **推荐**（AI 写代码后、commit 之前**主动核对**）：

**编译与测试**：
- [ ] `mvn clean compile` 或 `./gradlew compileJava` 通过
- [ ] `mvn test` 或 `./gradlew test` 全部通过
- [ ] 新增代码有对应单元测试（覆盖率不低于团队门槛）
- [ ] 没有遗留 `TODO` / `FIXME`（有的话必须显式 commit 提及）

**静态检查**：
- [ ] Checkstyle 通过
- [ ] SpotBugs 没有 Medium 级别以上警告
- [ ] p3c-pmd P3C 规约全部通过
- [ ] IDE 自动格式化已触发（`Ctrl + Alt + L`）

**代码完整性**：
- [ ] 没有死代码 / 注释掉的代码块
- [ ] 没有 `System.out.println`（生产代码）
- [ ] 没有 `// FIXME` 残留
- [ ] 没有 `import` 没用的类
- [ ] 没有 `static` 成员没被清理

### 2.4 不要 commit 的文件

🟡 **推荐**：

- ❌ IDE 配置：`.idea/`、`.vscode/`、`*.iml`、`*.iws`、`*.ipr`
- ❌ 编译产物：`target/`、`build/`、`out/`、`*.class`、`*.jar`
- ❌ 依赖缓存：`node_modules/`、`vendor/`（Java 不常用）
- ❌ 运行时产物：`logs/`、`*.log`
- ❌ 用户本地文件：`*.swp`、`*~`、`.DS_Store`、`Thumbs.db`
- ❌ 敏感信息：`.env`、`*.pem`、`*.key`、`password.txt`
- ❌ 临时文件：`*.tmp`、`*.bak`、`~$*`

详见 § 3 完整 `.gitignore` 模板。

### 2.5 大文件用 Git LFS

🟡 **推荐**：

- **> 100MB 的文件必须用 Git LFS**（Git 直接跟踪性能极差）
- 详情见 § 4

### 3.2 `.gitignore` 分类决策

🟡 **推荐**（跟 Unity 08 章节一致 + Java 特定调整）：

| 类别 | 典型条目 | 原因 |
|---|---|---|
| **编译产物** | `target/` / `build/` / `*.class` / `*.jar` | 编译时自动生成 |
| **IDE 配置** | `.idea/` / `.vscode/` / `*.iml` / `.classpath` | IDE 特定（团队成员可能用不同 IDE）|
| **OS 特定** | `.DS_Store` / `Thumbs.db` | 跨平台协作的差异 |
| **日志** | `*.log` / `logs/` | 运行时生成 |
| **临时文件** | `*.tmp` / `*.bak` / `*.swp` | 编辑器临时文件 |
| **敏感信息** | `.env` / `*.pem` / `secret*` | **绝不能入仓**（违反 = 安全事件）|
| **本地配置** | `application-local.*` | 团队成员本地个性化配置 |

### 3.3 `.gitignore` 全局 vs 项目级

🟡 **推荐**：

🟡 **推荐**：

- **项目根目录 `.gitignore`**（**所有团队成员**共享，必填）
- **全局 `~/.gitignore_global`**（**个人**忽略，本机特定的临时文件）

**全局配置**：
```bash
git config --global core.excludesFile ~/.gitignore_global
```

### 3.4 已经误 commit 的文件如何清理

🟡 **推荐**：

- **已经入仓的文件**单纯加 `.gitignore` 是不够的（Git 还会跟踪）
- 用 `git rm --cached` 移除跟踪：

```bash
# 从跟踪移除（保留本地文件）
git rm --cached target/
git rm --cached *.iml

# 提交
git commit -m "chore: 从跟踪移除 IDE / 编译产物文件"

# 推送
git push
```

### 3.5 `gitingore` 验证

🟢 **参考**：

```bash
# 检查哪些文件没有被忽略（应该只显示有意跟踪的文件）
git status --ignored

# 检查特定文件是否被忽略
git check-ignore -v path/to/file
```

### 3.6 不要把 `.gitignore` 写到子目录

🟡 **推荐**：

- **`.gitignore` 放项目根目录** 一个就够
- 子目录的 `.gitignore` 影响范围有限且易混乱
- 例外：构建工具自动生成（如 `src/main/resources/.gitkeep` 标记空目录）

## 4. Git LFS

### 4.1 哪些文件用 LFS

🟡 **推荐**（P3C 工程结构章节隐含）：

- **> 100MB 的二进制文件**用 Git LFS（Git 直接跟踪性能极差）
- 常见 Java 项目 LFS 应用：

| 文件类型 | 是否 LFS | 原因 |
|---|---|---|
| `*.jar` / `*.war`（制品）| ✅ 是 | 通常 > 10MB，且应在制品库 |
| `*.pdf`（设计文档 / 第三方指南）| ✅ 是 | 通常几个 MB 到几十 MB |
| `*.docx`（设计文档）| ⚠️ 视情况 | 小文件 < 1MB 不必 LFS |
| `*.png` / `*.jpg`（图标 / 截图）| ❌ 不必 LFS | 通常 < 几百 KB，Git 跟踪 OK |
| `*.mp4` / `*.mov`（演示视频）| ✅ 是 | 通常几十 MB 到几 GB |
| `*.proto`（Protobuf 定义）| ❌ 不必 LFS | 文本文件，跟代码一起 |

🟡 **推荐**：原则：

1. **二进制 + > 100KB 考虑 LFS**
2. **生成 / 编译产物**应该用制品库（Nexus / Artifactory），**不**入库
3. **设计文档**（PDF / Word）通常 LFS

### 4.2 .gitattributes 配置

🟡 **推荐**：项目根目录 `.gitattributes`：

```gitattributes
# 二进制大文件走 LFS
*.jar filter=lfs diff=lfs merge=lfs -text
*.war filter=lfs diff=lfs merge=lfs -text
*.pdf filter=lfs diff=lfs merge=lfs -text
*.psd filter=lfs diff=lfs merge=lfs -text
*.ai filter=lfs diff=lfs merge=lfs -text
*.mp4 filter=lfs diff=lfs merge=lfs -text

# 文本文件强制 LF（跨平台）
*.java text eol=lf
*.xml text eol=lf
*.yml text eol=lf
*.yaml text eol=lf
*.md text eol=lf
*.properties text eol=lf
*.sh text eol=lf
```

### 4.3 LFS 命令速查

🟢 **参考**：

```bash
# 安装 LFS
git lfs install  # 全局只需一次

# 跟踪文件类型（在每个仓库）
git lfs track "*.jar"
git lfs track "*.pdf"

# 查看跟踪列表
git lfs track

# 普通 git add + commit + push（LFS 自动接管）
git add bigfile.jar
git commit -m "feat: 添加初始数据库 jar"
git push
```

### 4.4 LFS 注意事项

🟡 **推荐**：

- **LFS 服务器容量有限**（GitHub 免费 1GB / GitLab 免费 5GB）
- **大型项目监控 LFS 用量**（超限要付费或换自建服务器）
- **LFS 文件必须 `.gitattributes`** 入仓才生效

## 5. 分支策略

### 5.1 Git Flow vs GitHub Flow vs Trunk Based

🟡 **推荐**：3 种主流分支策略选型：

| 策略 | 分支模型 | 适用 |
|---|---|---|
| **Git Flow** | `master` + `develop` + `feature/*` + `release/*` + `hotfix/*` | 传统 / 有版本号的项目 |
| **GitHub Flow** | `main` + `feature/*` + `hotfix/*` | 持续部署的项目（推荐 SaaS / Web 服务） |
| **Trunk Based** | 只有 `main`，短生命周期分支 | 高信任团队 + 高级 CI / 部署能力 |

🟡 **推荐**：

- **绝大多数 Java 后端项目**用 **GitHub Flow**（main + feature 分支 + PR）
- **有正式版本的库 / SDK** 用 **Git Flow**

### 5.2 分支命名规范

🟡 **推荐**：

| 类型 | 命名格式 | 示例 |
|---|---|---|
| **长期分支** | `main` / `master` / `develop` | `main` |
| **功能分支** | `feature/<ticket-id>-<short-desc>` | `feature/1234-add-payment-callback` |
| **修复分支** | `fix/<ticket-id>-<short-desc>` | `fix/5678-fix-npe-in-user-mapper` |
| **热修复分支** | `hotfix/<ticket-id>-<short-desc>` | `hotfix/prod-fix-payment-double-charge` |
| **发布分支** | `release/<version>` | `release/v1.2.0` |
| **实验性分支** | `experiment/<desc>` | `experiment/try-new-orm` |

🟡 **推荐**：

- **分支名小写**，多词用 `-` 分隔
- **不包含人名**（如 `john-fix-bug`，人会离开项目）
- **不包含完整句子**（如 `fix-the-issue-when-user-clicks-button`，过长）

### 5.3 主分支保护（GitHub / GitLab）

🟡 **推荐**：在 GitHub/GitLab 仓库设置中：

- **`main`** 必须设 branch protection：
  - ❌ 不允许直接 push
  - ✅ 必须通过 PR merge
  - ✅ 至少 1 个 reviewer 通过
  - ✅ CI / 测试通过才允许 merge
  - ✅ 不允许 force push
- **`develop`**（如用 Git Flow）类似保护

### 5.4 Commit 前同步主干

🟡 **推荐**：

```bash
# 提交前先拉主干
git fetch origin main
git rebase origin/main  # 或 git merge origin/main

# 此时再 push + 提 PR
```

🟡 **推荐**：

- **PR merge 前 rebase 最新 main**（避免冲突遗留到 merge）
- **不推荐直接 `git pull`**（会 merge commit 污染历史）

### 5.5 删除功能分支

🟡 **推荐**：

- **feature 分支合并后立即删除**（本地 + 远程）
- 避免仓库分支列表膨胀

```bash
# 合并后清理
git branch -d feature/1234-add-payment  # 本地
git push origin --delete feature/1234-add-payment  # 远程
```

## 6. Pull Request 流程

### 6.1 PR 创建要求

🟡 **推荐**（P3C 隐含）：

PR 标题和描述**必须**包含：

- **改动的目的**（Why）
- **改动的范围**（What 改了哪些文件）
- **测试覆盖**（新增 / 修改的测试）
- **关联 issue**（Closes #1234 / Refs #1234）
- **截图 / 录屏**（UI 改动时）

**PR 标题**遵循 Conventional Commits（与 commit 标题一致）：

```
feat(order): 添加订单取消接口
fix(payment): 修复支付回调幂等校验失败
```

### 6.2 PR 大小控制

🟡 **推荐**：

- **PR 不超 400 行代码变更**（超过容易 review 不仔细）
- 超过就**拆成多个小 PR**（一个 PR 一个功能）
- 大型重构可能要分阶段：先抽接口 → 再实现 → 再调用

🟡 **推荐**：

- 不接受 1000+ 行的 PR（review 不可靠）
- 不接受"未来用"代码（未用代码）

### 6.3 Reviewer 要求

🟡 **推荐**：

- **至少 1 个 reviewer 通过**（小型项目）
- **核心代码**（支付 / 订单 / 安全）至少 2 个 reviewer
- **Approve + CI 通过**才能 merge

### 6.4 自己 review 自己

🟡 **推荐**：

- **不允许自己 merge 自己的 PR**（必须别人 review）
- 如紧急修复：至少 1 个同事线上确认

### 6.5 Merge 策略

🟡 **推荐**：

| 策略 | 何时用 |
|---|---|
| **Squash merge** | feature 分支 → main（小 PR / 临时分支） |
| **Rebase merge** | 长期维护分支（保持线性历史） |
| **Merge commit** | release 分支（保留合并点） |

🟡 **推荐**：

- **不允许 force push 到 `main`**（保护历史）
- merge 后保留 PR 关联（issue auto-close）

### 6.6 Commit message 钩子（commit-msg）

🟡 **推荐**：用 Git hook 强制 commit message 格式：

```bash
# .git/hooks/commit-msg
#!/bin/bash
commit_msg=$(cat "$1")
regex='^(feat|fix|docs|style|refactor|perf|test|chore|build|ci|revert)(\([a-z-]+\))?!?: .{1,50}$'

if [[ ! "$commit_msg" =~ $regex ]]; then
    echo "❌ Commit message 不符合 Conventional Commits 格式"
    echo "   格式: <type>(<scope>): <subject>"
    echo "   示例: feat(order): 添加订单取消接口"
    exit 1
fi
```

用 `commitlint`（npm）也能达到同样效果。

## 7. Git 高级操作（AI 视角扩展）

### 7.1 Revert vs Reset

🟡 **推荐**：

| 场景 | 用法 |
|---|---|
| **撤销已 push 的 commit** | **`git revert <hash>`**（生成新 commit 撤销改动）|
| **撤销未 push 的 commit** | **`git reset --soft <hash>`**（保留改动到 staging）|
| **彻底删除本地 commit** | **`git reset --hard <hash>`**（**慎用，会丢代码**）|

🟡 **推荐**：

- **永远不要对已 push 的 commit 用 `git reset --hard`**（会与远程冲突，破坏历史）。即使只处理本地 commit，执行前也必须获得使用者明确授权，并告知会丢弃目标提交之后的本地提交及已跟踪文件的未提交改动。

### 7.2 Rebase vs Merge

🟡 **推荐**：

- **本地分支整理 commit 用 `git rebase`**（让历史线性美观）
- **公开分支合并用 `git merge`**（保留合并点）

✅ **正例**：
```bash
# 本地分支整理自己的 commit
git fetch origin
git rebase origin/main  # 把你分支的 N 个 commit 重新在最新 main 上重演
git push --force-with-lease  # 安全 force push（不会被覆盖别人的改动）
```

### 7.3 Bisect 找引入 bug 的 commit

🟢 **可选**：当生产出现 bug 时用 `git bisect` 找出第一个引入 bug 的 commit：

```bash
git bisect start
git bisect bad  # 当前 commit 是坏的
git bisect good v1.0.0  # 这个 tag 是好的

# Git 自动切到一个中间 commit，测试后告诉它是 good 还是 bad
# ... 重复 ...
git bisect reset  # 结束
```

### 7.4 Stash 临时保存工作

🟢 **参考**：

```bash
# 临时保存（应对紧急切分支）
git stash save "WIP: feature half done"

# 切到其他分支处理问题
git checkout hotfix/...

# 切回来
git checkout feature/...
git stash pop  # 恢复
```

### 7.5 Cherry-pick 选择性挑 commit

🟢 **参考**：

```bash
# 把某个 commit 从一个分支挑到另一个
git cherry-pick <hash>

# 多个 commit
git cherry-pick <hash1> <hash2>

# 范围
git cherry-pick <hash1>..<hash2>
```

### 7.6 Tag 发布版本

🟡 **推荐**（P3C 二方库版本号章节）：

- 二方库发布用**语义化版本**：`MAJOR.MINOR.PATCH`
- 发布时打 tag：

```bash
git tag -a v1.2.0 -m "release: version 1.2.0"
git push origin v1.2.0
```

### 7.7 危险命令清单（AI 写代码时不要做）

🟡 **推荐**：

- 下列命令可能使本地或远程改动、提交难以恢复；执行前必须获得使用者明确授权，确认具体目标和影响范围。
- ❌ `git push --force` 到公共分支（用 `--force-with-lease` 替代）
- ❌ `git reset --hard` 到已 push 的 commit
- ❌ `git checkout .` 删所有未提交的改动（**当前所有改动丢失**）
- ❌ `git clean -fd` 删除所有未跟踪文件（**包括新加的代码**）
