# 11 - Java 性能优化规则

> 🟢 本文件适用于 Java 项目的性能调优（JVM/GC/缓存/NIO 等）。
> 🔴 不适用：业务逻辑实现、UI 样式细节、第三方业务 SDK

---

## 1. JVM 内存模型

### 1.1 JVM 运行时数据区

🟡 **推荐**（AI 排查性能问题前必须理解）：

```
┌──────────────────────────────────────────────────┐
│                JVM 内存                           │
│  ┌────────────────────────────────────────────┐  │
│  │  堆 (Heap) — 共享                           │  │
│  │  ├─ Young Generation (新生代)              │  │
│  │  │  ├─ Eden (绝大部分对象在此创建 + 死亡) │  │
│  │  │  ├─ Survivor 0 / 1 (GC 后存活)         │  │
│  │  ├─ Old Generation (老年代) — 长寿命对象  │  │
│  └────────────────────────────────────────────┘  │
│                                                  │
│  ┌─────────┐  ┌────────────┐  ┌───────────────┐  │
│  │Metaspace│  │  Stack     │  │  PC / Native │  │
│  │(元空间) │  │  (栈)      │  │   Method      │  │
│  │类元数据 │  │线程私有    │  │   Stacks      │  │
│  └─────────┘  └────────────┘  └───────────────┘  │
└──────────────────────────────────────────────────┘
```

### 1.2 关键概念

🟡 **推荐**：

| 区域 | 用途 | 调优影响 |
|---|---|---|
| **Eden** | 新对象分配区 | 满了触发 `Minor GC` |
| **Survivor** | Minor GC 后存活的对象过渡区 | 多轮存活后进 Old |
| **Old Generation** | 长寿命对象 | 满了触发 `Full GC`（暂停时间最长）|
| **Metaspace** | 类元数据（代替 JDK 7 的 PermGen）| 类加载过多时 OOM |
| **Stack** | 线程私有，方法调用栈 | 栈深度过深抛 `StackOverflowError` |

### 1.3 内存溢出的常见类型

🟡 **推荐**（AI 排查 OOM 时立即对应）：

| OOM 类型 | 异常 | 常见原因 |
|---|---|---|
| **堆 OOM** | `OutOfMemoryError: Java heap space` | 内存泄漏 / 大对象 / 数据规模超预期 |
| **栈 OOM** | `StackOverflowError` | 无限递归 / 循环引用 |
| **元空间 OOM** | `OutOfMemoryError: Metaspace` | 类加载过多（动态代理 / JSP 编译）|
| **GC OOM** | `OutOfMemoryError: GC overhead limit exceeded` | 99% 时间做 GC 但回收不到 2% 内存 |
| **直接内存 OOM** | `OutOfMemoryError: Direct buffer memory` | Netty / NIO 分配过多堆外内存 |

## 2. GC 选型

### 2.1 主流 GC 收集器

🟡 **推荐**（AI 选择 GC 时立即对照）：

| GC | JDK 适用 | 暂停时间 | 吞吐量 | 适用场景 |
|---|---|---|---|---|
| **Serial GC** | 8+ | 长 | 高 | 单线程 / 客户端 / 小数据量 |
| **Parallel GC** | 8+ | 中 | **极高** | 批处理 / 后台计算 / 不在乎暂停 |
| **CMS** | 8（**JDK 9 起废弃**）| 短 | 中 | 老 Web 应用兼容（**不推荐新项目**）|
| **G1（Garbage First）** | 8u40+ 默认 | **短且可控** | 高 | **Web 服务首选（推荐）** |
| **ZGC** | 11+（JDK 15+ 生产可用）| **< 1ms** | 高 | 超大堆（TB 级）/ 超低延迟 |
| **Shenandoah** | 12+ | < 10ms | 高 | 与 ZGC 类似的低延迟选择 |
| **Epsilon GC** | 11+ | 无 GC | — | 测试 / 微服务无分配场景 |

### 2.2 GC 选型决策树

🟡 **推荐**（AI 项目初始化选 GC 时立即用）：

```
是否需要 < 10ms 暂停？
├─ 是 → 堆 > 16GB？
│     ├─ 是 → ZGC（JDK 17+）
│     └─ 否 → ZGC 或 Shenandoah（JDK 17+）
└─ 否 → G1（JDK 8u40+，默认）
```

🟡 **推荐**（P3C 服务器隐含）：

🟡 **推荐**：

- **JDK 8 项目**：**G1**（`-XX:+UseG1GC`），不推荐 CMS
- **JDK 11+ 项目**：**G1 默认**（已经不需要显式开启）或 ZGC（超低延迟）
- **JDK 17+ 项目**：**G1** 是默认首选，**ZGC** 用于超低延迟场景

### 2.3 Minor GC vs Major GC vs Full GC

🟢 **参考**：

- **Minor GC**：Young 区满，**暂停短**（毫秒级）
- **Major GC / Old GC**：Old 区满（部分 GC 是混合收集 G1 等）
- **Full GC**：整个堆 + 方法区，**暂停长（秒级）**，应避免

## 3. 性能分析工具（AI 视角扩展）

P3C 黄山版对性能工具几乎不提。AI 排查性能时**必备工具箱**如下。

### 3.1 JDK 内置工具

🟡 **推荐**：

| 工具 | 命令 | 用途 |
|---|---|---|
| **jstat** | `jstat -gcutil <pid> 1000` | 实时查看 GC 情况（每秒一次）|
| **jmap** | `jmap -heap <pid>` | 堆内存详情 |
| **jmap** | `jmap -histo:live <pid>` | 存活对象直方图（看哪些类占用大）|
| **jstack** | `jstack <pid>` | 线程栈快照（排查死锁 / 阻塞）|
| **jcmd** | `jcmd <pid> VM.native_memory summary` | JVM 本地内存详情 |
| **jinfo** | `jinfo -flags <pid>` | 当前 JVM 参数 |

### 3.2 Arthas（阿里开源 🔥）

🟡 **推荐**：

- **Arthas 是 Java 排查线上问题的首选工具**（生产环境不需要重启 / 不需要重新部署）
- 提供 dashboard / thread / jad / watch / trace / ognl 等功能

**常用命令**：

```bash
# 启动
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar

# 1. dashboard - 实时面板（线程 / 内存 / GC / 运行时信息）
dashboard

# 2. thread - 查看线程状态（CPU 占用最高的线程）
thread -n 3

# 3. jad - 反编译（看运行中的类是哪个版本，排查发布版本问题）
jad com.example.OrderService

# 4. watch - 监视某个方法的入参 / 返回值 / 异常
watch com.example.OrderService createOrder "{params, returnObj, throwExp}" -x 3

# 5. trace - 方法内部调用链 + 耗时
trace com.example.OrderService createOrder '#cost > 50'

# 6. tt - 时间隧道，录制方法调用（可重放）
tt -t com.example.OrderService createOrder

# 7. profiler - 火焰图
profiler start --event cpu
# 跑一段业务
profiler stop --format html -o /tmp/profile.html
```

🟡 **推荐**：线上排查流程：

```
发现接口慢 → dashboard 看整体状态 → thread 找最忙线程
        → trace 该方法找最慢子调用 → watch 异常看参数
        → jad 看是否发布了错误版本
```

### 3.3 async-profiler（火焰图）

🟡 **推荐**（高 CPU 场景必用）：

- **async-profiler** 生成 CPU 火焰图，**找热点方法最有效**
- 支持 Linux perf_events，**不依赖 JVMTI**，生产友好

```bash
# 抓 30 秒 CPU 火焰图
./profiler.sh -d 30 -f /tmp/flame.html <pid>
```

### 3.4 JFR（Java Flight Recorder）

🟡 **推荐**（深度排查时启用）：

- **JFR 是 JDK 自带的事件记录器**（商用级别）
- 启用方式：

```bash
# 启动时启用
java -XX:+UnlockDiagnosticVMOptions -XX:+DebugNonSafepoints -XX:+FlightRecorder -XX:StartFlightRecording=duration=60s,filename=recording.jfr -jar app.jar

# 动态启用（不重启）
jcmd <pid> JFR.start duration=60s filename=recording.jfr
jcmd <pid> JFR.stop
```

JFR 包含**锁 / GC / 类加载 / IO / 异常 / 线程 / safepoint** 等几乎所有事件。

### 3.5 VisualVM + MAT

🟢 **可选**（开发阶段 + 内存泄漏排查）：

- **VisualVM**：实时监控 JVM（轻量）
- **Eclipse MAT（Memory Analyzer）**：分析 heap dump，找内存泄漏

```bash
# 拿到 heap dump
jmap -dump:format=b,file=heap.hprof <pid>

# 用 MAT 打开（找 leak suspect）
```

### 3.6 Prometheus + Grafana（生产监控）

🟡 **推荐**：

- 生产环境必须接 **Prometheus + Grafana**（或 SkyWalking / ARMS）
- 暴露 actuator 端点：

```yaml
# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  metrics:
    tags:
      application: ${spring.application.name}
```

- 监控关键指标：**P99 / P95 响应时间 / QPS / GC 暂停 / 堆内存 / 线程数**

### 3.7 工具选型决策

🟡 **推荐**：

| 排查场景 | 推荐工具 |
|---|---|
| **整体监控** | Prometheus + Grafana |
| **线上实时排查** | Arthas（首选）|
| **CPU 热点找问题方法** | async-profiler 火焰图 |
| **深度事件记录** | JFR |
| **内存泄漏分析** | heap dump + MAT |
| **GC 详情** | jstat -gcutil / JFR |
| **线程死锁** | jstack / Arthas thread |
| **生产持续 profile** | async-profiler 定时抓 |

## 4. 性能调优 4 大支柱

P3C 隐含"避免重复 + 高效设计 + 异常处理 + 资源隔离" 4 维度，但没明说。AI 视角提炼 4 大调优支柱。

### 4.1 减少无效操作

🟡 **推荐**：

- 避免在循环里创建对象（GC 压力）
- 避免重复计算（用缓存 / 用现成结果）
- 避免过度日志（DEBUG 不开 / 生产仅 ERROR）
- 避免大事务（见 03 § 7.3）
- 避免深嵌套锁（短锁）

**反例**：
```java
// ❌ 循环里 new StringBuilder（GC 压力 + 多次扩容）
public String join(List<String> items) {
    StringBuilder sb = new StringBuilder();
    for (String item : items) {
        sb.append(item).append(",");
    }
    return sb.toString();
}

// ✅ 预估大小 + 复用
public String join(List<String> items) {
    StringBuilder sb = new StringBuilder(items.size() * 8);
    for (String item : items) {
        sb.append(item).append(',');
    }
    sb.setLength(sb.length() - 1);  // 删除末尾多余的 ","
    return sb.toString();
}
```

### 4.2 提升计算效率

🟡 **推荐**：

- 选对数据结构（见 01 § 4 集合处理 已讲）
- 用 `StringBuilder` 不 `+` 拼接
- 用基本类型不包装类型
- 用 `parallelStream()` 处理 CPU 密集列表（注意线程安全）
- 用 `ConcurrentHashMap` 不 `synchronized(map)`

### 4.3 异步与并行

🟡 **推荐**：

- IO 密集操作用异步（见 04 § 7 CompletableFuture）
- CPU 密集计算用并行（`parallelStream` / `ExecutorService`）
- 不阻塞主线程（Controller 调完 Service 立即返回）

### 4.4 资源复用与缓存

🟡 **推荐**：

- 数据库连接池调优（见 07 § 8 连接池）
- 线程池（见 04 § 2 线程池）
- 多级缓存（CPU L1/L2/L3 → JVM 堆 → 本地缓存 Caffeine → Redis 分布式）
- 对象池（如 Netty 的 `Recycler`）

## 5. 对象池与缓存

### 5.1 缓存层级

🟡 **推荐**（多级缓存架构，AI 项目初期规划时立即用）：

```
请求 → 本地缓存（Caffeine，TTL=秒级）→ Redis 分布式缓存（TTL=分钟级）
                                ↓ miss
                          DB（MySQL / PostgreSQL）
```

🟡 **推荐**：**70%+ 读场景**才考虑加缓存；**30%- 写场景**写优先。

### 5.2 缓存三大问题

🟡 **推荐**（AI 引入缓存时立即考虑）：

| 问题 | 含义 | 解决 |
|---|---|---|
| **缓存穿透** | 查询不存在的数据（绕过缓存直接打 DB）| 布隆过滤器 / 空值缓存（短 TTL）|
| **缓存击穿** | 热点 key 过期瞬间所有请求打 DB | 互斥锁 / singleflight / 逻辑过期 |
| **缓存雪崩** | 大量 key 同时过期 / 缓存服务宕机 | 过期时间加随机值 / 多级缓存 / 熔断降级 |

🟡 **推荐**：单飞模式（防止击穿）：

```java
public OrderDTO getByIdWithCache(Long id) {
    // 1. 先查缓存
    OrderDTO cached = cache.get(id);
    if (cached != null) return cached;

    // 2. 没查到：用 singleflight（多个请求只穿透一次到 DB）
    return cache.get(id, () -> orderRepository.findById(id).map(OrderMapper::toDTO).orElseThrow());
}
```

### 5.3 Caffeine 配置（本地缓存）

🟡 **推荐**：Caffeine 是 Spring Boot 默认的本地缓存实现：

```java
@Configuration
public class CacheConfig {
    @Bean
    public CaffeineCacheManager orderCacheManager() {
        CaffeineCacheManager manager = new CaffeineCacheManager();
        manager.setCaffeine(Caffeine.newBuilder()
            .expireAfterWrite(Duration.ofMinutes(5))  // 写入后 5 分钟过期
            .maximumSize(10_000)                      // 最多 10000 个 entry
            .recordStats());                         // 开启统计
        return manager;
    }
}
```

### 5.4 对象池

🟡 **推荐**：

- **不是所有对象都需要池化**（短寿命对象 new 比池化更快）
- 对象池**适用场景**：
  - **数据库连接**（必须池化）
  - **线程**（必须池化）
  - **Netty ByteBuf**（Recycler 池化）
  - **TCP 长连接 / Socket**（池化）
  - **HTTP 客户端**（如 Apache HttpClient 连接池）

🟡 **推荐**：

- **不要池化短寿命对象**（StringBuilder / 普通 POJO / Map）
- **不要池化大对象**（> 几十 KB）

### 5.5 大对象处理

🟡 **推荐**：

- **大对象（> 几十 KB）会直接进 Old Generation，频繁分配会触发 Full GC**
- 大文件下载 / 上传：**流式读写**不要一次性读入内存
- 用 `InputStream` / `OutputStream` 不用 `byte[]` 全缓存
- 大 JSON 字段：**JSONB 分字段存储**或拆表

### 5.6 缓存一致性

🟡 **推荐**：

- **更新 DB 后立即删除缓存**（不用 `update DB → update cache`，避免不一致）
- 用 **Canal 监听 binlog** 异步失效缓存是常见解耦方案
- **短暂不一致是可接受的**（最终一致性 < 1 秒），不强求强一致

## 6. NIO 与异步

### 6.1 同步阻塞 IO vs NIO

🟡 **推荐**：

| 模式 | 线程 / 连接 | 适用 |
|---|---|---|
| **BIO**（同步阻塞）| 1 线程 / 1 连接 | 小并发（< 1000）|
| **NIO**（同步非阻塞）| 1 线程 / N 连接（selector）| 高并发 IO |
| **AIO**（异步 IO）| 不需要 selector | 用得少（Netty 用 NIO）|
| **Netty** | NIO + 异步事件驱动 | **99% 高并发网络应用首选** |

### 6.2 Netty 实战

🟢 **参考**（项目级 / 不强制 AI 写代码立即遵守）：

- Netty 是 Java NIO 网络编程的事实标准
- 内置 ByteBuf 池化 / Pipeline 责任链 / 异步事件
- 用于：IM / RPC / 长连接 / 网关

### 6.3 异步数据库访问

🟡 **推荐**：

- Spring 项目用 **`spring-boot-starter-data-r2dbc`**（R2DBC 响应式）
- 或 **Spring + 异步 JDBC**（Future 包装 JDBC）

🟡 **推荐**：

- **不要用同步 JDBC 在 Netty 的 EventLoop 线程调用**（阻塞 IO 会卡死 EventLoop）

### 6.4 异步远程调用

🟡 **推荐**：

- 远程 RPC / HTTP 调用**必加超时**（避免线程无限等待）
- 用 **CompletableFuture** 并行调用多个远程服务（如 见 04 § 7）
- 用 **Resilience4j / Sentinel** 熔断降级（如 见 06 § 7）

### 6.5 异步日志

🟢 **参考**（生产可观测性重要）：

- **AsyncAppender**（Logback）：业务线程把日志丢到队列就返回，写盘由单独线程负责（见 09 § 11.4）
- **`neverBlock=true`**：队列满时**丢弃不阻塞**（宁丢日志不卡业务）

## 7. JVM 启动参数（P3C 强制）

### 7.1 堆大小设置

🟡 **推荐**（P3C 服务器第 4 条）：

- **线上生产环境，JVM 的 Xms 和 Xmx 设置一样大小的内存容量**
- **避免在 GC 后调整堆大小带来的压力**

**正例**：
```bash
java -Xms4g -Xmx4g -jar app.jar
# Xms = Xmx = 4GB，JVM 启动时直接申请 4GB（不再动态扩容）
```

### 7.2 OOM 自动 dump

🟡 **推荐**（P3C 服务器第 3 条）：

- **给 JVM 设置 `-XX:+HeapDumpOnOutOfMemoryError` 参数**
- **让 JVM 碰到 OOM 场景时输出 dump 信息**
- OOM 的发生有概率（相隔数月才出现一次），**现场信息对查错非常有价值**

```bash
java -XX:+HeapDumpOnOutOfMemoryError \
     -XX:HeapDumpPath=/var/log/oom-dump.hprof \
     -jar app.jar
```

🟡 **推荐**：

- 同时加 `-XX:OnOutOfMemoryError="kill -9 %p && /restart.sh"`（自动重启）

### 7.3 标准启动参数模板

🟡 **推荐**（生产 Spring Boot 项目通用模板）：

```bash
java \
  -Xms4g -Xmx4g \
  -Xss512k \
  -XX:MetaspaceSize=512m -XX:MaxMetaspaceSize=512m \
  -XX:+UseG1GC \
  -XX:MaxGCPauseMillis=200 \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/var/log/oom/ \
  -XX:+PrintGCDetails -XX:+PrintGCDateStamps \
  -Xloggc:/var/log/gc/gc.log \
  -XX:+UseGCLogFileRotation -XX:NumberOfGCLogFiles=10 -XX:GCLogFileSize=100M \
  -jar app.jar
```

### 7.4 容器感知

🟡 **推荐**（容器化部署必须）：

- **JDK 10+ 默认启用 cgroups 内存感知**（`-XX:+UseContainerSupport`，默认 `true`）
- **JDK 11+ 中 `-Xmx` 不指定时自动取容器内存限制**
- **容器环境建议显式指定**（避免 K8s OOM Kill）

```bash
# 推荐：让 JVM 自动探测容器内存（不显式 -Xmx）
java -jar app.jar
# JVM 自动取 max(container_memory_limit, 1GB) 的 25%
```

### 7.5 GC 日志

🟡 **推荐**：

- 生产环境**必须开 GC 日志**（便于事后排查）
- G1 默认有详细 log：

```bash
-verbose:gc \
-XX:+PrintGCDetails \
-XX:+PrintGCDateStamps \
-XX:+PrintTenuringDistribution \
-Xloggc:/var/log/gc.log
```

🟡 **推荐**：用 **GCViewer** 或 **gceasy.io** 在线解析 GC log。

### 7.6 启动时间优化（Cloud Native）

🟡 **推荐**：

- **CDS（Class Data Sharing）**：JDK 12+ 默认开启 `-Xshare:auto`，**减少启动时间 10%+**
- **AppCDS / Spring Native**：GraalVM 把 Java 编译为原生镜像，**启动 ms 级**
- **AppCDS 自定义**：

```bash
# 1. 启动时生成 archive
java -Xshare:dump -XX:SharedArchiveFile=app-cds.jsa -jar app.jar
# 2. 之后启动用 archive
java -Xshare:on -XX:SharedArchiveFile=app-cds.jsa -jar app.jar
```

### 7.7 危险启动参数

🟡 **推荐**（AI 启动参数检查清单）：

- ❌ **不要用 `-XX:DisableExplicitGC`**（隐藏 GC 调用问题）
- ❌ **不要用 `-Xmn` 强制新生代大小**（让 JVM 自动调整）
- ❌ **不要用 `-XX:+UseCMSCollector`**（JDK 14 移除）
- ❌ **不要用`-Xss` 设过大栈**（占内存，通常 256K / 512K 就够）
