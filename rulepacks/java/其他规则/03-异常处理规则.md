# 03 - Java 异常处理规则

> 🟢 本文件适用于 Java 项目的异常处理（checked/unchecked/业务异常/全局处理器）。<br>
> 🔴 不适用：业务逻辑实现、UI 样式设计

---



***

## 1. 异常分类

### 1.1 Java 异常三大类

🟡 **推荐**（必须理解才能正确处理）：

| 类型                              | 父类                              | 是否必须捕获       | 典型场景                                                      |
| ------------------------------- | ------------------------------- | ------------ | --------------------------------------------------------- |
| **Error**                       | `Throwable`                     | 否（无法恢复）      | `OutOfMemoryError` / `StackOverflowError`                 |
| **RuntimeException**（unchecked） | `RuntimeException`              | 否（可预检查规避）    | `NullPointerException` / `IndexOutOfBoundsException`      |
| **Checked Exception**           | `Exception`（非 RuntimeException） | **是**（编译器强制） | `IOException` / `SQLException` / `ClassNotFoundException` |

### 1.2 不要 catch 可预检查的 RuntimeException

🟡 **推荐**：

- **Java 类库中定义的可以通过预检查方式规避的** **`RuntimeException`** **不应该通过 catch 方式来处理**
  - 典型：`NullPointerException`、`IndexOutOfBoundsException`
  - **正例**：`if (obj != null) { obj.method(); }`
  - **反例**：
    ```java
    try { obj.method(); } catch (NullPointerException e) { ... }
    ```
- **例外**：无法通过预检查的（如 `NumberFormatException` 解析字符串数字）不得不 catch

### 1.3 异常不要做流程控制

🟡 **推荐**：

- **异常不要用来做流程控制、条件控制**
- **原因**：异常设计的初衷是解决程序运行中的各种意外情况；异常的处理效率**比条件判断低很多**（构造异常对象需要栈快照）

**反例**：

```java
// ❌ 用异常做循环终止
try {
    while (true) {
        iterator.next();
    }
} catch (NoSuchElementException e) {
    // 跳出循环
}

// ✅ 正例
while (iterator.hasNext()) {
    iterator.next();
}
```

## 2. 自定义异常体系（AI 视角扩展）

P3C 提到"推荐业界已定义过的自定义异常"，但**没给完整设计**。AI 在搭新项目时立即要用的异常体系。

### 2.1 业务异常基类

🟡 **推荐**：所有业务异常继承统一的 `BizException`：

```java
public class BizException extends RuntimeException {

    private final String errorCode;
    private final Object[] errorArgs;

    public BizException(String errorCode, String message) {
        super(message);
        this.errorCode = errorCode;
        this.errorArgs = null;
    }

    public BizException(String errorCode, String message, Object... errorArgs) {
        super(message);
        this.errorCode = errorCode;
        this.errorArgs = errorArgs;
    }

    public BizException(String errorCode, String message, Throwable cause) {
        super(message, cause);
        this.errorCode = errorCode;
        this.errorArgs = null;
    }

    public String getErrorCode() { return errorCode; }
    public Object[] getErrorArgs() { return errorArgs; }
}
```

### 2.2 错误码设计

🟡 **推荐**：错误码采用**分层分类**设计：

```
[A-BB-CCC]
 │ │  └── 3 位：具体错误编号
 │ └───── 2 位：业务模块
 └─────── 1 位：错误大类
```

| 第 1 位 | 大类      | 示例           |
| ----- | ------- | ------------ |
| 1     | 系统级错误   | 10001 系统内部异常 |
| 2     | 参数校验错误  | 20101 参数缺失   |
| 3     | 业务逻辑错误  | 30102 库存不足   |
| 4     | 第三方服务错误 | 40101 支付失败   |
| 5     | 权限错误    | 50101 无权限访问  |
| 9     | 未知错误    | 99999 系统繁忙   |

### 2.3 不允许抛裸 Exception/Throwable

🟡 **推荐**：

- **避免直接抛出** **`new RuntimeException()`**（没有业务含义）
- **不允许抛出** **`Exception`** **或** **`Throwable`**（过于宽泛，无法针对性处理）
- **应使用有业务含义的自定义异常**：`BizException` / `DAOException` / `ServiceException`

**反例**：

```java
// ❌ 没有错误码，调用方无法针对性处理
throw new RuntimeException("用户不存在");

// ❌ 范围太宽，把 Error 也接住了
throw new Exception("出错了");
```

**正例**：

```java
throw new BizException("30102", "库存不足，当前库存={0}", stockQty);
```

### 2.4 checked vs unchecked 选择

🟡 **推荐**：

| 场景                              | 选 unchecked（继承 RuntimeException） | 选 checked（继承 Exception） |
| ------------------------------- | -------------------------------- | ----------------------- |
| **业务逻辑错误**（库存不足 / 参数错误）         | ✅ 推荐                             | ❌                       |
| **调用方无法恢复的错误**                  | ✅ 推荐                             | ❌                       |
| **预期调用方必须处理的错误**（如 IOException） | ❌                                | ✅（编译器会强制）               |
| **跨 RPC / API 调用**              | ✅（避免污染接口签名）                      | ❌（checked 序列化难）         |

**主流选择**：99% 业务异常用 **unchecked**（继承 `BizException extends RuntimeException`），调用方不强制 try-catch，由全局异常处理器统一兜底。

## 3. 捕获与抛出

### 3.1 区分稳定与非稳定代码

🟡 **推荐**：

- catch 时**分清稳定代码和非稳定代码**
- **稳定代码**：无论如何不会出错的代码（不应 catch）
- **非稳定代码**：尽可能区分异常类型，再做对应的异常处理
- **大段 try-catch 使程序无法根据不同异常做出正确的应激反应**，不利于定位问题，是不负责任的表现

**正例**（用户注册场景）：

```java
// 区分不同的异常情况
if (containsIllegalChar(username)) {
    throw new BizException("20101", "用户名包含非法字符");
}
if (userRepository.existsByName(username)) {
    throw new BizException("20102", "用户名已存在");
}
if (isPasswordTooSimple(password)) {
    throw new BizException("20103", "密码过于简单");
}
// 业务逻辑
userRepository.save(new User(username, password));
```

### 3.2 捕获异常必须处理

🟡 **推荐**：

- **捕获异常是为了处理它**，不要捕获了却什么都不处理而抛弃之
- **不想处理就抛给调用者**
- **最外层的业务使用者必须处理异常**，将其转化为用户可以理解的内容

**反例**：

```java
// ❌ 捕获了什么都不做，吞掉异常
try {
    riskyOperation();
} catch (Exception e) {
    // 空的，bug 被吞了
}
```

**正例**：

```java
try {
    riskyOperation();
} catch (BizException e) {
    throw e; // 业务异常往上抛
} catch (IOException e) {
    log.error("调用外部接口失败", e);
    throw new BizException("40101", "外部服务调用失败", e);
}
```

### 3.3 捕获与抛出的类型必须匹配

🟡 **推荐**：

- **捕获异常与抛异常必须完全匹配**，或者捕获异常是抛异常的父类
- **如果预期对方抛的是绣球，实际接到的是铅球，就会产生意外情况**

**反例**：

```java
// ❌ method 抛 IOException，catch 的是 SQLException（不匹配，IOException 被吞了）
try {
    method();
} catch (SQLException e) {
    log.error("...", e);
}
```

### 3.4 方法返回值与 null

🟡 **推荐**：

- 方法的返回值**可以为 null**，**不强制**返回空集合或空对象
- **必须添加注释充分说明什么情况下会返回 null**
- **防止 NPE 是调用者的责任**——即使被调用方法返回空集合或空对象，调用者也必须考虑：
  - 远程调用失败
  - 序列化失败
  - 运行时异常等场景返回 null 的情况

### 3.5 异常链 cause

🟡 **推荐**：

- 包装异常时**保留原始异常作为 cause**（不要 `new BizException("xxx")` 不传 cause）
  - **正例**：`throw new BizException("40101", "支付失败", originalException);`
  - **反例**：`throw new BizException("40101", "支付失败");`（丢失原始栈）

## 4. NPE 防护（AI 视角扩展）

P3C 第 10 条列出 6 个 NPE 场景，AI 写代码时立即要查的清单。

### 4.1 6 大 NPE 场景

🟡 **推荐**：以下场景**必须做空指针判断或防御**：

1. **返回类型为基本数据类型，return 包装数据类型的对象时**（自动拆箱可能 NPE）
   ```java
   public int f() {
       return integerObject; // integerObject 为 null 时，拆箱抛 NPE
   }
   ```
2. **数据库的查询结果可能为 null**
3. **集合里的元素即使** **`isNotEmpty`，取出的数据元素也可能为 null**
   ```java
   if (CollectionUtils.isNotEmpty(list)) {
       process(list.get(0)); // list.get(0) 可能为 null
   }
   ```
4. **远程调用返回对象时**，**一律要求进行空指针判断**
5. **Session 中获取的数据**，建议 NPE 检查
6. **级联调用** **`obj.getA().getB().getC()`**，一连串调用易产生 NPE
   ```java
   // 正例：用 Optional
   Optional.ofNullable(user)
       .map(User::getAddress)
       .map(Address::getCity)
       .ifPresent(city -> log.info(city));
   ```

### 4.2 NPE 防御的 3 个工具

🟡 **推荐**：

| 工具                                                               | 适用场景   | 示例                                                              |
| ---------------------------------------------------------------- | ------ | --------------------------------------------------------------- |
| **`Optional`**                                                   | 多层级联调用 | `Optional.ofNullable(obj).map(o -> o.getXxx()).orElse(default)` |
| **Apache Commons Lang** `Validate` / `ObjectUtils.defaultIfNull` | 校验参数   | `Validate.notNull(param, "param must not be null");`            |
| **Java 9+** **`Objects.requireNonNullElse`**                     | JDK 9+ | `Objects.requireNonNullElse(value, defaultValue);`              |

## 5. try-catch-finally

### 5.1 finally 必须关闭资源

🟡 **推荐**：

- **finally 块必须对资源对象、流对象进行关闭**，有异常也要做 `try-catch`
- **JDK 7+** 优先使用 `try-with-resources`（自动关闭，`final` 不能包含 `return`）

### 5.2 不要在 finally 块中使用 return

🟡 **推荐**：

- **不要在 finally 块中使用** **`return`**
- **原因**：finally 块中的 `return` 返回后方法结束执行，**不会再执行 try 块中的** **`return`** **语句**

**反例**：

```java
public boolean check() {
    try {
        return true; // 不会执行
    } finally {
        return false; // 实际返回 false
    }
}
```

### 5.3 try-with-resources（AI 视角强化）

🟡 **推荐**（JDK 7+）：

- **所有实现** **`AutoCloseable`** **的资源必须在** **`try-with-resources`** **中使用**（Stream / Connection / Reader / Writer 等）

**正例**：

```java
// ✅ 多资源自动关闭
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql);
     ResultSet rs = ps.executeQuery()) {
    while (rs.next()) {
        process(rs);
    }
} catch (SQLException e) {
    throw new BizException("10101", "查询失败", e);
}
// 无需 finally，资源自动逆序关闭
```

**反例**（JDK 7 之前的写法）：

```java
Connection conn = null;
PreparedStatement ps = null;
ResultSet rs = null;
try {
    conn = dataSource.getConnection();
    ps = conn.prepareStatement(sql);
    rs = ps.executeQuery();
    while (rs.next()) {
        process(rs);
    }
} catch (SQLException e) {
    throw new BizException("10101", "查询失败", e);
} finally {
    if (rs != null) {
        try { rs.close(); } catch (SQLException ignored) {}
    }
    if (ps != null) {
        try { ps.close(); } catch (SQLException ignored) {}
    }
    if (conn != null) {
        try { conn.close(); } catch (SQLException ignored) {}
    }
}
```

### 5.4 try-catch 粒度

🟡 **推荐**：

- **不要用一个大** **`try-catch`** **包整段代码**——必须**按业务边界划分**

**反例**：

```java
public void process() {
    try {
        validate();
        query();
        update();
        notify();
    } catch (Exception e) {
        log.error("process failed", e); // 一锅端，无法定位
    }
}
```

**正例**：

```java
public void process() {
    validate(); // 单独 try，单独异常
    try {
        query();
    } catch (DAOException e) {
        log.error("查询失败", e);
        throw new BizException("10101", "查询失败", e);
    }
    try {
        update();
    } catch (DAOException e) {
        log.error("更新失败", e);
        throw new BizException("10102", "更新失败", e);
    }
    notify(); // 通知失败不影响主流程
}
```

## 6. 全局异常处理（Spring 生态 / AI 视角扩展）

P3C 没有全局异常处理章节。Spring 项目必备。

### 6.1 @ControllerAdvice 统一处理

🟡 **推荐**：Spring MVC 项目用 `@ControllerAdvice` + `@ExceptionHandler` 统一处理：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    /** 业务异常 */
    @ExceptionHandler(BizException.class)
    public ApiResponse<Void> handleBiz(BizException e) {
        log.warn("业务异常 code={} msg={}", e.getErrorCode(), e.getMessage());
        return ApiResponse.fail(e.getErrorCode(), e.getMessage());
    }

    /** 参数校验异常 */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ApiResponse<Void> handleValidation(MethodArgumentNotValidException e) {
        String msg = e.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + ":" + f.getDefaultMessage())
                .collect(Collectors.joining(";"));
        return ApiResponse.fail("20100", msg);
    }

    /** 未授权 */
    @ExceptionHandler(AccessDeniedException.class)
    public ApiResponse<Void> handleAccess(AccessDeniedException e) {
        return ApiResponse.fail("50101", "无权限访问");
    }

    /** 兜底异常 */
    @ExceptionHandler(Exception.class)
    public ApiResponse<Void> handleAny(Exception e) {
        log.error("系统异常", e);
        return ApiResponse.fail("99999", "系统繁忙，请稍后再试");
    }
}
```

### 6.2 统一响应格式

🟡 **推荐**：API 响应统一封装为 `ApiResponse<T>`：

```java
public class ApiResponse<T> {

    private final String code;
    private final String message;
    private final T data;
    private final long timestamp = System.currentTimeMillis();

    public static <T> ApiResponse<T> ok(T data) {
        return new ApiResponse<>("0", "success", data);
    }

    public static <T> ApiResponse<T> fail(String code, String message) {
        return new ApiResponse<>(code, message, null);
    }

    // 成功判断
    @JsonIgnore
    public boolean isSuccess() {
        return "0".equals(code);
    }

    // 构造方法、getter 略
}
```
### 6.3 不要在 Controller 里 try-catch 业务异常

🟡 **推荐**：

- **Controller 层不要 try-catch 后只** **`log.error()`** **就返回**，会让上层框架捕获不到统一处理
- **业务异常直接 throw**，由 `@ControllerAdvice` 统一处理

**反例**：

```java
// ❌ Controller 里 catch 后只 log
@PostMapping("/order")
public ApiResponse<Void> createOrder(@RequestBody OrderDTO dto) {
    try {
        orderService.create(dto);
        return ApiResponse.ok();
    } catch (BizException e) {
        log.error("订单创建失败", e);
        return ApiResponse.fail(e.getErrorCode(), e.getMessage());
    }
}
```

**正例**：

```java
// ✅ 直接 throw，由 @ControllerAdvice 统一处理
@PostMapping("/order")
public ApiResponse<Void> createOrder(@RequestBody OrderDTO dto) {
    orderService.create(dto); // 异常往外抛
    return ApiResponse.ok();
}
```

### 6.4 异常与 HTTP 状态码

🟡 **推荐**：

| 业务错误码前缀 | 业务含义          | HTTP 状态码     |
| ------- | ------------- | ------------ |
| 1xxxx   | 系统错误          | 500          |
| 2xxxx   | 参数错误          | 400          |
| 3xxxx   | 业务逻辑错误（如库存不足） | 200（业务错误码表达） |
| 4xxxx   | 第三方错误         | 502 / 503    |
| 5xxxx   | 权限错误          | 401 / 403    |

🟡 **推荐**：

- **HTTP 状态码必须反映 HTTP 层面的错误**（协议级错误）
- **业务错误用 200 + 业务错误码表达**（HTTP 层面成功，但业务失败）

## 7. 事务回滚（Spring 生态）

### 7.1 try-catch 中的事务回滚

🟡 **推荐**：

- **`try`** **块放到了事务代码中，catch 异常后如果需要回滚事务，必须手动回滚事务**
- Spring `@Transactional` 默认**只对** **`RuntimeException`** **和** **`Error`** **回滚**，**对 checked 异常不回滚**

**反例**：

```java
@Transactional
public void createOrder(OrderDTO dto) throws IOException {
    try {
        orderDao.insert(dto);
        fileStorage.save(dto.getFile()); // 可能抛 IOException（checked）
    } catch (IOException e) {
        log.error("文件保存失败", e);
        // ❌ 没指定 rollbackFor，事务不回滚！订单已插入，文件未保存 → 数据不一致
    }
}
```

**正例**：

```java
@Transactional(rollbackFor = Exception.class) // 显式指定所有异常都回滚
public void createOrder(OrderDTO dto) throws IOException {
    try {
        orderDao.insert(dto);
        fileStorage.save(dto.getFile());
    } catch (IOException e) {
        log.error("文件保存失败", e);
        // 抛运行时异常触发事务回滚
        throw new BizException("40101", "文件保存失败", e);
    }
}
```

### 7.2 @Transactional 失效场景（AI 视角扩展）

🟡 **推荐**（AI 写 `@Transactional` 方法时立即避开）：

| 失效场景                                                            | 原因                                                      |
| --------------------------------------------------------------- | ------------------------------------------------------- |
| **`@Transactional`** **加在** **`private`** **方法上**               | Spring AOP 代理不能拦截 private 方法                            |
| **`@Transactional`** **加在** **`final`** **方法 / 类上**             | 同上，AOP 不能重写 final 方法                                    |
| **`@Transactional`** **方法内部调用本类其他** **`@Transactional`** **方法** | 走 `this.xxx()` 而不是代理，事务不生效                              |
| **未抛异常直接** **`return`**                                         | 事务不会回滚（默认配置下）                                           |
| **抛出 checked 异常未指定** **`rollbackFor`**                          | 默认 `rollbackFor = RuntimeException.class`，checked 异常不回滚 |
| **异常被 try-catch 吞掉**                                            | 事务管理器看不到异常，不回滚                                          |
| **`@Transactional`** **注解所在类未被 Spring 托管**                      | Bean 没注入，事务不生效                                          |
| **多线程调用**                                                       | 事务上下文用 ThreadLocal 传递，子线程没有事务                           |

### 7.3 事务传播行为

🟡 **推荐**：AI 选择传播行为时的判断：

| 传播行为            | 含义               | 何时用                   |
| --------------- | ---------------- | --------------------- |
| `REQUIRED`（默认）  | 沿用已有事务，没有就开新事务   | 90% 场景                |
| `REQUIRES_NEW`  | 挂起当前事务，开新事务      | 记录操作日志（即使主事务回滚，日志也要留） |
| `NESTED`        | 在当前事务中开嵌套事务（保存点） | 部分回滚场景                |
| `SUPPORTS`      | 有事务就加入，没有就不开     | 查询方法                  |
| `MANDATORY`     | 必须在已有事务中调用       | 内部方法                  |
| `NEVER`         | 必须在无事务中调用        | 严格管控                  |
| `NOT_SUPPORTED` | 必须在无事务中执行        | 临时挂起事务                |

🟡 **推荐**：

- **禁止在事务方法中调用远程 RPC（HTTP / Dubbo）**：远程调用慢，会长事务持有数据库连接；远程失败导致本地事务回滚

## 8. RPC 返回值与 Result 模式（AI 视角扩展）

P3C 第 12 条提到 RPC 优先用 Result 方式。AI 在跨服务调用时立即要遵守。

### 8.1 RPC 返回方式对比

🟢 **参考**：

| 返回方式              | 优点                | 缺点                               |
| ----------------- | ----------------- | -------------------------------- |
| **抛异常**           | 强制调用方处理           | 频繁调用时序列化栈开销大；checked 异常污染接口      |
| **Result\<T> 包装** | 不抛异常，调用方显式判断；性能稳定 | 调用方必须 `if (!result.isSuccess())` |
| **返回 null**       | 简单                | 调用方忘记判空 → NPE                    |

🟡 **推荐**：**跨应用 RPC 调用优先使用 Result 方式**（P3C 第 12 条）：

```java
public class Result<T> {
    private final boolean success;
    private final String code;
    private final String message;
    private final T data;

    public static <T> Result<T> ok(T data) {
        return new Result<>(true, "0", "success", data);
    }

    public static <T> Result<T> fail(String code, String message) {
        return new Result<>(false, code, message, null);
    }

    public boolean isSuccess() { return success; }
    public String getCode() { return code; }
    public T getData() { return data; }
}
```

**使用**：

```java
Result<OrderDTO> result = orderService.getOrder(orderId);
if (!result.isSuccess()) {
    throw new BizException(result.getCode(), result.getMessage());
}
OrderDTO order = result.getData();
```

### 8.2 不要重复代码（DRY）

🟢 **参考**（P3C 第 13 条）：

- 避免出现重复的代码（Don't Repeat Yourself）
- 随意复制和粘贴代码必然导致代码重复；修改时需要修改所有副本，容易遗漏
- **必要时抽取共性方法，或者抽象公共类，甚至是组件化**

**正例**：多个 public 方法都需要数行相同的参数校验：

```java
private boolean checkParam(DTO dto) {
    if (dto == null) return false;
    if (StringUtils.isBlank(dto.getName())) return false;
    if (dto.getAge() < 0 || dto.getAge() > 150) return false;
    return true;
}
```
