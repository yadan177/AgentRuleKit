# 13 - Java 部署运维规则

> 🟢 本文件适用于 Java 项目部署与运维（Docker/K8s/JVM 容器化/CI/CD/监控告警）。
> 🔴 不适用：业务逻辑实现、API 设计

---

## 1. Docker 镜像基础

### 1.1 主流基础镜像选择

🟡 **推荐**：Java 项目主流基础镜像：

| 基础镜像 | 大小 | 适用 |
|---|---|---|
| **eclipse-temurin:17-jre-alpine** | ~180MB | 推荐首选（OpenJDK + Alpine） |
| **eclipse-temurin:21-jre-alpine** | ~190MB | JDK 21+ 项目 |
| **eclipse-temurin:17-jre-jammy** | ~280MB | Ubuntu base（兼容性更好） |
| **amazoncorretto:17-alpine** | ~200MB | AWS Lambda / 亚马逊云 |
| **azul/zulu-openjdk:17-jre-alpine** | ~180MB | Azul Zulu（高稳定性） |
| **alpine:3.19** | ~5MB | 不用 JRE，自己装 |

🟡 项目采用容器交付时可评估：

- ✅ **生产环境使用官方维护的 JRE 镜像**（eclipse-temurin / amazoncorretto / azul）
- ❌ **不要用 `openjdk:*`**（OpenJDK 官方镜像已迁移到 eclipse-temurin）
- ❌ **不要用 `latest` tag**（不可重现）

### 1.2 多阶段构建

🟡 **推荐**：

- **多阶段构建**减小镜像：编译阶段用 JDK，运行阶段用 JRE
- 最终镜像**只含 JAR + JRE**，**不含 Maven / 源代码**

```dockerfile
# 镜像、digest、构建工具和产物路径均为占位配置，必须按目标项目替换并验证。
# ===== 阶段 1: 构建 =====
FROM <Java 构建镜像>@sha256:<digest> AS builder
WORKDIR /build

# 先复制 pom 缓存依赖
COPY pom.xml .
RUN mvn dependency:go-offline -B

COPY src ./src
RUN mvn package -DskipTests -B

# ===== 阶段 2: 运行 =====
FROM <Java 运行时镜像>@sha256:<digest>
WORKDIR /app
COPY --from=builder /build/target/*.jar app.jar

EXPOSE 8080
CMD ["java", "-jar", "/app/app.jar"]
```

### 1.3 JVM 容器镜像选择

🟡 镜像选择必须核对项目 JDK、发行版支持周期、目标 CPU/操作系统、证书/字体/时区、JNI 与动态库需求。不要仅凭镜像体积选择 Alpine、distroless 或特定供应商；生产构建优先使用已验证的不可变 digest，并建立更新流程。

## 2. Dockerfile 规范

### 2.1 基础要求

🟡 **推荐**：

- **基础镜像指定 tag**（不用 `latest`）：
  ```dockerfile
  # ✅ 使用项目已验证的不可变镜像
  FROM <Java 运行时镜像>@sha256:<digest>

  # ❌ 坏
  FROM openjdk:latest
  FROM eclipse-temurin:latest
  ```

### 2.2 WORKDIR 与 COPY

🟡 **推荐**：

- **用绝对路径 WORKDIR**：
  ```dockerfile
  WORKDIR /app  # ✅ 绝对路径
  WORKDIR ./app  # ❌ 相对路径
  ```

- **每次 `RUN`/`COPY`/`ADD` 用单独层**（缓存友好）
- **COPY 充分利用层缓存**：先 COPY `pom.xml` / `package.json` 再 COPY 代码

### 2.3 多阶段构建精简镜像

✅ **结构示例**（体积取决于项目与运行时）：
```dockerfile
FROM <Java 构建镜像>@sha256:<digest> AS builder
WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline -B
COPY src ./src
RUN mvn package -DskipTests -B

FROM <Java 运行时镜像>@sha256:<digest>
RUN addgroup -S app && adduser -S app -G app
USER app
WORKDIR /app
COPY --from=builder /build/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

❌ **反例**（把构建工具、源码和运行产物放在同一运行镜像）：
```dockerfile
# ❌ 一个阶段构建
FROM <包含构建工具的镜像>
COPY . /build
RUN mvn package
EXPOSE 8080
CMD ["java", "-jar", "/build/target/*.jar"]
# 镜像里包含整个 JDK + Maven + 源代码
```

### 2.4 不要的 Dockerfile 实践

🟡 **推荐**（常见反模式）：

- ❌ **不要用 `ADD`**（除非要加远程 URL / 自动解压 tar；其他场景用 `COPY`）
- ❌ **不要用 `:latest` tag**（不可重现）
- ❌ **不要在镜像里存储密钥**（用环境变量 / Vault）
- ❌ **不要在 Dockerfile 里用 `sudo`**（应该用 USER）
- ❌ **不要在容器写数据到容器层**（用 volume / 挂载）

### 2.5 健康检查

🟡 仅在项目使用 GitHub Actions 时参考；Action 版本、JDK、构建命令和缓存策略必须与仓库已验证配置一致。

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD curl -f http://localhost:8080/actuator/health || exit 1
```

⚠️ 注意：
- **Alpine 镜像 `curl` 默认未安装**：用 `wget` / 安装 / `nc -z localhost 8080`
- 也可以用容器编排平台（K8s）的 probe 替代

### 2.6 .dockerignore

🟡 **推荐**：

项目根目录 `.dockerignore` 跟 `.gitignore` 类似：

```
target/
.git/
.idea/
*.iml
.vscode/
.gradle/
*.log
.DS_Store
```

## 3. JVM 容器化启动参数

### 3.1 容器感知（cgroups）

🟡 **推荐**：

- **JDK 10+ 默认启用 cgroups 内存感知**（`-XX:+UseContainerSupport`）
- **JDK 11+ 中 `-Xmx` 不显式指定时会自动取容器内存限制**
- **JDK 17+ 推荐不指定 `-Xmx`**，让 JVM 自动探测（避免 K8s OOM Kill 风险）

```bash
# ✅ 推荐（JDK 11+）：让 JVM 自动探测容器内存
java -jar app.jar
# JVM 自动取容器内存的 25%（MaxRAMPercentage 默认 25.0）

# ✅ 显式指定（明确控制）
java -XX:MaxRAMPercentage=75.0 -jar app.jar
# JVM 取容器内存的 75%，剩余 25% 留给 JVM 自身开销
```

### 3.2 标准容器启动参数

🟡 **推荐**：

```bash
exec java \
  -XX:+UseContainerSupport \
  -XX:MaxRAMPercentage=75.0 \
  -XX:InitialRAMPercentage=50.0 \
  -XX:+ExitOnOutOfMemoryError \
  -XX:+HeapDumpOnOutOfMemoryError \
  -XX:HeapDumpPath=/tmp/oom.hprof \
  -Djava.security.egd=file:/dev/./urandom \
  -jar /app/app.jar
```

### 3.3 OOM Exit 时不要重启整个容器

🟡 **推荐**：

- OOM 后让**进程退出**，由容器编排工具决定重启（K8s set `restartPolicy`）
- **`-XX:+ExitOnOutOfMemoryError`**：OOM 时直接退出进程（不再 fork），让容器被杀

### 3.4 安全随机数源

🟡 **推荐**：

- `SecureRandom` 在 Alpine 容器中默认阻塞，启动加 `-Djava.security.egd=file:/dev/./urandom` 避免

### 3.5 时区与文件编码

🟡 **推荐**：

- **容器内 JVM 默认时区是 UTC**（不是 Asia/Shanghai）
- 显式设置时区：

```bash
java -Duser.timezone=Asia/Shanghai -jar app.jar
```

- 或在 Dockerfile：
```dockerfile
ENV TZ=Asia/Shanghai
RUN ln -snf /usr/share/zoneinfo/$TZ /etc/localtime && echo $TZ > /etc/timezone
```

### 3.6 JVM 启动优化（CDS / GraalVM）

🟡 **推荐**：

- **CDS（Class Data Sharing）**：JDK 12+ 默认开启（见 见 11 § 7.6）
- **Spring Boot 3.x + GraalVM Native Image**：编译成原生镜像，启动毫秒级（适合 Serverless）

## 4. Kubernetes 部署

### 4.1 Deployment YAML 模板

🟡 **推荐**：最小可用模板：

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: prod
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-service
  template:
    metadata:
      labels:
        app: order-service
    spec:
      containers:
        - name: order-service
          image: registry.example.com/order-service:v1.2.0
          ports:
            - containerPort: 8080
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: prod
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-secrets
                  key: password
          resources:
            requests:
              cpu: 500m
              memory: 512Mi
            limits:
              cpu: 2000m
              memory: 2Gi
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 60
            periodSeconds: 15
            timeoutSeconds: 3
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 5
            timeoutSeconds: 3
            failureThreshold: 3
          startupProbe:
            httpGet:
              path: /actuator/health
              port: 8080
            failureThreshold: 30  # 30 × 5s = 150s 启动时间
            periodSeconds: 5
      terminationGracePeriodSeconds: 60
```

### 4.2 资源配置 requests vs limits

🟡 **推荐**：

- **必须设置 `requests`**（K8s 调度依据）
- **必须设置 `limits`**（防止单 Pod 占满节点）

🟡 **推荐**：资源配置经验值：

| 服务类型 | CPU request | CPU limit | Memory request | Memory limit |
|---|---|---|---|---|
| **轻量 API** | 100m | 500m | 128Mi | 512Mi |
| **一般 Web 服务** | 500m | 2000m | 512Mi | 2Gi |
| **批量任务** | 1000m | 4000m | 1Gi | 4Gi |

⚠️ **Memory limit 设置过高导致 OOM Kill**：建议 Memory limit ≤ JVM heap × 4（JVM + 堆外 + 元空间 + 直接内存）

### 4.3 健康检查 3 种 Probe

🟡 **推荐**（生产环境必须配齐 3 种）：

| Probe | 失败后果 | 何时用 |
|---|---|---|
| **livenessProbe** | 失败 → 杀 Pod 重启 | 应用进程"卡死但还在响应"（如死锁）|
| **readinessProbe** | 失败 → 从 Service 摘除 | 暂时无法服务（如依赖组件未就绪）|
| **startupProbe** | 失败 → 杀 Pod | 启动慢的应用（首次启动 > 60s）|

🟡 **推荐**：

- **`/actuator/health/liveness`** 和 **`/actuator/health/readiness`** 单独端点（Spring Boot Actuator 默认）
- **不要用 `/actuator/health`** 做 readiness（包含下游依赖状态，下游挂时 Pod 会被错误摘除）

### 4.4 Service + Ingress

🟡 **推荐**：

```yaml
# Service
apiVersion: v1
kind: Service
metadata:
  name: order-service
spec:
  selector:
    app: order-service
  ports:
    - protocol: TCP
      port: 80
      targetPort: 8080
```

```yaml
# Ingress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: order-service
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /api/orders
            pathType: Prefix
            backend:
              service:
                name: order-service
                port:
                  number: 80
```

### 4.5 ConfigMap / Secret

🟡 **推荐**（P3C 工程结构 · 服务器第 5 条隐含）：

- **配置项用 ConfigMap / Secret**，**不写在镜像里**
- **服务器内部重定向使用 forward**（如 Spring MVC `forward:`）
- **外部重定向地址使用 URL 拼装工具类来生成**（防 URL 维护不一致和安全风险）

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-service-config
data:
  application.yml: |
    spring:
      datasource:
        url: jdbc:mysql://mysql:3306/order
        username: order_user
    management:
      endpoints:
        web:
          exposure:
            include: health,info,metrics,prometheus
---
apiVersion: v1
kind: Secret
metadata:
  name: db-secrets
type: Opaque
stringData:
  password: your-strong-password
```

### 4.6 HPA（自动扩缩容）

🟡 **推荐**：

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: order-service
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-service
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

## 5. 优雅停机与健康检查

### 5.1 SIGTERM 优雅停机流程

🟡 **推荐**（P3C 工程结构 · 应用分层第 2 条隐含）：

- **应用收到 SIGTERM 时应进入"优雅停机"流程**：
  1. 停止接收新请求（readiness probe 失败 → 从 Service 摘除）
  2. 等待正在处理的请求完成（最多 30s）
  3. 关闭线程池 / 释放连接池 / 关闭 Spring Context
  4. JVM 退出

### 5.2 Spring Boot Actuator 优雅停机

🟡 **推荐**：

```yaml
# application.yml
management:
  endpoint:
    shutdown:
      enabled: true
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus,shutdown

server:
  shutdown: graceful

spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
```

```yaml
# K8s Deployment 配置
spec:
  terminationGracePeriodSeconds: 60  # K8s 给 60s 优雅停机
  containers:
    - name: app
      lifecycle:
        preStop:
          exec:
            command: ["sh", "-c", "sleep 10"]  # 给 readiness probe 10s 摘流时间
```

### 5.3 优雅停机检查清单

🟡 **推荐**：

- [ ] **不再接受新连接**：readiness probe 失败，K8s Service 摘除
- [ ] **处理完进行中的请求**（给 30-60s）
- [ ] **关闭线程池 / 数据库连接池**：`executor.shutdown()` + `awaitTermination`
- [ ] **关闭 Spring Context**：Spring 自动处理
- [ ] **释放外部资源**：MQ sender / 缓存连接
- [ ] **JVM 干净退出**（不 hang）

### 5.4 readiness vs liveness 配置要点

🟡 **推荐**：

| Endpoint | 用途 | **不应该**包含 |
|---|---|---|
| `/actuator/health` | 总健康度（含所有依赖）| - |
| `/actuator/health/liveness` | "进程是否活着" | 数据库连接 / Redis / MQ |
| `/actuator/health/readiness` | "能否服务请求" | - |

✅ **正例**：
```yaml
management:
  endpoint:
    health:
      probes:
        enabled: true  # 启用 /actuator/health/liveness 和 /readiness
      group:
        readiness:
          include: db, redis  # readiness 包含数据库等依赖
        liveness:
          include: ping   # liveness 不包含下游依赖
```

### 5.5 K8s Probe 失败回滚行为

🟢 **参考**：

| Probe | 失败 N 次后 | 默认 `failureThreshold` |
|---|---|---|
| `startupProbe` | 杀 Pod | 30（次）|
| `livenessProbe` | 杀 Pod | 3 |
| `readinessProbe` | 摘 Pod **不杀** | 3 |

## 6. 配置中心（Nacos / Apollo / Spring Cloud Config）

### 6.1 为什么需要配置中心

🟡 **推荐**：

- **不同环境的配置（dev / staging / prod）必须分离**，**不能改代码**
- **配置变更不需要重启**即可生效（部分场景）
- 敏感配置统一管理（Vault / Encrypted Properties）

### 6.2 主流配置中心选型

🟢 **参考**：

| 工具 | 特点 | 适用 |
|---|---|---|
| **Nacos**（阿里开源）| 注册中心 + 配置中心二合一 | 国内最常用 |
| **Apollo**（携程开源）| 完善的权限审计 + 灰度发布 | 企业级 |
| **Spring Cloud Config** | 与 Spring 无缝集成 | Spring 原生 |
| **HashiCorp Vault** | 专注密钥管理 | 金融 / 高安全 |

🟡 **推荐**：**国内 Java 项目首选 Nacos**（社区活跃，生态完整）。

### 6.3 Nacos 集成示例

🟡 **推荐**：

```xml
<!-- pom.xml -->
<dependency>
    <groupId>com.alibaba.cloud</groupId>
    <artifactId>spring-cloud-starter-alibaba-nacos-config</artifactId>
</dependency>
```

```yaml
# application.yml
spring:
  cloud:
    nacos:
      config:
        server-addr: nacos.example.com:8848
        file-extension: yaml
        namespace: prod
        group: DEFAULT_GROUP
        username: nacos
        password: ${NACOS_PASSWORD}
```

### 6.4 动态配置 + 注解

🟡 **推荐**：

```java
@RestController
@RefreshScope  // 配置变更时自动刷新
public class ConfigController {
    @Value("${feature.new-payment-enabled}")
    private boolean newPaymentEnabled;

    // ...
}
```

### 6.5 配置变更审计

🟡 **推荐**：

- **配置变更需要审计日志**（谁 / 何时 / 改了什么配置 / 灰度到哪个环境）
- **关键配置变更通知**：邮件 / 钉钉 / Slack
- **变更可回滚**：保留历史版本

## 7. CI/CD（持续集成 / 持续部署）

### 7.1 CI/CD 流水线标准阶段

🟡 **推荐**：

```
提交 → 静态检查 → 单元测试 → 构建 → 集成测试 → 构建镜像 → 部署 staging → 集成测试 → 部署 prod（灰度）
```

### 7.2 GitHub Actions 模板

🟡 **推荐**：

```yaml
# .github/workflows/build.yml
name: Build and Deploy

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<项目已验证版本>

      - name: Set up JDK
        uses: actions/setup-java@<项目已验证版本>
        with:
          java-version: '<项目支持版本>'
          distribution: '<项目采用的发行版>'

      - name: Cache Maven packages
        uses: actions/cache@<项目已验证版本>
        with:
          path: ~/.m2
          key: ${{ runner.os }}-m2-${{ hashFiles('**/pom.xml') }}

      - name: Static check (Checkstyle + SpotBugs + p3c-pmd)
        run: mvn verify -Pcheckstyle,spotbugs,p3c

      - name: Unit test
        run: mvn test -B

      - name: Integration test (Testcontainers)
        run: mvn verify -DskipUnitTests=true -B

      - name: Build JAR
        run: mvn package -DskipTests -B

      - name: Build Docker
        run: docker build -t registry.example.com/order-service:${{ github.sha }} .

      - name: Push Docker
        run: docker push registry.example.com/order-service:${{ github.sha }}

      - name: Deploy to staging
        if: github.ref == 'refs/heads/main'
        run: |
          kubectl set image deployment/order-service \
            order-service=registry.example.com/order-service:${{ github.sha }} \
            -n staging
```

### 7.3 灰度发布（金丝雀发布）

🟡 **推荐**（生产推荐）：

- **新版本先 1 个 Pod，验 OK 后全量**
- 用 **Argo Rollouts** / **Flagger** / **Nacos 权重**

```yaml
# Argo Rollouts 示例
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: order-service
spec:
  strategy:
    canary:
      steps:
        - setWeight: 10   # 10% 流量到新版本
        - pause: { duration: 5m }  # 暂停 5 分钟观察
        - setWeight: 50
        - pause: { duration: 5m }
        - setWeight: 100
      canaryService: order-service-canary
      stableService: order-service
  template:
    spec:
      containers:
        - name: order-service
          image: registry.example.com/order-service:v1.2.0
```

### 7.4 回滚策略

🟡 **推荐**：

- 每次发布保留前 N 个版本（`kubectl rollout history`）
- 失败时**30 秒内回滚**：`kubectl rollout undo deployment/order-service`
- 灰度发布期间有自动化指标监控（错误率 / P99 响应时间）异常自动回滚

### 7.5 CI/CD 关键反模式

🟡 **推荐**（AI 部署 / CI 时立即避开）：

- ❌ **不要**长期不清理的 master 没有任何保护
- ❌ **不要**没有自动化测试的发布流程
- ❌ **不要**手工 `scp` / `kubectl apply` 到生产环境
- ❌ **不要**没有审计日志的部署操作
- ❌ **不要**发布和数据库 DDL 同时进行（需要单向迁移，详见 见 07 § 11）

## 8. 监控告警

### 8.1 4 大黄金指标

🟡 **推荐**（Google SRE 推荐，AI 项目初期就配）：

| 指标 | 含义 | Java 监控实现 |
|---|---|---|
| **流量（Traffic）** | 请求 QPS | Micrometer `http.server.requests` |
| **错误（Errors）** | 失败率（HTTP 5xx）| 同样 `http.server.requests{status=5xx}` |
| **延迟（Latency）** | P50 / P95 / P99 响应时间 | Timer.percentile |
| **饱和度（Saturation）** | CPU / 内存 / 线程池利用率 | `process.cpu.usage` / `jvm.memory.used` |

### 8.2 Spring Boot Actuator 启用

🟡 **推荐**：

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

```yaml
# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus
  endpoint:
    health:
      show-details: when-authorized  # 不暴露详情到公网
      probes:
        enabled: true
    metrics:
      tags:
        application: ${spring.application.name}
      distribution:
        percentiles:
          - 0.5
          - 0.95
          - 0.99
        percentiles-histogram: true
```

### 8.3 Prometheus + Grafana 接入

🟡 **推荐**：

- Spring Boot 暴露 `/actuator/prometheus`（Prometheus 抓取格式）
- Prometheus 每 15 秒抓取
- Grafana 接 Prometheus 做仪表盘

```bash
# Prometheus 配置
scrape_configs:
  - job_name: 'order-service'
    metrics_path: '/actuator/prometheus'
    scrape_interval: 15s
    static_configs:
      - targets: ['order-service:8080']
```

### 8.4 关键告警规则

🟡 **推荐**（生产环境必须配置）：

| 告警 | 条件 | 严重度 |
|---|---|---|
| **Pod OOM Killed** | Kubernetes Events `OOMKilled` | P1 |
| **P99 延迟飙升** | P99 > 1s 持续 5 分钟 | P2 |
| **错误率突增** | HTTP 5xx > 5% 持续 2 分钟 | P1 |
| **数据库连接池耗尽** | HikariCP active = maxPoolSize | P2 |
| **JVM GC 频繁** | Full GC > 1 次 / 小时 | P2 |
| **磁盘将满** | 磁盘使用 > 85% | P2 |
| **磁盘已满** | 磁盘使用 > 95% | P1 |
| **心跳丢失** | Prometheus 抓取失败 > 2 分钟 | P1 |

### 8.5 APM（应用性能监控）

🟢 **可选**（高级监控）：

- **SkyWalking**（Apache）：分布式追踪，国产首选
- **ARMS**（阿里云）：商业 SaaS

## 9. 日志收集

### 9.1 集中式日志

🟡 **推荐**：

- **生产环境日志不能只在容器本地**（容器漂移 / 删除日志丢）
- 通过 **stdout / stderr** 输出 + 容器运行时采集（Filebeat / Fluentd）

```dockerfile
# Dockerfile 最后一行：日志输出到 stdout/stderr（容器采集需要）
CMD ["java", "-jar", "/app/app.jar"]
# 不要重定向到文件 —— K8s / Docker 会丢失
```

### 9.2 ELK / Loki Stack

🟢 **可选**：

- **Loki + Promtail + Grafana**：轻量、K8s 友好、查询快
- **ELK**（Elasticsearch + Logstash + Kibana）：功能强但重
- 云服务：**阿里云 SLS** / **AWS CloudWatch** / **GCP Cloud Logging** —— 一键接入

### 9.3 日志格式（参考 见 09 § 6）

🟡 **推荐**：

- **JSON 格式**（ELK / Loki 友好）
- **含 traceId**（链路追踪关联）
- **含主机 / Pod 名**（多实例区分）
- **含 application / env**（多服务区分）

### 9.4 日志归档

🟡 **推荐**：

- **本地 logback 按天滚动**（15 天，参考 见 09 § 10.4）
- **ELK / Loki 存 90 天**
- **法规要求存 6 个月 - 1 年**
