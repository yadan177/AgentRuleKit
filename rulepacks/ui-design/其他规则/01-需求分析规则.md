# 01 - UI 需求分析规则

> - 🟢 本文件适用于新产品、功能迭代、改版和设计审查前的需求理解。
> - 🔴 不适用：根据模板臆造用户、业务能力或研究数据。

---

## 1. 要回答的问题

需求分析把用户任务、内容、业务边界、实现限制和验收条件连接起来，不只是把需求换成页面名称。

| 问题 | 记录内容 |
|---|---|
| 为谁解决什么问题 | 有依据的用户、场景、阻碍、目标与非目标 |
| 在什么条件下使用 | 设备、输入、网络、权限、环境与适用平台 |
| 如何开始和结束 | 入口、前置条件、主任务、结果、返回与恢复 |
| 需要哪些内容 | 来源、长度、更新频率、空值、敏感性与本地化 |
| 什么算完成 | 可观察的行为、验证方式与尚未确定的标准 |

- 🔴 局部任务只补本次相关信息，复用已有需求与产品规则，不另写一套相同的产品文档。
- 🔴 页面数量从任务和内容推导，不预设一功能一页面；某些阶段可以通过声音、场景对象或系统反馈完成。

## 2. 输入与证据

优先读取当前产品需求、业务流程、研究与反馈、平台约束、品牌与设计系统、实现接口及实际设计文件。

- 🔴 用户分组、频率、性能和成功率有来源；没有研究时明确是假设，不编造人物故事、访谈或指标。
- 🔴 已确认不等于已验证；每项结论注明依据与适用范围，必要时安排验证。
- 🔴 对儿童、低熟练度或存在感知与操作障碍的用户，按实际项目识别理解、可达性和安全要求，不凭标签推断所有行为。
- 🔴 缺失信息会改变主流程、重要后果或实现契约时，给出候选与影响并澄清；不会阻塞的细节可作为假设继续探索。

❌ 反例：只有“页面更简洁”的要求，便增加注册、评分和排行榜，并声称用户更喜欢。

✅ 正例：核对现有任务与反馈，指出重复信息导致操作难找，在既有功能范围内提出布局与文案调整。

## 3. 内容与变化盘点

AI 根据需求和完整设计主动盘点本次相关区域，包含浮层、异常、重复成员及边角反馈。

| 类型 | 需要识别 |
|---|---|
| 固定内容 | 标题、标签、插画、品牌及其真实来源 |
| 动态内容 | 数据、用户输入、更新时机、长度和空值 |
| 交互反馈 | 输入方式所需的焦点、悬停、按压等候选 |
| 业务变化 | 加载、空、失败、权限、中断与恢复 |
| 连续属性 | 进度、时间、滚动、位置等范围与控制来源 |
| 独立控制 | 成员选择、显隐、替换、动画、复用与适配 |

- 🔴 状态候选依据 [交互规则](./02-交互设计规则.md) 进入设计，不把候选直接写成已采用状态。
- 🔴 内容、界面文案与功能承诺分别核对。缺少文案时可在授权范围内拟稿或使用明确占位，不能声称已获确认。
- 🔴 不为填满版面添加介绍、口号或技术解释；必要错误原因、恢复方法和操作后果仍应清楚表达。
- 🟡 只有进入资源交付时才补齐文件名、格式和导出细节，避免需求分析被切图清单淹没。

## 4. 范围与验收

本次范围明确保留、调整、新增和删除内容，以及前后依赖。优先级按用户目标、问题影响、证据与成本判断，沿用项目已有方法。

验收条件写成可观察结果，例如用户能定位当前步骤、取消后保留有效输入、失败后有明确重试方式。视觉形容词可辅助方向讨论，不能单独构成验收标准。

简报、流程与后续设计说明复用 [UI 文档模板](../../project-docs/ui-design/其他规则/03-UI设计文档模板.md)。

## 5. 完成检查

- [ ] 用户任务、范围与成功条件有依据。
- [ ] 平台、输入、内容与关键实现约束明确。
- [ ] 核心异常、权限、中断和恢复已识别。
- [ ] 已知事实、假设和未决选择分别记录。
- [ ] 本次必要元素由 AI 主动盘点，未无依据新增业务。
- [ ] 阻塞项集中处理，其他分析和探索已继续推进。
