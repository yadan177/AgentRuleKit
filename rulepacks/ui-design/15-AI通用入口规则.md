# 15 - UI 设计 AI 通用入口规则

> - 🟢 本文件适用于 AI 参与的 UI 分析、设计、审查、资源交付和落地跟踪。
> - 🔴 不适用：擅自批准业务选择、编造研究结果，或将工具成功回执当作设计验收。

---

## 1. 开始前核对

先读取当前项目的有效规则与[总览](./00-文档总览.md)，明确用户要的是分析、探索、修改、导出还是实现。检查本次相关的需求、平台与输入、设计文件、已有组件、内容、工程约束和未完成改动。

- 🔴 区分事实、假设、建议、已确认决定与已验证结果；找不到证据时说明缺口。
- 🔴 定位权威设计文件、版本、页面或节点及允许修改范围；不得把其他项目或历史稿当作当前基线。
- 🔴 读取现有约定、确认记录与实现能力，不要求用户重复提供仓库中已有的信息。
- 🟡 没有完整需求文档时可先整理已知信息与探索方案，记录假设，不把形式上的文档齐全设为开始分析的条件。

## 3. 决策与授权

确认的对象是未决选择，不是每一条操作。先完成可独立进行的盘点、候选、影响分析或预览，再集中提出确实阻塞的事项。

| 情况 | 处理方式 |
|---|---|
| 已有明确需求、项目约定或用户授权 | 在适用范围内继续执行，引用依据，不重复确认 |
| 探索稿、候选样式或可逆局部修正 | 在任务范围内制作并标明性质，不冒充已采用方案 |
| 新增业务能力、改变关键流程或破坏已有契约，且超出授权 | 给出具体方案、差异与影响后确认；继续无依赖工作 |
| 事实来源冲突或关键输入未知 | 标出冲突，核查来源；仅暂停依赖该结论的部分 |
| 发布组件库、覆盖正式资源等操作 | 按本次任务和项目的实际授权执行，不因规则增加重复审批 |

- 🔴 复用已确认的状态与组件，不自动补固定状态集；新增状态或改变行为时按 [02](./其他规则/02-交互设计规则.md) 说明依据与影响。
- 🔴 AI 主动盘点当前范围内的界面、独立控件与变化内容，不把发现漏项的工作交给用户。
- 🔴 用户确认整体方案不免除 AI 核对资源边界、状态语义与引用的责任。
- 🔴 未经证据支持的文案、产品承诺和研究结论不能进入正式说明；必要的文案设计在授权任务内提出并标明采用状态。

❌ 反例：用户已授权沿用现有按钮，只因规则要求“状态确认”又让用户逐个确认；或把探索中的新入口直接接入正式流程。

✅ 正例：记录已有按钮状态来源并完成改动；对确实超出范围的新入口提供具体影响，单独处理。

## 4. 写入与交付边界

- 🔴 只审查或解释时不修改设计文件。修改前核对目标和引用，修改后检查实际画面、节点组织和下游影响。
- 🔴 不在评审截图或脱离源组件的导出副本上继续维护第二套正式设计。
- 🔴 先确定原生组件、样式、矢量、位图和字体的实现角色，再按 06 导出；不按图层数量生成资源。
- 🔴 保护项目与并行工作。清理前核对实例、原型、正式导出与工程引用；确认可删除的临时或废弃内容按项目约定清理，不默认堆积归档副本。
- 🔴 设计调整、导出、导入工程和目标设备验证是不同操作，只报告实际完成的部分。

## 5. 验证与报告

按照当前任务执行相称的检查：流程与状态、实际画面与文案、组件引用、适配、资源重建、独立控制或目标实现。不能运行的部分说明环境和缺口。

交付报告简要说明：

1. 本次范围、采用的需求与设计基线。
2. 修改的页面、组件、状态、资源或文档。
3. 关键决定、依据及超出原范围的事项。
4. 实际完成的检查、验证层级与未验证内容。
5. 受影响消费者及仍需处理的问题。

局部任务不要求填写与其无关的长表。设计文档按配套规则同步，不把实现尚未完成写成设计任务未产出，也不把设计完成写成产品已验收。
