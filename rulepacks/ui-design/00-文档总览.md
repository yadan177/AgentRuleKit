# 00 - UI 设计规则总览

> - 🟢 本规则库适用于网站、桌面、移动端、游戏、XR 等交互产品的 UI 设计与交付。
> - 🔴 不适用：替代产品决策、目标平台规范、用户研究、品牌要求或真实实现证据。

---

## 1. 目标与边界

UI 设计应让目标用户在实际环境中理解信息、完成任务、识别反馈并从异常中恢复。视觉稿、可交互原型、资源交付、代码实现和目标设备验收分别记录，不能互相代替。

- 🔴 用户当前要求、项目事实和本地覆盖优先；已有授权与已确认决定在适用范围内持续有效。
- 🔴 先理解任务、内容、输入与平台，再选择交互和视觉形式；不按工具默认模板推导业务需求。
- 🔴 业务状态、输入反馈、选择值和连续属性分别建模，不把所有控件机械套成固定五态。
- 🔴 设计层级、可交互控件和运行时资源分别判断，图层数、页面数、状态数与资源数不要求相等。
- 🔴 按实现方式交付原生组件、样式、矢量或位图资源；不为所有平台强制生成底图和按钮 PNG。
- 🟡 先形成够用的设计基础，通过真实代表场景修订，再批量展开；局部调整只复核受影响范围。

## 2. 工作路径

| 任务 | 建议路径 | 应形成的证据 |
|---|---|---|
| 从零设计 | 需求与平台 → 参考与方向 → 基础首版 → 代表页验证 → 页面展开 → 交付 | 需求依据、方向选择、基础来源、流程与状态、验证记录 |
| 已有产品迭代 | 当前基线 → 问题与影响 → 复用或调整 → 对照验证 → 同步消费者 | 原有决定、本次差异、受影响页面与组件、结果 |
| 设计审查 | 明确范围 → 读取源稿与需求 → 走查 → 问题与建议 | 可定位的问题、任务影响、依据与修复建议 |
| 资源交付 | 已确认设计与实现方案 → 边界清单 → 导出或映射 → 重建与可控性检查 | 设计到资源或组件的映射、实际结果及缺口 |

交互分析可与参考调研并行。阶段表达依赖关系，不要求每次任务重走全流程，也不规定固定画板数或文件数。发现上游问题时回到对应决定修订。

❌ 反例：只调整已有按钮间距，却重新要求用户确认整套风格与全部状态；或凭一张漂亮截图宣称交互验收完成。

✅ 正例：沿用已有风格和状态，在授权范围内修正间距，检查相关实例与适配；新增业务行为单独提出。

## 4. 规则等级与项目差异

| 标识 | 含义 |
|---|---|
| 🔴 | 适用条件满足时必须执行 |
| 🟡 | 推荐，结合目标、证据和成本选择 |
| 🟢 | 可选，仅在有实际收益时采用 |

- 🔴 示例不是默认的配色、尺寸、控件状态或目录；项目特有值写入项目设计文档或本地规则。
- 🔴 平台参数注明来源、版本、单位和适用条件；跨平台参考不能自动证明本项目支持同样能力。
- 🔴 通用规则不依赖特定项目名、页面编号、字体、商业素材、设计工具账号或本机绝对路径。
- 🟡 默认使用清晰中文说明；已有项目语言、节点名、资源名和代码标识约定时沿用。

## 5. 维护与完成

规则正文在本包维护，文档格式与记录方法在配套文档包维护。适配器只引用入口，项目参数不回填为通用默认值。

- [ ] 主要任务、流程、必要状态和异常可追溯。
- [ ] 设计基础与实例有唯一来源，未引入无依据的新业务。
- [ ] 交付形式符合实现方式，视觉还原与独立控制分别检查。
- [ ] 设计、资源、实现和设备验证状态分别记录。
- [ ] 本次文档影响、实际检查与剩余缺口已说明。
