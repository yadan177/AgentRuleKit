# 04 - Unity AI 技术文档任务入口

> - 🟢 本文件适用于 Unity 项目的仓库理解、技术文档建立、更新、审查与代码同步。
> - 🔴 不适用：臆造项目事实、伪造运行验证，或将文档任务扩大为工程迁移、发布和代码重构。

---

## 1. 任务路由

| 任务 | 读取规则 | 执行重点 |
|---|---|---|
| 理解仓库并建立技术文档 / Code Wiki | 00、01、02、03 | 确定范围 → 入口与核心链路 → 内容覆盖 → 文档与验证 |
| 补充或更新一个模块的文档 | 01、02、相关模板 | 读取现有文档和该模块的提供方、消费者及测试 |
| 代码变更后的增量同步 | 01、02、相关模板 | 从实际差异判断受影响的模块、链路、契约和运行说明 |
| 目录整理或文档审查 | 00、01、02 | 事实、来源、覆盖、导航、重复与失效内容 |

- 🔴 先明确交付是阅读结论还是 Markdown 文件，以及全仓库还是指定模块；用户只要求理解仓库时，不自行批量创建文件。
- 🔴 阅读当前宿主已生效的项目规则、贡献约定和本项目文档入口；不把其他项目或其他工作树当作当前事实。
- 🟡 按任务读取必要专题，使用已有路径和术语；不存在的文档不作为继续分析的前置条件。

## 2. 理解仓库并首次建立文档

### 2.1 确定范围与证据

1. 识别当前工作目录、源码版本与相关未提交改动，记录分析范围；区分源码、发布版本和运行产物。
2. 盘点已有技术文档、索引、ADR 与项目入口，识别可复用内容、过时说明和缺口；不要先套目录或批量创建空模板。
3. 读取运行时、依赖、工作区、构建、配置、测试和 CI 的实际定义。默认不遍历依赖缓存、构建输出和无关第三方代码；它们是待核查契约或生成关系的必要来源时按需读取。
4. 盘点主要能力、运行单元与模块边界，建立“能力/模块 → 入口 → 关键实现 → 文档 → 验证状态”的对应关系；小项目用简表即可。

### 2.2 从入口追踪实现

1. 先理解启动与初始化：构建场景或实际引导入口、初始化顺序、程序集引用、Scene/Prefab 绑定和事件注册；区分编辑器工具、运行时代码及目标平台分支。
2. 按本次范围逐项追踪主要能力，说明触发条件、实际入口、模块协作、数据或状态变化及结果；继续检查关键失败、取消与清理路径。
3. 选择影响理解和修改的核心类、函数或组件，核对定义与实际使用位置，说明输入输出、调用方、副作用及契约；不为全部符号生成目录式说明。
4. 区分内部模块依赖与外部服务或包依赖，说明方向和用途。遇到动态注册、事件或配置驱动关系时交叉核对注册、消费与测试，不能凭导入关系推断实际执行。
5. 对照测试与现有运行记录，标注已实现、源码已核查、实际运行已验证及待确认范围。跨语言项目按所属实现读取对应技术栈规则，跨端链路保留统一入口。

大型仓库可按子系统分批完成，并在总览或交付中列出已覆盖、未覆盖及原因；只抽读少量文件时不能声称已完整理解全仓库。

### 2.3 组织内容与核对

1. 按 [组织规范](./01-技术文档组织与维护规范.md) 将内容映射到现有技术文档。先补技术总览、阅读导航和运行入口，再按需要补架构、模块、关键链路、契约与验证说明。
2. 按 [编写规范](./02-Unity技术文档编写规范.md) 和 [模板](./03-Unity技术文档模板.md) 写入已核查内容；短内容可合并，复杂主题按真实边界拆分，不新建重复的 Wiki 副本。
3. 关键结论给出相对路径、符号或配置来源。命令写明工作目录、前置条件、预期结果和实测情况；不能运行时说明原因，不补造成功记录。
4. 负责人优先从已有文档或团队约定确认；无法确认时按组织规范保留为草稿并列出待确认项，不臆造姓名，也不因此停止可独立完成的源码分析。
5. 通过根索引检查主要能力的文档覆盖、导航和来源链接；执行适用的已有本地检查。需要外部权限、真实设备或会修改业务数据的验证，按任务授权范围处理并明确未验证部分。

## 3. 后续增量同步

先检查实际代码、配置与文档差异，再沿受影响入口、调用方、消费者和测试判断范围；未知比较基线时说明范围限制，不假定完成了全量核查。

| 变化 | 需要核对的文档 |
|---|---|
| 新增、拆分、合并或删除模块 | 技术总览、模块职责、覆盖关系与导航 |
| 启动、注册、调用、事件或状态变化 | 核心链路、关键符号、数据流和生命周期 |
| 接口、类型、数据或存储变化 | 提供方与消费者、契约、兼容性和迁移说明 |
| 运行时、依赖、配置、脚本或目标平台变化 | 环境要求、新人上手、构建、运行与排障 |
| 验证方法、行为或技术决策变化 | 相关测试说明、验证状态、限制与 ADR |

- 🔴 更新受影响的事实、来源、状态与实质更新时间，保留仍有效的项目内容；不把局部同步扩大为全量重写。
- 🔴 新增或移除主要能力时更新已有覆盖矩阵；没有独立矩阵则维护根索引中的模块入口。
- 🔴 移动或重命名符号与文档后修复引用，扫描受影响范围中的旧术语和旧能力描述。
- 🔴 被替代的正式文档按组织规范标记废弃并给出替代路径；无须保留的临时资料不作为正式技术文档继续积累。

## 4. 交付与自检

交付时说明分析基线与覆盖范围、已修改文档及入口、关键事实依据、实际执行的验证、待确认项与未验证范围；判断无文档影响时给出依据。

- [ ] 总览 → 主要链路 → 模块与关键符号 → 契约及验证的阅读路线可用。
- [ ] 本次范围内主要能力已对应到实现和文档，未覆盖内容已明确。
- [ ] 结构关系来自实际源码或配置，未将声明、静态核查或构建等同于真实运行。
- [ ] 文档复用了已有目录和权威来源，无空模板、逐函数堆砌或重复维护。
- [ ] 现有文档检查、索引、相对链接、状态及受影响术语已核对。
