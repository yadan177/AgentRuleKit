# 01 - 技术文档组织与维护规范

> - 🟢 本文件适用于 Unity 技术文档的目录、索引、命名、元数据和生命周期。
> - 🔴 不适用：策划、美术、制作、运营或管理文档的组织与维护。

---

## 1. 技术文档的范围与主题基线

技术文档目录只承载程序侧工程事实，不承载完整项目文档。它优先使用 `项目文档/技术文档/`；团队已有稳定路径时可沿用，但不得为套用本规则迁移历史资料。策划、美术、制作、运营和管理资料可由项目既有规范管理，但不得放入 `技术文档/`。

`00` 至 `07` 是技术主题基线，不是八篇文档的固定清单，也不要求预先创建所有目录：

```text
项目文档/
└── 技术文档/
    ├── README.md
    ├── 00-新人上手.md
    ├── 01-技术总览.md
    ├── 02-架构与工程/            # 有真实内容时创建
    │   ├── README.md
    │   └── <中文主题>.md
    ├── 03-模块设计/              # 有真实内容时创建
    ├── 04-接口与数据/            # 有真实内容时创建
    ├── 05-测试与质量/            # 满足独立维护条件时创建
    ├── 06-运行维护/              # 有真实内容时创建
    ├── 07-技术决策记录/          # 有真实内容时创建
    └── 08-<新增技术主题>/        # 满足新增主题条件时创建
```

| 主题 | 回答的问题 | 默认形态 |
|---|---|---|
| `00-新人上手.md` | 如何开始工作 | 根目录稳定入口文档；环境、运行、验证、常见问题与求助入口 |
| `01-技术总览.md` | 项目技术全貌是什么 | 根目录稳定总览文档；Unity/包版本、架构地图、关键入口与术语 |
| `02-架构与工程/` | 工程如何组织 | 可扩展主题目录；程序集、目录、依赖、资源和配置入口 |
| `03-模块设计/` | 某功能如何实现 | 可扩展主题目录；职责、流程、边界、生命周期和验证 |
| `04-接口与数据/` | 模块如何交换数据 | 可扩展主题目录；协议、存档、schema 和版本兼容 |
| `05-测试与质量/` | 如何验证质量 | 条件创建的主题目录；测试策略、测试环境、质量门禁和性能基线 |
| `06-运行维护/` | 如何构建、发布和排障 | 可扩展主题目录；构建、资源流程、监控、恢复和排障手册 |
| `07-技术决策记录/` | 为什么这样设计 | 可扩展主题目录；ADR 和替代方案 |

- 🔴 `00-新人上手.md` 必须位于技术文档根目录，不再归入管理流程。
- 🔴 `02` 至 `07` 是主题，不是单篇文档名称；主题目录创建后必须同时包含 `README.md` 和至少一篇真实正文，禁止预建空目录或空模板。
- 🔴 `05-测试与质量/` 仅在测试资料有独立 负责人、独立更新节奏，或至少 3 篇长期维护资料时创建；否则把测试要求放在模块或运行维护文档中。
- 🔴 策划、美术、制作、运营、管理流程和代码规范不得混入技术文档目录；本规则不定义它们的目录结构。
- 🟡 性能、安全、网络和资源等横向主题，优先归入架构与工程、接口与数据、测试与质量或运行维护，不为每个关键词单独建目录。

## 2. 拆分、归类与新增主题

先搜索已有文档，再按以下顺序决定位置：

1. 已有文档能够回答同一个主要问题时，更新该文档。
2. 内容属于既有 `02` 至 `07` 主题，但拥有独立读者、来源、维护节奏、操作步骤、契约或技术决策时，在该主题目录新建一篇正文。
3. 内容仍不足以形成独立问题时，保留在现有正文的对应章节，不为一两段补充创建文件。
4. 只有现有 `00` 至 `07` 都无法合理容纳时，才评估新增 `08` 及后续一级技术主题。

新增一级技术主题必须同时满足：

- 🔴 主题具有清晰、长期的技术边界，不能通过调整既有主题解决。
- 🔴 它具有独立 负责人、维护生命周期、外部合规/风险约束，或至少 3 篇长期维护资料中的任一条件。
- 🔴 在 `01-技术总览.md` 与技术文档根目录 `README.md` 说明新增原因、适用范围和入口。

## 3. 索引、命名与链接

技术文档根目录 `README.md` 导航 `00`、`01` 和已创建的主题目录；主题目录的 `README.md` 只导航其下正文，不承载长篇说明。

```markdown
# <技术主题>

> 范围：<本目录解决的问题>

| 文档 | 说明 | 状态 | 负责人 |
|---|---|---|---|
| [<标题>](./<文件名>.md) | <一句话说明> | 有效 | <负责人> |
```

- 🔴 创建、移动、重命名或废弃文档后，必须更新技术文档根目录或最近一级主题目录的 `README.md`。
- 🔴 文件和目录使用简短、可搜索的中文名称；`README.md` 保持工具约定名称。
- 🔴 正文文件名不带日期、版本号、“最终版”或“新版”；子文档不使用无业务含义的连续编号，历史由 Git 管理。
- 🔴 引用必须给出具体路径、标题或代码符号，禁止只写“见代码”“见相关文档”。
- 🟡 跨文档术语统一登记在 `01-技术总览.md` 的术语区；不另建空的术语目录。

## 4. 元数据与状态

除 `README.md` 外，技术文档必须在文件开头包含以下元数据区；目标项目已有等价机制时可沿用。

元数据键名和状态值统一使用中文，禁止在同一项目中混用英文键名或英文状态值。

```yaml
---
标题: <标题>
创建日期: <YYYY-MM-DD>
负责人: <负责人或团队；草稿阶段无法确认时可填待确认>
状态: 草稿 | 有效 | 已废弃
最后更新: <YYYY-MM-DD>
关联文档: [<项目内相对路径>]
来源: [<代码符号、配置路径、契约或测试记录>]
---
```

- 🔴 `草稿` 必须写明待确认事项；`有效` 只记录当前有效事实；`已废弃` 必须说明替代路径。
- 🔴 `创建日期` 只在首次创建时填写；实质修改后更新 `最后更新`，纯排版和错字修正可不更新。
- 🔴 废弃技术文档保留原文、原因和替代路径，不直接删除；无须保留的非技术临时资料不适用本条。
- 🔴 `待确认` 只允许作为 `草稿` 的临时值；转为 `有效` 前必须明确到人员、团队或项目认可的责任角色，AI 不得臆造姓名。
- 🔴 功能修改者负责本次文档同步，负责人负责复核模块边界、事实、状态和后续维护；禁止让 `待确认` 长期代替责任归属。
- 🟡 `有效` 文档超过项目约定复查周期时由负责人复查；项目没有约定时默认以 90 天为提醒周期，但不因时间自动判定失效。

## 5. 权威来源与当前事实

- 🔴 当前能力必须与源码、公开类型、Scene、Prefab、资源、配置、数据迁移、契约和测试核对；需求、实施方案和旧文档只能说明目标或历史，不能单独证明已经实现。
- 🔴 项目应明确产品目标、跨端责任、运行时规则、工具行为以及精确字段的权威来源；其他文档只保留必要摘要和链接，避免复制同一事实。
- 🔴 过时术语和旧能力不得继续出现在当前说明中；需要保留的历史只写入文档变更记录、ADR 或 Git 历史。

## 6. 模块覆盖与维护门禁

- 🔴 新增、拆分、合并或删除具有独立职责、状态或维护节奏的业务模块时，必须检查模块文档、接口文档和索引是否同步。
- 🟡 中大型、多端或曾发生文档漂移的项目应维护“业务模块—源码/资源—文档”覆盖矩阵；小型项目可在技术文档 `README.md` 中使用简表，不强制新增配置文件。
- 🔴 项目已有文档检查命令时必须执行；检查至少应覆盖元数据、相对链接、模块映射和项目定义的废弃术语。自动化不能替代负责人对内容真实性和边界的复核。
- 🟡 推荐在每次提交执行轻量检查，按项目节奏执行全量扫描和负责人复核；频率由项目规模、风险和发布节奏决定。
