# 00 - Java 技术文档编写规范总览

> - 🟢 本规则库只适用于 Java 项目的技术文档。
> - 🔴 不适用：产品、设计、美术、运营和管理文档；也不以通用 Java 经验替代项目事实。

---

## 1. 目标与边界

技术文档应形成可导航的 Code Wiki：读者能够了解项目用途与边界、追踪主要功能、定位关键代码，并按证据运行和修改项目。“完整”以本次范围内主要能力、运行入口和关键链路的覆盖为准，不要求逐文件、逐类或逐函数编写说明；大型仓库分批分析时应列出已覆盖与未覆盖范围。

技术文档只管理工程、模块、契约、数据、测试、运行和技术决策。它解释项目事实和边界，不复制代码、配置或其他角色内容。

本规则库只管理技术文档，默认使用 `项目文档/技术文档/`；项目已有稳定路径与等价组织方式时沿用，并按组织规范建立阅读导航。它不定义完整项目文档的分类。产品需求、策划设计、美术规范、运营和管理流程由各自既有规范与责任人维护，不得混入技术文档目录。

| 合格特征 | 最低要求 |
|---|---|
| 可发现 | 从 `README.md` 找到文档 |
| 可验证 | 关键结论有代码、配置、契约或测试来源 |
| 易理解 | 结论在前，短段落、列表和必要表格优先 |
| 可维护 | 有 负责人、状态、更新时间和废弃路径 |

## 2. 核心原则

1. JDK、构建文件、模块、源码、配置、迁移、测试和部署事实优先。
2. 一篇文档只回答一个主要问题；不预建空目录或空模板。
3. 数值、接口、配置和 schema 只保留一个权威来源。
4. 已验证、提议、待确认和废弃内容必须显式区分。
5. 代码规范仍由 Java AI 编码规则库维护，不在技术文档中重复。
6. `00` 至 `07` 是技术主题基线，不是文档数量上限；主题下按真实维护需求扩展子文档，必要时才新增 `08` 及后续主题。
