# 01 - 技术文档组织与维护规范

> 🟢 本文件只适用于 Go 项目 `项目文档/技术文档/` 的目录、扩展、索引、命名、元数据和生命周期。
> 🔴 不适用：产品需求、策划设计、美术规范、运营和管理流程等非技术资料的组织与维护。

---

## 1. 技术文档的范围与主题基线

技术文档目录只承载工程事实，不承载完整项目文档。非技术资料可由项目的既有规范管理，但不得放入 `技术文档/`。

`00` 至 `07` 是技术主题基线，不是八篇文档的固定清单，也不要求预先创建所有目录：

```text
项目文档/
└── 技术文档/
    ├── README.md
    ├── 00-新人上手.md
    ├── 01-技术总览.md
    ├── 02-架构与工程/            # 有真实内容时创建
    │   ├── README.md
    │   └── <中文主题>.md
    ├── 03-模块设计/              # 有真实内容时创建
    ├── 04-接口与数据/            # 有真实内容时创建
    ├── 05-测试与质量/            # 满足独立维护条件时创建
    ├── 06-运行维护/              # 有真实内容时创建
    ├── 07-技术决策记录/          # 有真实内容时创建
    └── 08-<新增技术主题>/        # 满足新增主题条件时创建
```

| 主题 | 解决的问题 | 默认形态 |
|---|---|---|
| `00-新人上手.md` | 环境、权限、首次运行、验证和求助入口 | 根目录稳定入口文档 |
| `01-技术总览.md` | Go 版本、模块地图、关键入口和术语 | 根目录稳定总览文档 |
| `02-架构与工程/` | 包边界、依赖、配置、构建与工程约定 | 可扩展主题目录 |
| `03-模块设计/` | 模块职责、流程、并发/资源边界和验证 | 可扩展主题目录 |
| `04-接口与数据/` | HTTP/gRPC、消息、存储 schema 和兼容性 | 可扩展主题目录 |
| `05-测试与质量/` | 测试策略、质量门禁、性能基线和可观测性 | 条件创建的主题目录 |
| `06-运行维护/` | 构建、部署、排障、恢复和运行手册 | 可扩展主题目录 |
| `07-技术决策记录/` | ADR 与技术取舍 | 可扩展主题目录 |

- 🔴 `00-新人上手.md` 必须位于技术文档根目录。
- 🔴 `02` 至 `07` 是主题，不是单篇文档名称；主题目录创建后必须同时包含 `README.md` 和至少一篇真实正文，禁止预建空目录或空模板。
- 🔴 `05-测试与质量/` 仅在有独立 负责人、独立更新节奏或至少 3 篇长期维护资料时创建；否则将测试与质量内容写入相关模块或运行维护文档。
- 🔴 产品需求、策划设计、美术规范、运营、管理流程和代码规范不得混入技术文档目录；本规则不定义它们的目录结构。

## 2. 拆分、归类与新增主题

先搜索已有文档，再按以下顺序决定位置：

1. 已有文档能够回答同一个主要问题时，更新该文档。
2. 内容属于既有 `02` 至 `07` 主题，但拥有独立读者、来源、维护节奏、操作步骤、契约或技术决策时，在该主题目录新建一篇正文。
3. 内容仍不足以形成独立问题时，保留在现有正文的对应章节，不为一两段补充创建文件。
4. 只有现有 `00` 至 `07` 都无法合理容纳时，才评估新增 `08` 及后续一级技术主题。

新增一级技术主题必须同时满足：

- 🔴 主题具有清晰、长期的技术边界，不能通过调整既有主题解决。
- 🔴 它具有独立 负责人、维护生命周期、外部合规/风险约束，或至少 3 篇长期维护资料中的任一条件。
- 🔴 在 `01-技术总览.md` 与技术文档根目录 `README.md` 说明新增原因、适用范围和入口。

## 3. 索引与命名

技术文档根目录 `README.md` 导航 `00`、`01` 和已创建的主题目录；主题目录的 `README.md` 只导航其下正文：

```markdown
# <技术主题>

| 文档 | 说明 | 状态 | 负责人 |
|---|---|---|---|
| [<标题>](./<文件名>.md) | <一句话说明> | 有效 | <负责人> |
```

- 🔴 创建、移动、重命名或废弃文档后，更新技术文档根目录或最近一级主题目录的 `README.md`。
- 🔴 正文文件名使用简短中文主题；禁止日期、版本号、“最终版”和“新版”。子文档不使用无业务含义的连续编号。
- 🔴 引用必须给出具体路径、标题或 Go 符号，禁止只写“见代码”。
- 🟡 跨文档术语登记在 `01-技术总览.md` 的术语区。

## 4. 元数据与生命周期

除 `README.md` 外，技术文档使用：

元数据键名和状态值统一使用中文，禁止在同一项目中混用英文键名或英文状态值。

```yaml
---
标题: <标题>
创建日期: <YYYY-MM-DD>
负责人: <负责人或团队；草稿阶段无法确认时可填待确认>
状态: 草稿 | 有效 | 已废弃
最后更新: <YYYY-MM-DD>
关联文档: [<项目内相对路径>]
来源: [<代码符号、配置、契约或测试记录>]
---
```

- 🔴 `草稿` 写清待确认项；`有效` 只记录当前有效事实；`已废弃` 写明替代路径。
- 🔴 `创建日期` 只在首次创建时填写；实质修改更新 `最后更新`。
- 🔴 废弃技术文档保留原文、原因和替代路径，不直接删除；无须保留的非技术临时资料不适用本条。
- 🔴 `待确认` 只允许作为 `草稿` 的临时值；转为 `有效` 前必须明确到人员、团队或项目认可的责任角色，AI 不得臆造姓名。
- 🔴 功能修改者负责本次文档同步，负责人负责复核模块边界、事实、状态和后续维护；禁止让 `待确认` 长期代替责任归属。
- 🟡 `有效` 文档超过项目约定复查周期时由负责人复查；项目没有约定时默认以 90 天为提醒周期，但不因时间自动判定失效。

## 5. 权威来源与当前事实

- 🔴 当前能力必须与源码、公开类型、路由、配置、数据库迁移、契约和测试核对；需求、实施方案和旧文档只能说明目标或历史，不能单独证明已经实现。
- 🔴 项目应明确产品目标、跨端责任、后端规则、前端行为以及精确字段的权威来源；其他文档只保留必要摘要和链接，避免复制同一事实。
- 🔴 过时术语和旧能力不得继续出现在当前说明中；需要保留的历史只写入文档变更记录、ADR 或 Git 历史。

## 6. 模块覆盖与维护门禁

- 🔴 新增、拆分、合并或删除具有独立职责、状态或维护节奏的业务模块时，必须检查模块文档、接口文档和索引是否同步。
- 🟡 中大型、多端或曾发生文档漂移的项目应维护“业务模块—源码—文档”覆盖矩阵；小型项目可在技术文档 `README.md` 中使用简表，不强制新增配置文件。
- 🔴 项目已有文档检查命令时必须执行；检查至少应覆盖元数据、相对链接、模块映射和项目定义的废弃术语。自动化不能替代负责人对内容真实性和边界的复核。
- 🟡 推荐在每次提交执行轻量检查，按项目节奏执行全量扫描和负责人复核；频率由项目规模、风险和发布节奏决定。
