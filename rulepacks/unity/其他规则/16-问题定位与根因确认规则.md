# 16 - Unity 问题定位与根因确认规则

> - 🟢 本文件适用于 Unity 项目中 Bug、异常、报错、首次流程异常和非预期行为的排查与修复。
> - 🔴 不适用：已明确为功能开发、文案调整或纯格式修改的任务；但一旦涉及“为什么行为不符合预期”，即应遵守本文件。

---

## 1. 先定位，后修复

### 1.1 核心要求

- 🔴 **必须**先区分“现象”“报错发生的位置”和“根本问题”。现象不再出现或异常不再抛出，不代表根本问题已经解决。
- 🔴 **必须**在确认根本问题前完成定位，不得提交、合并或声称已经完成根治性修复。
- 🔴 **必须**基于可复现步骤、运行日志、状态数据、调用时序、代码实现、设备验证或其他可观察证据定位问题；不得将猜测、经验判断或偶然成功当作根本问题。
- 🔴 **必须**将根本问题描述为可验证的具体事实，例如“首次加载时读取到空数据后仍被标记为完成”“初始化任务未被触发”“生成任务失败后状态未复位”；不得只写“时序问题”“偶发问题”或“功能失效”。

### 1.2 根因确认度与未确认时的边界

根因确认度应在定位结论中标为高、中或低：

| 确认度 | 条件 |
|---|---|
| 高 | 有证据证明具体异常状态存在，并能说明它如何稳定导致当前现象；主要替代原因已被排除。 |
| 中 | 现有证据支持某个原因，但仍有合理替代原因或关键环节尚未验证。 |
| 低 | 仅有代码阅读、经验推测、片段日志或偶发观察，尚不能说明因果过程。 |

- 🔴 **必须**在确认度为中或低时，说明当前证据、尚未解决的疑点和需要的人类输入；禁止直接修改业务行为并称其为根治修复。
- 🟢 **可选**：为验证具体假设，添加最小、可回滚的临时日志、断点、测试或状态观测；应遵守 [07 - Unity 日志与调试规则](./07-日志调试规则.md)，完成定位后清理或收敛。
- 🟢 **可选**：用户明确要求紧急止血时，可实施范围受控的临时防护；必须明确它只降低风险、尚未解决的根本问题和后续根治条件。
- ❌ **禁止**：根因未确认时，以“修复”名义加入猜测性的业务改动、延时、无条件重试或默认值兜底。

## 2. 证据、候选原因与实际验证

### 2.1 观察证据

- 🔴 **必须**收集与问题相关的可获得证据：复现步骤、触发条件、实际表现、异常类型与堆栈（如有）、关键状态值、调用或事件时序、设备/平台差异、网络或 SDK 返回结果。
- 🔴 **必须**在无法稳定复现时明确标注“未复现”或“仅从现有记录推断”，降低结论确定性；不得把单次失败或偶发成功当作充分证据。
- 🔴 **必须**区分事实和推断。例如“首次加载时配置列表为空”是事实；“网络一定丢包”只是待验证假设。
- ❌ **禁止**：仅凭函数名、类名、单行报错或代码外观套用既有问题模式。

### 2.2 候选原因与证伪

- 🔴 **必须**在根因不唯一或不明显时，列出至少两个合理的候选原因；分别说明支持证据、反驳或排除依据，以及下一步验证方式。
- 🔴 **必须**优先寻找能够证伪候选原因的证据，不能只收集支持第一个猜测的材料。
- 🟡 **推荐**：用最小验证动作区分候选原因，例如检查首次回调是否触发、关键数据是否为空、生成任务是否实际执行、完成标记是否被过早设置。
- 🟢 **可选**：当证据已唯一确认问题时，不必人为凑出候选原因；应说明排除其他可能性的依据。

### 2.3 实际验证与因果说明

- 🔴 **必须**通过日志、断点、最小复现、测试、状态观测或其他适当方式，实际验证候选原因确实能导致观察到的现象；仅靠阅读代码或凭经验推测的原因只能称为“疑点”。
- 🔴 **必须**说明从根本问题到最终现象的过程：哪个状态为何异常、该状态如何影响后续行为，以及为何表现为当前问题。
- 🔴 **必须**自查：若只在当前报错行加判空、`try-catch`、默认值或直接返回，问题是否可能在其他位置再次出现；若可能，说明根本问题尚未找到。

## 3. 首次流程与重复流程

- 🔴 **必须**在首次进入、首次初始化、首次授权、首次标定、首次加载等路径异常，而重复进入、重试或重启后正常时，分别验证首次流程和重复流程。
- 🔴 **必须**确认关键数据和状态的产生、保存、传递、消费及完成标记是否完整；不得仅因界面显示正常、部分功能可用或重复流程成功，就假定首次初始化已完成。
- 🟡 **推荐**：将“仅首次异常、再次正常”作为排查线索，检查缓存、订阅时机、异步完成条件、初始化失败后的状态复位等差异；线索本身不是根本问题结论。
- 🟡 **推荐**：将原始首次故障路径保留为回归验证用例，避免只在已有缓存或已初始化状态下验证成功。

## 4. 修复边界与职责保持

### 4.1 修改位置

- 🔴 **必须**只修改造成异常状态或错误行为的责任代码、配置、数据或流程，而不是修改仅表现出症状的功能。
- 🔴 **必须**为每一处改动说明它与已确认根本问题的直接关系；根治确需改动多个模块时，每项改动都应有明确的因果理由。
- 🟡 **推荐**：保持既有职责边界。一个功能原本只负责输入、发射、UI 展示或创建对象时，不应承担初始化失败、数据缺失或生命周期错误的补救逻辑。

### 4.2 禁止默认补丁

- ❌ **禁止**默认通过增加等待时间、判空后直接返回、吞掉异常、无条件重试、限制用户操作、重复初始化、强制刷新或默认值兜底来替代根本修复。
- ❌ **禁止**因为多个功能出现异常，就分别修改每个功能以绕开症状。
- 🟡 **推荐**：防御性校验可用于保护边界和避免二次损害，但不能替代根本修复；如保留，必须说明其保护目的和适用条件。

## 5. 验证与交付

### 5.1 回归验证

- 🔴 **必须**重新执行原始复现步骤，确认原始现象消失。
- 🔴 **必须**验证修复没有破坏受影响功能原有职责，也没有只在重进、缓存命中或已初始化状态下“看起来正常”。
- 🟡 **推荐**：涉及首次流程时，至少验证首次路径、重复路径和异常/失败后的恢复路径；涉及设备或平台 SDK 时，记录实际验证的设备与环境。

### 5.2 交付说明

每次缺陷排查或修复完成时，AI 必须说明：

1. 原始现象、复现条件和影响范围。
2. 收集到的关键证据，以及被排除或仍待验证的候选原因和依据。
3. 已确认的根本问题、根因确认度，以及从问题到现象的过程。
4. 修改了什么、为什么修改该处，以及为什么不修改其他表现异常的功能。
5. 已执行的验证、未验证范围、临时防护和剩余风险。

## 6. 修改前自查清单

- [ ] 是否已记录可获得的复现步骤、触发条件和实际表现？
- [ ] 是否已取得异常/堆栈（如有）、关键状态、时序或其他相关证据？
- [ ] 是否明确区分了已确认事实、候选原因和未经验证的推断？
- [ ] 在根因不唯一或不明显时，是否列出了至少两个候选原因及其验证或排除依据？
- [ ] 是否已通过日志、断点、最小复现、测试或状态观测实际验证候选原因？
- [ ] 是否能说明根本问题如何导致最终现象，而非只指出报错发生的位置？
- [ ] 当前修改是否只是判空、延时、吞异常、默认值或其他症状补丁？
- [ ] 根因确认度是否如实说明？确认度不足时，是否仅进行诊断或经授权的临时止血？
- [ ] 是否计划按原始复现路径验证，并检查相关功能是否出现副作用？

## 7. 正反例

### 7.1 首次进入关卡时碰撞初始化失败

首次进入关卡后，角色可以移动，但投射物会穿过地面、射线检测不到机关、角色也可能进入本应阻挡的区域；返回主菜单再重新进入关卡后，一切恢复正常。

排查发现：

1. `LevelCollisionBootstrapper` 在 `Start` 中开始生成关卡碰撞体。
2. 此时 `LevelDataProvider.LoadAsync()` 尚未完成，生成器拿到的是空的关卡数据。
3. 生成器虽然没有生成任何碰撞体，却提前把 `m_isBuilt` 标记为 `true`。
4. 再次进入关卡时，关卡数据已在缓存中，生成器拿到有效数据，因此碰撞体正常生成。

- ❌ 不应在投射物脚本中增加“未检测到地面就延迟发射”。
- ❌ 不应在射线检测脚本中增加“首次进入关卡时重复检测”。
- ❌ 不应在角色控制器中增加“碰撞体未准备好时禁止移动”。
- ✅ 应修复关卡碰撞体初始化流程：只在关卡数据成功加载后开始生成碰撞体，并且只有确认生成成功后才设置 `m_isBuilt`。
- ✅ 投射物、射线检测和角色控制器继续只负责各自原有职责，不承担关卡碰撞体初始化失败的补救逻辑。

这个例子中，三个功能的异常表现不同，但“仅首次异常、重进后恢复”是重要线索。若按各自症状分别打补丁，会留下多处暗坑，且根本问题仍可能以其他形式出现。

### 7.2 常驻协程或异步回调持有已销毁对象

场景卸载后，一个常驻管理器启动的协程或异步回调仍持有场景对象引用；回调恢复执行时访问该对象，出现 `NullReferenceException`。

- ❌ 不应仅在回调中加入 `if (target == null) yield break;`，然后将报错消失视为已修复。
- ✅ 应确认协程或回调的实际宿主、引用注册位置和取消责任：例如常驻管理器没有在场景卸载时取消该操作或解除回调。
- ✅ 根本修复应落在操作所有权和生命周期绑定处：按项目既有模式取消操作、解除回调或使其不再持有失效的场景对象，而不是把空判断分散到每个回调点。

### 7.3 隐式脚本执行顺序导致读取默认值

组件 A 在 `Start()` 中读取组件 B 初始化的数据，却读到默认值。

- ❌ 不应直接把读取逻辑改成“读不到就用默认值兜底”。
- ✅ 应记录 A、B 的实际初始化顺序和数据赋值时机，确认是否依赖未被项目保证的执行顺序。
- ✅ 根本修复通常是建立显式初始化完成契约，例如由初始化协调者调用 `Init()` 或等待既有完成事件；只有在项目明确采用且适合时，才调整 Script Execution Order。
