# 02 - Unity 设计模式与架构指南

> - 🟢 本文件适用于 Unity 模块架构设计（单例/对象池/状态机/事件系统等）。
> - 🔴 不适用：业务逻辑实现、美术资源制作、平台原生 API 细节

---

## 1. 设计原则

🔴 **AI 架构决策前**必须先检查已有模块边界、程序集、依赖方向、生命周期和同类实现。本章中的模式是决策工具，不是要求每个项目都新增抽象、依赖注入容器、单例或事件总线的默认方案。

🟡 当已有实现能够满足当前需求时，优先沿用；只有出现明确的扩展、性能、测试或模块边界问题时，才引入相应模式，并记录理由与验证方式。

### 1.1 SOLID 总览

SOLID 是面向对象设计的五个核心原则。在 Unity 中合理应用，能让 MonoBehaviour、ScriptableObject 与系统类更易维护。

| 原则 | 简述 | 关注什么 |
|------|------|---------|
| **S** - 单一职责 | 一个类只做一件事 | 类的拆分粒度 |
| **O** - 开闭原则 | 对扩展开放，对修改关闭 | 通过多态扩展 |
| **L** - 里氏替换 | 子类可替换父类 | 继承体系设计 |
| **I** - 接口隔离 | 接口要小而专 | 接口拆分粒度 |
| **D** - 依赖倒置 | 依赖抽象不依赖具体 | 解耦与注入 |

### 1.2 单一职责原则（SRP）

**一个类应当只有**一个**引起它变化的原因。**

```csharp
// 不良 - 一个类承担多项职责
public class GameManager : MonoBehaviour
{
    public void SaveGame() { /* 保存 */ }
    public void LoadGame() { /* 加载 */ }
    public void UpdateUI() { /* UI 更新 */ }
    public void PlaySound() { /* 播放音效 */ }
}

// 良好 - 拆分为职责单一的类
public class SaveSystem { public void Save() { } }
public class LoadSystem { public void Load() { } }
public class UIController : MonoBehaviour { public void Refresh() { } }
public class AudioManager : MonoBehaviour { public void Play() { } }
```

> **Unity 实践提示**：把 MonoBehaviour 当作"视图+输入"，把业务逻辑放到普通 C# 类、ScriptableObject 或服务中。

### 1.3 开闭原则（OCP）

**对扩展开放，对修改关闭。**

```csharp
// 不良 - 频繁修改 if/else 分支
public float CalculateDamage(string weaponType)
{
    if (weaponType == "Sword") return 10f;
    if (weaponType == "Bow") return 7f;
    if (weaponType == "Magic") return 15f;
    return 0f;
}

// 良好 - 通过多态扩展
public abstract class Weapon
{
    public abstract float CalculateDamage();
}

public class Sword : Weapon { public override float CalculateDamage() => 10f; }
public class Bow : Weapon { public override float CalculateDamage() => 7f; }
public class Magic : Weapon { public override float CalculateDamage() => 15f; }
```

### 1.4 里氏替换原则（LSP）

**子类对象应当能够替换父类对象而不出错。**

```csharp
// 良好 - 遵循 LSP
public class Bird
{
    public virtual void Move() { }
}

public class Sparrow : Bird
{
    public override void Move() { /* 飞行 */ }
}

// 不良 - 鸵鸟不能飞，子类改变父类行为
public class Ostrich : Bird
{
    public override void Move() { throw new System.NotImplementedException(); }
}

// 更好 - 重构层次结构
public abstract class Bird { public abstract void Move(); }
public abstract class FlyingBird : Bird { public abstract void Fly(); }
public class Ostrich : Bird { public override void Move() { /* 跑 */ } }
```

### 1.5 接口隔离原则（ISP）

**客户端不应被迫依赖它们不用的接口。**

```csharp
// 不良 - 臃肿接口
public interface IUnit
{
    void Attack();
    void Heal();
    void CastSpell();
    void Gather();
}

// 良好 - 拆分小接口
public interface IAttacker { void Attack(); }
public interface IHealer { void Heal(); }
public interface ICaster { void CastSpell(); }
public interface IGatherer { void Gather(); }

public class Warrior : IAttacker { public void Attack() { } }
public class Priest : IHealer { public void Heal() { } }
```

### 1.6 依赖倒置原则（DIP）

**高层模块不应依赖低层模块；二者都应依赖抽象。**

```csharp
// 不良 - 直接依赖具体类
public class Player
{
    private MySQLDatabase m_db = new MySQLDatabase();
}

// 良好 - 依赖抽象
public interface IDatabase
{
    void Save(string data);
}

public class Player
{
    private readonly IDatabase m_db;
    public Player(IDatabase db) { m_db = db; }
}
```

### 1.7 KISS / YAGNI / DRY 原则

除了 SOLID，还有三条**更高层的设计原则**：

| 原则 | 含义 | 实践 |
|------|------|------|
| **KISS**（Keep It Simple, Stupid） | 简单优于复杂 | 不要过度设计，能用一个方法解决就别拆 5 个类 |
| **YAGNI**（You Aren't Gonna Need It） | 你不会需要它 | 不要为"未来可能用到"写代码，只写当前需要的 |
| **DRY**（Don't Repeat Yourself） | 不要重复自己 | 同一段逻辑不要在 3 处以上出现，提取为方法或类 |

**实战判断**：
- 当你犹豫"要不要拆成更小的类"时，**先 KISS**：保持简单
- 当你犹豫"要不要为未来加这个功能"时，**YAGNI**：等真要了再写
- 当你发现"这逻辑在 3 个地方都有"时，**DRY**：提取公共部分

```csharp
// ❌ 错：违反 KISS（为不可能的需求加抽象）
public interface IItemFactoryProviderFactory { ... }  // 抽象太多层

// ❌ 错：违反 YAGNI（为未来预留的"灵活点"）
public class Player
{
    private readonly IStrategy m_futureStrategy;  // 还没需求就预留
    public Player() { m_futureStrategy = null; }
}

// ❌ 错：违反 DRY（同一逻辑复制 3 处）
public void DoDamage(Enemy e) { m_health -= 10; }
public void DoFireDamage(Enemy e) { m_health -= 10; }  // 重复
public void DoIceDamage(Enemy e) { m_health -= 10; }  // 重复
```

## 2. 常用模式
### 2.1 单例模式（Singleton）

**用途**：生命周期、唯一性和访问边界都已由项目明确的全局服务（如音频或会话协调器）。

🔴 **先确认项目的启动与依赖方案**：已有依赖注入、服务定位器或 Bootstrap 时沿用它；不要为了套用本节新增单例。`Instance` 访问器不得搜场景或隐式创建对象，否则一次普通读取就会改变场景与初始化顺序。

```csharp
// 仅在项目已决定使用场景级单例时采用。
// 实例必须由 Bootstrap 或场景中的显式组件创建。
public abstract class SceneSingleton<T> : MonoBehaviour where T : SceneSingleton<T>
{
    private static T s_instance;
    public static T Instance => s_instance
        ?? throw new InvalidOperationException(
            $"{typeof(T).Name} 尚未由项目启动流程初始化。");

    protected virtual void Awake()
    {
        if (s_instance != null && s_instance != this)
        {
            Destroy(gameObject);
            return;
        }
        s_instance = (T)this;
    }

    protected virtual void OnDestroy()
    {
        if (s_instance == this)
            s_instance = null;
    }
}

// 使用
public class GameManager : SceneSingleton<GameManager>
{
    public void StartGame() { /* ... */ }
}

// 调用
GameManager.Instance.StartGame();
```

> ⚠️ **慎用**：单例会导致紧耦合、可测性差。优先用 ScriptableObject 注入或依赖注入；跨场景常驻、重复实例处理和测试替身都必须由项目启动流程定义，不能由基类猜测。

### 2.2 对象池模式（Object Pool）

**用途**：避免频繁实例化/销毁带来的 GC 压力（子弹、特效、敌人）。

```csharp
using UnityEngine.Pool;

public class BulletPool : MonoBehaviour
{
    [SerializeField] private Bullet m_bulletPrefab;
    private ObjectPool<Bullet> m_pool;

    private void Awake()
    {
        m_pool = new ObjectPool<Bullet>(
            createFunc: () => Instantiate(m_bulletPrefab),
            actionOnGet: bullet => bullet.gameObject.SetActive(true),
            actionOnRelease: bullet => bullet.gameObject.SetActive(false),
            actionOnDestroy: bullet => Destroy(bullet.gameObject),
            collectionCheck: false,
            defaultCapacity: 20,
            maxSize: 100
        );
    }

    public Bullet GetBullet() => m_pool.Get();
    public void ReturnBullet(Bullet bullet) => m_pool.Release(bullet);
}
```

### 2.3 状态模式（State）

**用途**：对象行为随状态变化（角色控制器、AI、UI 流程）。

```csharp
public interface IPlayerState
{
    void Enter();
    void Update();
    void Exit();
}

public class PlayerController : MonoBehaviour
{
    private IPlayerState m_currentState;

    public void ChangeState(IPlayerState newState)
    {
        m_currentState?.Exit();
        m_currentState = newState;
        m_currentState.Enter();
    }

    private void Update() => m_currentState?.Update();
}

public class IdleState : IPlayerState
{
    private readonly PlayerController m_controller;
    public IdleState(PlayerController c) { m_controller = c; }
    public void Enter() { /* 播放 idle 动画 */ }
    public void Update() { /* 检查输入，必要时 ChangeState(new RunningState(...)) */ }
    public void Exit() { }
}
```

### 2.4 观察者 / 事件模式（Observer / Event）

**用途**：解耦事件发布者与订阅者。

```csharp
public class Player : MonoBehaviour
{
    public event System.Action<int> OnHealthChanged;
    private int m_health = 100;

    public void TakeDamage(int amount)
    {
        m_health -= amount;
        OnHealthChanged?.Invoke(m_health);
    }
}

public class HealthBar : MonoBehaviour
{
    [SerializeField] private Player m_player;
    private void OnEnable() { m_player.OnHealthChanged += UpdateBar; }
    private void OnDisable() { m_player.OnHealthChanged -= UpdateBar; }
    private void UpdateBar(int health) { /* 更新 UI */ }
}
```

### 2.5 命令模式（Command）

**用途**：输入处理、撤销/重做、操作记录。

```csharp
public interface ICommand
{
    void Execute();
    void Undo();
}

public class MoveCommand : ICommand
{
    private readonly Transform m_target;
    private readonly Vector3 m_offset;
    public MoveCommand(Transform t, Vector3 offset) { m_target = t; m_offset = offset; }
    public void Execute() => m_target.position += m_offset;
    public void Undo() => m_target.position -= m_offset;
}

public class InputController : MonoBehaviour
{
    private readonly Stack<ICommand> m_history = new Stack<ICommand>();

    public void ExecuteCommand(ICommand cmd)
    {
        cmd.Execute();
        m_history.Push(cmd);
    }

    public void Undo()
    {
        if (m_history.Count > 0) m_history.Pop().Undo();
    }
}
```

### 2.6 策略模式（Strategy）

**用途**：可互换的算法（不同的移动方式、不同的攻击方式）。

```csharp
public interface IMovementStrategy
{
    void Move(Transform target, Vector3 direction);
}

public class WalkStrategy : IMovementStrategy
{
    public void Move(Transform t, Vector3 d) => t.position += d * 5f * Time.deltaTime;
}

public class FlyStrategy : IMovementStrategy
{
    public void Move(Transform t, Vector3 d) => t.position += d * 8f * Time.deltaTime;
}

public class Enemy : MonoBehaviour
{
    private IMovementStrategy m_movement;
    public void SetMovement(IMovementStrategy s) => m_movement = s;
    private void Update() => m_movement.Move(transform, Vector3.forward);
}
```

### 2.7 模板方法模式（Template Method）

**用途**：定义算法骨架，把可变步骤留给子类实现（UI 框架、关卡流程）。

```csharp
public abstract class UIPanel
{
    // 模板方法：定义打开/关闭的固定流程
    public void Open()
    {
        OnBeforeOpen();      // 1. 钩子方法
        Show();               // 2. 必须实现
        OnAfterOpen();       // 3. 钩子方法
    }

    public void Close()
    {
        OnBeforeClose();
        Hide();
        OnAfterClose();
    }

    protected abstract void Show();
    protected abstract void Hide();
    protected virtual void OnBeforeOpen() { }  // 钩子：可选覆盖
    protected virtual void OnAfterOpen() { }
    protected virtual void OnBeforeClose() { }
    protected virtual void OnAfterClose() { }
}

public class SettingsPanel : UIPanel
{
    protected override void Show() { gameObject.SetActive(true); }
    protected override void Hide() { gameObject.SetActive(false); }
    protected override void OnBeforeOpen() { /* 加载玩家设置 */ }
}
```

### 2.8 外观模式（Facade）

**用途**：为一组复杂子系统提供统一的高层接口（隐藏内部复杂性）。

```csharp
// ❌ 错：客户端直接调用多个子系统
public class GameStartup
{
    public void StartGame()
    {
        var audio = AudioManager.Instance;
        var ui = UIManager.Instance;
        var save = SaveSystem.Instance;
        audio.LoadSettings();
        ui.ShowLoadingScreen();
        save.LoadProgress();
        // 客户端要懂每个子系统的细节
    }
}

// ✅ 好：用外观模式封装
public class GameFacade
{
    public void StartGame()
    {
        AudioManager.Instance.LoadSettings();
        UIManager.Instance.ShowLoadingScreen();
        SaveSystem.Instance.LoadProgress();
    }

    public void QuitGame()
    {
        SaveSystem.Instance.SaveProgress();
        UIManager.Instance.HideLoadingScreen();
        AudioManager.Instance.SaveSettings();
    }
}

// 客户端只跟外观打交道
public class MainMenu : MonoBehaviour
{
    [SerializeField] private GameFacade m_facade;

    private void OnStartClicked() => m_facade.StartGame();
    private void OnQuitClicked() => m_facade.QuitGame();
}
```

## 3. 架构模式

### 3.1 ScriptableObject 架构（SOA）

**把可变状态、配置、共享数据抽到 ScriptableObject 中**，多个 MonoBehaviour 通过引用共享。

```csharp
[CreateAssetMenu(fileName = "GameSettings", menuName = "Game/Settings")]
public class GameSettings : ScriptableObject
{
    public float PlayerSpeed = 5f;
    public int MaxLevel = 50;
    public bool EnableDebugMode = false;
}

public class Player : MonoBehaviour
{
    [SerializeField] private GameSettings m_settings;
    private void Update()
    {
        transform.position += Vector3.forward * m_settings.PlayerSpeed * Time.deltaTime;
    }
}
```

> **好处**：美术/策划可直接在 Inspector 调参；多个系统可共享同一份配置。

### 3.2 MVC / MVVM 变体

Unity 没有官方的 MVC/MVVM 框架，但社区已有成熟实践：

- **Model**：纯 C# 类或 ScriptableObject（数据 + 业务规则）
- **View**：MonoBehaviour（仅负责显示、UI 、动画）
- **Controller / ViewModel**：MonoBehaviour 或普通类（处理输入、订阅 Model 变化、更新 View）

```csharp
// Model
public class PlayerData
{
    public int Health { get; set; }
    public event System.Action<int> OnHealthChanged;
    public void TakeDamage(int amount)
    {
        Health -= amount;
        OnHealthChanged?.Invoke(Health);
    }
}

// View
public class HealthBarView : MonoBehaviour
{
    [SerializeField] private PlayerData m_data;
    private void OnEnable() { m_data.OnHealthChanged += Refresh; }
    private void OnDisable() { m_data.OnHealthChanged -= Refresh; }
    private void Refresh(int health) { /* 调整 UI */ }
}
```

### 3.3 ECS（实体组件系统）

适用于**大量实体 + 重数据/重计算**（上千敌人、上万粒子）。Unity 提供了：

- **DOTS / Entities**：纯数据导向，最大性能。
- **社区轻量 ECS**：如 Entitas。

```csharp
// Unity DOTS 示例（简略）
public struct Position : IComponentData
{
    public float3 Value;
}

public class MoveSystem : ISystem
{
    public void OnUpdate(ref SystemState state)
    {
        foreach (var (transform, pos) in
                 SystemAPI.Query<RefRO<LocalTransform>, RefRW<Position>>())
        {
            /* 更新位置 */
        }
    }
}
```

> ⚠️ **注意**：DOTS 学习曲线较陡，UI/动画/物理的成熟度仍不及传统 MonoBehaviour 工作流，建议在性能关键子系统中引入，而不是全盘替换。

### 3.4 分层架构

按依赖方向从低到高分层，**单向依赖，禁止反向**：

| 层 | 职责 | 例子 |
|----|------|------|
| **Core**（领域层） | 纯 C# 业务逻辑，不依赖 Unity | 伤害计算、状态机、规则引擎 |
| **Gameplay**（游戏层） | 把 Core 包装成游戏逻辑 | Player、Enemy、Weapon |
| **Presentation**（表现层） | UI、动画、声音、相机 | UI Toolkit、Animator、AudioSource |
| **Infrastructure**（基础设施层） | IO、网络、平台 SDK | SaveSystem、Analytics、PlatformAPI |

**依赖方向**：
```
Presentation → Gameplay → Core
                ↓
           Infrastructure（各层都可依赖）
```

**好处**：
- Core 层可纯 C# 单元测试（不依赖 Unity）
- 换 UI 框架时不动 Gameplay / Core
- 换网络库时只动 Infrastructure

### 3.5 事件总线（EventBus）

**全局事件分发中心**，让任意两个系统通信而不直接耦合。

```csharp
// 简单实现
public static class EventBus<T> where T : struct
{
    private static event System.Action<T> s_listeners;
    public static void Subscribe(System.Action<T> listener) => s_listeners += listener;
    public static void Unsubscribe(System.Action<T> listener) => s_listeners -= listener;
    public static void Publish(T evt) => s_listeners?.Invoke(evt);
}

// 定义事件
public struct PlayerDiedEvent { public int PlayerId; }

// 发布
EventBus<PlayerDiedEvent>.Publish(new PlayerDiedEvent { PlayerId = 1 });

// 订阅（在 OnEnable / OnDisable）
EventBus<PlayerDiedEvent>.Subscribe(OnPlayerDied);
EventBus<PlayerDiedEvent>.Unsubscribe(OnPlayerDied);

private void OnPlayerDied(PlayerDiedEvent evt) { /* 处理 */ }
```

> **使用注意**：
> - 必须成对订阅/取消订阅（OnEnable + OnDisable）
> - 事件参数用 `struct` 避免 GC
> - 慎用，滥用会变成"事件 spaghetti"

## 4. 解耦原则

### 4.1 依赖抽象不依赖具体

- 🔴 跨模块通信 / 注入依赖时，**依赖接口或抽象类**，不依赖具体类
- 🔴 内部使用可以 new 自己的具体类（不要过度抽象）

```csharp
// ✅ 好：依赖抽象
public class Player
{
    private readonly IInput m_input;  // 接口
    public Player(IInput input) { m_input = input; }
}

// ❌ 错：依赖具体类（无法换实现 / 难测试）
public class Player
{
    private readonly KeyboardInput m_input;  // 具体类
}
```

### 4.2 接口隔离（ISP 实践）

- 🔴 接口要小而专，**一个接口只做一件事**（见 1.5 接口隔离原则）
- 🟡 接口命名用动词或形容词（`IDamageable` / `IHealable` / `ISerializable`），不用 `IPlayerInterface` 这种宽泛名

### 4.3 单向依赖（避免循环引用）

- 🔴 模块 A 依赖 B，B 不能再依赖 A
- 🟡 用事件 / 接口 / 抽象类**打破循环**

```csharp
// ❌ 错：循环依赖
public class Inventory { public Player Owner; }
public class Player { public Inventory Bag; }  // 循环

// ✅ 好：单向 + 事件
public class Inventory
{
    public event System.Action<Item> OnItemAdded;
    public void AddItem(Item item) { /* ... */ OnItemAdded?.Invoke(item); }
}

public class Player : MonoBehaviour
{
    [SerializeField] private Inventory m_inventory;
    private void OnEnable() { m_inventory.OnItemAdded += HandleItem; }
}
```

### 4.4 事件驱动解耦

- 🔴 系统间通信优先用**事件 / 委托**，不用直接引用
- 🟡 事件订阅要成对（OnEnable / OnDisable）

```csharp
// ✅ 系统 A 不直接引用系统 B，通过事件通信
public class ScoreSystem : MonoBehaviour
{
    public event System.Action<int> OnScoreChanged;

    public void AddScore(int delta) { /* ... */ OnScoreChanged?.Invoke(score); }
}

public class UIScore : MonoBehaviour
{
    [SerializeField] private ScoreSystem m_score;
    private void OnEnable() { m_score.OnScoreChanged += Refresh; }
    private void OnDisable() { m_score.OnScoreChanged -= Refresh; }
}
```

## 5. 代码异味与反模式

### 5.1 上帝类（God Class）

**症状**：一个类承担 10+ 职责，几千行代码，几十个字段。

**避免方法**：
- 按职责拆分（SRP）
- 用 ScriptableObject 分离配置
- 用 partial class 拆文件（仅做临时方案）

```csharp
// ❌ 错：上帝类
public class GameManager : MonoBehaviour
{
    public List<Enemy> Enemies;
    public List<Item> Items;
    public int Score;
    public float TimeLeft;
    public SaveData Save;
    public SettingsData Settings;
    public void Update() { /* 1000 行逻辑 */ }
    public void SaveGame() { }
    public void LoadGame() { }
    // ... 几十个方法
}

// ✅ 好：拆分
public class ScoreSystem : MonoBehaviour { /* 只管分数 */ }
public class SaveSystem : MonoBehaviour { /* 只管存档 */ }
public class GameManager : MonoBehaviour
{
    [SerializeField] private ScoreSystem m_score;
    [SerializeField] private SaveSystem m_save;
    // 只做协调
}
```

### 5.2 面条代码（Spaghetti Code）

**症状**：控制流混乱（goto / 深层 if 嵌套 / 长方法 / 跨模块直接访问）。

**避免方法**：
- 见名知意的短方法（一个方法 < 30 行）
- 早返回代替深层嵌套（见 `01-代码编写规则.md` 7.4）
- 不直接跨模块访问（用事件 / 接口）

### 5.3 过度设计（Over Engineering）

**症状**：为不可能的需求加抽象、为未来预留灵活点、3 行代码包 5 个类。

**避免方法**：
- **YAGNI**（见 1.7）：只为当前需求写代码
- **KISS**（见 1.7）：保持简单
- 出现 3 次以上重复才考虑抽象（DRY 触发条件）

```csharp
// ❌ 错：过度设计（3 行代码包了 5 个接口）
public interface IAttackable { void Attack(); }
public interface IDamageable { void TakeDamage(); }
public interface IKillable { void Die(); }
public abstract class ActorBase : MonoBehaviour, IAttackable, IDamageable, IKillable { }

// ✅ 好：等真的需要再抽象
public class Enemy : MonoBehaviour
{
    public void Attack() { }
    public void TakeDamage(int amount) { }
    public void Die() { }
}
```

### 5.4 复制粘贴反模式

**症状**：同一段逻辑在 3+ 处出现，复制粘贴得来。

**避免方法**：
- **DRY**（见 1.7）：3 次重复就提取
- 提取为方法、类、或 ScriptableObject 配置

```csharp
// ❌ 错：3 处重复
public void DoDamage(Enemy e) { e.Health -= 10; }
public void DoFireDamage(Enemy e) { e.Health -= 10; }  // 重复
public void DoIceDamage(Enemy e) { e.Health -= 10; }  // 重复

// ✅ 好：提取公共方法
public void ApplyDamage(Enemy e, int amount) { e.Health -= amount; }
```

## 6. 模块设计

### 6.1 模块边界（namespace / assembly）

- 🔴 一个 Assembly / namespace 一个模块，**模块间通过接口 / 事件通信**
- 🟡 大项目用 `.asmdef` 拆程序集（见 `01-代码编写规则.md` 3.4）

```text
Assets/
├── _Project/                # 项目代码（Assembly-CSharp）
│   ├── Core/                # 核心模块（纯 C#）
│   ├── Gameplay/            # 游戏模块（依赖 Core）
│   ├── UI/                  # UI 模块（依赖 Gameplay）
│   └── Infrastructure/       # 基础设施（Save / Analytics）
├── _ThirdParty/             # 第三方插件（独立 Assembly）
└── Plugins/
```

### 6.2 依赖注入（DI）

- 🔴 纯 C# 跨模块依赖优先使用构造函数注入；MonoBehaviour 的依赖沿用项目已验证的序列化、Bootstrap 或容器边界。
- 🟡 Unity 默认 Inspector 不能直接安全序列化普通接口字段。需要 Inspector 注入接口实现时，序列化已确认的 `MonoBehaviour`/`ScriptableObject` 引用并在初始化时校验其接口，或使用项目已有的序列化方案。
- 🟢 复杂项目只有在团队已评估并接纳容器时，才使用 Zenject、VContainer 或其他 DI 容器；不得因本规则新增依赖。

```csharp
// 简单注入：Unity Inspector
public class Player : MonoBehaviour
{
    [SerializeField] private MonoBehaviour m_inputSource;
    private IInput m_input;

    private void Awake()
    {
        m_input = m_inputSource as IInput
            ?? throw new InvalidOperationException("Input Source 必须实现 IInput。");
    }
}

// 构造函数注入：纯 C# 类
public class DamageCalculator
{
    private readonly IItemDatabase m_db;
    public DamageCalculator(IItemDatabase db) { m_db = db; }
}
```

### 6.3 模块通信方式

| 方式 | 适用场景 | 优缺点 |
|------|---------|--------|
| **直接引用**（`[SerializeField]`） | 1 对 1 强依赖 | 最直接，但耦合紧 |
| **事件 / 委托** | 1 对多、广播 | 解耦好，但事件多时管理难 |
| **事件总线（EventBus）** | 全局事件、跨模块 | 极解耦，但滥用变 spaghetti |
| **接口 + 服务定位器** | 跨模块、运行时切换 | 灵活，但增加复杂度 |
| **共享 ScriptableObject** | 配置 / 共享数据 | 易用，适合配置项 |

> **经验法则**：1 对 1 用直接引用；1 对多 / 不知道谁会监听用事件；全局配置用 SO。

## 7. 架构决策记录（ADR）

### 7.1 何时记录决策

写 ADR 的**时机**（项目已有 ADR 机制或本次决策会长期影响协作时）：
- 引入新框架 / 库
- 模块边界调整
- 性能优化（影响架构）
- 反范式选择（如"我们故意用单例"）
- 技术选型（如"我们用 Zenject 而不是 VContainer"）

写 ADR 的**好处**：
- 团队成员能快速了解"为什么这么设计"
- 半年后你自己回看不用从零推导
- 防止"重新讨论已经决定过的事"

### 7.2 ADR 模板

每个 ADR 一个文件（如 `docs/adr/0001-use-zenject.md`），结构如下：

- **状态**：已决定 / 已过时 / 已取代
- **背景**：为什么需要做这个决定
- **决策**：最终选了什么方案
- **后果**：正面 + 负面
- **备选方案**：考虑过的其他选项 + 没选的原因

**模板示例**（不要把示例放在真实 ADR 文件里，只是给你看格式；Zenject 仅为示例，不表示应在项目中引入该依赖）：

```text
### ADR-0001: 使用 Zenject 作为依赖注入容器

## 状态
2026-06-29 已决定 / 2026-07-15 已被 ADR-0005 取代

## 背景
项目达到 50+ MonoBehaviour 后，跨模块依赖变得难管理。
直接 [SerializeField] 引用导致 Inspector 拖拽工作量巨大。

## 决策
采用 Zenject 作为依赖注入容器。

## 后果
### 正面
- 模块间依赖自动注入，省去手动拖拽
- 单元测试可以替换 mock 实现

### 负面
- 学习曲线（团队需要理解 DI 概念）
- 启动时间 +50ms（容器初始化）

## 备选方案
### A. VContainer
- 优点：性能更好（编译时生成）
- 缺点：社区较小，文档不如 Zenject

### B. 自己实现简易 DI
- 优点：零依赖
- 缺点：维护成本高，容易出 bug
```

> ⚠️ 上面示例的 `## 状态` 等是 markdown 的二级标题，只是为了展示 ADR 内部结构。**真实 ADR 文件用真正的 `## 状态` 标题写**。
