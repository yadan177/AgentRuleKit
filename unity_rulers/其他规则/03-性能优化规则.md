# 03 - Unity 性能优化规则

> 🟢 本文件适用于 Unity 的帧时间、内存、GC、渲染、物理、加载和设备性能问题。
>
> 🔴 不适用：没有测量依据的全局优化、渲染管线迁移或为了性能而修改功能契约。

---

## 1. 先测量再修改

> **适用条件与验证**：存在可复现的性能症状、目标设备、场景、构建配置或项目性能预算时适用。

- 🔴 **必须**：记录复现路径、设备/Editor 或 Player、构建配置、采样区间和基线数据；不要把猜测当作瓶颈结论。
- 🔴 **必须**：优先使用项目已有的 Profiler、Frame Debugger、Memory Profiler、日志或性能测试；未执行设备验证时不得声称设备性能改善。
- 🟡 **推荐**：一次只验证一个可解释的改动，并比较正确性、帧时间、GC、内存、加载或功耗中受影响的指标。

## 2. 热路径与内存

> **适用条件与验证**：项目 Profiling 证据显示更新循环、回调、字符串、集合、装箱、查找或临时对象造成开销时适用。

- 🔴 **必须**：只优化已定位的热路径；缓存组件、查询结果或预分配集合前确认对象生命周期、失效条件和场景切换行为。
- 🔴 **必须**：避免在每帧路径中无依据地分配、反复查找、LINQ 枚举、字符串拼接或闭包捕获；如果项目已证明这些写法可接受，不得只为规则改写。
- 🟡 **推荐**：让数据结构和容量依据访问模式、数据规模和测量结果选择；对缓存/池化后的旧数据、引用和订阅进行清理验证。

## 3. 渲染、UI 与物理

> **适用条件与验证**：项目已确认当前渲染管线、UI 主负责框架、材质/Shader 策略和物理设置时适用。

- 🔴 **必须**：材质修改、批处理、实例化、Canvas 拆分、图集、物理查询和碰撞层设置必须符合当前管线与同模块做法，并用 Profiler/Frame Debugger 或功能测试验证。
- 🔴 **必须**：不要把 MaterialPropertyBlock、`RequireComponent`、NonAlloc 查询、对象池或某种 UI 框架当作无条件优化；它们的收益和兼容性取决于渲染管线、对象生命周期和测量结果。
- 🟡 **推荐**：UI 更新按可见性、数据变化和布局成本节流；物理查询按频率、命中数量、LayerMask 与结果所有权选择项目已有 API。

## 4. 加载与异步工作

> **适用条件与验证**：项目已有资源加载/卸载、协程或异步框架，且测量显示加载、实例化或后台工作影响体验时适用。

- 🔴 **必须**：资源加载、实例化、取消和释放成对，且句柄所有权明确；不要将资源加载 API 或释放方式从另一套资源系统复制过来。
- 🔴 **必须**：跨帧或异步优化不能绕过主线程限制、对象销毁检查、错误处理或用户可见的加载/失败状态。
- 🟡 **推荐**：在已有加载界面、优先级、缓存和预热机制内优化；先验证首帧、峰值内存和场景切换，而非仅测单次 API 耗时。

## 5. 验证与例外

- 🔴 **必须**：性能改动完成后复测同一场景和条件，并检查功能、资源释放、GC、帧时间与目标设备风险。
- 🟡 **推荐**：提交记录应包含基线、改动、结果、未覆盖设备和回归风险；无法量化收益时保留更简单、可维护的实现。

> **例外**：紧急稳定性修复可先做最小缓解，但需要在后续任务补齐复现、测量和回归验证。
