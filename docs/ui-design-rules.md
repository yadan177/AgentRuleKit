当前源码新增两个可选项目规则包，尚未发布：

| 规则包 | 内容与入口 | 安装关系 |
|---|---|---|
| `ui-design` | [设计总览](../rulepacks/ui-design/00-文档总览.md)、[AI 入口](../rulepacks/ui-design/15-AI通用入口规则.md)及六项专题 | 依赖 `common` 和 `project-docs/ui-design` |
| `project-docs/ui-design` | [文档总览](../rulepacks/project-docs/ui-design/其他规则/00-UI设计文档规则总览.md)、[任务入口](../rulepacks/project-docs/ui-design/其他规则/04-UI设计文档任务入口.md)及组织、正文、模板 | 依赖 `common`，可独立使用 |

UI 属于跨技术栈任务，设计包在现有 manifest 分类中使用 `common`，文档包使用 `documentation`；分类不表示默认安装。语言检测和桌面技术栈组合均不自动加入这两个包。当前通过项目配置选装，桌面安装页尚无 UI 专项选项。新增的是项目规则资产，不是 UI Skill、场景插件或新的设计工具连接。

## 保留的项目经验

用户指定 `K12_VR_Chemistry` 作为参考来源。其 UI 规则已经覆盖需求、交互、视觉、设计系统、验证及工具交付，以下方法继续保留：

- 先理解用户、任务、内容与平台，再建立方向、基础和代表场景。
- 多阶段任务先整理局部主线与 UI 清单，避免按每个流程节点新增页面。
- 区分容器与独立成员、选择值与输入焦点、业务状态与连续属性。
- 动态内容保留运行时控制，视觉还原与开发可控性分别检查。
- 变量、组件、实例、导出和资源保持权威来源与映射。
- XR 单位、输入、空间与设备验证单独核对，不把平面预览当作设备通过。

## 发现的问题与调整理由

这些问题主要出现在把项目经验推广到其他产品时，不表示原项目已确认的交付约定无效。

| 原规则或记录中的情况 | 本次调整 | 为什么更合适 |
|---|---|---|
| 00/05/06 要求每个界面固定交付整图、底图与控件状态图，按钮通常包含固定文字 | 按原生组件、样式、矢量、位图或混合实现选择交付；位图项目保留边界、Alpha、重建检查 | Web、原生应用与 Unity 可以有不同实现，不增加无用切图，也不损失动态文本、适配和可访问性语义 |
| 03/05/06 将运行时字体原文件设为统一交付项 | 区分系统字体、已有工程依赖和需交付文件，记录取得方式、字重、覆盖与使用条件 | 避免重复复制已有资源或把无法交付的字体当成必交项，仍保持可复现与来源追踪 |
| 15/01/02 多处要求制作前逐项确认状态数量，和“已有确认不重复审批”的条款存在张力 | 入口统一说明已有授权持续有效；明确事实可复用，真正超出范围或影响关键契约的选择集中处理 | AI 能完成已经授权的工作，用户只需决定未决问题，减少重复确认与不必要停顿 |
| 状态表强调整数数量，容易把焦点、选择、可用性与连续值混成一维 | 分维度记录状态、有效组合、优先级和控制来源，数量作为结果 | 更容易支持复杂控件与真实行为，避免变体组合爆炸和逐百分比切图 |
| 04 的基础页默认三块顶层面板，06 延续较多项目式目录/备份要求 | 保留可发现性与来源检查，展示结构和目录遵循目标项目；恢复依托已有版本控制与必要临时措施 | 不把某个项目的画布组织推广成通用限制，也不长期积累过程文件 |
| 项目设计文档已有基础、页面状态和交付清单，但没有独立的通用文档规则；基础总述与后续局部交付记录的时间、范围不同 | 新增五份 UI 文档规则，明确当前摘要、基线、采用、资源、实现和验证分别记录 | 防止“部分交付”被总括为“全部完成”或“仍全部暂缓”，支持设计到实现的交接与增量维护 |
| 参考项目的 `AGENTS.md` 列出 UI 入口，但 `agent-rules.yaml` 未列 `ui-design` | 新包进入仓库 manifest 生成、依赖解析、项目入口与安装测试 | 安装结果可以校验、预览更新和受管卸载，避免只存在入口提示却脱离选择配置 |

本次未改动 K12 工程、设计文件、资源或项目规则。其品牌色、字体选择、页面编号、设备型号、已批准状态与资源路径仍是项目事实，不进入共享规则默认值。

## 文档职责

配套文档保持五层结构：总览、组织与维护、编写规范、模板、任务入口。默认位置为目标项目的 `项目文档/产品设计/界面设计/`，已有等价目录时沿用。

设计说明记录采用意图、流程、状态、适配及交付契约；技术文档说明代码、绑定和运行行为。二者通过来源与版本关联。文档的“有效”只表示当前记录可信，不表示资源、实现和设备全部完成；实际进度与验证在对应条目分别说明。

## 本地选装与验证

使用当前源码构建的 CLI 和本地规则源。正式 Release 尚不包含新增包，不能向仍指向旧 Release 的项目配置追加包后宣称可更新。

在本仓库运行 `npm run build`。已有测试项目保留原配置与规则列表，只追加 `ui-design`，并确认 `source` 指向本地规则仓库。没有配置的新测试目录可使用以下完整示例：

```yaml
schemaVersion: 1
source:
  type: workspace
  path: /absolute/path/to/AgentRuleKit
rulepacks:
  - ui-design
targets:
  - codex
project:
  overrides: .agent-rules/overrides.md
updates:
  channel: stable
  strategy: manual
```

在本仓库运行，审查差异后应用：

```bash
node packages/cli/dist/index.js diff /absolute/path/to/test-project
node packages/cli/dist/index.js update /absolute/path/to/test-project --apply
node packages/cli/dist/index.js validate /absolute/path/to/test-project
```

`ui-design` 会带上文档包与通用入口；只整理设计文档时可选择 `project-docs/ui-design`，不要求语言标记或 Unity 依赖。已有未知 UI 文件或受管文件漂移仍由安装器拒绝覆盖，不直接向参考项目运行上述命令。

选装关系由 CLI 集成测试覆盖：默认不装 UI、显式选择带上文档依赖、预览不写入、更新与移除保留本地文件，以及文档包独立安装。结构与链接检查覆盖新增规则；这些测试不代表规则已在所有设计工具、项目与设备上完成实际设计任务验收。
