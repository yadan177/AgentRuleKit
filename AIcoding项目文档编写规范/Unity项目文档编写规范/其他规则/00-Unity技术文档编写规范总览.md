# 00 - Unity 技术文档编写规范总览

> 🟢 本规则库只适用于 Unity 项目的技术文档。<br>
> 🔴 不适用：策划、美术、制作、运营和管理文档；也不以通用经验替代项目事实。

---

## 1. 目标与边界

目标是让技术文档像代码一样可找到、可验证、可维护。规则库只管理程序侧的工程、模块、契约、测试、运行和技术决策；其他领域由其 owner 负责。

本规则库只管理 `项目文档/技术文档/`，不定义完整项目文档的分类。策划、美术、制作、运营和管理资料由各自既有规范与责任人维护；它们不得混入技术文档目录。

| 术语 | 含义 |
|---|---|
| 技术文档 | 描述 Unity 工程和程序侧事实、方案、操作与决策的文档 |
| 权威来源 | 代码、配置、数据资产、契约、测试记录或人工确认结论 |
| 新人上手 | 新成员完成环境搭建、运行、验证和基本排障的技术入口 |
| ADR | 需要长期追溯的架构决策记录 |

## 2. 合格文档的六个特征

| 特征 | 最低要求 |
|---|---|
| 可发现 | 从 `README.md` 能找到正确文档 |
| 可验证 | 关键结论能定位到权威来源 |
| 边界清楚 | 写明解决什么、不解决什么 |
| 易理解 | 先给结论，使用短段落、列表和必要表格 |
| 可演进 | 使用 Git、状态和替代链接，不创建“最终版”副本 |
| 可负责 | 有 owner、状态和实质更新时间 |

## 3. 核心原则

1. **事实优先**：Unity 版本、包、程序集、配置、代码和构建事实优先于本规则库。
2. **一文一责**：一篇文档回答一个主要问题；不把不相干主题拼成大杂烩。
3. **单一信源**：易变的数值、接口、配置和数据格式只保留一个权威维护点。
4. **结论在前**：先说明用途、范围和当前结论，再展开必要细节。
5. **主题基线**：`00` 至 `07` 是技术主题基线，`02` 至 `07` 可按真实维护需求扩展子文档；必要时才新增 `08` 及后续主题，不将其理解为文档数量上限。
6. **按需扩展**：有真实读者和维护需求才拆文档、建主题目录或新增主题，不预建空壳。
7. **状态诚实**：已验证、提议、待确认和废弃必须显式标注。

## 5. 规则优先级与维护

优先级依次为：用户任务和安全限制、目标项目事实与 `AGENTS.md`、本规则库、其他示例。

- 🔴 修改专题规则后，必须检查本总览、适配器路径和内部链接。
- 🔴 适配器只保留入口，不复制专题正文。
- 🟡 规则、技术主题或目录连续出现重复需求时再补充；不为假设的未来需求扩张体系。
