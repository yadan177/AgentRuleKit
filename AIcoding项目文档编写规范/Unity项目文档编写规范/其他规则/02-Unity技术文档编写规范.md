# 02 - Unity 技术文档编写规范

> 🟢 本文件适用于 Unity 工程、模块、接口、数据、测试、运行维护和 ADR 的技术正文。
> 🔴 不适用：将通用 Unity 经验、未经确认的方案或其他角色的结论写成项目事实。

---

## 1. 写作原则

- 🔴 **先结论后细节**：开头说明用途、范围、读者和不覆盖内容；读者不应先读完整篇才能知道文档是否相关。
- 🔴 **只写可验证内容**：关键结论必须来自代码、配置、数据、契约、测试或人工确认；缺证据时标记 `> ⚠️ 待确认：<问题>`。
- 🔴 **一段只表达一个意思**：优先短段落、列表、表格；删除背景铺垫、重复解释和无行动价值的套话。
- 🔴 **不复制第二份真相**：数值、接口签名、配置和 schema 指向权威来源；正文只保留必要的解释与约束。
- 🟡 关系复杂时使用 Mermaid；简单关系用一张表或几句话说明即可。

## 2. 状态与必备信息

| 状态 | 可写内容 | 必须说明 |
|---|---|---|
| `draft` | 待评审方案、待实现设计 | 当前状态、待确认项、验收条件 |
| `active` | 已确认的实现、契约、流程 | 适用范围、来源、限制、验证方式 |
| `deprecated` | 被替代的实现或决策 | 废弃原因、替代路径、生效时间 |

除索引外，每篇正文至少包含：

1. 用途、范围和前置知识。
2. 权威来源和当前状态。
3. 职责、流程、约束或操作步骤。
4. 边界、限制、待确认问题和验证方式。
5. 简短的文档变更记录。

## 3. Unity 事实要求

编写前，按任务检查实际项目中的 Unity/Package 版本、`.asmdef`、代码、Scene、Prefab、资源、`ProjectSettings/`、构建脚本和目标平台。

- 🔴 涉及生命周期、协程、事件、异步任务、资源句柄或实例时，说明创建方、所有者和释放/取消时机。
- 🔴 涉及资源系统、渲染管线、网络库、XR SDK 或平台能力时，以项目已有证据为准，禁止默认选择某种方案。
- 🔴 涉及接口、存档或数据格式时，说明提供方、消费方、兼容性和权威 schema/代码位置。
- 🔴 构建、发布和排障步骤写清前置条件、操作、预期结果、失败处理和验证点。

## 4. 引用与决策

| 内容 | 写法 |
|---|---|
| C# 行为 | 引用如 `CombatSystem.ApplyDamage()` 的稳定符号和相对路径 |
| 配置与数值 | 给出权威配置或数据资产位置，必要时标明版本 |
| 结构关系 | 说明各组件职责；复杂时使用 Mermaid |
| 关键取舍 | 写明背景、当前决定、主要替代方案和后果；长期影响时创建 ADR |

- 🔴 代码片段只用于说明调用边界或易错约束，不能替代实现源码。
- 🔴 不得写“项目使用某方案”却没有对应的包、配置或代码证据。

## 5. 完成前自检

- [ ] 开头有用途、范围和不覆盖内容。
- [ ] 关键结论能定位到来源，未知项已标记。
- [ ] 内容与 `draft`、`active` 或 `deprecated` 状态一致。
- [ ] 无重复维护的数值、接口、配置或 schema。
- [ ] 涉及 Unity 生命周期、资源、平台或兼容性时已说明边界。
- [ ] `README.md`、关联链接和文档变更记录已同步。
