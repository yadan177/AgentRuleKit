# 06 - Go 项目配置

> 🟢 本文件适用于 Go 项目的初始化与工程配置（go.mod / .golangci.yml / Makefile / 目录结构 / CI 集成）。<br>
> 🔴 不适用：业务逻辑实现、API 设计、数据库 schema 设计

---

## 1. 项目初始化

🔴 新建现代 Go 项目使用 Go modules；维护既有项目时先读取实际构建方式，未经授权不得为了套用模板迁移模块或工作区结构。

### 1.1 go.mod 必填字段

```go
module <项目实际模块路径>

go <项目支持的 Go 版本>

require (
    // 第三方依赖
)

require (
    // 间接依赖（自动生成）
)
```

🟡 推荐：

- `module` 使用稳定、可解析且与发布方式一致的导入路径；公开或跨仓库模块通常使用代码托管路径，纯内部模块遵循组织约定
- Go 版本遵循项目 `go.mod`、工具链、部署平台和团队支持范围；不得自行写入“当前 LTS”或升级版本
- 用 `go mod tidy` 保持依赖整洁
- 用 `go mod tidy && git diff --exit-code go.mod go.sum` 在 CI 中校验

❌ 不要：

- 在没有核对仓库发布方式和既有约定时擅自修改 module path
- 手动编辑 `require ( )` 块内的间接依赖
- 未经迁移评估就把既有 GOPATH 或 workspace 项目改造成单模块项目

### 1.2 项目目录结构

🟡 下列结构只作为多可执行程序或服务型仓库的参考；实际目录必须优先复用目标项目现有边界，库、CLI 和小型工具不要求套用完整结构。

```
my-project/
├── cmd/                    # 可执行程序入口（每个子目录一个 main）
│   └── server/
│       └── main.go
├── internal/               # 私有应用代码（外部无法 import）
│   ├── app/
│   ├── handler/
│   ├── service/
│   └── repository/
├── pkg/                    # 公开库代码（外部可 import）
│   └── client/
├── api/                    # API 定义（proto / openapi / graphql）
├── configs/                # 配置文件模板
├── deployments/            # 部署相关（Dockerfile / k8s / terraform）
├── scripts/                # 运维脚本（Makefile / shell）
├── test/                   # 集成测试 / 测试数据 / 测试工具
├── docs/                   # 设计文档 / 架构图
├── go.mod
├── go.sum
├── README.md
└── LICENSE
```

🟡 推荐：

- 不希望被仓库外部导入的包可放 `internal/`，具体层级以模块边界为准
- 可复用公共包沿用仓库现有布局；`pkg/` 只是社区惯例，不是 Go 工具链要求
- **每个可执行程序单独目录**——`cmd/server`、`cmd/cli` 互不影响

❌ 不要：

- 把互不相关的职责全部堆在根目录
- 仅凭模板把既有业务代码强行搬到 `internal/` 或 `pkg/`
- 为追求目录形式统一而重排稳定项目

### 1.3 入口文件

```go
// cmd/server/main.go
package main

import (
    "context"
    "log"
    "os"
    "os/signal"
    "syscall"

    "github.com/your-org/your-project/internal/app"
)

func main() {
    ctx, cancel := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer cancel()

    a, err := app.New(ctx)
    if err != nil {
        log.Fatalf("init app: %v", err)
    }
    defer a.Close()

    if err := a.Run(ctx); err != nil {
        log.Fatalf("run app: %v", err)
    }
}
```

🔴 必加约束：

- `main()` 保持为装配入口，不承载可复用业务逻辑
- 业务逻辑放入可测试的包；是否使用 `internal/app.Run` 由项目现有结构决定
- 长期运行的服务应按运行环境处理终止信号和资源释放；短命令行工具不强制套用服务模板

## 2. 静态检查：golangci-lint

🔴 必加约束：CI 必须运行与仓库当前工具链相容的静态检查，至少包含 `go vet` 与项目已经约定的检查。`.golangci.yml` 和 `golangci-lint run` 仅适用于已选用 golangci-lint 的项目；不要为套用本节模板擅自引入工具。

### 2.1 最小配置

```yaml
# .golangci.yml
run:
  timeout: 5m
  go: '<项目支持的 Go 版本>'
  tests: true

linters:
  disable-all: true
  enable:
    - errcheck       # 检查 error 是否被忽略
    - govet          # Go 官方检查
    - ineffassign    # 无效赋值
    - staticcheck    # 高级静态分析（SA* 系列）
    - unused         # 未使用变量 / 函数 / 导入

linters-settings:
  govet:
    enable-all: true
    disable:
      - fieldalignment  # 太严，禁用
```

### 2.2 推荐 Linters

| Linter | 用途 | 优先级 |
|---|---|---|
| `errcheck` | 未检查 error | 🟡 若项目使用 golangci-lint，推荐 |
| `govet` | 官方检查（含 printf / shadow） | 🔴 必加（可直接运行 `go vet`） |
| `staticcheck` | 高级静态分析 | 🟡 按项目工具链选择 |
| `ineffassign` | 无效赋值（如 `x = x`） | 🟡 按项目工具链选择 |
| `unused` | 未使用代码 | 🟡 按项目工具链选择 |
| `gocritic` | 100+ 检查项（性能 / 风格） | 🟡 推荐 |
| `gocyclo` | 圈复杂度（阈值 15） | 🟡 推荐 |
| `gofmt` / `gofumpt` | 比 gofmt 更严格 | 🟡 推荐 |
| `prealloc` | slice 预分配检查 | 🟢 可选 |
| `revive` | golint 替代 | 🟢 可选 |
| `nlreturn` | `return` 前必须有空行 | 🟢 可选 |
| `gocognit` | 认知复杂度 | 🟢 可选 |
| `misspell` | 拼写检查 | 🟢 可选 |

### 2.3 配置继承

🟡 推荐：项目内部可分层继承。

```yaml
# .golangci.yml
linters:
  presets:
    - std  # 标准检查集（基础）
    - bugs # bug 检测集
```

## 3. Makefile 任务自动化

🟡 推荐：为多步骤或多人协作项目提供统一命令入口。可使用 `Makefile`、`Taskfile`、脚本或仓库已有任务系统；小型库或已有 CI 约定不应仅为套用本节强制引入 `Makefile`。

### 3.1 最小模板

```makefile
# Makefile
BINARY := $(notdir $(CURDIR))
GO    ?= go

.PHONY: help build run test lint fmt tidy clean

help:           ## Show this help
	@awk 'BEGIN {FS = ":.*##"; printf "Usage:\n  make \033[36m<target>\033[0m\n"} /^[a-zA-Z_-]+:.*?##/ { printf "  \033[36m%-15s\033[0m %s\n", $$1, $$2 }' $(MAKEFILE_LIST)

build:          ## Build binary to bin/
	mkdir -p bin
	$(GO) build -ldflags="-s -w" -o bin/$(BINARY) ./cmd/server

run:            ## Run server locally
	$(GO) run ./cmd/server

test:           ## Run unit tests
	$(GO) test -race -cover ./...

lint:           ## Run golangci-lint
	golangci-lint run ./...

fmt:            ## Format code
	$(GO) fmt ./...
	gofmt -s -w .

tidy:           ## Tidy go.mod
	$(GO) mod tidy

clean:          ## Clean build artifacts
	rm -rf bin/
```

### 3.2 推荐目标

| 目标 | 作用 |
|---|---|
| `make build` | 编译二进制到 `bin/` |
| `make run` | 本地运行 |
| `make test` | 跑单元测试 |
| `make lint` | 跑 golangci-lint |
| `make fmt` | 格式化代码 |
| `make tidy` | 整理 go.mod |
| `make clean` | 清理构建产物 |
| `make docker-build` | 构建 Docker 镜像 |
| `make docker-run` | 跑 Docker 容器 |

🔴 必加约束：

- **`make help`** 必须输出可用目标列表（用 `awk` 自动提取 `##` 注释）
- 所有目标用 `.PHONY` 声明（避免与同名文件冲突）

❌ 不要：

- 用 `bash` 脚本代替 Makefile（可移植性差）
- 在 Makefile 里硬编码绝对路径

## 4. CI/CD 配置

🟡 团队协作或需要发布的项目应采用仓库现有 CI 平台；触发条件和门禁以项目分支策略为准。下例仅是 GitHub Actions 示例，不适用于本地工具、一次性程序或采用其他平台的仓库。

### 4.1 GitHub Actions 最小流程

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@<项目已验证版本>
      - uses: actions/setup-go@<项目已验证版本>
        with:
          go-version-file: go.mod
          cache: true
      - name: go mod download
        run: go mod download
      - name: gofmt
        run: |
          unformatted=$(find . -path ./vendor -prune -o -name '*.go' -exec gofmt -l {} +)
          if [ -n "$unformatted" ]; then
            echo "gofmt failed:"
            printf '%s\n' "$unformatted"
            exit 1
          fi
      - name: go vet
        run: go vet ./...
      - name: golangci-lint
        uses: golangci/golangci-lint-action@<项目已验证版本>
        with:
          version: <项目锁定版本>
      - name: test
        run: go test -race -coverprofile=coverage.out ./...
      - name: build
        run: go build -o bin/server ./cmd/server
```

### 4.2 按项目选择的验证步骤

| 步骤 | 工具 | 失败处理 |
|---|---|---|
| 依赖下载 | `go mod download` | — |
| 格式检查 | `gofmt -l` | 失败则 PR 不可合 |
| 静态检查 | `go vet` | 失败则 PR 不可合 |
| 静态检查 | 项目已采用时运行 `golangci-lint run` | 按项目门禁处理 |
| 单元测试 | `go test`，必要时加 `-race` | 按项目门禁处理 |
| 编译 | `go build` | 失败则 PR 不可合 |

🟡 推荐：

- 测试覆盖率采用仓库已有阈值；没有明确门禁时先由团队按风险确定
- 自动上传 coverage 到 Codecov / Coveralls
- 缓存 `~/.cache/go-build` 和 `~/go/pkg/mod` 加速 CI

## 5. 环境配置

### 5.1 配置加载（推荐 viper / envconfig）

🟡 推荐：用 [`spf13/viper`](https://github.com/spf13/viper) 或 [`kelseyhightower/envconfig`](https://github.com/kelseyhightower/envconfig) 加载配置。

```go
// 用 envconfig
type Config struct {
    Server   ServerConfig   `envconfig:"SERVER"`
    Database DatabaseConfig `envconfig:"DATABASE"`
    LogLevel string          `envconfig:"LOG_LEVEL" default:"info"`
}

type ServerConfig struct {
    Port         int           `envconfig:"PORT" default:"8080"`
    ReadTimeout  time.Duration `envconfig:"READ_TIMEOUT" default:"10s"`
    WriteTimeout time.Duration `envconfig:"WRITE_TIMEOUT" default:"10s"`
}
```

🔴 必加约束：

- 配置**必须**支持环境变量
- 配置**必须**有默认值
- 敏感信息（密码 / 密钥）**必须**从环境变量读取，不进代码库

### 5.2 12-Factor App 配置原则

🟡 推荐：

| 原则 | 实施 |
|---|---|
| 配置存环境变量 | 不进代码库 |
| 显式声明依赖 | `go.mod` 完整 |
| 配置存环境 | 不用本地配置文件（生产环境） |
| 后端服务当附加资源 | DB / Redis / MQ 走 URL |

❌ 不要：

- 配置硬编码（如 `const apiKey = "xxx"`）
- 配置文件进 Git（含密码 / 密钥）
- 不同环境用不同分支（用环境变量区分）

## 6. 构建配置

### 6.1 编译标志（ldflags）

🔴 必加约束：二进制**必须**注入版本号 / 提交 SHA / 构建时间。

```makefile
# Makefile 中的 build 目标
VERSION    := $(shell git describe --tags --always --dirty)
COMMIT     := $(shell git rev-parse --short HEAD)
BUILD_TIME := $(shell date -u '+%Y-%m-%dT%H:%M:%SZ')
LDFLAGS    := -s -w \
             -X 'main.Version=$(VERSION)' \
             -X 'main.Commit=$(COMMIT)' \
             -X 'main.BuildTime=$(BUILD_TIME)'

build:
	$(GO) build -ldflags="$(LDFLAGS)" -o bin/$(BINARY) ./cmd/server
```

```go
// cmd/server/main.go
package main

var (
    Version   = "dev"
    Commit    = "unknown"
    BuildTime = "unknown"
)
```

### 6.2 交叉编译

🟡 推荐：在 Makefile 提供交叉编译目标。

```makefile
.PHONY: build-all
build-all: ## Build for all platforms
	GOOS=linux   GOARCH=amd64 $(GO) build -o bin/$(BINARY)-linux-amd64   ./cmd/server
	GOOS=linux   GOARCH=arm64 $(GO) build -o bin/$(BINARY)-linux-arm64   ./cmd/server
	GOOS=darwin  GOARCH=amd64 $(GO) build -o bin/$(BINARY)-darwin-amd64  ./cmd/server
	GOOS=darwin  GOARCH=arm64 $(GO) build -o bin/$(BINARY)-darwin-arm64  ./cmd/server
	GOOS=windows GOARCH=amd64 $(GO) build -o bin/$(BINARY)-windows-amd64.exe ./cmd/server
```

### 6.3 Docker 多阶段构建

🟡 推荐：用多阶段构建减小镜像体积。

```dockerfile
# Dockerfile
# 基础镜像占位符必须替换为项目已验证、可复现的镜像引用，生产构建优先锁定 digest。
# ---- 阶段 1：构建 ----
FROM <Go 构建镜像>@sha256:<digest> AS builder

WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download

COPY . .
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /server ./cmd/server

# ---- 阶段 2：运行 ----
FROM <运行时镜像>@sha256:<digest>

RUN apk --no-cache add ca-certificates
WORKDIR /app
COPY --from=builder /server /app/server

EXPOSE 8080
ENTRYPOINT ["/app/server"]
```

🔴 必加约束：

- 使用多阶段构建（最终镜像 < 20MB）
- 用 `alpine` 或 `scratch` 而非 `ubuntu`（减小体积）
- 设 `CGO_ENABLED=0`（避免 glibc 依赖）
- 非 root 用户运行

## 7. AI 项目配置清单

AI 创建 / 修改 Go 项目配置时，必须按此清单核查：

### 7.1 基础结构

- [ ] `go.mod` 含完整 module 路径（Git URL 形式）
- [ ] Go 版本与 `go.mod`、CI 和部署平台一致
- [ ] 包边界沿用项目现有结构；新增公开包经过明确设计
- [ ] 多可执行程序项目的入口边界清晰
- [ ] 应用入口只承担项目约定的装配和生命周期职责

### 7.2 静态检查

- [ ] 静态检查复用项目现有工具和配置；未采用 golangci-lint 时不强制创建 `.golangci.yml`
- [ ] CI 配置运行 `gofmt -l` 检查
- [ ] CI 运行项目已采用的静态检查命令

### 7.3 构建与发布

- [ ] 构建入口与项目已有 Makefile、Taskfile、脚本或 CI 保持一致
- [ ] ldflags 注入 Version / Commit / BuildTime
- [ ] 项目使用容器时检查镜像分层、最小权限和运行用户

### 7.4 CI/CD

- [ ] CI 平台和触发条件沿用仓库配置，不默认限定 GitHub Actions
- [ ] 运行与改动相称且项目已采用的格式、静态检查、测试和构建命令
- [ ] 覆盖率采用项目既有阈值和统计口径
- [ ] CI 失败 PR 不可合并（保护分支）

### 7.5 配置与环境

- [ ] 敏感信息从环境变量读取
- [ ] 配置有默认值
- [ ] 配置来源、默认值、覆盖优先级和敏感信息边界符合项目部署方式
