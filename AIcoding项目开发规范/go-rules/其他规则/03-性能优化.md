# 03 - Go 性能优化

> 🟢 本文件适用于 Go 项目的性能优化（热路径/内存分配/GC 等）。

> 🔴 不适用：业务逻辑实现、UI 样式细节、第三方业务 SDK

---

## 1. 何时优化（最重要的规则）

🔴 必加约束：**未测量，不优化**

> 性能相关的指导**仅适用于热路径**（hot path）。
> —— **Uber Go 性能规约**

**绝大多数代码不需要性能优化**。**过早优化**是万恶之源——会让代码变复杂、可读性变差、维护成本上升，**却没有可测量的收益**。

### 1.1 优化前的 3 个问题

1. **这是热路径吗？**（每请求 / 每秒执行 > 1000 次？）
2. **pprof 显示这里是瓶颈吗？**（不要靠直觉——测量）
3. **改完代码后 benchmark 真的变快了吗？**（不要靠"看起来更快"）

**3 个问题任一答"否"→ 不优化**。

### 1.2 优化顺序（先低风险，后高风险）

```
1. 算法复杂度（O(n²) → O(n log n)）     ← 最大收益
2. 减少分配（sync.Pool / 预分配）        ← 中等收益
3. 用更快的 API（strconv 替代 fmt）     ← 小收益
4. unsafe / 汇编                          ← 最后手段
```

**1 → 2 → 3 → 4**。**永远不要从 4 开始**。

## 2. pprof 信号识别（什么时候哪里慢）

🟡 推荐：性能出问题**第一步**用 pprof 定位

### 2.1 CPU profile

```go
import _ "net/http/pprof"

// 在 main() 中启动 pprof HTTP 服务
go func() {
    log.Println(http.ListenAndServe("localhost:6060", nil))
}()

// 然后用 go tool 分析
// $ go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30
```

**信号**：

- **`runtime.scanobject`** 占大头 → **GC 压力**（减少分配）
- **`runtime.mallocgc`** 高 → **分配过多**（用 sync.Pool / 预分配）
- 某个业务函数占大头 → **算法问题**（先优化算法）

### 2.2 内存 profile

```bash
# heap profile（默认单位：字节）
go tool pprof http://localhost:6060/debug/pprof/heap

# 看哪些对象分配最多
(pprof) top 10
(pprof) list <funcname>  # 看某函数具体的分配
```

**信号**：

- **inuse_space** 持续增长 → **内存泄漏**（找未释放的引用）
- **alloc_space** 持续增长 → **分配过多**（找可 sync.Pool 的对象）

### 2.3 goroutine profile

```bash
go tool pprof http://localhost:6060/debug/pprof/goroutine
```

**信号**：

- goroutine 数 > 10000 → **goroutine 泄漏**（找没有 stop 信号的 goroutine——见 ）

### 2.4 三个关键指标

| 指标 | 命令 | 关心的信号 |
|---|---|---|
| **CPU** | `pprof profile` | 哪个函数耗时最多 |
| **内存分配** | `pprof heap` | 哪个对象 / 哪行代码分配最多 |
| **goroutine 数** | `pprof goroutine` | 是否泄漏 |

> 详细 pprof 教程见 [Go 官方博客：Profiling Go programs](https://go.dev/blog/pprof)

### 2.5 trace（高级）

trace 比 pprof 更细——可以看**单次请求的完整时间线**（goroutine 调度 / GC / syscall / 网络）。用于排查**罕见的偶发慢请求**。

```bash
# 1. 采集 trace（默认 1 秒）
curl -o trace.out http://localhost:6060/debug/pprof/trace?seconds=5

# 2. 用 go tool trace 打开（启动浏览器查看）
go tool trace trace.out
```

> 注意：trace 是独立工具，不走 pprof。`go tool trace` 会启动本地 Web UI，可以查看 goroutine 调度、GC 暂停、网络阻塞、syscall 等细粒度时间线。

### 2.6 在线服务接入 pprof 的安全提示

🟡 推荐

- `net/http/pprof` **仅在内部网络暴露**——不要绑定 `0.0.0.0`
- **生产环境用 auth middleware 保护**（basic auth / mTLS / IP 白名单）
- 或用 [Pyroscope](https://pyroscope.io/) / [Parca](https://www.parca.dev/) 等持续 profiling 平台

## 3. 字符串与字节转换

🔴 必加约束：热路径上的字符串 / 字节操作必须遵守本节

### 3.1 优先使用 `strconv` 而非 `fmt`

```go
// 反例（143 ns/op, 2 allocs/op）
s := fmt.Sprint(rand.Int())

// 正例（64.2 ns/op, 1 alloc/op）
s := strconv.Itoa(rand.Int())
```

**性能差异 2x+**。热路径上**永远**用 `strconv`：

| 转换 | `fmt` | `strconv` |
|---|---|---|
| `int → string` | `fmt.Sprint(i)` | `strconv.Itoa(i)` |
| `string → int` | `fmt.Sscanf(s, "%d", &i)` | `strconv.Atoi(s)` |
| `float → string` | `fmt.Sprint(f)` | `strconv.FormatFloat(f, 'f', -1, 64)` |
| `bool → string` | `fmt.Sprint(b)` | `strconv.FormatBool(b)` |
| `[]byte → string` | `string(b)` | **OK**（编译器优化，无拷贝）|

> 反射（`fmt.Sprintf("%v", x)`）**更慢**——只在调试 / 错误消息里用。

### 3.2 避免重复字符串与字节切片转换

```go
// 反例（22.2 ns/op）—— 每次循环都重新分配
for i := 0; i < b.N; i++ {
    w.Write([]byte("Hello world"))
}

// 正例（3.25 ns/op）—— 一次性转换 + 复用
data := []byte("Hello world")
for i := 0; i < b.N; i++ {
    w.Write(data)
}
```

**性能差异 7x+**。

### 3.3 `string` ↔ `[]byte` 的拷贝成本

🟡 推荐

- `[]byte` → `string`：无拷贝（编译器优化）—— 可直接 `string(b)`
- `string` → `[]byte`：**有拷贝**——避免在热路径反复转
- **修改字符串**：必须 `[]byte(s)`，**会拷贝**——避免在热路径用

```go
// 谨慎：每次都拷贝整个字符串
for _, path := range paths {
    if bytes.HasPrefix([]byte(path), prefix) { /* ... */ }
}

// 更好：批量转换一次
prefixBytes := []byte(prefix)
for _, path := range paths {
    if bytes.HasPrefix([]byte(path), prefixBytes) { /* ... */ }
    // 或更优：先判断长度再转
}
```

## 4. 容器预分配

🔴 必加约束：知道容量时**必须**预分配

### 4.1 map 容量提示

```go
// 反例：map 不断扩容
files, _ := os.ReadDir("./files")
m := make(map[string]os.DirEntry)
for _, f := range files {
    m[f.Name()] = f
}

// 正例：一次性预分配
files, _ := os.ReadDir("./files")
m := make(map[string]os.DirEntry, len(files))
for _, f := range files {
    m[f.Name()] = f
}
```

**注意**：map 的容量提示**不是硬保证**——只是 hint。即使容量未满，添加元素时仍可能发生分配（用于 hashmap 桶调整）。

### 4.2 slice 容量（关键）

```go
// 反例（2.48s）—— 不断 append 触发多次扩容
data := make([]int, 0)
for k := 0; k < size; k++ {
    data = append(data, k)
}

// 正例（0.21s）—— 一次性预分配容量
data := make([]int, 0, size)
for k := 0; k < size; k++ {
    data = append(data, k)
}
```

**性能差异 10x+**。**slice 的容量是硬保证**——编译器按 `make()` 给的容量分配足够内存，`append()` 不到容量上限不分配。

**与 `make([]T, length)` 的区别**：

```go
make([]T, 0)       // 长度 0，容量 0
make([]T, length)  // 长度 = capacity = length
make([]T, 0, cap)  // 长度 0，容量 cap（可 append 到 cap）
```

**热路径上**：

- 知道最终长度 → `make([]T, length)` （一次到位）
- 知道上限但边 append 边填充 → `make([]T, 0, cap)`

### 4.3 sync.Pool 复用对象（高级）

🟡 推荐：高频创建 / 销毁的对象用 `sync.Pool`

```go
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func process(data []byte) {
    buf := bufPool.Get().(*bytes.Buffer)
    defer func() {
        buf.Reset()
        bufPool.Put(buf)
    }()
    buf.Write(data)
    // ...
}
```

**注意**：

- `sync.Pool` 里的对象**随时可能被 GC 清空**——不能依赖它存数据
- 适合 **bytes.Buffer / 结构体**等高频分配的临时对象
- **不要**用它管理**带状态的长生命周期对象**（连接池用其他方案）

## 5. 反射与类型断言的成本

🟡 推荐

### 5.1 反射（reflect）的成本

- **慢**：比直接调用慢 **10-100x**
- **类型不安全**：编译期无法检查
- **不可内联**：影响编译器优化

**使用原则**：

- **库代码**允许用（一次性能损失，全项目受益）
- **热路径**用**类型断言 / generics**（Go 1.18+）替代

```go
// 反例：热路径用反射
func process(v any) {
    rv := reflect.ValueOf(v)
    // ... 复杂逻辑
}

// 正例：泛型（Go 1.18+）
func process[T any](v T) {
    // 编译期生成具体类型代码，无反射开销
}
```

### 5.2 类型断言的成本

- `value, ok := x.(T)` —— **几乎无成本**（编译期优化）
- `reflect.TypeOf(x)` —— **慢**（涉及反射）

```go
// 热路径上：用类型断言，不用 reflect
if s, ok := x.(string); ok {
    return s
}
```

### 5.3 JSON 序列化

- **`encoding/json`**：用反射——慢，但标准库 / 互操作性好
- **热路径上**用 [`json-iterator/go`](https://github.com/json-iterator/go) 或 [`easyjson`](https://github.com/mailru/easyjson) —— 5-10x 加速
- **生成代码**方式（easyjson）比 **drop-in 替换**方式（json-iterator）**略快**

```go
// 标准库
data, _ := json.Marshal(user)

// 热路径：json-iterator（drop-in 替换）
import jsoniter "github.com/json-iterator/go"
var json = jsoniter.ConfigCompatibleWithStandardLibrary
data, _ := json.Marshal(user)
```

## 6. benchmark 怎么写

🔴 必加约束：**改完热路径必须跑 benchmark 验证**

### 6.1 基本模板

```go
// 1、benchmark 函数名以 BenchmarkXxx 开头
// 2、参数 *testing.B
// 3、内部用 for i := 0; i < b.N; i++ { ... } 控制循环
func BenchmarkSplitHostPort(b *testing.B) {
    // 准备测试数据（不计入 benchmark 时间）
    input := "192.0.2.0:8000"

    // 重置 timer（如果准备阶段有分配）
    b.ResetTimer()

    for i := 0; i < b.N; i++ {
        _, _, _ = net.SplitHostPort(input)
    }
}
```

### 6.2 运行 benchmark

```bash
# 跑单个 benchmark
go test -bench=BenchmarkSplitHostPort -benchmem

# 跑包内所有 benchmark
go test -bench=. -benchmem

# 跑多次取平均（更稳定）
go test -bench=BenchmarkXxx -benchmem -count=10

# 比较两个版本（用 benchstat）
# 1、当前代码保存
go test -bench=BenchmarkXxx -benchmem -count=10 > old.txt
# 2、改完代码
go test -bench=BenchmarkXxx -benchmem -count=10 > new.txt
# 3、对比
benchstat old.txt new.txt
```

### 6.3 benchmark 编写规范

🟡 推荐

- **准备数据**放在 `b.ResetTimer()` 之前
- **防止编译器优化掉**：把结果赋给 `package` 级变量（不要用 `_ =`）
- **并行 benchmark**：用 `b.RunParallel`
- **子测试**：`b.Run("case_name", func(b *testing.B) { ... })`

```go
var result string  // 防止编译器优化掉

func BenchmarkConcat(b *testing.B) {
    b.Run("plus", func(b *testing.B) {
        for i := 0; i < b.N; i++ {
            result = ""
            for j := 0; j < 100; j++ {
                result += "x"
            }
        }
    })
    b.Run("builder", func(b *testing.B) {
        for i := 0; i < b.N; i++ {
            var sb strings.Builder
            for j := 0; j < 100; j++ {
                sb.WriteString("x")
            }
            result = sb.String()
        }
    })
}
```

### 6.4 跑 benchmark 必看 3 个指标

```
BenchmarkConcat-8   1000000   1234 ns/op   128 B/op   2 allocs/op
                  ^         ^         ^         ^         ^
                  名字      CPU       时间      每次分配  每次分配
                                       (纳秒)    字节数    次数
```

- **`ns/op`**：每次操作耗时（越低越好）
- **`B/op`**：每次操作分配字节数（越低越好）
- **`allocs/op`**：每次操作分配次数（越低越好）

> **allocs/op 比 ns/op 更值得关注**——分配压力直接影响 GC。

## 7. 常见热路径反模式

🔴 必加约束：热路径上**避免**这些写法

### 7.1 用 `+` 拼大量字符串

```go
// 反例：每次 + 都产生新 string + 拷贝
for i := 0; i < 10000; i++ {
    s += strconv.Itoa(i)
}

// 正例：用 strings.Builder 或 strings.Join
var sb strings.Builder
sb.Grow(50000) // 预分配
for i := 0; i < 10000; i++ {
    sb.WriteString(strconv.Itoa(i))
}
s := sb.String()
```

**性能差异 100x+**（10000 次拼接）。

### 7.2 用 `fmt.Sprintf` 拼字符串

```go
// 反例：反射 + 大量分配
s := fmt.Sprintf("user %s (id=%d) created at %s", name, id, time.Now())

// 正例
s := "user " + name + " (id=" + strconv.Itoa(id) + ") created at " + time.Now().Format(time.RFC3339)

// 多个变量时：strings.Builder
var sb strings.Builder
sb.WriteString("user ")
sb.WriteString(name)
sb.WriteString(" (id=")
sb.WriteString(strconv.Itoa(id))
sb.WriteString(") created at ")
sb.WriteString(time.Now().Format(time.RFC3339))
s := sb.String()
```

### 7.3 defer 在热路径

🟡 推荐：**热路径**考虑不用 `defer`（微小但可测的开销）

```go
// 普通代码：defer 是好的（可读性 >> 性能）
p.Lock()
defer p.Unlock()

// 热路径：考虑不用 defer（每 ns 都重要）
p.Lock()
// ... 操作
p.Unlock()
```

> `defer` 的额外开销通常很小；仅在性能分析已证明其处于纳秒级热点时再考虑替代方案。默认优先保证资源释放与可读性。

### 7.4 在循环里 append 字符串

```go
// 反例：循环里 += 字符串
for _, v := range values {
    s += v
}

// 正例：Builder
var sb strings.Builder
for _, v := range values {
    sb.WriteString(v)
}
s := sb.String()
```

### 7.5 `range` 复制大切片 / 大结构体

🟡 推荐

```go
// 反例：每次迭代都拷贝整个结构体
for _, item := range bigStructs {
    process(item)
}

// 正例：用 index 访问 + 指针
for i := range bigStructs {
    process(&bigStructs[i])
}
```

### 7.6 频繁创建临时 slice / map

```go
// 反例：每次调用都分配新 map
func (s *Stats) Snapshot() map[string]int {
    m := make(map[string]int, len(s.data))
    for k, v := range s.data {
        m[k] = v
    }
    return m
}

// 如果 Stats 有 sync.Pool 化：
// 考虑复用 map（但要注意 GC 和并发安全）
```
