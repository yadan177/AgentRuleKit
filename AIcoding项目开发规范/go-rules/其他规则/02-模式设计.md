# 02 - Go 模式设计

> 🟢 本文件适用于 Go 项目常用的设计模式（函数式选项/表驱动测试/接口隔离等）。<br>
> 🔴 不适用：业务逻辑实现、具体 API 端点设计、Go 语法细节

---

## 1. 函数式选项模式（Function Options）

🔴 必加约束：构造器参数 ≥ 3 个且可能扩展时，**必须**用此模式

### 1.1 为什么用

- **避免**调用方传 `false, false, nil, nil` 之类**无信息量**的参数
- **可扩展**——加新参数不破坏旧调用方
- **可测试 / mock**——选项是值（`cacheOption(true)`），可在测试中比较
- 选项可实现 `fmt.Stringer`——调试时可读

### 1.2 标准实现（推荐）

```go
package db

type options struct {
    cache  bool
    logger *zap.Logger
}

// Option 是公开 API，但 apply 是非导出方法——外部无法伪造 Option
type Option interface {
    apply(*options)
}

type cacheOption bool

func (c cacheOption) apply(opts *options) {
    opts.cache = bool(c)
}

func WithCache(c bool) Option {
    return cacheOption(c)
}

type loggerOption struct {
    Log *zap.Logger
}

func (l loggerOption) apply(opts *options) {
    opts.logger = l.Log
}

func WithLogger(log *zap.Logger) Option {
    return loggerOption{Log: log}
}

// Open 构造器：addr 是必填，其余都是可选
func Open(addr string, opts ...Option) (*Connection, error) {
    o := options{
        cache:  defaultCache,
        logger: zap.NewNop(),
    }
    for _, opt := range opts {
        opt.apply(&o)
    }
    // ...
}
```

**调用**：

```go
// 全部默认
db.Open(addr)

// 仅设置 logger
db.Open(addr, db.WithLogger(log))

// 多个选项
db.Open(addr, db.WithCache(false), db.WithLogger(log))
```

### 1.3 何时用 vs 不用

| 场景 | 用法 |
|---|---|
| **必填 1-2 个 + 多个可选扩展** | ✅ 函数式选项（标准实现） |
| **参数稳定不会扩展** | 用普通多参数（`Open(addr, cache, logger)`） |
| **所有参数都是必填** | 用**参数结构体**（`Open(Config{Addr, Cache, Logger})`） |
| **需要向后兼容 + 复杂配置** | 两者结合：`Open(cfg Config, opts ...Option)` |

### 1.4 闭包实现（不推荐）

Uber 提到可以用闭包实现，但**优先用 struct-based 实现**：

```go
// 反例：闭包——无法比较、无法实现 Stringer
type Option func(*options)
func WithCache(c bool) Option {
    return func(o *options) { o.cache = c }
}

// 正例：struct + 非导出方法（见 § 1.2）
```

理由：struct 选项可比较、可用作 map key、可实现 `Stringer`、可在 mock 中断言。

## 2. 表驱动测试（Table-Driven Tests）

🔴 必加约束：测试**多种输入 / 输出组合**时，必须用此模式

### 2.1 基本结构

```go
func TestParseHostPort(t *testing.T) {
    tests := []struct {
        give     string
        wantHost string
        wantPort string
    }{
        {give: "192.0.2.0:8000", wantHost: "192.0.2.0", wantPort: "8000"},
        {give: "192.0.2.0:http", wantHost: "192.0.2.0", wantPort: "http"},
        {give: ":8000",          wantHost: "",         wantPort: "8000"},
        {give: "1:8",            wantHost: "1",        wantPort: "8"},
    }
    for _, tt := range tests {
        t.Run(tt.give, func(t *testing.T) {
            host, port, err := ParseHostPort(tt.give)
            require.NoError(t, err)
            assert.Equal(t, tt.wantHost, host)
            assert.Equal(t, tt.wantPort, port)
        })
    }
}
```

### 2.2 命名约定

🟡 推荐

- 测试切片名：`tests`
- 单个用例名：`tt`
- 字段前缀：`give`（输入） / `want`（期望输出） / `wantErr`（期望错误）

### 2.3 何时不用

🔴 必加约束：**测试体复杂 / 有条件分支时不用**

```go
// 反例：表里有 shouldCallX / shouldCallY / setupMocks 等条件字段——可读性崩溃
tests := []struct {
    give         string
    want         string
    wantErr      error
    shouldCallX  bool
    shouldCallY  bool
    giveXResp    string
    giveXErr     error
    giveYResp    string
    giveYErr     error
}{
    // ... 多个 case，每个 case 的 setup / verify 都不一样
}
for _, tt := range tests {
    t.Run(tt.give, func(t *testing.T) {
        // setup mocks
        if tt.shouldCallX { xMock.EXPECT().Call().Return(tt.giveXResp, tt.giveXErr) }
        if tt.shouldCallY { yMock.EXPECT().Call().Return(tt.giveYResp, tt.giveYErr) }
        // ...
    })
}
```

**改写**——拆为多个独立 `Test...` 函数：

```go
// 正例：每个测试只测一种行为
func TestShouldCallX(t *testing.T) { /* ... */ }
func TestShouldCallYAndFail(t *testing.T) { /* ... */ }
```

**判定标准**：

- 表里出现 `shouldX` / `expectCall` / `setupMocks func(...)` 字段 → 拆
- `for` 循环体超过 15 行 → 拆
- 表里的字段有**半数以上在某 case 不被使用** → 拆

### 2.4 并行测试

🟡 推荐

测试**只读**输入时，加 `t.Parallel()` 加速：

```go
for _, tt := range tests {
    t.Run(tt.give, func(t *testing.T) {
        t.Parallel()
        // 测试体
    })
}
```

> Go 1.22+ 循环变量在每次迭代独立，**不需要** `tt := tt` 显式拷贝。
> Go 1.21 及以下必须显式 `tt := tt` 或在 `t.Run` 参数里传值。

## 3. 接口隔离

🔴 必加约束：**消费者侧定义接口**，不要生产者侧

### 3.1 消费者侧定义（小接口）

```go
// 反例：生产者侧定义大接口（暴露所有方法）
package storage
type Storage interface {
    Get(key string) (any, error)
    Set(key string, value any) error
    Delete(key string) error
    List() ([]string, error)
    Sync() error
}

// 正例：消费者侧只定义自己需要的接口
package user
type UserStore interface {
    Get(key string) (any, error)  // user 包只关心 Get
}
```

**理由**：

- **解耦**——`user` 包不依赖 `storage` 包的具体接口
- **易测试**——mock 时只需实现 `Get`
- **演进**——`storage` 加新方法不影响 `user` 包

### 3.2 接口要小

🟡 推荐

- 接口方法数 **≤ 3** 最佳
- **单方法接口**最易 mock（如 `io.Reader` / `io.Writer`）
- **消费者侧**只定义自己用的方法

### 3.3 验证接口实现

🔴 必加约束

**导出类型若声明实现某接口**，必须在**编译期**验证：

```go
type Handler struct{ /* ... */ }

// 编译期验证：*Handler 实现了 http.Handler
var _ http.Handler = (*Handler)(nil)

func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) { /* ... */ }
```

- 指针类型用 `(*T)(nil)` 作零值
- 结构体类型用 `T{}` 作零值
- 一旦不满足接口，这行**编译失败**——比 runtime panic 强 100 倍

### 3.4 接口不传指针

🟡 推荐

```go
// 反例
func process(s *Service) { /* ... */ }
type Service interface { /* ... */ }
var s *Service = &realService // 指针指向接口——几乎从不需要

// 正例
func process(s Service) { /* ... */ } // 接口按值传
var s Service = realService           // 直接存接口
```

> 接口由（类型指针 + 数据指针）两部分组成，本身已经间接。**指向接口的指针**无意义。

## 4. 接收者类型选择（值 vs 指针）

🔴 必加约束

### 4.1 决策树

| 场景 | 用 |
|---|---|
| **方法要修改接收者** | 指针接收者 `func (s *S) Set(...)` |
| **结构体含 `sync.Mutex` / `atomic` 等不能拷贝的字段** | 指针接收者 |
| **结构体较大（≥ 64 字节）或含切片 / map** | 指针接收者（避免拷贝） |
| **结构体是小型的不可变值**（如 `time.Time` / `net.IP`） | 值接收者 |
| **map 元素必须用值接收者** | 值接收者（map 元素不可寻址） |
| **混用值 + 指针接收者** | ❌ 禁止——会让人困惑 |

### 4.2 一致性

🔴 必加约束

**同一类型的所有方法必须用同一种接收者**——不要一半值一半指针。

```go
// 反例：混用
func (s *Server) Start() error { /* ... */ }
func (s Server) Addr() string  { /* ... */ } // 编译能过，但风格混乱

// 正例：全指针
func (s *Server) Start() error { /* ... */ }
func (s *Server) Addr() string { /* ... */ }
```

### 4.3 接口满足的微妙差异

```go
type S struct{}
func (s S)  Read() {} // 值接收者
func (s *S) Write() {} // 指针接收者

// S 和 *S 都满足 Read
var s S
s.Read()    // ok
(&s).Read() // ok
// s.Write()  // 编译错误：s 不可寻址（map 元素同理）
// (&s).Write() // ok
```

**规则**：

- 指针接收者的方法**只能**在可寻址值上调用
- **map 元素**不可寻址——存值类型 + 指针接收者 = 只能 `m[k] = &S{...}` 然后调用
- **slice 元素**可寻址

## 5. 构造器与 New 函数

### 5.1 New 函数约定

🟡 推荐

- 构造器名 `New<TypeName>()`：返回 `*T`
- 参数多时用 [§ 1 函数式选项](#1-函数式选项模式function-options)
- 失败时返回 `error`（不 panic，不 `os.Exit`）

```go
// 标准构造器
func NewServer(addr string, opts ...Option) (*Server, error) {
    if addr == "" {
        return nil, errors.New("addr is required")
    }
    s := &Server{
        addr:    addr,
        timeout: defaultTimeout,
        logger:  zap.NewNop(),
    }
    for _, opt := range opts {
        opt.apply(s)
    }
    return s, nil
}
```

### 5.2 何时用 New vs 直接字面量

| 场景 | 用法 |
|---|---|
| **需要校验参数** | `New*` 返回 `(*T, error)` |
| **需要默认值填充** | `New*` |
| **需要资源分配 / 锁初始化** | `New*` |
| **简单的数据载体（DTO / POJO）** | 直接 `&T{...}` 字面量 |
| **无内部状态的小结构体** | 直接字面量 |

### 5.3 私有类型用 `newXXX` / `makeXXX`

🟢 可选

- 内部辅助构造器用小写 `newT(...)` / `makeT(...)` 命名
- 通常**不导出**——仅包内部使用

### 5.4 文件中的函数排序

🟡 推荐

- 导出的 `New<Type>()` / `NewType()` 放在**类型定义之后**、该类型其他方法之前
- 同一文件中的函数**按接收者分组**
- 工具函数放文件**末尾**

```go
// 正例
type Server struct{ /* ... */ }

func NewServer(addr string) *Server { /* ... */ }

func (s *Server) Start() error  { /* ... */ }
func (s *Server) Stop() error   { /* ... */ }
func (s *Server) Addr() string  { /* ... */ }

func calcTimeout(d time.Duration) time.Duration { /* 工具函数放末尾 */ }
```

## 6. AI Go 项目常见反模式清单

🔴 必加约束：AI 写 Go 项目时，**必须主动避开**以下反模式。本节是 Go 02 的核心增量——Uber 风格指南没有这些，是专门针对 AI 的常见错误总结。

### 6.1 不要过度抽象（YAGNI）

```go
// ❌ 反模式：提前抽象——"未来可能有多种实现"
package user

type Repository interface {  // AI 凭直觉写的接口
    Get(id string) (*User, error)
    Save(u *User) error
}

type MySQLRepository struct{ db *sql.DB }  // 实际只有 MySQL 一种实现

// ✅ 正例：出现第二个实现时再提取接口
package user

type Repository struct{ db *sql.DB }  // 先用具体类型
func (r *Repository) Get(id string) (*User, error) { /* ... */ }
func (r *Repository) Save(u *User) error { /* ... */ }

// 当出现第二个实现（如 Redis / Mock）时，再提取接口
// type UserRepository interface { Get(...); Save(...) }
```

**判定标准**：
- 只有一个实现的接口 → 过度抽象
- "为了测试方便"不是提前抽象的理由——用具体类型的 mock 更简单（参见 ）
- **接口提取的触发条件**：出现 **第二个实现**

### 6.2 不要用 Go 写 Java 风格的工厂模式

```go
// ❌ 反模式：Java 工厂模式硬搬到 Go
type UserFactory interface {
    CreateUser(name string) (*User, error)
}

type DefaultUserFactory struct{}
func (f *DefaultUserFactory) CreateUser(name string) (*User, error) {
    return &User{Name: name, CreatedAt: time.Now()}, nil
}

// ✅ 正例：Go 风格——直接构造函数
func NewUser(name string) (*User, error) {
    if name == "" {
        return nil, errors.New("name is required")
    }
    return &User{Name: name, CreatedAt: time.Now()}, nil
}
```

**Go 不需要工厂模式的原因**：
- Go 没有构造函数重载——`New*` 函数就是构造器
- 接口满足是隐式的——不需要 Factory 来"选择实现"
- 依赖注入直接通过构造函数参数实现

### 6.3 不要用指针传递切片 / map

```go
// ❌ 反模式：切片指针（99% 情况不需要）
func processItems(items *[]Item) {
    for _, item := range *items { /* ... */ }
}

// ✅ 正例：直接传切片值
func processItems(items []Item) {
    for _, item := range items { /* ... */ }
}

// 只有一种情况需要切片指针：函数要修改切片本身的长度/容量
func addItem(items *[]Item, item Item) {
    *items = append(*items, item)  // 必须用指针
}
```

**同理 map**：
- `func process(m *map[string]int)` → ❌ 99% 不需要
- `func process(m map[string]int)` → ✅ map 本身就是引用类型

### 6.4 不要把 Go 当 OOP 语言写

```go
// ❌ 反模式：Java 思维硬搬 Go
type User struct {
    BaseModel  // 继承 BaseModel——Go 用组合，不是继承
    name string
}
func (u *User) GetName() string { return u.name }  // getter
func (u *User) SetName(n string) { u.name = n }   // setter

// ✅ 正例：Go 风格——直接访问字段，不需要 getter/setter
type User struct {
    ID        int
    Name      string  // 导出字段直接访问
    CreatedAt time.Time
}

// 只有需要校验/副作用时才写 setter
func (u *User) SetName(n string) error {
    if n == "" {
        return errors.New("name cannot be empty")
    }
    u.name = n
    return nil
}
```

**Go 的 OOP 哲学**：
- 没有 `class` / `extends` / `implements` 关键字
- 组合优先于继承（embedding 不是继承）
- 接口满足是隐式的（鸭子类型）
- **没有 getter/setter 的文化**——除非真的需要

### 6.5 不要忽略 context 传递

```go
// ❌ 反模式：忽略 context，请求取消时 goroutine 泄漏
func (s *Service) GetUser(id string) (*User, error) {
    return s.repo.GetUser(context.Background(), id)  // 新建 context，丢失取消信号
}

// ✅ 正例：透传 context
func (s *Service) GetUser(ctx context.Context, id string) (*User, error) {
    return s.repo.GetUser(ctx, id)  // 透传，上游取消能终止下游
}
```

**context 传递规则**：
- 第一个参数永远是 `ctx context.Context`
- 永远透传，不要 `context.Background()`
- 只有 `main` / `init` / 测试函数可以新建 context

### 6.6 不要在循环中 defer

```go
// ❌ 反模式：循环内 defer——资源泄漏（defer 函数退出才执行）
func processFiles(paths []string) error {
    for _, path := range paths {
        f, err := os.Open(path)
        if err != nil {
            return err
        }
        defer f.Close()  // ❌ 循环结束前不会执行，文件句柄泄漏
        // 处理 f...
    }
    return nil
}

// ✅ 正例 1：循环内用闭包包裹
func processFiles(paths []string) error {
    for _, path := range paths {
        if err := func() error {  // 闭包每次退出时执行 defer
            f, err := os.Open(path)
            if err != nil {
                return err
            }
            defer f.Close()  // ✅ 闭包退出就执行
            // 处理 f...
            return nil
        }(); err != nil {
            return err
        }
    }
    return nil
}

// ✅ 正例 2：显式 Close（不用 defer）
func processFiles(paths []string) error {
    for _, path := range paths {
        f, err := os.Open(path)
        if err != nil {
            return err
        }
        // 处理 f...
        f.Close()  // 显式关闭
    }
    return nil
}
```

### 6.7 反模式检查清单

🔴 AI 写完 Go 代码后自查反模式：

- [ ] 没有只有一个实现的接口（YAGNI）
- [ ] 没有 Java 风格的工厂模式（用 `New*` 函数代替）
- [ ] 没有切片 / map 的指针传递（除非要改长度）
- [ ] 没有不必要的 getter/setter（Go 不搞 JavaBean 那套）
- [ ] `context.Context` 是函数第一个参数且被透传
- [ ] `defer` 不在循环内
- [ ] 没有 `init()` 函数（用 `New*` 显式初始化）
- [ ] 没有 `common` / `util` / `helper` 垃圾桶包

## 7. SOLID 5 原则的 Go 落地

🔴 必加约束：AI 写 Go 项目时，**不要照搬 Java/C# 的 SOLID 例子**——Go 的语言特性让 4/5 条 SOLID 被内置满足，仅 1-2 条仍需 AI 主动注意。本节说明每条原则在 Go 中**是被语言自动保证、还是仍需 AI 决策**。

### 7.1 SRP — 单一职责（仍需 AI 注意）

**Go 状态**：⚠️ 部分内置（包级强制），但 struct 级不强制——AI 容易堆出 God Struct。

**Go 怎么落地**：
- **包（package）是天然的职责边界**——一个包只做一件事，跨包靠 `internal/` 限制可见性（详见 § 8 包设计原则）
- **struct 内部**仍需 AI 自觉——Go 没强制"一个 struct 一个职责"

```go
// ❌ 违反 SRP - God Struct
type UserService struct {
    db          *sql.DB
    emailClient *smtp.Client
    redisClient *redis.Client
    logger      *zap.Logger
    cache       map[string]User
}

func (s *UserService) CreateUser(...) { /* 写 DB */ }
func (s *UserService) SendWelcomeEmail(...) { /* SMTP */ }
func (s *UserService) CacheUser(...) { /* Redis */ }
func (s *UserService) LogAudit(...) { /* 日志 */ }

// ✅ 遵循 SRP - 拆为职责单一的 struct
type UserRepository struct{ db *sql.DB }      // 只管持久化
type EmailNotifier struct{ client *smtp.Client } // 只管邮件
type UserCache struct{ rdb *redis.Client }    // 只管缓存
type AuditLogger struct{ logger *zap.Logger } // 只管审计日志

type UserService struct {  // 编排层 - 只负责组合
    repo   UserRepository
    notify EmailNotifier
    cache  UserCache
    audit  AuditLogger
}
```

**AI 判定标准**：
- struct 方法数 **> 5 个** → smell，可能违反 SRP
- struct 字段 **> 7 个** → smell
- struct 名字带 `Manager` / `Helper` / `Util` 后缀 → 90% 是 God Struct

### 7.2 OCP — 开闭原则（Go 写起来最自然）

**Go 状态**：✅ **Go 最擅长这个**——函数式选项 + 接口组合，无需子类化即可扩展。

**Go 怎么落地**：三种武器，按场景选：

| 武器 | 适用场景 | 例子 |
|---|---|---|
| **函数式选项**（§ 1） | 构造器参数扩展 | `Open(addr, WithCache(false), WithLogger(log))` |
| **接口 + 多种实现** | 行为可替换 | `Notification` 接口 + Email/SMS/Push 实现 |
| **中间件链** | HTTP/RPC 请求处理 | `Middleware func(http.Handler) http.Handler` |

```go
// OCP 正例：通过接口扩展（新策略无需修改已有代码）
type CompressionStrategy interface {
    Compress(data []byte) ([]byte, error)
}

type GzipCompression struct{}
func (GzipCompression) Compress(data []byte) ([]byte, error) {
    var buf bytes.Buffer
    gw := gzip.NewWriter(&buf)
    gw.Write(data)
    gw.Close()
    return buf.Bytes(), nil
}

type ZstdCompression struct{}
func (ZstdCompression) Compress(data []byte) ([]byte, error) {
    return zstd.Compress(nil, data)
}

type Storage struct {
    compress CompressionStrategy  // 依赖接口
}

func (s *Storage) Save(data []byte) error {
    compressed, _ := s.compress.Compress(data)  // 不关心哪种压缩
    return s.write(compressed)
}

// 新增 LZ4 压缩：实现 CompressionStrategy 接口，不修改 Storage
type Lz4Compression struct{}
func (Lz4Compression) Compress(data []byte) ([]byte, error) { /* ... */ }
```

**vs Java**：Java 用 `extends` / `implements`，Go 用**接口满足**（鸭子类型）——AI 不要写 `class CompressionStrategy extends Strategy` 之类。

### 7.3 LSP — 里氏替换（Go 自动满足）

**Go 状态**：✅ **空操作**——Go 无继承、无 override、无虚函数，子类改父类契约在 Go 里**写不出来**。

```go
// Java 里违反 LSP 的经典例子（子类改变父类约定）
// class Square extends Rectangle {
//     void setWidth(double w) { this.width = w; this.height = w; }  // 改了父类约定
// }
// Rectangle r = new Square();
// r.setWidth(5); r.setHeight(4);
// assert r.area() == 20;  // 实际是 16
//
// Go：没有 extends，Square 和 Rectangle 是两个独立类型，无法替换

type Rectangle struct{ Width, Height float64 }
type Square struct{ Side float64 }  // 独立类型，不"继承" Rectangle
```

**AI 注意**：
- Go 的 LSP 风险**不在继承**，在**接口实现**——实现接口时不要在某些条件下 `panic` 或返回错误状态码（违反接口契约）
- 用 `var _ Interface = (*Type)(nil)`（§ 3.3）编译期验证接口实现一致性

### 7.4 ISP — 接口隔离（Go 02 § 3 已覆盖）

**Go 状态**：✅ **Go 02 § 3 单独成章**，本节不重复。核心要点回顾：

- **消费者侧定义接口**（不要生产者侧）
- 接口方法数 **≤ 3** 最佳
- 单方法接口最易 mock（如 `io.Reader` / `io.Writer`）
- 用 `var _ Interface = (*Type)(nil)` 编译期验证

### 7.5 DIP — 依赖倒置（Go 用接口实现）

**Go 状态**：⚠️ 部分内置（duck typing），但**"高层模块不应依赖低层模块"仍需 AI 自觉**。

**Go 怎么落地**：三层架构的依赖方向

```
┌─────────────────────────┐
│  高层（orchestration）    │  ← UserService, OrderFacade
│  依赖接口（抽象）          │
└──────────┬──────────────┘
           │ 依赖
           ▼
┌─────────────────────────┐
│  接口定义（消费者侧）      │  ← UserRepository, EmailNotifier
│  在高层包内定义            │
└──────────┬──────────────┘
           │ 被实现
           ▼
┌─────────────────────────┐
│  低层（具体实现）          │  ← MySQLUserRepository, SMTPEmailNotifier
│  在低层包内               │
└─────────────────────────┘
```

```go
// ❌ 违反 DIP - 高层直接依赖低层
package service
import "myapp/internal/mysqlrepo"  // 高层直接 import 低层

type UserService struct {
    repo *mysqlrepo.UserRepo  // 紧耦合：换 DB 类型就炸
}

// ✅ 遵循 DIP - 高层依赖接口，接口在高层定义
package service

// 接口在 service 包（高层）定义，不在 repo 包（低层）
type UserRepository interface {
    Get(id string) (*User, error)
    Save(u *User) error
}

type UserService struct {
    repo UserRepository  // 依赖抽象，不依赖具体
}

func NewUserService(repo UserRepository) *UserService {
    return &UserService{repo: repo}
}

// 低层实现接口（在低层包）
package mysqlrepo
import "myapp/internal/service"

type UserRepo struct{ db *sql.DB }

func (r *UserRepo) Get(id string) (*service.User, error) { /* ... */ }
func (r *UserRepo) Save(u *service.User) error { /* ... */ }

// 编译期验证实现关系
var _ service.UserRepository = (*UserRepo)(nil)
```

**AI 判定标准**：
- **高层包 import 低层包的具体类型** → 违反 DIP
- **接口定义在低层包（生产者侧）** → 违反 DIP（详见 § 3.1 消费者侧定义）
- **构造函数接收具体类型而非接口** → 违反 DIP

### 7.6 KISS / YAGNI / DRY（跨语言通用）

🟡 推荐。Go 项目同样适用三条高层原则。**Go 视角补充**：

| 原则 | Go 实践 |
|---|---|
| **KISS** | 不要为了"未来扩展"提前定义接口——出现第二个实现时再提取（见 § 6.2 不要过度抽象） |
| **YAGNI** | 不要写 `FutureFeature()` 占位方法——Go 编译器会警告未使用方法 |
| **DRY** | 重复 3 处的逻辑提取为包级函数（不是 struct 方法） |

### 7.7 SOLID 在 Go 里的优先级

🔴 必加约束：AI 写 Go 项目时，**优先级**应是：

1. **ISP / DIP / KISS**（高频违反，必须主动注意）
2. **SRP**（中频违反，struct 级需自觉）
3. **OCP**（低频违反，函数式选项 + 接口组合已内置大部分场景）
4. **LSP**（空操作，无需关注）

**Go vs Java 优先级对比**：

| 原则 | Java 优先级 | Go 优先级 | 差异原因 |
|---|---|---|---|
| SRP | 高 | 中 | Java class 多，Go struct + package 拆分更细 |
| OCP | 高 | 低 | Go 函数式选项 + 接口组合已内置 |
| LSP | 高 | 极低 | Go 无继承，LSP 自动满足 |
| ISP | 中 | **极高** | Go 接口由消费者定义，AI 容易在生产者侧写大接口 |
| DIP | 中 | **高** | Go 无 IoC 容器，AI 容易 `import` 具体包 |

## 8. 包设计原则（Go 架构的核心）

🔴 必加约束：Go 项目架构**首先看包边界**，再谈模式 / 接口 / 设计原则——一个好的包结构胜过任何 SOLID 例子。本节是 Go 02 真正的核心增量（Uber 指南散落在多处）。

### 8.1 包（package）作为模块边界

**Go 的核心哲学**：**包是模块边界，不是命名空间**。

```go
// ❌ 错：把 package 当命名空间用（Java/Python 思维）
package models  // "models 包"——把所有数据模型塞一起
type User struct{}
type Order struct{}
type Product struct{}
type Invoice struct{}

// ✅ 好：包按职责切分（业务边界）
package user
type User struct{}
type Service struct{}  // user 业务

package order
type Order struct{}
type Service struct{}  // order 业务

package billing
type Invoice struct{}
```

**关键判断**：
- 一个包内的所有类型应该有**同一个变化原因**（SRP 在包级）
- 如果你犹豫"这个类型该放 user 包还是 order 包"，说明你该建第三个包

### 8.2 包命名规则

🔴 必加约束：**包名是小写单词，不要下划线、不要驼峰、不要复数**。

| 规则 | 正例 | 反例 |
|---|---|---|
| **小写单词** | `package user` | ❌ `package User` ❌ `package USER` |
| **不要下划线** | `package http` | ❌ `package http_server` ❌ `package http-server` |
| **不要驼峰** | `package auth` | ❌ `package authService` |
| **不要复数** | `package user` | ❌ `package users` ❌ `package models` |
| **不要泛词** | `package user` | ❌ `package common` ❌ `package util` ❌ `package helper` |
| **简洁** | `package buf` | ❌ `package bytebuffer` |

**为什么不要泛词**（`common` / `util` / `helper`）：

```go
// ❌ package common 是"垃圾桶包"——任何不知道放哪的代码都丢这
package common
func FormatTime(t time.Time) string { /* ... */ }
func SendEmail(to string) error { /* ... */ }  // 跟时间格式化有什么关系？
func ValidatePhone(p string) bool { /* ... */ }

// ✅ 按职责拆
package timefmt
func Format(t time.Time) string { /* ... */ }

package mailer
func Send(to string) error { /* ... */ }

package validate
func Phone(p string) bool { /* ... */ }
```

`common` 包会让包内类型**互相没有内聚性**，违反 SRP。一旦你的项目出现 `common/` 或 `util/` 目录，**立刻 smell**。

### 8.3 包大小判断

🟡 推荐：包的大小决定项目可维护性。

| 指标 | 警告线 | 说明 |
|---|---|---|
| **包内 .go 文件数** | > 10 个 | 包可能职责不清 |
| **包导出符号数** | > 30 个 | 包可能是"上帝包" |
| **包被 import 次数** | > 50 次 | 包可能是核心基础设施（合理） |
| **包 import 别的包数** | > 10 个 | 包可能依赖过重 |

**判定标准**：包内所有 `.go` 文件加起来 ≤ 1000 行最舒服。超过 3000 行考虑拆。

### 8.4 internal 包（Go 独有的可见性控制）

🔴 必加约束：**包内实现细节用 `internal/` 目录强制隔离**——这是 Go 独有的访问控制机制。

```
myapp/
├── internal/
│   ├── auth/         # 只有 myapp 及其子包能 import
│   ├── database/     # 外部项目无法 import
│   └── cache/
├── pkg/
│   └── api/          # 公开 API（任何项目都能 import）
└── cmd/
    └── server/
```

```go
// internal/auth/auth.go
package auth

// ✅ 这个函数只有 myapp 内部能用
func HashPassword(p string) (string, error) { /* ... */ }

// 外部项目想 import？
// import "github.com/me/myapp/internal/auth"
//
// 编译错误：use of internal package not allowed
```

**internal 目录规则**：
- `internal/` 目录下的包只能被**以 `internal/` 父目录为根的目录树**内的代码 import
- 这是 Go 编译器**强制**的，不是约定
- 常用结构：`internal/foo` 放实现细节，`pkg/foo` 放公开 API

### 8.5 init() 反模式

🔴 必加约束：**init() 函数是 smell，应该避免**。

```go
// ❌ init() 反模式：隐式副作用
package db

var conn *sql.DB

func init() {
    var err error
    conn, err = sql.Open("postgres", "...")
    if err != nil {
        log.Fatal(err)  // 进程启动就挂，无法测试
    }
}

// 调用方
func GetUser(id string) (*User, error) {
    var name string
    err := conn.QueryRow("SELECT name FROM users WHERE id = $1", id).Scan(&name)  // conn 是 init() 隐式注入
    // ...
}
```

**init() 的 4 大问题**：
1. **隐式副作用**——import 就执行，测试时无法跳过
2. **全局状态**——`conn` 是包级变量，测试间相互污染
3. **错误处理弱**——init 里只能 `log.Fatal`，无法 `return error`
4. **依赖不透明**——读代码看不出 conn 何时初始化

**正确做法**：用 `New*` 函数显式初始化，依赖通过参数传递：

```go
// ✅ 显式构造 + 依赖注入
package db

type DB struct {
    conn *sql.DB
}

func Open(dsn string) (*DB, error) {
    conn, err := sql.Open("postgres", dsn)
    if err != nil {
        return nil, fmt.Errorf("open db: %w", err)
    }
    return &DB{conn: conn}, nil
}

func (d *DB) Close() error { return d.conn.Close() }
func (d *DB) GetUser(id string) (*User, error) { /* ... */ }

// 调用方
func main() {
    db, err := db.Open(os.Getenv("DSN"))
    if err != nil { log.Fatal(err) }
    defer db.Close()

    user, err := db.GetUser("123")
    // ...
}
```

**init() 合法使用场景**（少之又少）：
- 注册驱动（如 `_ "github.com/lib/pq"`）
- 静态配置校验（编译期常量）
- **绝大多数情况下都应该用 `New*` 替代**

### 8.6 包间依赖方向

🔴 必加约束：**包依赖应单向，禁止循环 import**。

```
✅ 健康的依赖图（单向）
cmd/server → service → repository → database
                ↓
              model

❌ 循环 import（编译错误）
package A imports B
package B imports A  // import cycle not allowed
```

**处理循环依赖**：
1. **抽公共依赖到第三个包 C**——A、B 都 import C
2. **依赖注入**——把 import 改成函数参数或接口
3. **重新审视设计**——循环依赖往往是"职责没切清"的信号

**依赖反转原则在包级**：高层包定义接口，低层包实现接口（详见 § 7.5 DIP + § 3.1 消费者侧接口）。

### 8.7 包路径与项目结构

🟡 推荐：标准 Go 项目布局（来自 [golang-standards/project-layout](https://github.com/golang-standards/project-layout)，社区共识）：

```
myapp/
├── cmd/                  # 入口：每个二进制一个目录
│   ├── server/
│   │   └── main.go       # bin: myapp-server
│   └── cli/
│       └── main.go       # bin: myapp-cli
│
├── internal/             # 私有代码（仅 myapp 内可见）
│   ├── auth/
│   ├── user/
│   └── order/
│
├── pkg/                  # 公开 API（外部可 import）
│   └── api/
│
├── api/                  # API 定义（OpenAPI / Protobuf / GraphQL schema）
│   └── openapi.yaml
│
├── configs/              # 配置文件模板
│   └── config.example.yaml
│
├── scripts/              # 构建 / 部署脚本
│
├── test/                 # 集成测试 / 测试数据
│   └── testdata/
│
├── docs/                 # 文档
│
├── go.mod                # 模块定义
├── go.sum
├── Makefile              # 常用命令
└── README.md
```

**关键判断**：
- `cmd/` 放入口，每个可执行文件一个子目录
- **`internal/` 优先于 `pkg/`**——默认用 internal，只在真的要暴露给外部时才用 pkg
- 不要为了"对称"硬拆包——`cmd/foo/internal/bar` 通常是过度设计

### 8.8 包的导入风格

🟡 推荐：

```go
// ✅ 标准导入顺序：标准库 / 第三方 / 内部包
import (
    "context"
    "fmt"
    "time"

    "github.com/spf13/cobra"
    "go.uber.org/zap"

    "myapp/internal/auth"
    "myapp/internal/user"
)

// ❌ 错：所有 import 混在一起
import (
    "myapp/internal/auth"
    "fmt"
    "github.com/spf13/cobra"
    "time"
    "myapp/internal/user"
)
```

**`goimports` 工具**：自动格式化 import 顺序和分组——CI 流水线必跑。

### 8.9 包级文档

🟡 推荐：**包声明之前必须有 package 注释**。

```go
// ✅ 好：包注释说明包的用途
// Package auth 提供用户认证和授权服务。
// 支持 JWT、OAuth2 和基于会话的认证。
package auth

// ❌ 错：无包注释
package auth
```

包注释应该回答：
- 这个包做什么？（不做什么）
- 何时使用这个包？
- 主要类型 / 函数是什么？（一句话即可）

### 8.10 包设计检查清单

🔴 AI 写完 Go 代码后自查：

- [ ] 包名是小写单词、无下划线、无复数、无泛词
- [ ] 包内类型都有同一变化原因（SRP）
- [ ] 包大小 < 1000 行，导出符号 < 30 个
- [ ] 实现细节放在 `internal/`，不暴露在 `pkg/`
- [ ] 没有 `init()` 函数（或最多 1 个用于驱动注册）
- [ ] 没有循环 import
- [ ] 依赖方向单向（cmd → service → repository → database）
- [ ] 包注释存在，说明用途
- [ ] import 分三组（标准库 / 第三方 / 内部）
