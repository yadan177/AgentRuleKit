# 08 - Go 版本控制规则

---

> 🟢 本文件适用于 Go 项目中**所有 Git 操作**——提交代码、管理分支、打 tag、配置 `.gitignore` 和 Git LFS<br>
> 🔴 **不适用**：GitHub PR/MR 流程（Code Owner、`/lgtm`、审批策略——这些是人类团队流程，AI 不需要）<br>
> 🟡 核心原则：**提交历史是代码的日记**——好的提交信息让 3 个月后的人（包括你自己）能看懂为什么这么改

## 1. Commit 规范

### 1.1 Conventional Commits 格式

🔴 必加约束：**所有 commit message 必须遵循 [Conventional Commits](https://www.conventionalcommits.org/) 格式**

```
<type>(<scope>): <subject>

<body>

<footer>
```

**最简形式**（日常高频使用）：

```
<type>(<scope>): <subject>
```

| 部分 | 必须 | 说明 | 示例 |
|---|---|---|---|
| `type` | ✅ | 提交类型（见 § 1.2） | `feat` |
| `scope` | 🟡 | 影响范围（可选） | `handler` |
| `subject` | ✅ | 简短描述（≤ 50 字符，中文英文均可） | `添加用户登录接口` |
| `body` | ❌ | 详细描述（每行 ≤ 72 字符） | 说明为什么这样改、影响范围 |
| `footer` | ❌ | 关联 issue / breaking change | `Closes #123` |

```bash
# 正例：日常提交
git commit -m "feat(handler): 添加用户登录接口"
git commit -m "fix(repo): 修复空切片导致的 nil panic"
git commit -m "refactor(service): 提取公共校验逻辑"
git commit -m "chore(deps): 升级 go.uber.org/zap 到 v1.27.0"

# 反例：无信息量
git commit -m "fix bug"
git commit -m "update code"
git commit -m "WIP"            # 如果必须 WIP，用 WIP: 前缀
git commit -m "."              # 完全无意义
```

### 1.2 type 分类

🔴 必加约束

| type | 含义 | 示例 |
|---|---|---|
| `feat` | 新功能 | `feat(api): 添加订单列表接口` |
| `fix` | 修 bug | `fix(repo): 修复查询超时未传递 ctx` |
| `docs` | 仅文档变更 | `docs(readme): 更新本地开发步骤` |
| `style` | 不影响代码逻辑的格式调整 | `style: 统一 import 分组` |
| `refactor` | 重构（不改变外部行为） | `refactor(service): 提取用户校验函数` |
| `perf` | 性能优化 | `perf(query): 添加索引减少慢查询` |
| `test` | 添加/修改测试 | `test(handler): 补充登录接口测试` |
| `chore` | 构建/工具/依赖变更 | `chore(ci): 升级 golangci-lint 到 v4` |
| `ci` | CI/CD 配置变更 | `ci: 添加多 Go 版本测试矩阵` |
| `revert` | 回退某次提交 | `revert: 回退 feat(api): 添加订单列表接口` |

> **区分 `refactor` vs `style`**：`refactor` 改变了代码结构但外部行为不变；`style` 只改了空格、换行、import 排序等纯格式。

### 1.3 scope 约定

🟡 推荐

| scope | 对应目录/模块 | 示例 |
|---|---|---|
| `handler` | `internal/handler/` | `feat(handler): 添加用户列表接口` |
| `service` | `internal/service/` | `fix(service): 修复订单金额计算` |
| `repo` | `internal/repository/` | `perf(repo): 批量插入改用事务` |
| `model` | `internal/model/` | `refactor(model): 提取公共字段到 Base` |
| `middleware` | `internal/middleware/` | `feat(middleware): 添加限流中间件` |
| `api` | `api/` | `docs(api): 更新 OpenAPI 规范` |
| `config` | `configs/` | `chore(config): 调整连接池参数` |
| `deps` | `go.mod` / 依赖 | `chore(deps): 升级 go 到 1.22` |
| `ci` | `.github/` | `ci: 添加覆盖率上传` |
| `db` | `db/migrations/` | `feat(db): 添加用户表 migration` |

**不需要 scope 的场景**：

- 全局影响（如 `style: 统一全项目 gofmt`）
- 跨多个模块的小改动（scope 列举不全反而误导）

### 1.4 subject 编写规则

🔴 必加约束

| 规则 | 正例 | 反例 |
|---|---|---|
| ≤ 50 字符 | `feat(api): 添加用户登录接口` | `feat(api): 添加用户登录接口，包含用户名密码校验、JWT token 生成和返回` |
| 动词开头、中文 | `添加用户登录接口` | `用户登录接口添加` |
| 不加句号 | `添加用户登录接口` | `添加用户登录接口。` |
| 不描述"怎么做" | `修复查询超时` | `给查询加了 context timeout 参数`（细节放 body） |
| 使用祈使语气 | `添加` / `修复` / `重构` | `添加了` / `修复了` |

### 1.5 body 编写规则

🟡 推荐：以下情况**必须**写 body

1. **为什么这样改**而不是别的方案
2. **影响了哪些地方**（其他模块、外部 API）
3. **破坏性变更**（BREAKING CHANGE）

```bash
# 正例：完整的 commit
git commit -m "fix(repo): 修复空切片导致的 nil panic

将 GetUsers 的空结果从 return nil 改为 return []User{}，
避免上游 json.Marshal 输出 null 而非 []。

影响范围：
- internal/repository/user_repo.go: GetUsers
- internal/handler/user_handler.go: ListUsers 不再需要空判断

BREAKING CHANGE: GetUsers 的返回值从 nil 变为 []User{}，
如有调用方依赖 nil 判断需同步修改。

Closes #234"
```

### 1.6 提交粒度

🟡 推荐

| 原则 | 说明 |
|---|---|
| **一个 commit 做一件事** | 不要在一个 commit 里同时改 3 个不相关的模块 |
| **原子性** | 每个 commit 应该能独立 review、独立 revert |
| **不提交 WIP** | 用 `git rebase -i` 合并 WIP 提交后再 push |

```bash
# 反例：一个 commit 包含太多无关改动
git commit -m "feat: 各种修改"  # 包含了新增 API + 修复 bug + 升级依赖

# 正例：拆分为多个独立 commit
git commit -m "feat(api): 添加用户列表接口"
git commit -m "fix(repo): 修复空切片 nil panic"
git commit -m "chore(deps): 升级 go.uber.org/zap"
```

### 1.7 提交频率

🟡 推荐

- **小步提交、频繁 push**——每完成一个可独立 review 的单元就提交
- 不要攒一周的代码一次性提交——冲突风险高、review 难度大
- 不要 push 到共享分支后再 `rebase` / `force push`（除非是自己的 feature 分支）

## 2. .gitignore 模板

### 2.1 Go 项目 .gitignore

🔴 必加约束：**每个 Go 项目必须包含 `.gitignore`**，至少包含以下内容

```gitignore
# === 编译产物 ===
/bin
*.exe
*.exe~
*.dll
*.so
*.dylib

# === 测试与覆盖率 ===
*.test
*.out
coverage.out
coverage.html

# === Go workspace ===
go.work
go.work.sum

# === IDE ===
.idea/
.vscode/
*.swp
*.swo
*~

# === 操作系统 ===
.DS_Store
Thumbs.db

# === 依赖（如果提交 vendor 则删除下面一行） ===
vendor/

# === 环境变量文件 ===
.env
.env.local
.env.production

# === 临时文件 ===
tmp/
temp/
```

### 2.2 规则说明

| 条目 | 原因 |
|---|---|
| `/bin` | 编译输出目录——二进制文件不应进入版本控制 |
| `*.test` / `*.out` / `coverage.out` | 测试产物——每次 `go test` 都会重新生成 |
| `go.work` / `go.work.sum` | workspace 文件——个人开发环境配置，不应提交（详见 [09-§ 1.3](09-依赖与构建.md)） |
| `vendor/` | 大多数项目用 Go modules 代理，不需要提交 vendor |
| `.idea/` / `.vscode/` | IDE 配置——每个人的 IDE 配置不同，不应强制统一 |
| `.env` | 环境变量——可能包含密钥，绝不应提交 |
| `tmp/` / `temp/` | 临时文件——无版本控制价值 |

### 2.3 特殊情况

🟡 推荐：以下情况需要调整 `.gitignore`

| 场景 | 调整 |
|---|---|
| **提交 vendor**（离线构建/合规要求） | 删除 `vendor/` 行；添加 `vendor/*/` + `!vendor/modules.txt` |
| **Magefile / Taskfile** 构建工具 | 不忽略相关构建产物 |
| **Protobuf 生成代码** | 生成目录一般**提交**（方便不装 protoc 的开发者） |

```gitignore
# 示例：提交 vendor（合规场景）
# vendor/*           # 忽略 vendor 下所有
# !vendor/modules.txt  # 但保留 modules.txt（Go 需要）

# 示例：不忽略 protobuf 生成代码
# api/gen/ 不在 .gitignore 中
```

### 2.4 验证 .gitignore

```bash
# 检查是否还有应忽略但未忽略的文件
git ls-files --others --ignored --exclude-standard

# 检查某个文件是否被忽略
git check-ignore -v path/to/file
```

## 3. Git LFS

### 3.1 什么时候用 Git LFS

🔴 必加约束：**大文件（> 5 MB）和二进制文件必须用 Git LFS 管理**，不要直接提交到 Git

| 文件类型 | 是否用 LFS | 说明 |
|---|---|---|
| `.png` / `.jpg` / `.gif` / `.svg` | 🟡 推荐 | 大图必须；小图标可选 |
| `.mp4` / `.mov` / `.avi` | 🔴 必须 | 视频文件几乎都 > 5 MB |
| `.zip` / `.tar.gz` | 🔴 必须 | 压缩包不可 diff |
| `.bin` / `.exe` / `.dll` | 🔴 必须 | 编译产物不可 diff |
| `.pb.go` / 生成的 `.go` | ❌ 不用 | Go 生成代码应直接提交（文本可 diff） |
| `.sql` / `.yaml` / `.json` | ❌ 不用 | 文本文件，Git 可高效存储 |

### 3.2 .gitattributes 配置

🔴 必加约束：使用 LFS 的项目必须在根目录放置 `.gitattributes`

```gitattributes
# .gitattributes

# 图片
*.png filter=lfs diff=lfs merge=lfs -text
*.jpg filter=lfs diff=lfs merge=lfs -text
*.jpeg filter=lfs diff=lfs merge=lfs -text
*.gif filter=lfs diff=lfs merge=lfs -text
*.ico filter=lfs diff=lfs merge=lfs -text

# 视频 / 音频
*.mp4 filter=lfs diff=lfs merge=lfs -text
*.mov filter=lfs diff=lfs merge=lfs -text
*.avi filter=lfs diff=lfs merge=lfs -text
*.mp3 filter=lfs diff=lfs merge=lfs -text
*.wav filter=lfs diff=lfs merge=lfs -text

# 文档
*.pdf filter=lfs diff=lfs merge=lfs -text
*.pptx filter=lfs diff=lfs merge=lfs -text
*.docx filter=lfs diff=lfs merge=lfs -text

# 压缩包
*.zip filter=lfs diff=lfs merge=lfs -text
*.tar.gz filter=lfs diff=lfs merge=lfs -text
```

### 3.3 安装与使用

```bash
# 安装 Git LFS（一次性）
brew install git-lfs
git lfs install

# 追踪文件类型
git lfs track "*.png"
git lfs track "*.mp4"

# 查看当前追踪规则
git lfs track

# 迁移已有大文件到 LFS
git lfs migrate import --include="*.png,*.mp4" --everything
```

## 4. 分支与标签策略

### 4.1 分支模型

🔴 必加约束：采用 **Trunk-Based Development**（主干开发）或其简化变体

```
main          ← 主干：始终可部署
  │
  ├── feat/user-login      ← 功能分支：从 main 拉出，合并回 main
  ├── fix/order-panic      ← 修复分支：从 main 拉出，合并回 main
  └── chore/upgrade-go     ← 杂项分支
```

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 主干，始终可部署 | 永久 |
| `feat/<name>` | 功能开发 | 开发完成后合并到 main 并删除 |
| `fix/<name>` | bug 修复 | 修复完成后合并到 main 并删除 |
| `chore/<name>` | 依赖升级、工具变更 | 完成后合并到 main 并删除 |
| `release/v1.2.0` | 发布分支（按需） | 发布后合并回 main 并删除 |

### 4.2 分支命名

🟡 推荐

```
<type>/<short-description>
```

```bash
# 正例
feat/user-login
feat/order-refund
fix/nil-pointer-in-repo
fix/timeout-on-large-query
chore/upgrade-go-1.22
chore/update-cicd

# 反例
my-branch               # 无类型前缀
feature/addUserLogin    # 不要用 feature（用 feat）
bugfix/nilpointer       # 不要用 bugfix（用 fix）
user-login              # 看不出是功能还是修复
```

### 4.3 标签（Tag）策略

🔴 必加约束：**每次发版必须打 tag**，采用语义化版本

```bash
# 正例：语义化版本
git tag -a v1.0.0 -m "首次正式发布"
git tag -a v1.1.0 -m "新增用户登录功能"
git tag -a v1.1.1 -m "修复空切片 panic"

# 推送 tag
git push origin v1.0.0

# 推送所有 tag
git push origin --tags
```

| tag 格式 | 说明 | 示例 |
|---|---|---|
| `v<MAJOR>.<MINOR>.<PATCH>` | 语义化版本 | `v1.2.3` |
| `v<MAJOR>.<MINOR>.<PATCH>-rc<N>` | 预发布版本 | `v1.2.3-rc1` |
| `v<MAJOR>.<MINOR>.<PATCH>-alpha<N>` | Alpha 版本 | `v2.0.0-alpha1` |

> 语义化版本详细规则见 。

### 4.4 Tag 与 CI/CD 的关系

🟡 推荐

| 触发条件 | CI 行为 |
|---|---|
| push 到 `main` | 运行 lint + test；生成开发版构建产物 |
| push `v*` tag | 运行完整 CI；构建生产版二进制；发布 release |
| PR 到 `main` | 运行 lint + test；不部署 |

```yaml
# .github/workflows/release.yml 示例
name: Release

on:
  push:
    tags:
      - 'v*'

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.22'
      - name: 编译
        run: make build
      - name: 发布
        run: |
          # 上传二进制到 release
          gh release create ${{ github.ref_name }} \
            --title "${{ github.ref_name }}" \
            --generate-notes \
            bin/*
```

## 5. AI 提交前自检

### 5.1 提交前必跑命令

🔴 必加约束：AI 提交前必须运行仓库规定且与改动相称的检查。下列是常见 Go 模块的**候选清单**，需按仓库脚本、改动范围、平台与 CI 约定选择；不要为了“全跑”而擅自引入工具、修改依赖或执行与任务无关的破坏性操作。

```bash
# 1. 格式化
go fmt ./...

# 2. import 排序（仅项目已采用 goimports 时）
find . -path ./vendor -prune -o -name '*.go' -exec goimports -w {} +

# 3. 静态分析
go vet ./...

# 4. 编译验证
go build ./...

# 5. 依赖同步（仅依赖声明或仓库流程要求时；先查看 diff）
go mod tidy

# 6. 测试（race 仅在目标平台、测试时长和项目约定允许时）
go test -race ./...

# 7. 综合检查（仅项目已采用时）
golangci-lint run ./...
```

### 5.2 提交前核对清单

**每次 `git commit` 前，AI 应主动核对**：

#### 代码质量

- [ ] 项目规定的格式化已执行（通常为 `go fmt ./...`）
- [ ] 若仓库使用 goimports，已按其脚本或配置完成 import 整理
- [ ] 与改动相称的 `go vet ./...`、构建和测试无报错
- [ ] 若依赖声明变更或仓库要求，已执行 `go mod tidy` 并复核 `go.mod` / `go.sum` 差异
- [ ] 若项目要求且运行环境支持，race 测试已通过

#### 提交信息

- [ ] Commit message 遵循 Conventional Commits 格式
- [ ] `type` 选择正确（feat / fix / refactor / chore 等）
- [ ] `subject` ≤ 50 字符，动词开头
- [ ] 破坏性变更已标注 `BREAKING CHANGE`
- [ ] 修复 issue 已标注 `Closes #<N>`

#### 文件内容

- [ ] 没有提交二进制文件（除非已配置 LFS）
- [ ] 没有提交 `.env` / 密钥 / token
- [ ] 没有提交 `vendor/`（除非项目明确要求）
- [ ] 没有提交 `go.work` / `go.work.sum`
- [ ] 没有提交 IDE 配置（`.idea/` / `.vscode/`）
- [ ] 没有提交 `tmp/` / `temp/` 临时文件

#### 分支与合并

- [ ] 当前在正确的分支上（不是直接在 `main` 上改）
- [ ] 分支名符合 `<type>/<description>` 格式
- [ ] 提交前已 `git pull --rebase`（避免无意义 merge commit）
- [ ] 没有 force push 到共享分支

### 5.3 提交命令模板

```bash
# AI 写代码完成后的示例流程（先替换为仓库实际脚本）
go fmt ./... && go vet ./... && go build ./... && go test ./...

# 确认无误后
git add -A
git diff --cached --stat   # 确认变更范围
git commit -m "<type>(<scope>): <subject>"

# 如有需要
git commit -m "<type>(<scope>): <subject>

<body>
"
```

### 5.4 不要提交的内容

🔴 必加约束

| 内容 | 原因 |
|---|---|
| 密码 / API Key / Token | 安全——即使私有仓库也不提交 |
| `go.work` / `go.work.sum` | 个人开发环境——通过 `GOWORK=off` 忽略 |
| IDE 配置 | 个人偏好——每个开发者 IDE 不同 |
| `vendor/` | 默认不提交——用 Go modules 代理（除非有合规要求） |
| 临时文件 | 无版本控制价值 |
| 编译产物（`/bin`） | 可重建——`go build` 随时生成 |
| 日志文件 | 运行时产物——不反映代码状态 |

### 5.5 撤销与修正

🟡 推荐

```bash
# 修正最后一次 commit（未 push 时）
git commit --amend -m "修正后的 commit message"

# 修正最后一次 commit 的文件
git add forgotten_file.go
git commit --amend --no-edit

# 合并最近 3 个 WIP commit 为一个
git rebase -i HEAD~3
# 保留第一个 pick，其余改为 squash 或 fixup

# 撤销某次提交（保留改动）
git reset --soft HEAD~1

# 丢弃未提交的改动（危险！）
git checkout -- file.go       # 丢弃单个文件
git reset --hard HEAD         # 丢弃所有未提交改动
```
