# 08 - Unity 版本控制规则

> 🟢 本文件适用于 Unity 项目版本控制（.gitignore/.meta/LFS/场景拆分）。

> 🔴 不适用：GitHub PR/MR 流程、Code Owner 配置

---

## 1. Unity 资源协作底线

### 1.1 1. .meta 文件入库不规范

Unity 用 `.meta` 文件记录每个 Asset 的 GUID / 导入设置。使用 Git 或其他需要追踪资源变更的版本控制系统时，应遵守以下规则：

- ❌ **不要** 在 `.gitignore` 里写 `*.meta`（这是新人最常犯的错）
- ✅ **所有** Asset（脚本 / 场景 / Prefab / 贴图 / 字体 …）都必须有对应的 `.meta` 文件
- ✅ Asset 与 `.meta` 必须 **同步提交**——单独提交 Asset 不提交 .meta 会导致 GUID 不一致，队友本地丢失引用
- 🟡 推荐通过 Unity 编辑器重命名、移动和删除 Asset；若使用文件系统或脚本，必须连同 `.meta` 一起移动或删除，并在 Editor 中验证引用。

> 🔑 **判断方法**：打开 `Assets/`，每个文件旁边都有一个对应的 `.meta` 文件，缺一不可。

### 1.2 2. Library / Temp / Logs 入库

Unity 编辑器生成的本地缓存目录，**禁止入库**：

```gitignore
# 必加
/Library/
/Temp/
/Logs/
/obj/
/Build/
/Builds/

# 强烈建议加
/UserSettings/         # Unity 2020+ 新增，部分项可入，但一般全 ignore
/Recordings/           # Unity 录制器输出

# IDE 缓存（按需）
/.vs/
/.idea/
*.csproj
*.sln
*.suo
*.user
```

> ⚠️ 不要入库 Library 的原因：Library 里有 1-3 万个文件，体积 5-20 GB，**队友 pull 下来也必须重新生成**（依赖本地 Unity 版本和 Asset Store cache）。

### 1.3 3. 大资源未用 LFS（FBX / 贴图 / 音频）

当仓库托管平台、团队配额或文件体积策略要求时，使用 **Git LFS**。例如 GitHub 拒绝超过 100MB 的单文件；其他平台与自建仓库应以实际限制为准：

```bash
git lfs install                  # 一次性安装
git lfs track "*.fbx"
git lfs track "*.psd"
git lfs track "*.wav"
git lfs track "*.mp3"
git lfs track "*.mp4"
git add .gitattributes            # 将 LFS 跟踪规则入库
```

- LFS 文件会替换成轻量指针（pointer），实际文件存在 LFS 服务器
- 正常安装并启用 Git LFS 后，clone/checkout 会自动下载受跟踪文件；只有使用 `GIT_LFS_SKIP_SMUDGE`、跳过 smudge 或看到 pointer 文件时，再执行 `git lfs pull`。
- 不要把所有 PNG 都加 LFS；是否追踪纹理应按目录、资源类型、单文件体积、仓库配额和团队现有 `.gitattributes` 决定。
- 新增规则后用 `git check-attr filter -- <文件路径>` 验证目标大文件确实被 LFS 跟踪；Git attributes 不能按文件大小自动筛选。

### 1.4 4. 未确认的主分支流程

- 🔴 **必须**先检查仓库的分支保护、贡献指南和团队协作流程。
- 🟡 已启用 PR 审查或分支保护时，走 **feature 分支 → PR → review → merge** 流程。
- ❌ 未经团队约定，不得假设所有仓库都禁止直接 `git push origin main`，也不得绕过已配置的保护规则。

### 1.5 5. 改 Unity Package Manager 引用但没同步 Packages/manifest.json

Unity **Package Manager（UPM）** 的依赖全部记在 `Packages/manifest.json` 里：

```json
{
  "dependencies": {
    "com.unity.xr.management": "4.4.0",     // 示例：以项目当前已验证版本为准
    "com.unity.addressables": "1.21.0",     // 示例：不要写 latest
    "com.unity.textmeshpro": "3.0.6"        // 示例：不要从本节复制版本号
  }
}
```

- ❌ **不要** 写 `"com.unity.xr.management": "latest"`（不可复现，队友拉下来版本可能不同）
- ✅ **不要** 走 `Window > Package Manager` 装包后忘记提交 manifest.json
- ✅ 项目存在 `Packages/packages-lock.json` 时，将其与 `manifest.json` 一并提交；若团队另有锁定策略，以其为准。
- ✅ 移除包时也用 Package Manager 操作，自动从 manifest.json 删除


## 2. 团队约定的推荐做法

### 2.1 1. Unity .gitignore 标准模板

推荐用 **GitHub 官方 Unity .gitignore** 起步，再加团队定制项：

```gitignore
# ========================================
# Unity 标准忽略（基于 github/gitignore）
# ========================================
[Ll]ibrary/
[Tt]emp/
[Oo]bj/
[Bb]uild/
[Bb]uilds/
[Ll]ogs/
[Uu]ser[Ss]ettings/
[Mm]emoryCaptures/
[Rr]ecordings/

# Asset meta data should only be ignored when the corresponding asset is also ignored
!/[Aa]ssets/**/*.meta

# Uncomment this line if you wish to ignore the asset store tools plugin
# /[Aa]ssets/AssetStoreTools*

# ========================================
# Visual Studio / Rider IDE
# ========================================
.vs/
.idea/
*.csproj
*.unityproj
*.sln
*.suo
*.tmp
*.user
*.userprefs
*.pidb
*.booproj
*.svd
*.pdb
*.mdb
*.opendb
*.VC.db

# ========================================
# Builds
# ========================================
*.apk
*.aab
*.unitypackage
*.app

# ========================================
# Crashlytics generated file
# ========================================
crashlytics-build.properties

# ========================================
# Packed Addressables
# ========================================
/[Aa]ssets/[Aa]ddressable[Aa]ssets[Dd]ata/*/*.bin*

# ========================================
# Temporary auto-generated Android Assets
# ========================================
/[Aa]ssets/[Ss]treamingAssets/aa.meta
/[Aa]ssets/[Ss]treamingAssets/aa/*
```

> 💡 **关键**：`!/[Aa]ssets/**/*.meta` 这一行（用 `!` 反向规则）必须保留——把 `*.meta` 从忽略里排除，保证 Asset 的 meta 入库。

### 2.2 2. 资源命名前缀（与 09 资源管理规则配合）

资源类型用统一前缀，便于搜索 / 区分：

| 类型 | 前缀 | 示例 |
|------|------|------|
| Texture | `Tex_` | `Tex_Icon_Sword.png` |
| Material | `Mat_` | `Mat_Stone.mat` |
| Prefab | `Prefab_` | `Prefab_Enemy_Zombie.prefab` |
| Audio | `Audio_` / `Sfx_` / `Bgm_` | `Sfx_Click.wav` |
| Animation | `Anim_` | `Anim_Walk.anim` |
| Shader | `Shader_` | `Shader_Toon.shader` |
| ScriptableObject | `SO_` | `SO_PlayerStats.asset` |
| Font | `Font_` | `Font_Main.ttf` |

> 完整命名规则见 [09-资源管理规则 § 2 命名约定](./09-资源管理规则.md)。

### 2.3 3. 场景拆分（按模块）

多人协作时 **一个场景一个模块**，避免冲突：

```
Assets/Scenes/
├── Bootstrap.unity       # 启动场景（Build Index 0）
├── MainMenu.unity        # 主菜单
├── Loading.unity         # 加载
├── Level_01.unity        # 关卡 1
├── Level_02.unity        # 关卡 2
└── Sandbox.unity         # 测试场景（不入库或单独分支）
```

- ✅ 按模块拆场景，每个场景只放自己模块的内容
- ✅ 用 **SceneManager.LoadSceneAsync** 加载，不把所有东西塞一个场景
- ✅ 测试场景（Sandbox / Test_xxx）用 [SerializeField] 字段保护，**正式版不要 commit**
- ✅ 同一时间 **多人在同一场景** 容易冲突，拆小场景能减少冲突概率

### 2.4 4. Prefab Variant 与 Overrides

Prefab 是 Unity 协作的核心，**不要直接改 Base Prefab**：

- ✅ **继承用 Variant**：右击 Base Prefab > Create > Prefab Variant
- ✅ **修改场景实例**：用 Override > Apply 或 Override > Revert
- ❌ **不要** 直接在场景里改 Prefab 默认值（Apply 后会污染 Base）
- ✅ Base Prefab 只放公共结构（角色通用模型、UI 通用组件），具体数值在 Variant 或场景实例改
- ✅ Variant 文件也要提交 .meta + .prefab

### 2.5 5. commit message 规范（Conventional Commits）

项目已采用 Conventional Commits 时，使用以下格式：

```text
<type>(<scope>): <description>

[body]

[footer]
```

| type | 用途 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(player): add double jump` |
| `fix` | 修 bug | `fix(ui): fix layout in iPhone 14` |
| `chore` | 杂项（依赖 / 配置） | `chore: bump addressables to 1.21.0` |
| `refactor` | 重构 | `refactor(ai): extract FSM base class` |
| `perf` | 性能优化 | `perf(render): reduce draw calls by 30%` |
| `test` | 测试 | `test(combat): add hit detection tests` |
| `docs` | 文档 | `docs(readme): update build instructions` |
| `style` | 代码格式（不影响逻辑） | `style: fix unused using directives` |
| `build` | 构建系统 | `build(android): add 64-bit only flag` |

> 💡 **AI 自检**：提交信息必须遵循目标仓库已有的格式；仅在项目采用 Conventional Commits 时使用上面的模板。

### 2.6 6. 分支策略

**主分支模型示例**（适合部分中小团队；已有 trunk-based、GitHub Flow 或其他约定时不得迁移）：

```text
main                # 生产环境 / 已发布版本（受保护）
  ├── develop       # 集成分支（受保护）
  │     ├── feature/player-jump
  │     ├── feature/shop-ui
  │     └── feature/quest-system
  └── hotfix/xxx    # 紧急修复（从 main 拉，合并回 main + develop）
```

| 分支类型 | 命名 | 来源 | 合并到 |
|---------|------|------|--------|
| 主干 | `main` / `master` | — | — |
| 集成分支 | `develop` | main | — |
| 功能分支 | `feature/<name>` | develop | develop |
| 修复分支 | `fix/<name>` | develop | develop |
| 紧急修复 | `hotfix/<name>` | main | main + develop |
| 个人分支 | `dev/<name>` | develop | 仅个人 |

### 2.7 7. PR 检查清单

项目采用 PR 流程时，可按以下清单审核；实际门槛以仓库的 CI、分支保护和团队约定为准：

- [ ] 标题符合 Conventional Commits
- [ ] 描述清楚改了什么、为什么改
- [ ] **Unity 编辑器内能打开场景**（最常见的"我本地能跑"问题）
- [ ] **编译通过**（Player + Editor 双平台）
- [ ] .meta 文件全部入库（没有遗漏）
- [ ] 没有大文件（> 100MB）直接入库（应该走 LFS）
- [ ] Packages/manifest.json 同步（如果改了依赖）
- [ ] 资源命名前缀符合约定
- [ ] CI 全绿（自动化构建 + 自动化测试）
- [ ] 至少 1 个 reviewer approve

### 2.8 8. Packages/manifest.json 版本固定

```json
{
  "dependencies": {
    "com.unity.xr.management": "4.4.0",
    "com.unity.addressables": "1.21.0",
    "com.unity.textmeshpro": "3.0.6"
  }
}
```

- ✅ 用 **具体版本号**（"4.4.0"），不用 `"latest"` / `"^4.0.0"`
- ✅ 升级包时 `Packages/packages-lock.json` 自动更新，**两个文件都要提交**
- ✅ 用 **UPM 仓库**（Git URL / scoped registry）时也锁 commit hash：

```json
{
  "dependencies": {
    "com.company.internal": "https://github.com/company/pkg.git#abc123def"
  }
}
```


## 3. 可选的协作能力

### 3.1 1. Git LFS 完整配置（lfs 配置 + .gitattributes）

`.gitattributes` 文件入库，规定 LFS 追踪规则：

```gitattributes
# 示例：只把团队确认的大型源资源或媒体类型纳入 LFS；不要直接复制为全仓规则
*.fbx filter=lfs diff=lfs merge=lfs -text
*.psd filter=lfs diff=lfs merge=lfs -text
*.tga filter=lfs diff=lfs merge=lfs -text
*.wav filter=lfs diff=lfs merge=lfs -text
*.mp3 filter=lfs diff=lfs merge=lfs -text
*.ogg filter=lfs diff=lfs merge=lfs -text
*.mp4 filter=lfs diff=lfs merge=lfs -text
*.mov filter=lfs diff=lfs merge=lfs -text
*.unitypackage filter=lfs diff=lfs merge=lfs -text
*.a filter=lfs diff=lfs merge=lfs -text
*.so filter=lfs diff=lfs merge=lfs -text
*.dll filter=lfs diff=lfs merge=lfs -text

# PNG 是否放入 LFS 由目录与资源体积策略决定；.gitattributes 不支持用 ! 规则排除已匹配模式
```

- LFS 存储、流量和保留策略由当前托管平台与组织套餐决定，提交前检查团队配额与计费策略。
- 中小项目按 `.gitattributes` 精细化追踪，不要“一把梭”。

### 3.2 2. Smart Merge（Unity YAML 合并工具）

Unity 场景 / Prefab 文件是 YAML 格式，多人改同一个 Prefab 时 Git 默认文本合并会冲突——配 Smart Merge：

**方式 1：项目级 `.gitattributes`**

```gitattributes
*.unity        merge=unityyamlmerge
*.prefab       merge=unityyamlmerge
*.asset        merge=unityyamlmerge
```

**方式 2：全局 Git 配置**

```bash
git config --global merge.unityyamlmerge.driver "UnityYAMLMerge.exe merge -p %O %A %B %A"
```

- Smart Merge 只能处理 **字段级冲突**（不同字段 / 不同 GameObject）
- **真正冲突**（同一字段两人改不同值）仍需手动解决——合并后 Unity 打开，编辑器内会标红
- Smart Merge 工具路径：`<Unity 安装目录>/Editor/Data/Tools/UnityYAMLMerge.exe`

### 3.3 3. CI 自动构建（Build Automation）

**避免"在我电脑上能跑"问题**：

| CI 平台 | 特点 | Unity 集成 |
|--------|------|-----------|
| **Unity Cloud Build** | Unity 官方 | 一键配置 |
| **GameCI** | GitHub Actions | 免费 / 需 Docker |
| **GitLab CI** | 自托管 | 自配 Unity License |

**典型 CI 流程**：

```yaml
# .github/workflows/unity-build.yml
name: Unity Build
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    container: unityci/editor:2022.3.0f1
    steps:
      - uses: actions/checkout@v3
        with:
          lfs: true                # 必须 fetch LFS
      - name: Build Android APK
        run: |
          mkdir -p build
          /opt/unity/Editor/Unity \
            -batchmode \
            -projectPath . \
            -buildTarget Android \
            -executeMethod BuildScript.BuildAndroid \
            -quit
      - uses: actions/upload-artifact@v3
        with:
          name: APK
          path: build/Build.apk
```

> ⚠️ CI **必须 fetch LFS**，否则大资源丢失，编译报错。
