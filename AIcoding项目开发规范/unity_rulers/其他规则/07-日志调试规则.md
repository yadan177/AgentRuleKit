# 07 - Unity 日志与调试规则

> 🟢 本文件适用于 Unity 运行时日志、开发包诊断、错误上报边界与性能排障。
>
> 🔴 不适用：为单个功能引入日志框架、把客户端日志当作服务端事实，或在正式包输出未脱敏诊断信息。

---

## 1. 统一入口与职责

> **适用条件与验证**：先检查项目已有日志门面、错误上报、构建类型、Scripting Define Symbols、隐私策略和同模块调用方式。

- 🔴 **必须**：业务代码统一调用项目日志门面；除日志门面、已隔离的 Editor 工具或项目已有异常上报封装外，不直接调用 `Debug.Log*`。
- 🔴 **必须**：日志门面统一负责等级、分类、格式、显示、脱敏、采样和构建剔除；不得在每个业务调用点重复写 `#if UNITY_EDITOR` 或 `#if DEVELOPMENT_BUILD`。
- 🟡 **推荐**：将运行时诊断与正式包错误上报分开。后者只保留经脱敏、限频和项目批准的事件。

## 2. 五级日志与分类筛选

> **适用条件与验证**：项目需要在 Editor 或 Development Build 中按等级、业务域或问题线路筛选日志时适用。

- 🔴 **必须**：五级日志仅通过统一门面输出：`Trace`（细节）、`Debug`（开发状态）、`Info`（关键流程）、`Warn`（可恢复异常）、`Error`（失败）。等级语义、分类名称和默认掩码由项目维护，不能由单个业务脚本改变。
- 🔴 **必须**：显示策略使用可组合的等级掩码与分类过滤；调用点只提供等级、分类、消息和可选上下文。
- 🟡 **推荐**：中文协作项目的日志正文使用中文，说明发生了什么和关键上下文；分类、枚举值及结构化字段键遵循项目既有的稳定命名，不为翻译而破坏检索与关联。
- 🟡 **推荐**：Editor/Development Build 默认只开启 `Warn | Error`，按排障需要临时开启其他等级；高频 `Trace` 需要明确关闭/采样策略。

```csharp
using System;

[Flags]
public enum LogLevel
{
    None = 0,
    Trace = 1 << 0,
    Debug = 1 << 1,
    Info = 1 << 2,
    Warn = 1 << 3,
    Error = 1 << 4,
    All = Trace | Debug | Info | Warn | Error,
}

public static class ProjectLog
{
    // 项目可在 Editor 调试面板或开发配置中调整；不是业务代码的全局开关。
    public static LogLevel EnabledLevels = LogLevel.Warn | LogLevel.Error;
    public static string EnabledCategory = null;

    [System.Diagnostics.Conditional("UNITY_EDITOR")]
    [System.Diagnostics.Conditional("DEVELOPMENT_BUILD")]
    public static void Write(
        LogLevel level,
        string category,
        string message,
        UnityEngine.Object context = null)
    {
        var categoryMatches = string.IsNullOrEmpty(EnabledCategory) ||
            (!string.IsNullOrEmpty(category) &&
             category.StartsWith(EnabledCategory, StringComparison.Ordinal));
        if ((EnabledLevels & level) == 0 || !categoryMatches)
        {
            return;
        }

        var prefix = $"[{category}][{level}] {message}";
        if (level == LogLevel.Error)
        {
            Debug.LogError(prefix, context);
        }
        else if (level == LogLevel.Warn)
        {
            Debug.LogWarning(prefix, context);
        }
        else
        {
            Debug.Log(prefix, context);
        }
    }

    [System.Diagnostics.Conditional("UNITY_EDITOR")]
    [System.Diagnostics.Conditional("DEVELOPMENT_BUILD")]
    public static void Exception(string category, Exception exception, UnityEngine.Object context = null)
    {
        if ((EnabledLevels & LogLevel.Error) != 0)
        {
            Debug.LogException(exception, context);
        }
    }
}
```

## 3. 构建策略与正式包边界

> **适用条件与验证**：项目需要区分 Editor、Development Build 和正式 Release 时适用。

- 🔴 **必须**：将 `Conditional("UNITY_EDITOR")` / `Conditional("DEVELOPMENT_BUILD")` 集中在日志门面的 `void` API 上。Release 不定义这些符号时，所有 `ProjectLog.Write` 与 `ProjectLog.Exception` 调用及其参数求值都会在编译期移除。
- 🔴 **必须**：不要用 `if (Debug.isDebugBuild)` 替代构建剔除，也不要把 `return`、状态更新、网络请求或其他业务逻辑放进日志条件编译块。
- 🔴 **必须**：正式包需要的崩溃、支付、认证或安全事件走项目已有上报接口；不得因为关闭本地五级日志而丢失产品要求的受控诊断。
- 🟡 **推荐**：如项目需要 QA/灰度包额外日志，使用已定义且受构建系统管理的符号或配置，而不是在业务代码中散落宏。

## 4. 调用与排障

> **适用条件与验证**：项目已有 `ProjectLog` 等等价门面时适用；名称、分类和上报接口必须替换为项目真实实现。

```csharp
ProjectLog.Write(LogLevel.Debug, "Network", $"请求已发起：requestId={requestId}", this);
ProjectLog.Write(LogLevel.Warn, "Network", $"请求超时，准备重试：requestId={requestId}，当前重试次数={retryCount}", this);
ProjectLog.Exception("Resource", exception, this);
```

- 🔴 **必须**：日志不得包含令牌、密码、支付信息、完整个人数据、密钥、未脱敏请求载荷或生产服务端内部细节。
- 🔴 **必须**：性能结论先通过项目已有 Profiler、Frame Debugger、Memory Profiler 或可复现设备测试确认；日志只能辅助定位，不能替代证据。
- 🟡 **推荐**：临时排障时仅调整门面的等级/分类筛选，完成后恢复默认值并清理不再需要的临时事件。

## 5. 验证与例外

- 🔴 **必须**：验证 Editor/Development Build 中等级和分类筛选、Release 中调用剔除、异常路径、脱敏与项目错误上报的受影响部分。
- 🟡 **推荐**：交付时说明开启的等级、分类、实际验证构建、未覆盖设备和隐私/上报风险。

> **例外**：Editor 专用菜单、Inspector 和导入工具可以使用当前项目约定的 Editor 输出；它们必须处于 Editor 专用编译范围，不能泄漏到运行时程序集。
