# 08 - JavaScript 测试规则

> 🟢 本文件适用于 JavaScript/TypeScript 单元测试、集成测试、端到端测试与质量保障。<br>
> 🔴 不适用：业务逻辑实现、UI 样式设计、第三方 SDK

---

## 1. 🔴 硬约束 · 这些绝对不要写

### 1.1 没有断言的测试

```js
// ❌
test('user login', () => {
  login('alice', 'pass');
});

// ✅
test('user login succeeds with valid credentials', async () => {
  const result = await login('alice', 'pass');
  expect(result.token).toBeDefined();
  expect(result.user.name).toBe('alice');
});
```

### 1.2 测试间共享状态（顺序依赖）

```js
// ❌ 用 beforeAll 修改全局,其他测试受污染
let user;
beforeAll(() => { user = createUser(); });

test('update user', () => {
  user.name = 'bob';
  expect(user.name).toBe('bob');
});

test('user original name', () => {        // ❌ 受上一个测试影响
  expect(user.name).toBe('alice');
});

// ✅ 每个测试独立 setup / teardown
let user;
beforeEach(() => { user = createUser(); });
afterEach(() => { /* cleanup */ });
```

### 1.3 测试实现细节（白盒过深）

```js
// ❌ 测试实现细节(换个实现方式就挂)
expect(component.find('div.UserCard').length).toBe(1);

// ✅ 测行为不测实现(用户视角)
expect(screen.getByText('alice')).toBeInTheDocument();
expect(screen.getByRole('button', { name: /logout/i })).toBeVisible();
```

### 1.4 异步测试漏 await

```js
// ❌ 测试在断言前就结束了
test('fetch user', () => {
  fetchUser(1).then(user => {
    expect(user.name).toBe('alice');        // 没执行
  });
});

// ✅ async 函数 + await
test('fetch user', async () => {
  const user = await fetchUser(1);
  expect(user.name).toBe('alice');
});
```

### 1.5 假数据写在测试外

```js
// ❌ 模块顶层常量,所有测试共享
const testUser = { name: 'alice' };          // 改了影响所有测试

// ✅ factory + beforeEach 重置
function createTestUser(overrides = {}) {
  return { id: 1, name: 'alice', age: 25, ...overrides };
}
beforeEach(() => { testUser = createTestUser(); });
```

## 2. 🟡 推荐 · 团队约定

### 2.1 测试层次

下表比例只用于解释常见结构，不是统一指标。实际分布应根据模块风险、运行成本、历史缺陷和项目现有测试体系决定。

| 层级 | 比例 | 工具 | 用途 |
|------|------|------|------|
| **Unit** | 70% | Vitest / Jest | 单个函数 / 类 |
| **Integration** | 20% | Vitest + MSW / Supertest | 多个模块协作 |
| **E2E** | 10% | Playwright / Cypress | 用户关键路径 |

### 2.2 测试覆盖率门槛

| 类型 | 判断原则 |
|------|------|
| 核心业务逻辑 | 优先覆盖关键分支、失败路径和状态转换 |
| 工具函数 / 纯函数 | 按复用范围和边界条件提高覆盖 |
| UI 组件 | 重点验证用户可观察行为、交互与可访问性 |
| E2E | 覆盖项目确认的关键用户路径，不用代码覆盖率替代流程验收 |

🔴 覆盖率阈值沿用仓库和 CI 现有配置；AI 不得自行写入统一百分比。覆盖率只能辅助发现漏测，不能证明行为正确。

### 2.3 TDD 流程（项目采用时）

1. **红**：先写测试，跑通（失败）
2. **绿**：写最小实现让测试通过
3. **重构**：在测试保护下优化代码

### 2.4 Mock 边界

优先在进程外边界、非确定性来源或高成本依赖处使用 mock/fake；是否替换内部协作者取决于测试层次，不能用 mock 固化实现细节。

```js
// ✅ mock fetch
vi.spyOn(global, 'fetch').mockResolvedValue({
  ok: true,
  json: async () => ({ name: 'alice' }),
});

// ❌ 仅为验证内部调用次数而 mock 纯实现细节
vi.spyOn(userService, 'formatUser');
```

**常见 mock 目标**：

- HTTP（`fetch` / `axios`）
- 时间（`Date.now` / `setTimeout`）
- 随机数（`Math.random`）
- localStorage / IndexedDB
- 第三方 SDK（埋点 / 监控）

### 2.5 测试命名（describe / it 描述行为）

```js
// ✅ describe 组件 / 类,it 描述行为
describe('UserService', () => {
  it('should throw when email is invalid', async () => {
    await expect(userService.create({ email: 'bad' }))
      .rejects.toThrow('Invalid email');
  });

  it('should return user when credentials valid', async () => {
    const user = await userService.login('alice@example.com', 'pass');
    expect(user.token).toBeDefined();
  });
});
```

### 2.6 测试结构（AAA）

```js
test('discount calculation', () => {
  // Arrange
  const user = { level: 'gold' };

  // Act
  const discount = getDiscount(user);

  // Assert
  expect(discount).toBe(0.2);
});
```

### 2.7 Vitest vs Jest

| 工具 | 优势 | 何时选 |
|------|------|------|
| **Vitest** | 更快 / 原生 ESM / Vite 集成 | 新项目 / Vite 项目 |
| **Jest** | 生态成熟 / 文档多 | 已有项目 / React Native |

**不要**两套混用。

## 3. 🟢 可选 · 视情况

### 3.1 E2E（Playwright / Cypress）

**核心链路才做 E2E**：

- 注册 / 登录 / 支付
- 关键业务转化路径

```js
// playwright example
test('user can login', async ({ page }) => {
  await page.goto('/login');
  await page.fill('input[name=email]', 'alice@example.com');
  await page.fill('input[name=password]', 'pass');
  await page.click('button[type=submit]');
  await expect(page).toHaveURL('/dashboard');
});
```

### 3.2 视觉回归（Chromatic / Percy）

UI 组件库 / 设计系统项目做。

### 3.3 Mutation Testing（Stryker）

检测无效测试（mock 全部实现也能通过的测试）。

### 3.4 属性测试（fast-check）

随机输入测试不变量。
