# 08 - Java 测试规则

> 🟢 本文件适用于 Java 单元测试与质量保障（JUnit 5/Mockito/TDD/覆盖率）。

> 🔴 不适用：业务逻辑实现、UI 样式设计、第三方 SDK

---

## 1. AIR 原则（P3C 强制）

### 1.1 AIR 总览

🟡 **推荐**（P3C 第 1 条）：

- 好的单元测试必须遵守 **AIR 原则**
- 单元测试在线上运行时，感觉像空气（AIR）一样并不存在，但在测试质量的保障上，却是非常关键的
- 宏观上，具有**自动化 / 独立性 / 可重复执行**的特点

| 字母 | 含义 | 说明 |
|---|---|---|
| **A** | Automatic（自动化）| 全自动执行、非交互、产出 PASS/FAIL 信号 |
| **I** | Independent（独立性）| 测试用例之间**不互相调用**，**不依赖执行顺序**|
| **R** | Repeatable（可重复）| 不受外部环境影响（时间 / 网络 / 数据库 / 文件系统）|

### 1.2 自动化的要求

🟡 **推荐**（P3C 第 2 条）：

- 单元测试**全自动执行**且**非交互**
- 测试用例通常被定期执行（持续集成），执行过程必须完全自动化
- **输出结果需要人工检查的测试不是好的单元测试**
- **单元测试中不准使用 `System.out` 来进行人肉验证**，**必须使用 `assert` 验证**

**反例**：
```java
// ❌ 用 System.out 人肉验证
@Test
void testAdd() {
    int result = calculator.add(2, 3);
    System.out.println("Result is: " + result);  // 期望开发者自己看
}
```

**正例**：
```java
// ✅ 用 assert 验证
@Test
void testAdd() {
    int result = calculator.add(2, 3);
    assertEquals(5, result);
}
```

### 1.3 独立性

🟡 **推荐**（P3C 第 3 条）：

- **保持单元测试的独立性**
- 测试用例之间**不能互相调用**，**不能依赖执行先后次序**
- **反例**：`method2` 需要依赖 `method1` 的执行结果作为输入

### 1.4 可重复性

🟡 **推荐**（P3C 第 4 条）：

- 单元测试**可以重复执行**，不能受外界环境影响
- 持续集成每次 check in 都会执行；如果对外部环境（网络 / 服务 / 中间件）有依赖，**会导致持续集成机制的不可用**
- **正例**：设计代码时把 SUT（System Under Test）的依赖改成**注入**，测试时用 DI 框架注入本地（内存）实现或 Mock 实现

## 2. JUnit 5 基础（AI 视角扩展）

P3C 仅讲原则，AI 视角补全 JUnit 5 现代用法。JDK 11+ 项目用 JUnit 5（JUnit 4 已停止维护）。

### 2.1 JUnit 5 vs JUnit 4

🟡 **推荐**：

| 维度 | JUnit 4 | JUnit 5 |
|---|---|---|
| 包 | `org.junit.Test` | `org.junit.jupiter.api.Test` |
| 扩展模型 | `@RunWith` | `@ExtendWith` |
| 嵌套测试 | ❌ | ✅ `@Nested` |
| 动态测试 | ❌ | ✅ `@TestFactory` |
| 生命周期 | `@Before / @After` | `@BeforeEach / @AfterEach` |
| DisplayName | 无 | ✅ `@DisplayName` |

### 2.2 标准测试方法结构

🟡 **推荐**：

```java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.DisplayName;
import static org.junit.jupiter.api.Assertions.*;

@DisplayName("订单服务单元测试")
class OrderServiceTest {

    @Test
    @DisplayName("创建订单 - 成功场景")
    void shouldCreateOrder_whenValidRequest() {
        // Arrange（准备）
        OrderRequest req = new OrderRequest(100L, List.of(item1, item2));
        when(orderRepository.save(any(Order.class))).thenReturn(savedOrder);

        // Act（执行）
        OrderDTO result = orderService.create(req);

        // Assert（断言）
        assertNotNull(result);
        assertEquals(100L, result.getUserId());
        verify(orderRepository).save(any(Order.class));
    }
}
```

🟡 **推荐**：命名遵循**三段式**（`shouldXxx_whenYyy` 或 `given_when_then`）：
- 测试方法名读起来像"句子"
- IDE 通过方法名导航时更清晰
- 失败日志自动展示长方法名

### 2.3 生命周期注解

🟡 **推荐**：

```java
class OrderServiceTest {
    private OrderService orderService;
    private OrderRepository orderRepository;  // 模拟对象

    @BeforeAll
    static void setupClass() { /* 整个测试类运行前执行一次 */ }

    @BeforeEach
    void setup() {  // 每个测试方法前执行（替代 @Before / setUp）
        orderRepository = mock(OrderRepository.class);
        orderService = new OrderService(orderRepository);
    }

    @AfterEach
    void teardown() { /* 每个测试方法后执行 */ }

    @AfterAll
    static void teardownClass() { /* 整个测试类运行后执行一次 */ }
}
```

### 2.4 DisplayName 命名规范

🟡 **推荐**：

- **类级**用 `@DisplayName` 描述被测类的职责
- **方法级**用 `@DisplayName` 描述测试场景

```java
@DisplayName("OrderService")
class OrderServiceTest {
    @Test
    @DisplayName("create：库存不足时抛异常")
    void create_throwsWhenStockNotEnough() { ... }
}
```

## 3. Mockito（AI 视角扩展）

P3C 没讲 Mockito。AI 写 Java 测试必用。

### 3.1 Mockito 5.x 基本用法

🟡 **推荐**：

```java
// 创建 mock
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {

    @Mock
    private OrderRepository orderRepository;  // 自动创建 mock

    @InjectMocks
    private OrderService orderService;  // 自动注入上面的 mock

    @Test
    void testCreateOrder() {
        // given：定义 mock 行为
        Order saved = new Order(1L, "ORDER-001", OrderStatus.PAID);
        when(orderRepository.save(any(Order.class))).thenReturn(saved);

        // when
        OrderDTO result = orderService.create(req);

        // then
        assertEquals("ORDER-001", result.getOrderNo());
        verify(orderRepository, times(1)).save(any(Order.class));
    }
}
```

### 3.2 常用 Mockito API

🟡 **推荐**：

| 方法 | 用途 |
|---|---|
| `mock(Class)` / `@Mock` | 创建 mock 对象 |
| `when(mock.method()).thenReturn(value)` | 定义 mock 行为 |
| `when(mock.method()).thenThrow(Exception)` | mock 抛异常 |
| `when(mock.method()).thenAnswer(invocation -> ...)` | 复杂 mock（如根据参数返回值）|
| `verify(mock).method(args)` | 验证方法被调用 |
| `verify(mock, times(1)).method()` | 验证调用次数 |
| `verify(mock, never()).method()` | 验证从未调用 |
| `verifyNoInteractions(mock)` | 验证零交互 |
| `ArgumentMatchers.any(Class)` | 匹配任何参数 |
| `ArgumentCaptor<T>` | 捕获方法参数（验证参数内容）|

### 3.3 静态方法 mock

🟡 **推荐**：优先通过依赖注入、时钟/随机数等可替换边界避免静态 mock。确有必要时，先检查项目的 Mockito 版本和 mock maker 配置：Mockito 5 默认使用 inline mock maker，通常**不需要**额外声明 `mockito-inline`；旧版本或已有配置应遵循项目当前方式，不要仅为本示例新增或混用 mock maker。

```java
// mock 静态方法
try (MockedStatic<LocalDateTime> mocked = Mockito.mockStatic(LocalDateTime.class, Mockito.CALLS_REAL_METHODS)) {
    mocked.when(LocalDateTime::now).thenReturn(LocalDateTime.of(2024, 1, 15, 10, 30));

    // 测试代码
    Order order = orderService.createAtNow(req);
    assertEquals(LocalDateTime.of(2024, 1, 15, 10, 30), order.getCreatedAt());
}
```

### 3.4 void 方法验证

🟡 **推荐**：

```java
// ✅ 验证 void 方法被调用
@Mock private EventPublisher eventPublisher;

@Test
void shouldPublishEvent_whenOrderCreated() {
    orderService.create(req);
    verify(eventPublisher).publish(argThat(event ->
        event instanceof OrderCreatedEvent));
}

// ❌ 不要试图对 void 方法 stub 返回值
when(eventPublisher.publish(any())).thenReturn(...);  // 编译错
```

### 3.5 不要 mock 的对象

🟡 **推荐**：

- **不要 mock value 对象 / DTO / 简单数据类型**（自己 new 即可）
- **不要 mock 静态常量 / 枚举**
- **不要 mock 你不拥有的接口**（别人的代码）
- **不要全 mock 真实对象的所有方法**（反而比真对象难维护）

### 3.6 Spy vs Mock

🟡 **推荐**：

- **`mock()`**：所有方法默认返回默认值（int→0 / String→null / Collection→空集合）
- **`spy()`**：默认调真实方法，只拦截部分方法（覆盖真实调用）

```java
@Spy
private OrderService realOrderService = new OrderService(realRepository);

// 只 mock 一个方法
doReturn(mockedOrder).when(realOrderService).specialCase();

@Test
void testSpecialCase() {
    Order result = realOrderService.specialCase();  // 走 mock
    Order normal = realOrderService.normal();  // 走真实方法
}
```

## 4. AssertJ 流畅断言（AI 视角扩展）

P3C 没说"用哪个 assert 库"。**AI 写测试推荐 AssertJ（优于 JUnit 自带）**。

### 4.1 为什么用 AssertJ 而不是 JUnit Assertions

🟡 **推荐**：

| 维度 | JUnit Assertions | AssertJ |
|---|---|---|
| 可读性 | `assertEquals(5, list.size())` | `assertThat(list).hasSize(5)` |
| 失败提示 | 仅显示期望值和实际值 | 详细描述 + 高亮差异 |
| 链式断言 | 不支持 | ✅ |
| IDE 自动补全 | 一般 | 优秀（所有 `assertThat(x)` 弹出 `hasXxx` 方法）|

### 4.2 AssertJ 常用断言

🟡 **推荐**：

```java
import static org.assertj.core.api.Assertions.*;

@Test
void shouldValidateOrder() {
    OrderDTO order = orderService.create(req);

    // 对象断言
    assertThat(order).isNotNull()
                     .satisfies(o -> {
                         assertThat(o.getStatus()).isEqualTo(OrderStatus.PAID);
                         assertThat(o.getAmount()).isEqualByComparingTo(new BigDecimal("99.50"));
                     });

    // 集合断言
    assertThat(order.getItems())
        .isNotEmpty()
        .hasSize(3)
        .extracting("name")
        .containsExactly("item1", "item2", "item3");

    // 异常断言
    assertThatThrownBy(() -> orderService.create(invalidReq))
        .isInstanceOf(BizException.class)
        .hasMessageContaining("参数错误");
}
```

### 4.3 BigDecimal / LocalDateTime / 浮点比较

🟡 **推荐**：

```java
// ❌ BigDecimal 用 equals 比较会失败（1.0 vs 1.00 精度不同）
assertEquals(new BigDecimal("1.00"), new BigDecimal("1.0"));  // ❌ 失败

// ✅ 用 isEqualByComparingTo（按数值比较，忽略 scale）
assertThat(new BigDecimal("1.00")).isEqualByComparingTo(new BigDecimal("1.0"));

// ✅ LocalDateTime / LocalDate 用 isEqualTo（无需 equals）
assertThat(order.getCreatedAt()).isEqualTo(LocalDateTime.of(2024, 1, 15, 10, 30));

// ❌ 浮点用 == 比较会失败
assertEquals(0.1 + 0.2, 0.3);  // ❌

// ✅ 用 isCloseTo 指定 delta
assertThat(0.1 + 0.2).isCloseTo(0.3, within(0.0001));
```

## 5. 参数化测试（AI 视角扩展）

### 5.1 为什么用参数化测试

🟡 **推荐**：

- 同一段逻辑要测多种输入时，用 `@ParameterizedTest` + 数据源（**比重复 `assertEquals` 5 遍好得多**）
- 测试失败时**自动报告哪个 case 失败**

### 5.2 参数源选择

🟡 **推荐**：

| 参数源 | 适用 |
|---|---|
| `@ValueSource` | 简单字面量（int / String / enum）|
| `@EnumSource` | 枚举值 |
| `@MethodSource` | 复杂对象（流式）|
| `@CsvSource` | CSV 字符串 |
| `@CsvFileSource` | CSV 文件 |
| `@NullSource` / `@EmptySource` / `@NullAndEmptySource` | 边界值（null / 空）|

**正例**：

```java
@ParameterizedTest
@ValueSource(ints = {0, 1, 100, Integer.MAX_VALUE})
@DisplayName("validateAge：所有合法年龄都通过")
void shouldValidateAge_whenLegalAge(int age) {
    assertThat(validator.isLegalAge(age)).isTrue();
}

@ParameterizedTest
@MethodSource("invalidAgeCases")
@DisplayName("validateAge：非法年龄都拒绝")
void shouldReject_whenIllegalAge(int age) {
    assertThatThrownBy(() -> validator.requireLegalAge(age))
        .isInstanceOf(BizException.class);
}

static Stream<Arguments> invalidAgeCases() {
    return Stream.of(
        Arguments.of(-1),
        Arguments.of(151),
        Arguments.of(Integer.MIN_VALUE)
    );
}
```

## 6. 覆盖率标准

### 6.1 P3C 覆盖率目标

🟡 **推荐**（P3C 第 8 条）：

- **单元测试基本目标**：**语句覆盖率达到 70%**
- **核心模块**：**语句覆盖率和分支覆盖率都要达到 100%**
- 在工程规约的应用分层中提到的 **DAO 层 / Manager 层 / 可重用度高的 Service**，都应该进行单元测试

### 6.2 JaCoCo 配置

🟡 **推荐**：JaCoCo 是 Java 社区主流的覆盖率工具：

```xml
<!-- pom.xml -->
<plugin>
    <groupId>org.jacoco</groupId>
    <artifactId>jacoco-maven-plugin</artifactId>
    <version>0.8.11</version>
    <executions>
        <execution>
            <goals>
                <goal>prepare-agent</goal>
                <goal>report</goal>
            </goals>
        </execution>
        <execution>
            <id>check-coverage</id>
            <phase>verify</phase>
            <goals>
                <goal>check</goal>
            </goals>
            <configuration>
                <rules>
                    <rule>
                        <element>BUNDLE</element>
                        <limits>
                            <limit>
                                <counter>INSTRUCTION</counter>
                                <minimum>0.70</minimum>
                            </limit>
                            <limit>
                                <counter>BRANCH</counter>
                                <minimum>0.70</minimum>
                            </limit>
                        </limits>
                    </rule>
                </rules>
            </configuration>
        </execution>
    </executions>
</plugin>
```

🟡 **推荐**：

- **CI 流水线集成覆盖率检查**：低于门槛构建失败

### 6.3 覆盖率的解读

🟢 **参考**：覆盖率数字的意义：

| 覆盖率 | 含义 |
|---|---|
| **100% 行覆盖** | 每个可执行语句都跑过 1 次 |
| **100% 分支覆盖** | 每个 if / else 都跑过 |
| **100% 路径覆盖** | 所有逻辑路径覆盖（最难）|

🟡 **推荐**：

- **不要追求 100% 行覆盖**（实际意义不大）
- **关键业务路径 100% 分支覆盖**比"100% 行覆盖"更重要

## 7. BCDE 原则（P3C 强制）

### 7.1 BCDE 总览

🟡 **推荐**（P3C 第 9 条）：编写单元测试代码遵守 **BCDE 原则**，以保证被测试模块的交付质量：

| 字母 | 含义 | 用法 |
|---|---|---|
| **B** | Border（边界）| 循环边界 / 特殊取值 / 特殊时间点 / 数据顺序 |
| **C** | Correct（正确）| 正确的输入并得到预期的结果 |
| **D** | Design（与设计结合）| 与设计文档结合编写单元测试 |
| **E** | Error（错误）| 强制错误信息输入（非法数据 / 异常流程 / 非业务允许输入）并得到预期结果 |

### 7.2 边界值测试

🟡 **推荐**：AI 写测试时必查的边界情况：

```java
@ParameterizedTest
@MethodSource("ageCases")
@DisplayName("年龄校验：所有合法 / 非法边界")
void testAgeValidation(int age, boolean expected) {
    assertThat(validator.isLegalAge(age)).isEqualTo(expected);
}

static Stream<Arguments> ageCases() {
    return Stream.of(
        // 边界 B - Border
        Arguments.of(0, true),         // 最小合法
        Arguments.of(1, true),         // 紧邻边界
        Arguments.of(150, true),       // 最大合法
        Arguments.of(149, true),       // 紧邻最大边界
        // 错误 E - Error
        Arguments.of(-1, false),       // 紧邻最小非法
        Arguments.of(151, false),      // 紧邻最大非法
        Arguments.of(Integer.MAX_VALUE, false)
    );
}
```

### 7.3 错误输入测试

🟡 **推荐**（P3C 第 9 条 E）：

- **强制错误信息输入**（非法数据 / 异常流程 / 非业务允许输入），并得到预期的结果
- **不要只测正确路径** —— 异常路径必须测

**反例**：
```java
@Test
void testCreateOrder() {
    // ❌ 只测正常路径
    orderService.create(validReq);
}
```

**正例**：
```java
@ParameterizedTest
@DisplayName("createOrder：异常路径")
@MethodSource("invalidRequests")
void shouldThrowException_whenInvalidRequest(OrderRequest req, String expectedCode) {
    assertThatThrownBy(() -> orderService.create(req))
        .isInstanceOf(BizException.class)
        .satisfies(e -> assertThat(((BizException) e).getErrorCode()).isEqualTo(expectedCode));
}

static Stream<Arguments> invalidRequests() {
    return Stream.of(
        Arguments.of(new OrderRequest(null, items), "20101"),      // 用户 ID 为空
        Arguments.of(new OrderRequest(100L, null), "20102"),       // 商品列表为空
        Arguments.of(new OrderRequest(-1L, items), "20103")        // 用户 ID 无效
    );
}
```

## 8. 测试代码质量（P3C 强制）

### 8.1 增量代码必测

🟡 **推荐**（P3C 第 6 条）：

- **核心业务 / 核心应用 / 核心模块的增量代码确保单元测试通过**
- **新增代码及时补充单元测试**，如果新增代码影响了原有单元测试，**请及时修正**

### 8.2 测试目录

🟡 **推荐**（P3C 第 7 条）：

- 单元测试代码**必须写在工程目录**：`src/test/java`
- **不允许写在业务代码目录下**（如 `src/main/java`）
- 源码构建时会跳过 `src/test/java`；单元测试框架默认扫描此目录

🟡 **推荐**：

- 测试类**与被测类同包不同目录**（如 `src/main/java/com/example/OrderService.java` ↔ `src/test/java/com/example/OrderServiceTest.java`）
- 同包保证测试可以访问包内私有方法（如有需要）

### 8.3 不要假设数据库有数据

🟡 **推荐**（P3C 第 10 条）：

- **对于数据库相关的查询 / 更新 / 删除等操作，不能假设数据库里的数据是存在的**
- **直接操作数据库插入**数据并不可靠
- **反例**：删除某一行数据的测试，先**手动**加一行数据，但这一行不符合业务插入规则，导致测试结果异常

**正例**（用 Testcontainers 或内存数据库）：
```java
@DataJpaTest
@AutoConfigureTestDatabase(replace = Replace.ANY)  // 用 H2 替换
class OrderRepositoryTest {
    @Autowired private OrderRepository orderRepository;
    @Autowired private TestEntityManager entityManager;

    @BeforeEach
    void setup() {
        // 程序化插入测试数据
        entityManager.persist(new Order("ORDER-001", OrderStatus.UNPAID));
    }

    @Test
    void shouldFindOrderByNo() {
        Optional<Order> result = orderRepository.findByOrderNo("ORDER-001");
        assertThat(result).isPresent();
    }
}
```

### 8.4 数据库测试隔离

🟡 **推荐**（P3C 第 11 条）：

- **和数据库相关的单元测试**，可以设定**自动回滚机制**，**不给数据库造成脏数据**
- **或者**对单元测试产生的数据有明确的前后缀标识
- **正例**：阿里 RDC 内部使用 `RDC_UNIT_TEST_` 前缀标识数据

```java
@TestTransactional  // 自动在测试方法结束时回滚
@Test
void testUpdateOrder() {
    Order order = orderRepository.save(new Order("TEST-001"));
    order.setStatus(OrderStatus.PAID);
    orderRepository.save(order);
    // 测试结束后自动回滚，数据库干净
}
```

### 8.5 业务代码应可测

🟡 **推荐**（P3C 第 15 条）：

为了更方便地进行单元测试，业务代码应**避免**以下情况：

| 反模式 | 原因 | 重构建议 |
|---|---|---|
| 构造方法中做的事情过多 | 难构造 + 业务逻辑难测 | `init()` 方法 / `@PostConstruct` |
| 过多的全局变量和静态方法 | 难以隔离 | 依赖注入 |
| 过多的外部依赖 | 集成测试难写 | 抽象接口 + Mock |
| 过多的条件语句 | 分支覆盖难做 | 卫语句 / 策略模式 / 状态模式 |

## 9. TDD 流程（AI 视角扩展）

### 9.1 什么是 TDD

🟢 **参考**（P3C 没明说 TDD）：

- TDD（Test-Driven Development，测试驱动开发）：**先写失败的测试 → 让测试通过 → 重构**
- 三步循环：**Red → Green → Refactor**

### 9.2 三步循环示例

🟡 **推荐**：

```java
// 步骤 1 Red：先写测试（编译 / 运行都会失败）
@DisplayName("折扣计算器")
class DiscountCalculatorTest {
    @Test
    void shouldApply10PercentDiscount_whenOrderOver100() {
        DiscountCalculator calc = new DiscountCalculator();
        BigDecimal discount = calc.calculateDiscount(
            new BigDecimal("150"),  // 订单金额 150
            CustomerType.NORMAL
        );
        assertEquals(new BigDecimal("15.00"), discount);  // 期望 9 折
    }
}

// 此时 DiscountCalculator 类还不存在，编译失败 → Red

// 步骤 2 Green：写最小实现，让测试通过
class DiscountCalculator {
    public BigDecimal calculateDiscount(BigDecimal amount, CustomerType type) {
        if (amount.compareTo(new BigDecimal("100")) > 0) {
            return amount.multiply(new BigDecimal("0.10"));
        }
        return BigDecimal.ZERO;
    }
}

// 测试通过 → Green

// 步骤 3 Refactor：重构（提取常量 / 消除重复）
class DiscountCalculator {
    private static final BigDecimal DISCOUNT_THRESHOLD = new BigDecimal("100");
    private static final BigDecimal VIP_DISCOUNT_RATE = new BigDecimal("0.15");
    private static final BigDecimal NORMAL_DISCOUNT_RATE = new BigDecimal("0.10");

    public BigDecimal calculateDiscount(BigDecimal amount, CustomerType type) {
        if (amount.compareTo(DISCOUNT_THRESHOLD) <= 0) {
            return BigDecimal.ZERO;
        }
        BigDecimal rate = type == CustomerType.VIP
            ? VIP_DISCOUNT_RATE
            : NORMAL_DISCOUNT_RATE;
        return amount.multiply(rate);
    }
}
// 重构后测试仍通过 → Refactor 完成
```

### 9.3 TDD 适合场景

🟢 **可选**：

| 场景 | TDD 适合度 |
|---|---|
| **核心业务逻辑**（订单创建 / 折扣计算 / 状态机）| ⭐⭐⭐⭐⭐ |
| **数据转换**（DTO ↔ Entity）| ⭐⭐⭐⭐ |
| **算法实现** | ⭐⭐⭐⭐⭐ |
| **UI 界面** | ⭐⭐ |
| **基础设施**（Controller / 配置类）| ⭐⭐ |
| **Bug 修复**（先写再现 bug 的测试）| ⭐⭐⭐⭐⭐ |

## 10. 集成测试与端到端测试（AI 视角扩展）

### 10.1 测试金字塔

🟡 **推荐**：

```
        /\          E2E（少、高价值）
       /  \         - 跨系统真实场景
      / E2E\        - 慢（数分钟级别）
     /______\
    /        \      集成测试（中等数量）
   /Integration\    - 跨模块 / 跨服务
  /______________\   - 中等速度（秒级）
 /                  \
/      Unit          \  单元测试（大量、低成本）
\____________________/ - 单一方法 / 单一类
                      - 极快（毫秒级）
```

🟡 **推荐**：

- **单元测试应占 70%+**（金字塔底层）
- **集成测试 20%**
- **E2E 测试 < 10%**（慢、脆、难维护）

### 10.3 Testcontainers（真实数据库测试）

🟡 **推荐**：Testcontainers 是测试时拉真实 Docker 容器的工具，比 H2 更接近生产：

```xml
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>mysql</artifactId>
    <version>1.19.7</version>
    <scope>test</scope>
</dependency>
```

```java
@Testcontainers
@SpringBootTest
class OrderRepositoryIntegrationTest {

    @Container
    static MySQLContainer<?> mysql = new MySQLContainer<>("mysql:8.0")
        .withDatabaseName("test_db")
        .withUsername("test")
        .withPassword("test");

    @DynamicPropertySource
    static void registerProperties(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", mysql::getJdbcUrl);
        registry.add("spring.datasource.username", mysql::getUsername);
        registry.add("spring.datasource.password", mysql::getPassword);
    }

    @Autowired private OrderRepository orderRepository;

    @Test
    void shouldSaveAndFind() {
        Order saved = orderRepository.save(new Order("ORDER-001"));
        assertThat(orderRepository.findById(saved.getId())).isPresent();
    }
}
```

### 10.4 不要对单元测试存在误解

🟢 **参考**（P3C 第 16 条）：

- ❌ "那是测试同学干的事情" → 单元测试是**开发同学的职责**
- ❌ "单元测试代码是多余的" → **好的单元测试能规避线上故障**
- ❌ "单元测试代码不需要维护" → 一年半载不维护，几乎处于废弃状态
- ✅ "好的单元测试能够最大限度地规避线上故障"
