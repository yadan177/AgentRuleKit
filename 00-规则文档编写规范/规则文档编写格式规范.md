# 00 - 规则文档编写格式规范

> 🟢 本文件适用于 go、java、js、ts、unity、pico 及后续子项目中的普通 Markdown 规则文档与 `.md` 入口文档。
>
> 🔴 不适用：业务代码注释、设计/接口/部署文档，以及必须使用工具专有元数据的规则配置文件。

---

## 1. 适用范围与优先级

### 1.1 普通规则文档

🔴 **必须**：普通规则文档（包括总览、通用入口、专题规则、`AGENTS.md` 和手动使用说明）遵守本文件的标题、分隔线、编号和最小内容要求。

🔴 **必须**：用户任务、仓库已有约定和更具体的子项目规则优先于本文件；本文件不授权修改项目代码、依赖、版本或架构。

### 1.2 工具专有配置文件

🟢 **可选**：工具要求专有格式时，配置文件可不遵守普通 Markdown 的“H1 首行”规则。例如 Cursor 的 `.cursor/rules/*.mdc` 可保留其要求的 YAML frontmatter。

🔴 **必须**：专有配置文件只保留工具元数据和短入口指令，完整规则仍只维护在普通 Markdown 规则库中；不得为了适配多个工具复制多套完整规则。

🔴 **必须**：工具格式、存储路径或触发方式未经官方文档或实际项目验证时，不得臆造配置文件。

## 2. 普通 Markdown 结构

### 2.1 顶部结构

普通 Markdown 文档必须使用以下顺序：

```markdown
# NN - 文档名称

> 🟢 可选：本文件适用于……
> 🔴 可选：本文件不适用于……

---

## 1. 第一章
```

🔴 **必须**：文件首行直接是 H1（`# NN - 文档名称`）；H1 前不得有 BOM、空行、注释或 YAML frontmatter。

🔴 **必须**：H1 与顶部分隔线之间、顶部分隔线与第一个 H2 之间各保留一个空行。

🔴 **必须**：普通 Markdown 在代码围栏外只保留一道 `---`，且只能作为顶部结构分隔线。章节之间及章节内部不得再使用单独一行的 `---`；用 H2/H3、列表、表格或段落留白表达层次。

🟢 **可选**：H1 与顶部分隔线之间只允许“适用范围”类 blockquote。导言、阅读指引、任务表和术语说明应放入第一个 H2 章节。

### 2.2 文件标题与名称

🔴 **必须**：规则文档 H1 使用 `# NN - 名称` 格式；`NN` 使用两位阿拉伯数字，例如 `00`、`01`、`14`。

🟡 **推荐**：文件名与 H1 编号保持一致，例如 `14-AI通用入口规则.md` 对应 `# 14 - AI 通用入口规则`。既有稳定路径需要保留时，可只修正文档标题，不做无授权的批量重命名。

## 3. 标题编号与层级

### 3.1 编号格式

| 层级 | 格式 | 示例 |
|---|---|---|
| H2 | `## N. 标题` | `## 1. 使用方式` |
| H3 | `### N.M 标题` | `### 1.1 开始前检查` |
| H4 | `#### N.M.K 标题` | `#### 1.1.1 配置来源` |

🔴 **必须**：H2 从 `1` 开始，在整份文档中连续递增，不跳号、不使用 `0` 或小数编号。

🔴 **必须**：H3 的首位必须等于其所属 H2 编号，次位从 `1` 起连续递增；切换 H2 后重新从 `.1` 开始。H4 同理，前两位必须等于所属 H3。

🟡 **推荐**：没有足够内容时不要为凑层级创建空 H3/H4 章节。

### 3.2 可读性边界

🟡 **推荐**：H2 表达完整主题，H3 表达可独立执行或验证的子主题；避免跳过 H2 直接使用 H3。

❌ **禁止**：使用视觉样式（加粗、引号、横线）伪装标题层级，或在标题中堆叠过长的规则正文。

## 4. 规则内容的最小单元

### 4.1 条件化规则模板

涉及技术选择、版本、依赖、框架、命令、运行环境或项目结构的规则，使用以下模板：

```markdown
### N.M 规则名称

**适用条件**：项目已具备的依赖、版本、框架、模块或运行环境前提。

🔴 **必须**：不可省略的边界或安全要求。

🟡 **推荐**：在适用条件满足时的默认做法。

🟢 **可选**：需要权衡后才采用的方案。

**验证**：可执行的构建、测试、配置检查、日志、指标或审查方法。

**例外**：可以偏离规则的条件、授权人和补充验证。
```

🔴 **必须**：规则只使用项目已有证据支持的版本、依赖、API、配置、数据库对象、测试命令和部署资源。

🔴 **必须**：不得把特定 JDK、Unity 版本、框架、包管理器、渲染管线、数据库或云平台写成跨项目的无条件前提；不确定时要求探测、沿用既有实现或明确询问。

🟡 **推荐**：并非每个小节都要同时出现三种等级标识；出现的等级必须准确。纯背景说明、表格和流程图不强行添加等级图标。

### 4.2 示例与引用

🔴 **必须**：示例必须标注前提，且可在该前提下成立；不得把示例中的类、包、密钥、地址、命令、测试结果或云资源伪装成项目事实。

🟡 **推荐**：只在高风险、易误解或存在常见反模式的位置提供正反例；不要求每条规则机械成对举例。

🔴 **必须**：示例涉及密钥、凭证、个人数据、生产地址或破坏性命令时，使用占位符并说明风险，不得给出可直接损害项目的操作指令。

### 4.3 验证与交付

🔴 **必须**：涉及改动的规则写明验证方法；无法验证时说明原因、未验证范围和风险。

🔴 **必须**：不得声称编译、测试、打包、部署或安全扫描已通过，除非实际执行并获得结果。

## 5. 文档模板与反例

### 5.1 普通规则文档模板

```markdown
# 04 - 示例专题规则

> 🟢 本文件适用于满足指定前提的项目任务。
> 🔴 不适用：与本专题无关的架构迁移。

---

## 1. 使用范围

说明任务边界、优先级和关联规则。

## 2. 规则主题

### 2.1 条件化规则

**适用条件**：项目已使用某项能力。

🔴 **必须**：沿用项目现有契约。

🟡 **推荐**：在可验证时采用最小改动。

**验证**：执行仓库已有的相关检查，或说明未执行原因。

**例外**：迁移或升级需要用户明确授权。
```

### 5.2 常见错误

| ❌ 错误 | ✅ 正确 |
|---|---|
| `---` 或 YAML frontmatter 出现在普通 `.md` 的 H1 前 | 普通 `.md` 首行直接为 `# NN - 名称` |
| `# 标题\n\n---\n\n> 适用范围` | `# 标题\n\n> 适用范围\n\n---\n\n## 1. ...` |
| H2 之间继续插入单独一行 `---` | 仅在顶部保留一道 `---`，以编号标题和留白分段 |
| `## 1. ...` 后直接写 `### 2.1 ...` | H3 与父 H2 对齐：`### 1.1 ...` |
| “所有项目必须升级到某版本” | “项目已支持该能力时可使用；否则沿用既有实现或询问” |
| 为每个工具复制一份完整规则 | 保留一个 `.ai-rules/<domain>/` 规则源，适配器只写短入口 |

## 6. AI 自检与验收

### 6.1 普通 Markdown 自检

- [ ] 首行是 `# NN - 名称`，无前置内容。
- [ ] 代码围栏外恰有一道 `---`，位于 H1（及可选适用范围）之后、首个 H2 之前。
- [ ] H2/H3/H4 编号连续，且父子编号一致。
- [ ] 本地 Markdown 链接可解析；外部链接和工具配置路径有依据。
- [ ] 技术选择已写清适用条件；未把示例当作项目事实。
- [ ] 有改动时写明验证、未验证项和风险。

本仓库修改规则后，执行 `node scripts/verify-rules.mjs`。该脚本检查四套规则库的普通 Markdown 结构、相对链接和适配器入口；它不替代人工对技术事实、示例正确性和工具官方配置的复核。

### 6.2 工具配置文件自检

- [ ] 仅在工具官方格式或项目既有配置已确认时使用 frontmatter 或专有目录。
- [ ] 配置仅作为短入口，定位到唯一完整规则源。
- [ ] 不复制完整专题规则，不臆造自动加载能力。

## 7. 与其他规则的关系

本文件规定规则文档的结构和最低可验证性要求；各子项目的 `00-文档总览.md` 规定专题导航、技术边界与优先级，`AI通用入口规则.md` 规定项目开发时的能力探测、变更边界和交付要求。

跨子项目引用本文件时，使用相对于当前文件的真实路径；不得复制路径示例后不校验链接。
